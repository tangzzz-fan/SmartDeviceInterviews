## 二、专题 1：低功耗优化（深挖版）

### 高频考点
* BLE 连接参数与功耗 tradeoff（含数字）
* App 侧能耗大头（定位/网络/唤醒/屏幕）
* 测量方法：不量化不罢休
* 低功耗模式（Low Power Mode）适配
* 与固件协作的功耗分工

### 必掌握知识点
* 三层视角：App 系统层（后台任务、唤醒频率、定位/网络占用）、BLE 链路层（connection interval、slave latency、扫描窗口、notify 合并）、硬件协作层（谁决定连接参数、谁聚合数据、传感器 ODR）。
* 测量：Xcode Energy Log 看趋势，Instruments Energy 定位函数级耗电，真机电流计/功耗仪出绝对数字；场景矩阵：待机 / 空闲连接 / 实时同步 / 夜间睡眠监测 / OTA，分别测。
* 典型优化案例量级（估算示例）：空闲连接 interval 30ms→300ms + slave latency 2，连接态空闲电流约 15mA→3mA；传感器 ODR 100Hz→25Hz（睡眠期），整机功耗再降一档。

### 答题模板
「我做过一次功耗优化。先建测量基线：待机、空闲连接、同步三个场景用电流计各测 30 分钟。然后砍三刀：1) BLE 空闲期把 interval 从 30ms 拉到 300ms、开 slave latency，数据同步期再临时收紧；2) 传感器数据让固件聚合后批量 notify，App 端减少唤醒；3) 后台任务合并，避免每小时单独跑。结果空闲电流从 xx mA 降到 xx mA，整机续航从 x 天到 y 天（估算），并沉淀了功耗回归场景，每次发版前测一遍。」

### 追问应对
* 「为什么不同时拉大 interval？」答：实时指令时延要求，控制通道与批量数据通道参数分开。
* 「怎么证明是 App 的锅还是固件的锅？」答：分层测量——App 关闭 BLE 看系统基线，再分别开扫描/连接/同步，看哪一步抬升最明显。

### 翻车点
* 只讲方案没有数字；把功耗全归到固件；不知道 Low Power Mode 下系统会限制后台能力。

## 三、专题 2：设备 OTA（深挖版）

### 高频考点
* 完整 OTA 流程与协议细节（分包/流控/校验）
* 中断恢复与断点续传
* 失败回滚与变砖防护
* 版本与协议兼容（升级前后协议可能变化）
* OTA 与产测工具链复用

### 必掌握知识点
* 流程：版本检查 → 下载固件包（校验 MD5/SHA + 签名）→ BLE 分块传输（每包 CRC，窗口流控，如 20 包一确认）→ 传输完成整体校验 → 写入 flash → 切换 bootloader → 重启 → 上报版本。
* 协议细节：DFU service 里一般有控制点（start/data/verify/abort）与传输特征；包格式含 opcode、总长度、包序号、数据、CRC；App 记录已传 offset 与最后确认包序号，重连后从 offset 续传。
* 可靠性：双 bank（A/B）回滚；电量低于阈值拒绝开始；传输中断设备自动回滚到旧固件；传输期间防止设备关机/休眠。
* 兼容：OTA 前后协议版本可能不同——连接后先做协议版本协商，新固件用新字段，App 兼容旧协议；升级顺序（先升级 App 还是固件）要有规则。
* 量产复用：同一套 DFU 协议可在产测环节用于首版固件烧录，App 侧 OTA 代码与产测脚本共用解析/校验逻辑。

### 答题模板
「OTA 我把中断恢复当一等公民设计：分块传输带包序号和 CRC，App 记录已传 offset，重连后从 offset 续传而不是重来；固件做双 bank，升级失败自动回滚；电量低于 30% 拒绝开始。最难的是协议兼容：新固件可能改协议，所以连接后先交换协议版本，App 保持向后兼容。量产时同一套 DFU 协议直接复用到产测烧录，少维护一套工具链。最终 OTA 成功率 99.x%（估算）。」

### 追问应对
* 「设备在传输中关机了怎么办？」答：bootloader 恢复模式 + 双 bank 回滚 + 重启后断点续传，三层兜底。
* 「怎么保证固件包没被篡改？」答：签名校验 + 传输 CRC + 整体哈希三重验证。

### 翻车点
* 只讲「上传固件」不讲协议与恢复；不知道双 bank；不提协议版本兼容（面试官很吃这个点）。

## 四、专题 3：离线数据同步（深挖版）

### 高频考点
* 设备端/App 端/云端三侧各自「不丢不重」的机制
* 增量同步与幂等
* 冲突解决规则
* 断网、杀 App、换设备的兜底

### 必掌握知识点
* 设备侧：未确认数据持久化（环形缓冲/Flash），带单调递增 seq；App 回确认（ack 最新 seq）后才清除。
* App 侧：先落本地时序库再上报；持久化「已确认/待上传」状态，被杀重启可续；按 seq 去重。
* 云侧：增量拉取（since_id/cursor）、幂等键（client_msg_id 唯一）、冲突规则（健康数据设备为准、用户编辑走版本号）。
* 补偿三路：BGTaskScheduler 后台拉起、push 到达触发、下次启动对账；对账协议：设备返回最新 seq，App 从断点补拉。
* 常见丢数据场景与对策：连接中断（断点续传）、App 被杀（本地持久化 + 启动对账）、设备端覆盖（环形缓冲 + 定期上报水位）。

### 答题模板
「我的原则是 App 当网关、先落盘再上传。设备端数据带 seq 和 CRC，未确认的持久化在本地；App 收到先写 GRDB 再回 ack；云同步走增量 + 幂等键，失败进队列，后台任务、push、启动对账三路补偿。冲突规则提前定：设备采集数据以设备为准，用户编辑数据走版本号合并。这样断网、杀 App、换设备都不会丢。」

### 追问应对
* 「设备缓冲满了怎么办？」答：水位上报 + 优先同步最旧数据 + 告警，必要时提示用户；缓冲大小按「最坏离线时长 × 数据速率」设计。
* 「两端同时改了同一份数据？」答：版本号合并，云端裁决，App 端提示冲突。

### 翻车点
* 只讲 App 侧，忽略设备端持久化与云端幂等；冲突规则含糊。

## 五、专题 4：音频采集与处理

### 高频考点
* BLE 传音频的吞吐与实时性约束（含数字）
* 采样率/位深/缓冲/时延
* 端侧 vs 云侧算法分工
* 穿戴场景：语音助手、通话、录音

### 必掌握知识点
* 数据量测算：16kHz、16bit、单声道 = 256 kbps ≈ 32 KB/s；48kHz、16bit = 768 kbps ≈ 96 KB/s。BLE notify 实测吞吐约 200–600 KB/s（2M PHY + 大 MTU，受外设栈限制），所以 16k 音频可行，48k 需压缩（Opus 24–64 kbps 很常见）或加大缓冲。
* 链路：麦克风采集（采样率/位深/声道）→ 缓冲（环形缓冲，防丢帧）→ 时间戳标注 → 编码/压缩 → BLE 分块传输 → App 解码 → 播放/存储/上传。
* 时延控制：缓冲大小与丢帧率 tradeoff；实时场景（通话/语音助手）缓冲小，录音/上传场景可缓冲大一点。
* 端云分工：降噪、回声消除（AEC）、唤醒词可以在端侧（低时延、省流量），大模型语音理解在云侧；断网时端侧降级（本地处理或暂存）。
* 数据质量：与参考设备对比（频响、信噪比）、环境噪声下的鲁棒性验证。

### 答题模板
「穿戴设备传音频，瓶颈是 BLE 吞吐和实时性。16kHz/16bit 单声道约 32 KB/s，BLE notify 实测能到 200–600 KB/s（估算），所以 16k 直传可行；48k 我建议端侧压缩（Opus）再传。链路是采集→环形缓冲→时间戳→编码→分块传输→App 解码。实时场景缓冲压小控时延，录音场景缓冲放大防丢帧。降噪和唤醒词放端侧，理解放云侧，断网走端侧降级。」

### 追问应对
* 「音频和传感器时间戳为什么要对齐？」答：语音+传感器融合（如声纹+动作）需要精确时间关系，不对齐特征就错位。
* 「掉包怎么办？」答：包序号 + 重传/前向纠错（FEC）+ 缓冲隐藏（PLC），按场景取舍。

### 翻车点
* 说不清吞吐数字；把降噪都推给云侧；不知道 Opus 这类编码在低码率下的位置。

## 六、专题 5：传感器数据处理

### 高频考点
* 常见穿戴传感器与数据链路
* 采样率（ODR）、滤波与特征
* 时间戳对齐
* 数据质量验证

### 必掌握知识点
* 常见传感器：PPG 光学心率（ODR 25–100Hz）、加速度计（50–200Hz）、陀螺仪（100–400Hz）、磁力计、温度、气压（高度）、皮肤电导。
* 数据链路：采样 → 缓冲 → 滤波（低通去噪，截止频率按场景：静息 vs 运动）→ 特征提取（均值/方差/峰值/频域）→ 算法（计步、睡眠分期、活动识别、心率）→ 存储 → 同步。
* 滤波方法：一阶低通/IIR 简单去噪；互补滤波与卡尔曼用于姿态解算（IMU 融合）；运动伪影（心率被甩动干扰）用质量标签而非硬算。
* 时间戳对齐：设备本地单调时钟 + 定期对时（App 校准 offset），或统一到设备相对时间；不对齐会导致多传感器融合特征错位、云测算法无法复现。
* 数据质量：与参考设备（医疗级/专业手环）对比误差（心率 ±3bpm 量级）、缺失率、异常值比例；产线校准（如电池、温度）。

### 答题模板
「传感器链路我关注三件事：采样、时间戳、质量。采样按场景定 ODR：睡眠期心率 25Hz 够用，运动期 100Hz；加速度计 100Hz 做活动识别。时间戳用设备单调时钟 + App 定期对时，否则多传感器特征对不上。质量上，PPG 受运动伪影影响大，我会加质量标签而不是硬算，再用参考设备做误差验证，心率误差控制在 ±3bpm（估算）。」

### 追问应对
* 「为什么不用云侧算心率？」答：端侧算省流量省功耗，且实时性要求高；云侧只做长期趋势与训练。
* 「原始数据还是特征上传？」答：默认上传特征/摘要，原始数据按需或抽查，省功耗省带宽。

### 翻车点
* 只讲「收集数据」不讲滤波/质量/时间戳；分不清加速度计与陀螺仪的用途。

## 七、专题 6：C/C++ 与嵌入式基础

### 高频考点
* C/C++ 语言基础（指针、内存、结构体、位运算）
* 嵌入式概念（寄存器、中断、RTOS、通信总线）
* 协作能力：能读懂固件日志、能提有效 bug、知道协议栈

### 必掌握知识点（App 工程师视角，够协作即可）
* C/C++：指针与引用、栈/堆/静态区、struct 对齐与 padding、位域、大小端（BLE 协议普遍小端）、volatile（寄存器/中断共享变量）、static/extern、函数指针、位操作（掩码/移位）。
* 嵌入式：内存映射寄存器、ISR 要短（置标志 + 主循环处理）、看门狗、RTOS 基础（任务/信号量/队列）、DMA 降低 CPU 占用、构建（Makefile/CMake）、调试（JTAG/SWD、UART 日志）。
* 总线：UART（调试/低速率）、SPI（传感器/Flash，高速同步）、I2C（传感器/小容量，多设备寻址），能说清区别与选型。
* BLE SoC 平台认知：Nordic nRF52（SoftDevice 协议栈）、nRF53（Zephyr）、STM32WB、ESP32；固件日志常见格式与等级。
* 协作：接口契约文档、日志约定（时间戳/等级/模块）、问题分级（App/固件/协议/硬件），能看懂固件侧 buffer 与时序约束。

### 答题模板
「我日常不写固件，但合作时能读懂固件日志、看懂协议栈相关的 buffer 和时序概念。比如上次联调丢包，我判断可能是固件 buffer 溢出，因为 App 侧发了 200 包但固件日志显示只收 150 包，且没有 ack 窗口——这和固件代码里环形缓冲深度有关。我熟悉 UART/SPI/I2C 的区别、中断要短、volatile 的作用这些嵌入式常识，能帮固件同事一起定位，而不是只甩锅。」

### 追问应对
* 「你说你了解 C/C++，指针和引用区别？」答：引用是别名不可空，指针可空可重指；面试官在测你是否真懂，答对即可。
* 「大小端影响什么？」答：多字节字段的字节序不一致会解析错乱，协议文档必须写明；BLE 多为小端。

### 翻车点
* 装懂被追问穿帮——只讲确定会的；把「会用 Arduino」说成「懂嵌入式」；不知道 volatile/ISR 这类高频词。

## 八、专题 7：EVT / DVT / PVT 与量产交付

### 高频考点
* 各阶段定义与软件职责
* 产测（烧录/校准/功能测试）
* 试产与量产问题响应
* 版本冻结与变更控制

### 必掌握知识点
* EVT（工程验证）：功能验证与设计确认，软件重点是协议定型、功能联调、允许大改；交付物是可用 demo + 联调问题清单。
* DVT（设计验证）：设计定型，做可靠性/稳定性/OTA/功耗/认证测试；软件重点是修回归、补自动化、固化基线。
* PVT（量产验证）：验证产线能力，重点是产测工具链、良率、量产问题响应；软件重点是把产测流程跑稳。
* 产测项：烧录 MAC/SN、校准（电池/温度/传感器）、BLE 连接与功能自检、固件版本校验；产测工具可用 App 或独立工具，协议与正式 App 一致。
* 试产/量产：试产暴露产线问题（夹具、烧录速度、工位覆盖）；量产看直通率/良率/返工率；问题响应走 FA（失效分析）：复现 → 根因 → 纠正措施 → 预防。
* 版本冻结：硬件（HW）与固件（FW）版本锁定，App 要兼容已出货设备的固件版本矩阵；变更走 ECO/变更控制。

### 答题模板
「我完整跟过一个产品从 EVT 到量产：EVT 阶段我负责把 BLE 协议定型和功能联调跑通，问题允许大改；DVT 阶段做稳定性和 OTA 专项，固化了基线；PVT 阶段配合产测，把烧录、校准、BLE 自检流程跑稳，处理产线直通率问题。软件侧我最深的体会是版本冻结——App 必须维护已出货固件的兼容矩阵，不能因为新固件改协议就把老设备丢掉。」

### 追问应对
* 「量产阶段 App 每天会遇到什么问题？」答：产线环境（信号干扰、多设备同时连）、固件版本混杂、异常数据流；要日志可追踪、错误可分类。
* 「EVT 发现协议要改，怎么推动？」答：带数据（问题复现率、影响面）+ 兼容方案（版本协商/双协议），联合评审快速决策。

### 翻车点
* 说不出各阶段缩写含义；把量产问题当测试问题处理（没有 FA 思维）；不提兼容矩阵。

## 九、加分项专属高频面试题（带答题要点）

1. **穿戴设备续航怎么优化？** → 三层视角 + 测量基线 + 数字（专题 1 模板）。
2. **音频流走 BLE 的瓶颈？** → 吞吐测算（32KB/s vs 96KB/s）+ 压缩 + 缓冲时延（专题 4）。
3. **心率数据质量怎么保证？** → 质量标签 + 参考设备误差验证 + 时间戳（专题 5）。
4. **OTA 到一半断电？** → 双 bank 回滚 + 断点续传 + bootloader 恢复（专题 2）。
5. **离线同步什么时候会丢数据？** → 设备缓冲满 / App 被杀 / 云端去重；三路补偿兜底（专题 3）。
6. **你 C/C++ 到什么程度？** → 指针/内存/struct/大小端/volatile + 协作实例（专题 6）。
7. **EVT 发现协议问题怎么推动？** → 数据 + 兼容方案 + 联合评审（专题 7）。
8. **量产阶段 App 侧职责？** → 产测工具链、兼容矩阵、日志可追踪（专题 7）。
9. **传感器时间戳不对齐会怎样？** → 融合特征错位、云算法不可复现（专题 5）。
10. **低功耗下连接不能断，怎么办？** → 分层参数 + 场景切换 + 断连快速恢复（专题 1 + B6）。

## 十、硬件专题 STAR 故事补充

### H1：功耗优化（对标专题 1）
* S：续航只有 1.5 天，用户差评集中。
* T：把续航拉到 3 天（目标数字）。
* A：建场景测量基线 → BLE 空闲参数拉大 + 固件聚合 notify → 后台任务合并 → 发版前功耗回归。
* R：续航 1.5→3 天（估算），功耗回归成为发布门槛。

### H2：量产联调 / 产测（对标专题 7）
* S：PVT 阶段产线直通率只有 80%，卡在 BLE 连接不稳定。
* T：三天内把直通率拉到 95% 以上。
* A：现场抓包发现产线信号干扰 + 多设备同时连接冲突 → 产测工具加连接重试与信道选择 → 与产线工程师定夹具环境规范。
* R：直通率 80%→96%（估算），沉淀产测 checklist。

### H3：传感器数据质量（对标专题 5）
* S：心率算法在运动场景误差大，用户投诉。
* T：把运动场景心率误差降到 ±5bpm 以内（估算目标）。
* A：加运动伪影质量标签 → 调 ODR 与滤波 → 与参考设备做对比验证 → 端云分工调整。
* R：运动场景误差达标，误报投诉下降。
