# T5 教练出题集：架构与并发模式

> 学员人设：Swift/SwiftUI 开发者（见 [[01-学员人设卡.md]]）；预期在「把 MVVM/Coordinator 当 GoF 背、SwiftUI 里硬套 UIKit 导航、手动 DI 想不起 @Environment、Actor 当锁用」上暴露漏洞。
> 挂靠：UIKit MVC、全局依赖、手动导航、锁/队列经验；SwiftUI 状态管理、NavigationStack、@Environment、actor、Sendable。
> 使用纪律：学员卡住按「弱→中→强」逐级给提示，禁止跳级；直接要答案 → 拒答并反问「这是局部解法还是整体形状」（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | Swift 存量锚点 |
|---|------|-----------|------------|
| M1 | 模式 vs 架构：局部解法 vs 整体形状 | 模式看 Forces 匹配，架构看变更隔离；MVVM/Coordinator 是架构风格不是 GoF 模式 | MVC 是整体形状，delegate 是局部解法 |
| M2 | MVVM 是「状态与视图的解耦」 | View=声明式（body 是函数）、ViewModel=状态与逻辑、Model=数据；状态来源与拥有权决定选型 | UIKit MVC 里 Controller 越写越胖 |
| M3 | 导航是「页面流的编排」 | UIKit 时代 Coordinator 解决「谁 push 谁」；SwiftUI NavigationStack 把路径变成数据；Coordinator 只在混编/深层流程仍有价值 | `UINavigationController` 手动 push/pop |
| M4 | 依赖注入是「依赖关系的显式化」 | 手动注入 > 容器；DI 让可测试性成立；SwiftUI `@Environment` 是官方注入通道 | 全局依赖、static let 单例满天飞 |
| M5 | Actor 是「隔离域」不是「锁的语法糖」 | actor 串行执行、可重入、跨隔离域要 Sendable；「共享可变状态」的设计决策先于并发实现 | GCD 串行队列 + 锁的经验 |

学员自检要求：合上表复述 M1–M5，并各举一个自己项目里的架构/并发场景。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 SwiftUI 时代 Coordinator 是否过时？**
- 正方：NavigationStack 把导航变成数据（path 数组），声明式 + 可恢复，手写 Coordinator 是 UIKit 惯性。
- 反方：深层业务流（登录后跳转链、多 tab 联动、混编桥接）仍需要「导航逻辑」这一层，纯数据 path 表达不了跨模块编排。
- 对迁移者的意义：不是「用不用 Coordinator」，而是「导航逻辑放哪」——数据化优先，需要编排层时再引入。

**D2 依赖注入：手动 / 容器 / @Environment？**
- 正方：手动注入零依赖、类型安全、可读；@Environment 是 SwiftUI 官方通道；容器解决「大工程装配」但引入魔法。
- 反方：小工程手写注入样板多，容器自动装配省事。
- 对迁移者的意义：默认手动 + @Environment，容器是团队规模/复杂度到了才考虑的选项。

**D3 Actor 是否让锁 / 队列模式消失？**
- 正方：actor 把「串行 + 隔离」内建，锁和串行队列的手写样板可以退役。
- 反方：actor 可重入、死锁风险不同、性能有 hop 成本；锁在某些热路径仍必要。
- 对迁移者的意义：先做「共享状态设计决策」（该不该共享），再选实现（actor / 值类型 / 锁）。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只能复述定义 = 不过。**每题都要有「问题-约束」维度，只背名字不算回答。**

### C1 模式 vs 架构的分工？

问题：用你自己的话定义「架构风格」与「设计模式」的边界（局部解法 vs 整体形状、Forces 匹配 vs 变更隔离）；举一个「把架构当模式背」或「把模式当架构用」的错误例子。

### C2 MVVM 的边界：ViewModel 该放什么、不该放什么？

问题：说出 ViewModel 的职责（状态 + 业务逻辑 + 可测试）与红线（不碰 View、不持有生命周期）；SwiftUI 里 `@State` / `@StateObject` / `@Observable` 各适合什么状态，怎么选。

### C3 Coordinator 的适用边界？

问题：NavigationStack 的 path 数据化解决了什么（可恢复、可编程）、没解决什么（跨模块编排、混编、深层业务流）；给出「该用 Coordinator」与「不该用」的判断标准。

### C4 手动注入 vs 容器 vs @Environment 的取舍？

问题：三种方式的依赖可见性、类型安全、样板量、测试便利各是什么；给一个「该用 @Environment 却用了全局单例」的真实场景。

### C5 Actor 的隔离语义？

问题：说出 actor 的三条语义（串行执行、可重入、隔离域 + Sendable 边界）；与 GCD 串行队列的差异（可重入 vs 死锁、编译期隔离 vs 运行时约定）。

### C6 「共享可变状态」的设计决策？

问题：给出决策路径：该不该共享 → 共享粒度 → 实现选型（值类型 / actor / 锁）；用你项目里的一个「本来要加锁」的场景演示怎么用值类型或 actor 消除锁。

## 四、代码任务题（4 道，代码通道，挂 Phase 5 载体）

判定标准：本机 `swift` CLI 跑通 + 输出符合预期 + 学员逐行能讲 = 过。代码落 `代码/T5/`，输出贴回作答稿。

### Q1 MVVM 小工程（载体 5.1）

任务：写一个 SwiftUI 列表 + 状态管理小工程（如搜索 + 收藏列表）：朴素版（状态全在 View）vs MVVM 版（ViewModel + @Observable）。对比：状态归属、可测试性、修改点。

### Q2 导航对拍（载体 5.1）

任务：同一个「登录后进入主界面，可回退」流程，写两版：NavigationStack path 数据化版 vs 手动导航/Coordinator 版（可注释化 UIKit 对照）。对比：可恢复性、跨模块跳转的表达力。

### Q3 DI 三态对拍（载体 5.1）

任务：同一个「需要 Logger + Cache 的服务」，写三版：全局单例版、手动注入版、@Environment 版（SwiftUI 场景可注释化）。对比：测试替换点、依赖可见性。

### Q4 Actor 化重构（载体 5.1）

任务：把「共享可变缓存」（字典 + 锁，GCD 版）重构为 actor 版，并发读写打印证明安全；再写一个「actor 可重入」的翻车现场（await 挂起时状态被改），说明与锁的差异。
