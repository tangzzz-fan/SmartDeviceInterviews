# T3 教练出题集：结构型模式

> 学员人设：Swift/SwiftUI 开发者（见 [[01-学员人设卡.md]]）；预期在「Adapter/Facade 混用、Decorator/Proxy 分不清、继承惯性直接套协议组合」上暴露漏洞。
> 挂靠：extension 适配、类型包装、网络层封装；语言内建协议、泛型、`some`/`any`。
> 使用纪律：学员卡住按「弱→中→强」逐级给提示，禁止跳级；直接要答案 → 拒答并反问「这里变化的是接口还是行为」（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | Swift 存量锚点 |
|---|------|-----------|------------|
| M1 | Adapter 是「接口翻译」 | 让不兼容的接口协作：包装现有类型，把它的接口翻译成目标协议 | extension 适配第三方类型、类型包装 |
| M2 | Facade 是「统一入口」 | 子系统复杂时给一个简单门面，调用方不碰子系统内部 | 网络层统一入口、`XXXClient` |
| M3 | Decorator 是「可叠加的职责附加」 | 同一接口 + 递归包装，职责可叠加可组合 | extension 是静态补丁，Decorator 是运行时组合 |
| M4 | Proxy 是「控制访问的替身」 | 懒加载 / 缓存 / 权限 / 日志 / 远程；结构像 Decorator，Forces 不同（控访问 vs 加职责） | Swift 的懒加载属性、包装类型 |
| M5 | 结构型模式共用「组合优于继承」 | 协议组合是 Swift 主承载；判断先问「变化的是接口还是行为」 | 语言内建之前继承泛滥，因为组合样板贵 |

学员自检要求：合上表复述 M1–M5，并各举一个自己项目里的结构场景。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 Swift 里继承还有用吗（结构型语境）？**
- 正方：Swift 的协议 + extension + 泛型让「组合 + 复用」都便宜，继承只剩「is-a 身份」一个理由。
- 反方：UIKit/AppKit 生态建立在继承上（UIViewController 家族）；与 ObjC 互操作、框架回调仍要求继承。
- 对迁移者的意义：判断标准是「变化的是行为（组合）还是身份（继承）」，不是口号站队。

**D2 Facade 与 Adapter 的边界在哪？**
- 正方：Adapter 翻译接口（让 A 能用到 B），Facade 简化入口（让调用方不用认识子系统）——方向不同，不该混。
- 反方：实践中一个类常常既翻译又简化，边界是事后贴的标签。
- 对迁移者的意义：能说出「翻译」与「简化」的区别，并接受混合形态的诚实标注。

**D3 Proxy 与 Decorator 结构相同，靠什么区分？**
- 正方：靠 Forces/意图——Proxy 控访问，Decorator 加职责；同一个包装类在不同场景身份不同。
- 反方：运行时行为往往重叠（缓存既是控制访问也是附加职责），区分是文档工作不是代码工作。
- 对迁移者的意义：判模式先问约束，实现相同没关系；命名时按主导意图命名并写注释。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只能复述定义 = 不过。**每题都要有「问题-约束」维度，只背名字不算回答。**

### C1 Adapter 与 Facade 的区别？

问题：用「方向」区分两者：Adapter 解决什么问题（接口不兼容）、Facade 解决什么问题（子系统太复杂）；各给一个你在 Swift 项目里写过的真实例子，并说明怎么判断一个类更像哪个。

### C2 Decorator 在 Swift 里的实现形态？

问题：说出 Decorator 的递归包装结构（同一协议 + 包装引用 + 转发 + 附加职责）；对比 extension：为什么 extension 不是 Decorator？Swift 里协议默认实现 / 包装结构体分别适合什么场景？

### C3 Proxy 与 Decorator 怎么区分？

问题：给懒加载、缓存、权限校验、日志、指标上报五个场景，逐个判定「更像 Proxy 还是 Decorator」并说明理由；然后给出两者的判断轴（控访问 vs 加职责）。

### C4 「组合优于继承」的结构型判断标准？

问题：给出可操作标准（变化的是行为还是身份、是否需要替换/叠加、类型身份是否参与泛型约束），并用一个「继承惯性、该用协议组合」的例子验证。

### C5 Swift 协议 + 泛型对结构型模式的影响？

问题：Adapter 还需要吗？`some`/`any`、泛型约束让「接口适配」变便宜还是变复杂？给一个「Swift 里不用写 Adapter 类也能适配」的例子（如协议 + extension 适配第三方类型）。

### C6 结构型模式的共同代价？

问题：所有结构型模式都引入间接层。说出间接层的三类成本（可读性、调试、性能），并给出「什么时候收益大于成本」的判断标准；用你见过的「包装套包装」反例说明。

## 四、代码任务题（4 道，代码通道，挂 Phase 3 载体）

判定标准：本机 `swift` CLI 跑通 + 输出符合预期 + 学员逐行能讲 = 过。代码落 `代码/T3/`，输出贴回作答稿。

### Q1 网络层 Facade + Adapter（载体 3.1）

任务：模拟一个第三方 SDK（如旧的 `SDKClient`，方法名/参数不友好），写两层：Adapter 把 SDK 翻译成自己的 `HTTPClient` 协议；Facade 提供统一入口（`APIClient`，封装 baseURL/鉴权/序列化）。打印证明调用方只依赖 Facade。

### Q2 缓存 Proxy（载体 3.1）

任务：给一个「按 id 拉取用户」的接口加缓存 Proxy：第一次真实获取、之后命中缓存，打印请求次数证明缓存生效；并说明这个包装是 Proxy（控访问）还是 Decorator（加职责），为什么。

### Q3 Decorator 链（载体 3.1）

任务：实现可叠加的日志 / 指标 / 重试三个 Decorator，包装同一个「网络请求」协议，打印调用顺序证明职责叠加；再写一个反例：顺序敏感时 Decorator 为什么危险（如重试包在日志外 vs 内）。

### Q4 协议组合 vs 继承对拍（载体 3.1）

任务：同一需求（一个带缓存 + 日志 + 校验的数据源）两版实现：继承版（基类覆写）vs 协议组合版（包装组合），量化对比（类型数、修改点、可替换性），给出你的结论。
