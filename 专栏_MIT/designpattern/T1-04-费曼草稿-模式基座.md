# T1-04 费曼草稿：模式基座（示例）

> **示例文件**：本文件演示「脱稿重推 + 语言内建对照 + 60 秒讲稿」长什么样，用于格式参考，**不是真实产物**。

## 一、五模型脱稿重推

- **M1 模式 = 问题-约束-解法三元组**：模式不是代码模板。我自己的说法：模式是「在某种约束下，一类反复出现的问题的标准化答案」。判断一个东西是不是模式，先问它解决什么问题、在什么约束下成立——而不是它长得像什么。
- **M2 模式是词汇**：团队说「走 delegate」比描述十行机制省事。所以模式名字的价值是沟通，不是考试。先认问题再对号。
- **M3 语言内建优先**：Swift 把很多 GoF 实现变便宜了——拷贝、闭包、Combine 都是。但便宜不等于免费：闭包版 Command 没有撤销栈，Combine 订阅要自己管寿命。
- **M4 结构重于实现**：继承绑身份，组合绑行为。Swift 里协议 + extension 让组合既便宜又能复用。
- **M5 引入是负债决策**：每个模式都多一层间接。引入前记三行账：问题、代价、撤出条件。

## 二、语言内建对照

| Swift 惯用写法 | 对应模式 | 注意 |
|---------------|---------|------|
| protocol delegate | Strategy + Observer 混血 | 拆 should（决策）/ did（事件） |
| 闭包参数 | Command / Strategy 轻量版 | 无撤销栈 |
| Combine / @Observable | Observer | 订阅寿命自己管 |
| struct 值语义 | Prototype | 赋值即独立副本 |
| extension 适配 | Adapter（免包装版） | 需要状态时仍要包装 |

## 三、一个例子讲到底

我的搜索模块：原来一个 delegate 协议里混了「要不要加载更多」（决策）和「加载完成了」（事件）两种方法。按 T1 拆法，决策改成闭包属性、事件保留回调——不用新框架，就是把「问题」先分清楚。

## 四、60 秒讲稿

「设计模式不是 23 个名字。它是一套'问题-约束-解法'的检索系统：先问这段代码在解决什么、被什么约束着，再决定要不要套名字。Swift 已经把很多模式变便宜了——拷贝就是 Prototype，闭包就是命令，Combine 就是观察者——但便宜不等于免费，订阅要管寿命，闭包没有撤销栈。所以学模式学的不是背名字，是判断什么时候该引入、什么时候该拒绝。拒绝也要有理由，那才是真的会了。」
