## 一、概念题：提示梯与评分要点

### C1 Adapter 与 Facade 的区别？
- 弱提示：两个模式各自解决什么「痛」？一个是「接口对不上」，一个是「东西太多太乱」。
- 中提示：Adapter 改变的是「形状」还是「复杂度」？Facade 呢？
- 强提示：Adapter = 翻译（接口不兼容，包装后符合目标协议）；Facade = 简化（子系统内部不变，只给一个门面）。方向不同：Adapter 向内适配，Facade 向外简化。
- 评分要点：
  - 死记硬背典型：「Adapter 是封装，Facade 也是封装。」（无方向维度）
  - 真懂特征：能说出「翻译 vs 简化」的方向差异，Swift 例子真实。
- 参考答案：Adapter 让不兼容接口协作（翻译）；Facade 给复杂子系统统一入口（简化）。例：旧 SDK 包装成自己的协议 = Adapter；`APIManager` 统一 baseURL/鉴权/序列化 = Facade。

### C2 Decorator 在 Swift 里的实现形态？
- 弱提示：Decorator 的「结构」是什么——同一个协议、一个包装引用、转发调用、附加职责。extension 能做到「转发」吗？
- 中提示：extension 是给类型「加方法」（编译期静态），还是「包一个对象在运行时转发」？
- 强提示：Decorator = 递归包装（`protocol P` + `struct D: P { let wrapped: P; func f() { wrapped.f(); extra() } }`）；extension 是静态补丁（所有实例生效、不可组合顺序），不是运行时职责叠加。
- 评分要点：
  - 死记硬背典型：「extension 就是给类型加方法，等于 Decorator。」（静态/动态不分）
  - 真懂特征：能写出递归包装结构，讲清 extension 静态 vs Decorator 动态。
- 参考答案：Swift 里 Decorator 用「协议 + 包装结构体/类」实现，职责可叠加；extension 是编译期静态补丁，无法按实例选择职责组合，所以不是 Decorator。

### C3 Proxy 与 Decorator 怎么区分？
- 弱提示：五个场景的共同问题：包装的目的是「控制别人怎么用」还是「额外加东西」？
- 中提示：懒加载/缓存/权限/远程——都是在「访问」这件事上做手脚；日志/指标——是在「调用」之外加东西。
- 强提示：判断轴 = Forces：Proxy 控制访问（懒加载/缓存/权限/远程替身），Decorator 附加职责（日志/指标/重试，可叠加）；实现常重叠，按主导意图命名并注释。
- 评分要点：
  - 死记硬背典型：「有缓存就是 Proxy，加日志就是 Decorator。」（背标签，未讲 Forces）
  - 真懂特征：能按「控访问 vs 加职责」逐个判定五个场景，并接受混合形态。
- 参考答案：懒加载/缓存/权限/远程 = Proxy（控访问）；日志/指标 = Decorator（加职责）；重试按视角两可——挂在访问控制侧算 Proxy，挂在职责叠加侧算 Decorator。

### C4 「组合优于继承」的结构型判断标准？
- 弱提示：继承给了你身份 + 复用，代价是绑死一个父类；组合给了可替换，代价是样板。什么场景必须身份？
- 中提示：UIKit 的 `UIViewController` 子类、ObjC 互操作、框架回调——这些要求什么？
- 强提示：可操作标准：行为可替换/可叠加 → 协议组合；需要共享实现且行为固定 → 协议默认实现或继承；类型身份参与泛型约束/存储/框架回调 → 继承。例：网络层「带缓存的数据源」用组合包装，不搞 `BaseDataSource` 基类。
- 评分要点：
  - 死记硬背典型：「组合优于继承。」（口号）
  - 真懂特征：给出标准 + 真实例子，能说继承仍合理的场景。
- 参考答案：变化的是行为 → 组合；必须 is-a 身份（框架/互操作/泛型身份）→ 继承。Swift 协议默认实现让组合也能复用。

### C5 Swift 协议 + 泛型对结构型模式的影响？
- 弱提示：Swift 能不能给「别人写的类型」补上你自己的协议？什么机制？
- 中提示：`extension ThirdPartyType: MyProtocol { ... }` ——这是「接口翻译」吗？是不是免费的 Adapter？
- 强提示：协议 + extension 让「类型适配」经常不需要包装类（免 Adapter）；但需要附加状态/统一入口时仍要包装（Facade）或组合（Decorator）。泛型让适配更类型安全，也让包装样板更可见。
- 评分要点：
  - 死记硬背典型：「Swift 里模式都没用了。」（把内建吸收当废除）
  - 真懂特征：能区分「免 Adapter」与「仍需 Facade/Decorator」的边界。
- 参考答案：extension 适配第三方类型 = 免包装的 Adapter；需要状态、生命周期、统一入口时仍用包装。泛型/`some`/`any` 提升类型安全，不消灭结构型模式。

### C6 结构型模式的共同代价？
- 弱提示：多一层包装，读代码多跳几个文件？断点栈深几层？每次调用多几次转发？
- 中提示：三类成本：可读性（跳转）、调试（栈深/抽象掩盖真实类型）、性能（转发开销）。什么信号说明收益大于成本？
- 强提示：判断标准：包装是否对应「真实的替换/叠加需求」（能指出至少一个变化点）；包装层数是否可数（>3 层且无记账 = 反例）；性能敏感路径是否实测过。
- 评分要点：
  - 死记硬背典型：「包装是好的设计。」（无成本维度）
  - 真懂特征：能列三类成本，用「变化点 + 层数 + 实测」判定，举真实反例。
- 参考答案：结构型模式都付间接层税（可读性/调试/性能）；收益 = 有真实变化点（替换/叠加/控制访问）；层数失控且无记账 = 滥用信号。

## 二、争议焦点参考立场

- **D1 继承存废**：Swift 里继承只剩身份理由，但 UIKit/互操作/框架回调仍要求它；判断看「变化的是行为还是身份」。
- **D2 Facade vs Adapter**：方向不同（翻译 vs 简化），混合形态允许但必须诚实标注主导意图。
- **D3 Proxy vs Decorator**：靠 Forces/意图区分，实现重叠不改变命名纪律——按主导意图命名并写注释。

## 三、代码题：评分要点与提示

### Q1 网络层 Facade + Adapter
- 评分要点：Adapter 翻译 SDK → 自己的协议；Facade 统一入口（baseURL/鉴权/序列化收敛）；调用方只依赖 Facade；打印证明。
- 参考答案要点：`protocol HTTPClient` + `SDKClientAdapter: HTTPClient`（翻译）；`APIClient`（Facade）组合 HTTPClient + 鉴权/序列化；业务代码只碰 `APIClient`。

### Q2 缓存 Proxy
- 评分要点：请求计数证明缓存命中；能说明为什么是 Proxy（控访问：懒加载/缓存）而非 Decorator；边界诚实（缓存也可视为职责，按主导意图命名）。
- 参考答案要点：`UserLoaderProxy` 包 `UserLoader`，命中返回缓存不调下层；打印 `fetchCount`。

### Q3 Decorator 链
- 评分要点：日志/指标/重试可叠加且顺序可配；打印证明职责叠加；能演示顺序敏感反例（重试包在日志外 vs 内的行为差异）并解释。
- 参考答案要点：`LoggingDecorator` / `MetricsDecorator` / `RetryDecorator` 都实现同一协议；顺序不同 → 日志次数/重试粒度不同。

### Q4 协议组合 vs 继承对拍
- 评分要点：两版都可运行；量化真实（类型数、修改点、可替换性）；结论与账一致。
- 参考答案要点：继承版 `BaseDataSource` + 子类覆写；组合版 `CachedDataSource`/`LoggingDataSource` 包装；组合版可任意组合、替换，继承版新增能力要动继承树。
