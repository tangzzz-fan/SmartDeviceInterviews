## 一、概念题：提示梯与评分要点

### C1 模式 vs 架构的分工？
- 弱提示：一个模式管多大范围？一个架构管多大范围？
- 中提示：模式解决「一个类簇/一段流程」的问题；架构定义「模块边界、数据流方向、依赖规则」。MVVM 改变的是哪种？
- 强提示：模式看 Forces 匹配（局部、可替换）；架构看变更隔离（整体、长期演进）。错误例：「我们用 MVVM 模式」其实在说架构风格；「这段逻辑用 Observer 模式」在说局部解法。
- 评分要点：
  - 死记硬背典型：「MVVM 是一种设计模式。」（概念不分层）
  - 真懂特征：能按「范围与评判标准」区分，给真实错误例。
- 参考答案：模式 = 局部解法（Forces 匹配）；架构风格 = 整体形状（变更隔离）。MVVM/Coordinator 是架构风格；用错层级会让决策标准错位。

### C2 MVVM 的边界：ViewModel 该放什么、不该放什么？
- 弱提示：ViewModel 的「测试目标」是什么——不依赖 View 也能测的逻辑。那 View 相关的（布局/动画）该放哪？
- 中提示：`@State` 是视图私有临时态；`@StateObject`/`@Observable` 是跨视图共享模型；ViewModel 管的是「状态 + 逻辑」，不碰 UIKit/SwiftUI 视图类型。
- 强提示：放：状态、输入转换、业务/导航逻辑、可测纯函数；不放：View 引用、布局、动画、生命周期。选型：视图私有 → `@State`；共享对象 → `@Observable` + `@Environment`；纯计算 → 结构体/函数。
- 评分要点：
  - 死记硬背典型：「ViewModel 就是模型。」（职责不清）
  - 真懂特征：能给放/不放清单与状态选型，用例子验证。
- 参考答案：ViewModel = 状态 + 可测逻辑；View 相关一律不进；状态按作用域选 `@State`（私有）/`@Observable`（共享）/函数（纯计算）。

### C3 Coordinator 的适用边界？
- 弱提示：NavigationStack 的 path 是数据——它能恢复导航状态吗？它能表达「跨模块跳转 + 前置条件检查」吗？
- 中提示：path 解决「导航状态数据化」（可恢复/可编程/可深链）；不解决「跳转逻辑编排」（登录后去哪、多 tab 联动、A 模块请求 B 模块页面）。
- 强提示：判断标准：导航逻辑是否需要「独立于 View 的编排层」——深层业务流/混编/跨模块 → Coordinator 或导航服务；纯线性页面 → path 足够。SwiftUI 里 Coordinator 常退化成「导航服务」协议。
- 评分要点：
  - 死记硬背典型：「SwiftUI 不需要 Coordinator。」（一刀切）
  - 真懂特征：能说 path 解决了什么、没解决什么，给适用边界。
- 参考答案：path 数据化解决可恢复/可编程；跨模块编排、前置条件、混编桥接仍需导航层；判断看「导航逻辑复杂度和 View 的耦合」。

### C4 手动注入 vs 容器 vs @Environment 的取舍？
- 弱提示：三者的共同点是「依赖不进全局、从外部给」；差异在「怎么给、多显式、多少样板」。
- 中提示：手动注入最显式但样板多；@Environment 是 SwiftUI 官方通道（按视图树传递）；容器自动装配但依赖「魔法」与运行时错误。
- 强提示：默认手动 + @Environment；容器在「大工程、装配点集中、团队约定」时才划算。反例：全局挂 `static let` 单例 = 依赖隐式化，测试要重置全局状态。
- 评分要点：
  - 死记硬背典型：「用 DI 容器。」（无默认顺序）
  - 真懂特征：给默认顺序与升级条件，举真实反例。
- 参考答案：手动注入（默认，显式）→ @Environment（SwiftUI 树内）→ 容器（大工程装配）。全局单例是最差默认，因为它隐式且不可替换。

### C5 Actor 的隔离语义？
- 弱提示：actor 的方法在同一时刻能有多少个在执行？挂起时呢？
- 中提示：await 挂起时 actor 让出执行权（可重入）；GCD 串行队列则是排队不重入。隔离域 = 状态只能经 actor 方法访问（编译期），Sendable 是跨域传值的类型级承诺。
- 强提示：三条语义：串行（同刻一个方法）、可重入（await 处让位）、隔离（状态私有 + Sendable 边界）。与 GCD 串行队列差异：可重入 vs 死锁风险、编译期隔离 vs 运行时约定。
- 评分要点：
  - 死记硬背典型：「actor 就是串行队列。」（漏可重入与隔离）
  - 真懂特征：三条语义全讲，能说出与队列/锁的差异。
- 参考答案：actor = 串行执行 + 可重入 + 隔离域；可重入是并发安全设计（不堵门），但要求 check-then-act 谨慎；Sendable 是跨域传递的编译期契约。

### C6 「共享可变状态」的设计决策？
- 弱提示：先问「这个状态真的需要被多个人共享吗」——能不能改成值类型传递？
- 中提示：能值化 → 不共享；必须共享 → 按粒度选 actor（状态 + 方法）或锁（热路径小临界区）；「本来要加锁」的场景常能用「状态收进一个 actor」消除锁。
- 强提示：决策路径：该不该共享（值类型优先）→ 共享粒度（对象级 actor vs 临界区锁）→ 实现（actor/值类型/锁）。例子：缓存字典 → `actor Cache`，调用方 await 访问，锁消失。
- 评分要点：
  - 死记硬背典型：「并发就用 actor。」（没先做共享决策）
  - 真懂特征：走完整决策路径，演示锁 → actor 的重构。
- 参考答案：值类型优先（不共享）；必须共享时 actor 收状态（串行 + 隔离）；锁留给热路径小临界区；决策先于实现。

## 二、争议焦点参考立场

- **D1 Coordinator**：NavigationStack path 优先（数据化）；跨模块/混编/深层流程保留导航层；站死「必须/必须不用」= 半过。
- **D2 DI**：默认手动 + @Environment；容器是规模到了的升级，不是默认；全局单例是最差默认。
- **D3 Actor vs 锁**：actor 内建串行+隔离，退役大部分锁/队列样板；可重入与 hop 成本是新的认知点；热路径锁仍合理。

## 三、代码题：评分要点与提示

### Q1 MVVM 小工程
- 评分要点：两版都可运行；状态归属对比清楚（View 私有 vs ViewModel）；可测试性有证据（ViewModel 可脱离 View 测）；修改点量化。
- 参考答案要点：朴素版 `@State` 全在 View，逻辑不可测；MVVM 版 `@Observable ViewModel` 承载状态 + 逻辑，测试直接 new ViewModel。

### Q2 导航对拍
- 评分要点：path 版可恢复/可编程；手动版表达跨模块跳转；对比结论明确（何时用哪个）。
- 参考答案要点：`NavigationPath` 数据化（可恢复、可深链）；手动导航/Coordinator 显式编排（前置条件、跨模块）；混编场景 Coordinator 仍有用。

### Q3 DI 三态对拍
- 评分要点：三版依赖可见性对比；测试替换点清楚（单例版要重置全局）；@Environment 版说明 SwiftUI 传递机制。
- 参考答案要点：单例版依赖隐藏、测试需重置；手动注入版构造传参最显式；@Environment 版按视图树注入（`@Environment(\.logger)`）。

### Q4 Actor 化重构
- 评分要点：actor 版并发读写安全（打印证明无竞态）；可重入翻车现场真实（await 挂起状态被改）；能说清与锁的差异。
- 参考答案要点：`actor Cache` 收字典；`await cache.set(...)`；可重入反例：`get` 里 await 网络后基于旧值写 → 被别人改过，需要 check-then-act 处理。

## 四、使用纪律

- 判分只认证据：概念看「局部 vs 整体」「共享决策路径」推理链，代码看实跑输出与记账。
- 失真自查：把架构风格当模式背、actor 当锁用讲不清可重入 = 半懂当过关，需重跑。
