## 一、概念题：提示梯与评分要点

### C1 什么是设计模式？为什么「背 23 个名字」是无效学法？
- 弱提示：先别想「模式」，想「我在 Swift 项目里反复遇到的那类问题长什么样」——问题形状是什么，不是代码长相。
- 中提示：一个解法如果在两个完全不同的场景里都被反复用，它固定下来的东西是什么？是代码抄来抄去，还是「问题-约束-解法」的结构？
- 强提示：三元组 = 问题（什么信号 / 什么变化点）+ 约束（环境强加的边界，如线程、生命周期、单一职责）+ 解法（结构化答案）。背名字 = 只记住第三元，丢了前两元，所以遇到真问题对不上号。
- 评分要点：
  - 死记硬背典型：「模式是经过验证的可复用解决方案。」（只背定义，没有问题/约束维度，说不出失效机制）
  - 真懂特征：能用自己的 Swift 例子讲三元组；能说出背名字失效的机制（名字与 Forces 脱钩，识别时没有检索键）。
- 参考答案：模式 = 在特定约束下反复出现的问题的结构化解法；学习顺序是问题 → 约束 → 解法，名字只是检索键；背名字失效是因为「先有名字后有问题」的顺序颠倒，识别时只能靠长相猜。

### C2 GoF 四要素里 Forces 为什么最关键？
- 弱提示：四要素是 Context / Problem / Forces / Solution——哪个要素一变，同一个解法就会从「正确」变成「错误」？
- 中提示：同样的「包装一个对象并转发调用」，在「需要控制访问」和「需要附加职责」两个约束下，GoF 里分别叫什么？
- 强提示：Proxy 与 Decorator 结构几乎一样（都持有一个引用、都转发调用），区别全在 Forces：Proxy 控访问（懒加载/权限/缓存/远程），Decorator 加职责（可叠加、不改变接口）。还有 Strategy vs State 同理。
- 评分要点：
  - 死记硬背典型：「Decorator 是动态继承。」（只描述实现长相，没讲 Forces 身份）
  - 真懂特征：能举出结构同、Forces 异的模式对（Proxy/Decorator 或 Strategy/State），并说清判断依据（约束决定意图）。
- 参考答案：Forces 是「约束与张力」，决定解法是否匹配；结构长相相同 ≠ 模式相同，模式身份由「解决什么问题、在什么约束下」决定。判模式先问 Forces，再对类图。

### C3 语言内建优先：Swift 吸收了哪些 GoF 模式？
- 弱提示：先列 Swift 语言特性清单：值语义、闭包、协议、枚举、Combine、actor……再逐个问「GoF 里谁的工作被它抢了」。
- 中提示：拷贝是哪个模式的解法？把一段行为当参数传是哪个模式的对象替代？发布订阅是哪个模式？
- 强提示：Prototype→值语义（struct 拷贝即原型复制）；Command→闭包（捕获环境的一等值）；Strategy→函数参数 / 协议；Observer→Combine / @Observable；接口隔离→协议。吸收后省掉「显式对象 + 样板」，但失去显式对象带来的扩展点（闭包版 Command 没有撤销栈，Combine 订阅要自己管寿命）。
- 评分要点：
  - 死记硬背典型：「Swift 里不用学设计模式了。」（把吸收当废除）
  - 真懂特征：至少 3 个吸收关系，且每个都能说出「省了什么、失去什么」。
- 参考答案：语言内建吸收模式 ≠ 模式消失，而是「默认路径变便宜、显式路径仍存在」；学习重点是知道默认路径（拷贝/闭包/Combine）和它的边界（撤销、多播、动态替换时要回到显式对象）。

### C4 组合优于继承：判断标准是什么？
- 弱提示：继承给了你什么（类型身份 + 实现复用）、绑死了什么（一个父类）；组合给了你什么（行为可替换）、代价是什么（样板/装配）。
- 中提示：Swift 里协议 + extension + 泛型约束能表达「多个能力叠加」；继承能表达「is-a 身份」。哪些场景必须 is-a（与 ObjC 互操作、框架要求、存储类型身份）？
- 强提示：可操作标准：行为可替换/可叠加 → 协议组合；需要共享实现且行为固定 → 协议默认实现或继承；类型身份参与泛型约束/存储/框架回调 → 继承仍合理。语言内建之前继承泛滥是因为没有便宜的组合（extension 是静态补丁）。
- 评分要点：
  - 死记硬背典型：「组合优于继承，所以别用继承。」（口号，无判断标准）
  - 真懂特征：给出可操作标准并用自己的例子验证；能说出继承仍合理的场景。
- 参考答案：继承 = 身份 + 实现（绑死）；组合 = 行为装配（可替换）。Swift 协议默认实现让「组合 + 复用」都便宜，但 is-a 身份、ObjC 互操作、框架要求仍需要继承；判断先问「变化的是行为还是身份」。

### C5 protocol delegate 是哪种模式？
- 弱提示：delegate 的「问题」是什么——一个对象想把自己的某件事交给另一个对象决定/处理。这对应 GoF 哪一类（行为型）里的哪个？
- 中提示：NotificationCenter / Combine 是「多个对象想监听状态变化」；闭包参数是「把一段行为当参数传」。分别对应哪个模式？
- 强提示：protocol delegate ≈ Strategy（变化点交给协议，运行时替换）+ Observer（一对一回调，weak 引用防环）；NotificationCenter ≈ Observer；Combine/@Observable ≈ Observer（属性级）；闭包 ≈ Command / Strategy（行为参数化）。
- 评分要点：
  - 死记硬背典型：「delegate 是 Observer 模式。」（只记一个名字，没讲混血与边界）
  - 真懂特征：能区分 delegate 的 Strategy/Observer 双重身份，并说出 Swift 里按「问题」选承载（协议/闭包/Combine）而不是按语法惯性。
- 参考答案：Swift 的协议/闭包/Combine/@Observable 是多个模式的混血承载；用的时候不是换语法，而是先问「问题是什么」：变化点决策 → 协议；一次性行为 → 闭包；多播状态变化 → Combine/@Observable；一对一回调 → weak 协议。

### C6 模式滥用怎么判定？
- 弱提示：「负债」指什么——多一层间接，读代码要跨几个文件？改一个行为要动几处？测试要 mock 几个接口？
- 中提示：用 C4 记账：问题是什么、约束是什么、引入模式后代价是什么。什么时候账算不平？
- 强提示：滥用特征：没有「问题-约束」直接套名字；间接层收益小于成本（一行能改完的事拆成 5 个文件）；模式成了团队默认（「新代码必须分层」）而非问题驱动。
- 评分要点：
  - 死记硬背典型：「过度设计不好。」（无判定标准）
  - 真懂特征：给出可操作标准（账算不平 / 收益小于成本 / 约束不匹配）并用自己的反例演示。
- 参考答案：模式是负债决策：引入时记「问题-约束-代价」并写明撤出条件；滥用 = 先有名字后有问题的顺序颠倒，或账算不平（收益 < 间接层成本）仍硬上。

## 二、争议焦点参考立场

- **D1 GoF 在 Swift 时代**：合理立场是「问题结构永不过时，实现形态被内建吸收」——学 Forces 分析，不照搬类图；站死「过时」或「必须学」而无边界 = 半过。
- **D2 模式 vs 架构**：模式是局部解法（看 Forces 匹配），架构是整体形状（看变更隔离）；MVVM/Coordinator 是架构风格，用架构标准评判。
- **D3 什么时候拒绝**：约束不匹配 / 语言内建已覆盖 / 团队不熟 / 收益小于成本，任一成立即拒绝，且拒绝要给出可复现理由；「简单点」不算理由。

## 三、代码题：评分要点与提示

### Q1 模式识别器
- 评分要点：4 段每段都要有「候选模式 + 问题 + 约束 + Swift 等价」四元输出；至少一段结论是「不是模式/多模式混血」并有理由；只标名字不给约束 = 半过。
- 参考答案要点：A protocol delegate → Strategy（+Observer 混血），weak 协议或闭包属性；B `static let` 单例 → Singleton，问题=全局共享，约束=线程安全初始化，要注意可变状态批评；C 静态工厂 → Factory Method，静态工厂/协议；D 闭包回调 → Command 变体（行为参数化），闭包承载。

### Q2 三元组练习
- 评分要点：3 个真实问题三元组完整（问题/约束/解法）；至少一个「不用模式」结论有理由；编造项目 = 作废。
- 参考答案要点：格式示范——问题：设置页里多个 cell 点击后行为不同；约束：行为数量会涨、不想 if/else 爆炸；解法：Strategy（协议+实例数组）或直写 if/else（行为固定时）。结论可以是「行为固定 → 不用模式」。

### Q3 Prototype 对拍
- 评分要点：打印证据证明 struct 赋值独立、class 赋值共享；能讲「值语义 = 内建 Prototype」（拷贝即原型复制）；class 手写深拷贝思路清楚。
- 参考答案要点：struct Draft 赋值 = 逐字段拷贝（Array 成员 CoW），改 b 不影响 a；class Storage 赋值共享同一实例，改 b 连坐 a；class 要手写深拷贝才有独立副本，Swift struct 默认路径免费。

### Q4 模式引入记账
- 评分要点：两版都可运行；量化维度真实（行数/文件数/修改点/测试数）；结论明确且与账一致（账算不平还硬引入 = 判半过）。
- 参考答案要点：记账模板——问题：重试逻辑散落多处；约束：重试策略将来可能换（指数退避/固定间隔）；代价：引入 Strategy 后多 1 个协议 + N 个实现 + 装配点；结论：若策略确实多变 → 引入，若只有一种策略 → 直写并注释「需要时再提取」。

## 四、使用纪律

- 判分只认证据：概念看「问题-约束」推理链，代码看实跑输出与记账；撞墙记录须有真实报错。
- 失真自查：学员全题全对 → 人设失效；只背名字不讲 Forces → 识别失守需重跑；代码全靠抄也能判过 → 双通道失守。
