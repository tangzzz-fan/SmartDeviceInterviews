# T1 教练出题集：模式基座

> 本线为新建设计模式线（MIT-DesignPattern-Migration）。原料 = 学员 Swift/iOS 存量（protocol delegate/NotificationCenter/Combine/闭包/static let 单例/static func 工厂），教练按既有知识重建模型骨架。
> 学员人设：Swift/SwiftUI 开发者（见 [[01-学员人设卡.md]]）；预期在「把 GoF 当处方背、Singleton 万能化、继承惯性直接套协议组合、模式滥用判定」上暴露漏洞。
> 使用纪律：学员卡住按「弱→中→强」逐级给提示，禁止跳级；直接要答案 → 拒答并反问「你先识别出的问题是什么、约束是什么」（C1/C2）。提示与评分要点在密卷（仅教练分支），本文件是题干版。

## 一、共识：5 个核心心智模型

| # | 模型 | 一句话骨架 | Swift 存量锚点 |
|---|------|-----------|------------|
| M1 | 模式 = 问题-约束-解法三元组 | 模式不是代码模板，是「在什么约束下解决什么问题」的结构化答案；同一个解法在不同约束下是不同模式 | delegate 不是「协议」，而是「把变化点交给调用方」的解法 |
| M2 | 模式是词汇，价值在沟通 | 模式压缩沟通成本：「用 Observer」比描述十行机制省一个段落；先认问题再对号，禁止背名字 | 团队说「走 delegate」时没人再描述实现 |
| M3 | 语言内建优先 | 现代语言会「吸收」模式：Swift 值语义吸收 Prototype、闭包吸收 Command/Strategy、Combine 吸收 Observer、协议吸收接口隔离 | 语言内建之前这些都要手写 |
| M4 | 结构重于实现：组合优于继承 | 继承绑定类型身份，组合只绑定行为；Swift 的协议 + extension 让组合更便宜 | extension 是静态补丁，不是类型级组合 |
| M5 | 引入模式是负债决策 | 每个模式都带来间接层（可读性/调试/测试成本）；引入前要记账：解决什么问题、付什么代价、什么时候撤 | 见过「为模式而模式」的代码，说不清好在哪 |

学员自检要求：合上表复述 M1–M5 并各举一个自己项目里的例子；读不懂 → 按零基规则先补前置。

## 二、争议：专家吵得最凶的 3 个焦点

**D1 GoF（1994）在 Swift/SwiftUI 时代还剩多少价值？**
- 正方最强论据：模式是语言无关的「问题结构」，SwiftUI 里 Observer/Command/状态提升仍然成立；GoF 的类图过时但 Forces 分析不过时。
- 反方最强论据：GoF 大量实现被语言内建吸收（拷贝、闭包、Combine、协议默认实现），照搬类图是负资产；学「内建特性」比学「绕路实现」更正确。
- 对迁移者的意义：正确姿势是「先学问题-约束，再学语言内建改写，最后才是 GoF 术语」——术语是检索键，不是答案。

**D2 模式与架构的分工是什么？**
- 模式派：模式就是架构的积木，MVVM/Coordinator 只是更大粒度的模式。
- 架构派：模式是局部解法（一个类簇/一段流程），架构是整体形状（模块边界、数据流方向、依赖规则）；混着背会两头都说不清。
- 对迁移者的意义：本线 T1–T4 管局部解法，T5 才进架构层；评判标准不同（模式看 Forces 匹配，架构看变更隔离）。

**D3 什么时候该拒绝一个模式？**
- 正方：约束不匹配、语言内建已覆盖、团队不熟、收益小于间接层成本——四个条件任一成立就拒绝；拒绝要能说出理由而不是「简单点」。
- 反方：拒绝往往是因为不熟；「先写简单版，需要时再引入」在需求频繁变化时会欠下重构债。
- 对迁移者的意义：本线把「拒绝」也当考点——能论证拒绝的模式学习者，比能背出所有模式的人更接近会用。

## 三、概念拷问题（6 道，口述通道）

判定标准：能讲出「为什么」并迁移到新场景 = 过；只能复述定义 = 不过。**每题都要有「问题-约束」维度，只背名字不算回答。**

### C1 什么是设计模式？为什么「背 23 个名字」是无效学法？

问题：用自己的话定义「设计模式」，必须包含「问题-约束-解法」三个维度；然后解释：一个程序员把 GoF 23 个模式的名字和类图都背下来了，为什么遇到真问题还是用不出来？失效的机制是什么？

### C2 GoF 四要素里 Forces 为什么最关键？

问题：GoF 四要素是 Context / Problem / Forces / Solution。说出每个要素的作用，然后论证「Forces 决定模式身份」：举一个「两个模式结构长得几乎一样、但 Forces 不同所以是不同模式」的例子（如 Proxy 与 Decorator），并说明判断依据。

### C3 语言内建优先：Swift 吸收了哪些 GoF 模式？

问题：至少说出三个「被 Swift 语言特性吸收」的 GoF 模式（如值语义→Prototype、闭包→Command/Strategy、Combine→Observer），每个说明：内建机制是什么、吸收后省掉了什么、**又失去了什么**（例如闭包版 Command 没有撤销栈）。

### C4 组合优于继承：判断标准是什么？

问题：说出「组合优于继承」在 Swift 里的可操作判断标准（什么情况用协议组合、什么情况继承仍然合理、协议默认实现在这中间扮演什么角色），并用你项目里的一个例子验证。不许只说口号。

### C5 protocol delegate 是哪种模式？

问题：Swift 里 protocol delegate / 闭包参数 / NotificationCenter / Combine / @Observable 各自对应哪个（或哪几个）GoF 模式？protocol delegate 为什么常被说成「Strategy 与 Observer 的混血」？

### C6 模式滥用怎么判定？

问题：给「为了模式而模式」的代码做一次 C4 记账：列出它的负债（间接层、调试成本、修改点数量），并给出你判断「该不该引入」的可操作标准。用你见过的真实反例说明。

## 四、代码任务题（4 道，代码通道，挂 Phase 1 载体）

判定标准：本机 `swift` CLI 跑通 + 输出符合预期 + 学员逐行能讲 = 过。代码落 `代码/T1/`，输出贴回作答稿。

### Q1 模式识别器（载体 1.1）

任务：读入下面 4 段代码片段，对每段输出「候选模式 + 问题 + 约束 + Swift 等价写法」四元组。至少一段的结论必须是「不是模式，只是普通写法」或「多模式混血」，并说明理由。

```swift
// 片段 A：protocol delegate
protocol LoginDelegate: AnyObject {
    func loginDidSucceed(_ vc: LoginVC)
}

// 片段 B：单例
final class NetworkManager {
    static let shared = NetworkManager()
    private init() {}
}

// 片段 C：静态工厂
enum PaymentFactory {
    static func make(type: PaymentType) -> Payment {
        switch type {
        case .alipay: return Alipay()
        case .wechat: return WeChat()
        }
    }
}

// 片段 D：闭包回调
button.addAction(UIAction { [weak self] _ in self?.didTap() }, for: .touchUpInside)
```

### Q2 三元组练习（载体 1.1 前置）

任务：从你自己真实写过的项目里选 3 个「反复出现的问题」，各写一个「问题-约束-解法」三元组，并给出候选模式（可以没有）。**至少一个三元组的结论必须是「结论：不用模式」**，并给出理由。

### Q3 Prototype 对拍：值语义为什么「免费」实现了 Prototype（载体 1.2）

任务：实现一个 class 存储盒 + struct 包装的最小例子，打印证明：struct 赋值后两边独立（拷贝语义内建），class 赋值后共享（需要手写深拷贝）。再说明 class 场景为什么不能靠 struct 白拿、需要手写深拷贝（注释说明即可）。用 print 输出证明「Swift 的默认路径就是 Prototype」。

脚手架：
```swift
final class Storage { var items: [String] = [] }
struct Draft { var storage: Storage }
// var a = Draft(...); var b = a; b.storage.items.append("x")  // 观察 a 是否被连坐
```

### Q4 模式引入记账（载体 1.1 收尾）

任务：选一个「小功能」（如按钮点击后的重试逻辑），写两版实现——版本一：朴素直写；版本二：套 Strategy 或 Observer（协议/闭包任一）。量化对比：行数、文件/类型数、修改一个行为要动几处、测试数量。最后给出明确结论（该引入 / 不该引入）和你的「问题-约束-代价」账。
