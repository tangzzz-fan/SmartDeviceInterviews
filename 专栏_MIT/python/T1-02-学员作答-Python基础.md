## 二、争议焦点

**F1 GIL 是缺陷吗**：有条件成立。CPU 密集多线程拿不到并行，这确实是限制；但 IO 密集场景 GIL 基本无感，而且 numpy/torch 这类 C 扩展在计算时会释放 GIL，所以 LLM 训练这种重计算场景其实绕开了它。我的立场：**对「纯 Python CPU 密集多线程」是缺陷，对生态整体是历史权衡**。自评：有把握（工程直觉主场）。

**F2 全量类型注解**：大型多人长期项目该上，脚本和数据探索不必。我在 Swift 里被编译器兜底惯了，深知「没编译器时纪律要补位」——typing + mypy 就是 Python 的替代纪律。但胶水代码强推全量注解是形式主义。自评：有把握。

**F3 何时放弃惰性**：数据太大内存放不下时用生成器；反过来，需要**多次遍历同一批数据**、或者要**随机访问/取长度**时就该物化成 list。还有一个场景我想不太确定：调试的时候，list 能直接打印全量，生成器只能消费一次，看现场不方便。自评：半懂半猜（调试那条是现推的）。

## 三、概念口述题

**C1**：
- 第 1 段：`a` 变成 `[1, 2, 3]`。`b = a` 没有复制，两个名字指同一个 list。Swift 里 Array 是值语义，`b.append` 会触发 CoW，a 不受影响——这个我确定。
- 第 2 段：我判断 `a` **不受影响**，还是 `[[1, 2], [3, 4]]`——都 copy 了嘛，b 改 b 的。
- 第 3 段：刷题时见过这个坑，两次打印是 `['x']` 和 `['x', 'y']`，默认列表会累积。但为什么我下一题再说，这里只有「坑的印象」。
- Swift 对照：值语义 + CoW，b 写时复制，a 不变。
- 自评：**半懂半猜**（第 2 段我是凭「copy 了就该隔离」的直觉，没底）。

**C2**：默认列表记住上次调用……我推到这一层：`def` 语句应该是在**定义时**就执行了，不是每次调用都重新执行，所以那个 `[]` 只创建了一次，后面调用共享它。至于这个默认值**存在哪里**、为什么函数能「记住」，我说不清——猜测是跟函数对象绑在一起？函数在 Python 里好像也是对象。自评：**半懂半猜**（机制层到「定义时求值一次」为止，存储位置是猜的）。

**C3**：`is` 比较是不是同一个对象（身份），`==` 比较值相不相等。`[[0]*3]*3`……我认为是三行各自独立，改 `m[0][0]` 只影响第一行。不踩坑的建法我会写列表推导：`[[0]*3 for _ in range(3)]`——刷题时背过这个写法，但说实话我不太确定为什么 `*` 那种写法不行。自评：**纯猜**（矩阵那段）/ 有把握（is vs ==）。

**C4**：for 循环背后：先拿一个迭代器（`iter(obj)`？），然后反复取下一个元素（`next()`？），取完了抛一个异常结束——`StopIteration` 这个名字我记得到。「可迭代对象」是能被 for 的东西，「迭代器」是真正干活维护进度的东西，两者区别我能说到这但再往下就糊了。生成器表达式不能遍历两次：我知道**现象**——消费完就空了，但为什么，我猜是它「记住了已经走到哪」，状态用完就没了。自评：**半懂半猜**。

**C5**：
- ① GIL 锁什么：同一时刻只让一个线程执行 Python 代码。锁的到底是什么实体……我说是「解释器的执行权」？再细就说不出。
- ② CPU 密集没收益好理解：大家轮流拿锁等于串行。IO 密集有收益——我**听说过**线程等 IO 时会把锁让出去，别的线程趁机跑，但「在哪个点释放」讲不出。
- ③ multiprocessing：每个进程一个独立的 Python 解释器，各有各的 GIL，所以真并行。这条我有把握，进程隔离的心智从 iOS 多进程经验来。
- 自评：**半懂半猜**（①②糊，③有把握）。

**C6**：
- ① `@deco` 本质是 `f = deco(f)`，高阶函数。这个我写过简单的，确定。
- ② 带参的 `@retry(times=3)`：比无参的多一层……`retry(times=3)` 得先执行、返回一个真正的装饰器再去包函数。为什么多这层——因为参数要在装饰之前就定下来？我只能说到这。
- ③ `functools.wraps`：不加的话被装饰函数的 `__name__` 会变成 wrapper 的名字，调试时一堆 wrapper 分不清谁是谁。我在脚本里撞过这个。为什么「重要」除了调试我还说不上更多。
- 自评：**半懂半猜**。

## 四、代码任务通道

**Q4 预测**（写代码前立的）：
| 场景 | 单线程 | 多线程 | 多进程 |
|------|--------|--------|--------|
| CPU 密集 | 基线 | ≈基线（可能更慢） | ≈快 4 倍 |
| IO 密集 | 基线 | ≈快 8 倍 | 也快，但没必要 |

理由：GIL 让 CPU 密集多线程轮流拿锁；IO 等待时释放锁；进程各有解释器。

**实跑结果**（`.venv/bin/python`，CPython 3.12.13，四题退出码均为 0，完整输出在批改稿可复查）：

- Q1 翻车合集：三个现场全部复现（默认参数 `['x']→['x','y']`、矩阵三行 id 相同整列联动、dict 被函数偷改），三个修复版断言全过；附加发现 `dict(d)` 只隔一层，嵌套还得 deepcopy。
- Q2 分页加载器：百万条分 4 页（30万×3 + 残余 10万），总条数 1000000；第二次消费打印 `[]`，现象与注释解释一致。
- Q3 重试装饰器：前两次失败日志 + 第三次 `200 OK`；`__name__` 打印为 `flaky_api`，wraps 生效；超次数正确抛出（共尝试 2 次）。
- Q4 实测：CPU 密集 单线程 1.01s / 多线程 0.91s / 多进程 0.29s；IO 密集 单线程 3.23s / 多线程 0.41s / 多进程 0.46s。**预测与实测一致**——多线程 CPU 没有并行收益（甚至不显著快），多进程 3.5 倍提速，IO 多线程 8 倍提速。
