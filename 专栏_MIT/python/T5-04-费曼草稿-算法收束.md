# T5-04 费曼草稿：算法收束（Python 标准库武器化）

> 学员写回稿。规则：不看任何资料重推五模型，写「给外行讲懂」的版本；按题干条款③，本轮以「Swift 版 vs Python 版」对比小节为骨架。

## 一、五模型重推（脱稿版）

**M1 LRU = 两个 O(1) 的乘积**：LRU 要同时做到「O(1) 找到任意键」和「O(1) 找到并踢掉最旧者」——哈希表只给前者（它无序），双链只给后者（它找键要 O(n)），把节点同时挂在两个结构里（哈希存 key→节点，双链存使用顺序），两个 O(1) 相乘才是 LRU。OrderedDict 就是这个结构的标准库化身：move_to_end = 摘节点接头，popitem(last=False) = 摘最旧。

**M2 流式 Top-K 选对堆**：维护「K 个最大」用的是**最小堆**——堆顶是这 K 个里最弱的，语义是「门槛」：新来的比门槛大才替换，判断只看堆顶 O(1)。总复杂度 O(n log k)。bisect.insort 不是对手：二分只解决「找位置」O(log k)，list.insert 的搬移是 O(k)，流式插满就是 O(nk)。

**M3 DP 三件套 + Python 专属陷阱**：状态定义 → 转移方程 → 初始化边界，三步里 Python 的初始化有专属坑：`[[0]*n]*m` 是 m 个同一行的别名（外层乘法复制的是引用不是对象）。本轮我概念全对还是手滑复发，病根分析：别名让「写第 i 行」和「读第 i-1 行」串成一件事，01 背包被悄悄变成完全背包，**没有对拍断言就静默通过**——这是全线最深的一次陷阱复盘。

**M4 复杂度定增长，常数定起点**：同一个 O(n)，纯 Python 循环求和 67ms，sum() 16ms，numpy 0.13ms——算法复杂度一样，常数差出两个数量级，因为字节码逐条解释 vs C 层直循环的每步开销差 10~100 倍。反直觉的一面：n 小的时候 O(n) 的 C 层实现能吊打 O(1) 的纯 Python 结构（Q1 实测容量 64 时朴素版更快，8192 时才显形 27 倍）——**「O(1) 一定快」是错的，耗时断言必须扫容量**。

**M5 武器表**：bisect（二分定位）、heapq（最小堆）、deque（双端+单调队列）、Counter（计数）、切片（批处理）。手写二分、手写计数、手写滑窗都是「武器旧」的信号；每个武器一句适用边界比背 API 值钱。

## 二、Swift 版 vs Python 版（本轮骨架）

| 维度 | Swift 侧心智 | Python 侧真相 | 对照结论 |
|------|-------------|--------------|---------|
| 二维数组初始化 | `Array(repeating:)` 值语义逐份拷贝，改一份不牵连 | `[[0]*n]*m` 复制引用，改一行全体变 | **值语义是白送的保险，引用语义要自己买**——买法：推导式初始化 + 对拍断言 |
| 循环开销 | 编译后 for 循环与 reduce 几乎同速（实测 0.4ms vs 0.4ms，1.00×） | for 循环比 sum() 慢 4.1×，比 numpy 慢 500× | Swift 里「怎么写都行」的循环习惯，搬到 Python 就是性能债——**瓶颈在解释器不在算法** |
| 引用环 | 双链互指必须 weak 破环（ARC 不收环） | 敢用强引用互指（分代 GC 兜底），但摘节点手动断链是纪律 | 语言替你还的债都有对价：Swift 对价是 weak 心智负担，Python 对价是 GC 延迟与断链纪律 |
| 优化器 | swiftc -O 会删掉没人用的计算（DCE 墙：reduce 被测代码整段消失） | CPython 不删你的代码，但会解释执行每一条 | **跨语言基准先怀疑计时器，再怀疑编译器优化掉了被测代码**——Swift 侧的新教训 |
| 标准库 | 泛型算法（sort/reduce）本来就是首选 | 内置武器（sorted/sum/Counter）是「把常数拉回来」的关键 | 两侧殊途同归：生产代码优先标准库，手写版本的价值只在面试与学习 |

## 三、给 iOS 同事讲懂（自检段落）

模拟对象：只会 Swift、没写过 Python 的同事，场景是「你要转 Python 做后端/ML，算法功底够，我怕你踩什么」。

> 「你的算法功底一分不用丢，丢的是三个 Swift 白送你的保险。第一，二维数组初始化：Swift 里 Array 是值语义，repeating 出来的每行各自独立；Python 的 `[[0]*3]*4` 四行是同一个对象——我刷题几百道，这轮还是栽了，而且栽得隐蔽：01 背包被它悄悄变成完全背包，不写测试根本发现不了。第二，别信复杂度直觉：你在 Swift 里 O(n) 和 O(1) 差不了几毫秒，Python 里 64 个元素的 O(n) 列表操作就是快过 O(1) 的纯 Python 双链——常数被 C 层实现吞掉了，规模拉大才显形。第三，写基准测试小心编译器：你习惯 `_ =` 扔掉不用的结果，在 swiftc -O 下这会让被测代码被整段删掉，测出 0 毫秒——把结果存下来打印，优化器才不敢删。」

自检结果：三条「白送的保险」框架同事秒懂——「保险」这个比喻比「语义差异」好讲，因为它带责任归属（谁替你兜底、对价是什么）。卡壳过一次：讲 DCE 墙时我先说「编译器优化太激进」，同事反问「那怎么防」，我才意识到重点是**基准测试的防御纪律**而不是吐槽编译器——教训复用（同 T3）：观点先于形式，先说「怎么办」再说「为什么」。

## 四、60 秒讲稿（电梯版）

Python 刷题和 Swift 刷题思路一样，规则变了：复杂度只管增长曲线，常数才定起点——C 实现的内置函数比纯 Python 循环快一到两个数量级，小规模时 O(n) 甚至能赢 O(1)。三个保命纪律：二维表初始化用推导式别用乘号；耗时结论必须扫容量不许单点断言；跨语言基准先怀疑计时器和编译器，再怀疑代码。

## 五、本轮学习复盘

本轮是强项区翻转考法：思路层全过，六堵墙全在常数/测量/陷阱层——这说明「会做」和「做得对、测得准」之间隔着整整一层工程纪律。三条方法论收编（接 T3/T4 的清单）：① **耗时断言必须扫容量，不许单点断言**（Q1 常数直觉被打穿的直接产物）；② **测量方法学**：perf_counter + 重复取 min（min 只会被噪声拉长不会被缩短）、跨语言基准先怀疑计时器再怀疑编译器 DCE；③ **「学过 ≠ 写熟题不犯」的处方是清单化**——陷阱知识放进「下笔前自查清单」（二维表必推导式），比指望肌肉记忆可靠。C6 的半过提醒我：专用结构（单调队列）与通用结构（堆）的取舍，差在「这个结构只能回答什么问题」的视野层——T6 的 async 工具选型（TaskGroup vs 手搓）预期是同类考题。
