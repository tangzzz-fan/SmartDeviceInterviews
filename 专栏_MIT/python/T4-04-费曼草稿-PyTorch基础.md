## 一、五模型重推（脱稿版）

**M1 Tensor = ndarray + 记账本**：数值计算和 numpy 一样，但开了 requires_grad 之后，每次运算都在计算图上「记一笔」——输出张量挂一个 grad_fn，记录是哪个运算、存了反向需要的中间量。backward 不是沿函数调用栈走（函数早返回了），而是在这张运行时的 DAG 上逆拓扑序遍历，每个节点拿存下的中间量算局部导数，链式相乘，最后在叶参数的 .grad 里累加。**图是对象不是代码**——这是我本轮换掉的最大旧心智。

**M2 动态图：现搭现拆**：每次 forward 现建一张图，backward 用完默认释放非叶节点的缓冲区——所以同一张图不能 backward 两次（要留就 retain_graph=True，GAN、多 loss 分传是真实场景）。动态图的代价是图级优化做不了；torch.compile 把动态图 trace 成静态图再编译，两条路线在收敛。

**M3 梯度是累加不是覆盖**：.grad 语义是「把本图的贡献加上去」，不清场。这是 feature：梯度累积（显存不够时攒 micro-batch，loss 取平均时数学等价大 batch）、多任务多 loss。引擎没法预知你调几次 backward，覆盖会悄悄弄丢合法的前一次梯度——累加是线性安全的默认。zero_grad 是调用者的纪律，不是引擎的义务。

**M4 nn.Module = 参数容器 + 行为协议**：`__setattr__` 是守门人——赋 Parameter 进 _parameters 字典、赋子 Module 进 _modules 字典，parameters() 递归这两张字典收集；普通 tensor 属性不会被收集（实测 print 为空）。训练走 `model(x)` 而不是 `model.forward(x)`，因为 `__call__` 管 hook（监控/特征提取全靠它）。register_buffer 是第三类：参与 forward、不要梯度、随 state_dict 保存（BatchNorm 的 running_mean）。

**M5 五步循环，每步都有「去掉会怎样」**：forward（建图）→ loss（定优化目标）→ zero_grad（不清则累加爆炸，等效 lr 线性膨胀）→ backward（算 grad；去掉则 step 拿 None/陈旧梯度）→ step（用 grad 改 param；放前面则滞后一步）。DataLoader 侧：Dataset 管「第 i 个样本」，DataLoader 管「怎么组 batch」。

## 二、推导链断环自查清单（批改遗留项①）

三轮三个断点：T2 PCA 拉格朗日链、T3 MLE→交叉熵三环、T4 ReLU 门。共同规律写成清单：
1. **非线性/门控处必查**：ReLU、sigmoid、softmax——「显然没影响的一环」恰是断环高发区（ReLU 门漏乘，W1 全错而 W2 全对，误差分布直接指出断点在下游）。
2. **归一化/平均的系数必查**：mean 损失的 1/N、batch 合并的权重分母——「平均的平均」先写每份分子分母再合并。
3. **跨框架布局必查**：weight 的 (in,out)/(out,in)、dtype——换框架先 print 形状与精度，别拿旧心智猜。
4. **兜底纪律**：一切手写导数/手写合并，必须有数值对拍或性质断言，对拍误差分布本身就是断点定位器。

## 三、Swift/iOS 对照小节

- **version counter = 「遍历时禁止修改」的同一哲学**：Swift 里枚举数组时改数组当场 crash，torch 里 backward 依赖的中间量被 in-place 改过当场 RuntimeError——都是「宁可炸，不装对」，防止拿着被污染的数悄悄算错。
- **存 loss 张量做统计 = retain cycle**：张量引用着计算图，图存着所有中间量——把 loss 张量留在循环里就像强引用闭包里的 self，显存/内存随时间泄漏；`.item()` 就是那声 `[weak self]`。
- **view/detach/clone = 引用语义的所有权管理**：Swift 的 CoW 替你做「写时复制」，torch 不做——view 是借出引用（写穿透），clone/detach 是交接所有权。分界线不是性能是「这块内存接下来归谁动」。
- **`__call__` vs 直接调 forward = 协议入口 vs 绕过协议**：像 delegate 模式里你不直接调实现方法、走统一入口才能触发框架的钩子。

## 四、给 iOS 同事讲懂（自检段落，T4 强制）

模拟对象：只会 UIKit/Swift、没碰过 ML 的同事。

> 「把模型训练想成记账。forward 是花钱：每笔开销都留一张小票（计算图上记一条边，小票上存着反向要用的数字）。backward 是对账：从总账单（loss）出发，沿着小票一路倒着追，算出『每个员工该为总账单负多少责』——这就是每个参数的梯度。有两个规矩：第一，对账是**往上加**不是覆盖——因为有时你要把几张小账合起来一起对（显存不够时分批训练），系统不知道你对几次账，覆盖会弄丢前一次的结果；所以每次重新对账前要自己喊一声『清账本』（zero_grad）。第二，小票上的数字**不许涂改**——每个张量有版本号，你涂改了，对账时发现版本对不上直接报错，宁可报错也不拿涂改过的数算出错的账。至于为什么不能直接调 forward 要 model(x)——就像你不会绕过 delegate 入口直接调实现方法，统一入口才有 hook 给你挂监控。」

自检结果：记账类比我同事接得住（「版本号不许涂改」他立刻联想到遍历时修改 crash）；「梯度往上加」用「分批对账」讲通了用途。卡壳过一次：解释「图是对象不是代码」时我先说「图存在内存里」——同事问「哪块内存、谁持有」，我答成「张量持有 grad_fn」才具体化。**教训复用：讲引用语义的东西，先回答『谁持有什么』，Swift 工程师的直觉入口就是所有权。**

## 五、60 秒讲稿（电梯版）

训练一个模型就是记账与对账：forward 花钱留小票（计算图），backward 沿小票倒着追责算出每个参数该负多少（梯度）。梯度是累加的——分批对账要靠它，所以每轮对账前自己清账本（zero_grad）。小票上的数字不许涂改，涂改了版本号对不上当场报错。五步循环 forward→loss→zero_grad→backward→step，每一步去掉都会出具体事故：累加爆炸、拿陈旧梯度、优化错目标。nn.Module 靠 `__setattr__` 自动登记参数，走 `model(x)` 统一入口才有 hook。
