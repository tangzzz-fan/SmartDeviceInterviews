## 一句话骨架

**Python 里一切皆对象，名字只是贴在对象上的标签；可变对象默认共享，隔离要靠你显式拷贝且分深浅两层；协议不靠声明靠魔术方法；迭代器是统一的消费接口但生成器是一次性的；并发天花板由 GIL 划定——IO 靠线程/asyncio，CPU 靠多进程。**

## 二、五个模型用自己的话重推

**M1 名字是标签，不是盒子。**`a = [1,2]; b = a` 之后只有一个 list 对象、两张标签。所以改 b 就是改 a——不是「b 影响了 a」，而是根本没有两个东西。Swift 里变量像带类型的盒子，赋值触发值复制（或 CoW 延迟复制）；Python 的「复制」只发生在你显式喊 copy 的时候。

**M2 隔离要显式，拷贝分深浅。**`a.copy()` 只复制外层容器，内层元素还是同一批对象——所以浅拷贝矩阵改一格会整列联动。要彻底隔离用 `copy.deepcopy`。还有个更隐蔽的变体：可变默认参数 `def f(x=[])`——def 语句在定义时执行一次，那个 `[]` 被挂进函数对象的 `__defaults__`，所有调用共享它。修复套路统一：None 哨兵 + 函数体内新建。

**M3 协议靠魔术方法，duck typing 替代声明。**Swift 里协议是显式契约（`conformsTo` 可查）；Python 里行为就是契约——实现了 `__iter__` 就能被 for，调用方根本不查你的类型。自由换来了责任：没有编译器兜底，纪律（测试、类型注解）得自己补位。

**M4 迭代器是统一消费接口，生成器是一次性的。**for 循环展开就是 `iter()` 拿迭代器 + 反复 `next()` + `StopIteration` 收场。关键区分：**可迭代对象是工厂**（list 每次 iter 出个新迭代器，所以能遍历无数次），**生成器对象自产自销**（iter 返回自己，状态耗尽即空）——Q2 里我想二次遍历分页器得到空列表，撞的就是这堵墙。

**M5 GIL 划定并发天花板。**GIL 锁的是 CPython 解释器的全局状态（根源是引用计数的线程安全），效果是同一时刻只有一个线程执行 Python 字节码。推论三条：CPU 密集多线程轮流拿锁没有并行收益（实测 1.01s vs 0.91s），多进程各有解释器真并行（0.29s）；IO 密集时线程等待会释放 GIL，多线程收益明显（3.23s → 0.41s）。numpy/torch 在 C 层计算时主动放锁，所以 LLM 的重计算场景其实绕开了 GIL。

## 三、Swift/iOS 对照小节

| Swift 心智 | Python 现实 | 翻译要点 |
|-----------|-----------|---------|
| Array/Dictionary 值语义 + CoW | list/dict 引用语义，默认共享 | 边界处显式拷贝；嵌套结构先想深浅 |
| 赋值即复制的直觉 | 赋值即贴标签 | 「赋值即复制」是 T1 最大病灶，已在 C3 复攻重塑，T5 DP 初始化是复发高危区 |
| protocol 显式声明 | 魔术方法 + duck typing | 协议隐式化，测试与注解补纪律位 |
| Sequence 可反复 makeIterator | 生成器 = 工厂与消费者合一 | 惰性管道默认一次性，要复用先物化或 tee |
| GCD 并发队列 / actor | GIL 下的线程/进程/asyncio | 先判 IO 还是 CPU 密集再选工具；「丢到另一个队列」的本能在 Python 要换成「换执行模型」 |
| 编译器兜底 | 运行时才见真章 | 撞墙前移：id() 打印、断言、实跑验证成为日常 |

## 四、给 iOS 同事讲的 60 秒版本

「把 Python 想成一个没有值语义、没有编译器兜底的 Swift：变量是便利贴不是盒子，list 赋给别人就是共享同一份数据，想隔离得自己 copy，还分深浅两层；函数定义时就执行了一次，默认参数是挂在函数对象身上的，可变默认参数会跨调用累积；for 循环背后是 iter/next 协议，生成器是一次性消费；线程被 GIL 锁成伪并行——等 IO 时放锁所以 IO 密集多线程有用，CPU 密集必须多进程。我们 Q4 实测过：CPU 密集多进程快 3.5 倍，IO 密集多线程快 8 倍，数据在代码里。」
