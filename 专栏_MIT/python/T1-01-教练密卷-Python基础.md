## 一、概念题评分要点与提示

### C1 三段现场 + Swift 对照
- **判分点**：①第1段 a=[1,2,3] 且说出「两个名字指同一对象」；②第2段 a=[[1,2,99],[3,4]] 且说出 copy 是浅拷贝、内层对象仍共享；③第3段 ['x'] 与 ['x','y']；④Swift 对照：Array 是值语义 + CoW，b.append 触发写时复制，a 不受影响。
- **弱提示**：先想 M1——赋值语句里到底复制了什么？
- **中提示**：第2段用 `id(a[0])` 和 `id(b[0])` 思考；第3段想「默认值在函数定义还是调用时求值」。
- **强提示**：Python 变量是标签不是盒子；`.copy()` 只复制外层容器一层；Swift Array 是 struct，赋值后首次写触发 CoW。
- **复习线变式题**（答得太顺时追加）：`t = ([1,2], [3,4]); t[0] += [9]` 会发生什么？（元组不可变但元素可变，抛 TypeError 前列表已被改——考「不可变容器装可变对象」）

### C2 默认参数机制
- **判分点**：①def 语句是可执行语句，模块加载/定义时执行一次；②默认值对象求值后挂在函数对象的 `__defaults__` 上；③每次调用不传参就复用同一对象，可变对象的修改因此累积；④修复：默认 None + 函数体内新建。能说出 `f.__defaults__` 加分。
- **弱提示**：定位到「定义 vs 调用」两个时机——默认值属于哪个时机？
- **中提示**：函数也是对象，默认值存在它身上——可以 `print(tag.__defaults__)` 验证。
- **强提示**：def 执行时 `[]` 只求值一次并绑到函数对象的 `__defaults__` 元组，之后每次调用共享它。
- **复习线变式题**：默认值是 `tuple()` 或 `1` 时还有这个坑吗？为什么社区仍建议 None 哨兵？

### C3 is/== 与浅拷贝矩阵
- **判分点**：①`is` 比身份（同一对象/id）、`==` 比值（调 `__eq__`）；②`[[0]*3]*3` 外层复制的是三个**同一内层 list 的引用**，改一行即三行联动；③两种修法：列表推导 `[ [0]*3 for _ in range(3) ]`（每次新建内层）或 `copy.deepcopy`。
- **弱提示**：`*` 对 list 做的是拷贝还是重复引用？
- **中提示**：打印 `[id(row) for row in m]` 看看三个 id。
- **强提示**：`[x]*n` 产生 n 个指向同一对象的引用；推导式每次循环重新求值 `[0]*3`，才是 n 个独立对象。
- **复习线变式题**：`[0]*3` 本身为什么没有这个坑？（int 不可变，共享无害）

### C4 for 协议与生成器一次性
- **判分点**：①for 先调 `iter(obj)` 拿迭代器（要求实现 `__iter__`），再反复 `next()`（`__next__`）直到 `StopIteration`；②可迭代对象 = 有 `__iter__`（每次返回新迭代器），迭代器 = 有 `__next__` 且自带状态；③生成器对象本身就是迭代器，状态（挂起的帧）消费完即 Exhausted，第二次 `iter()` 返回的是它自己，直接 StopIteration。
- **弱提示**：for 循环可以被手动展开成哪两个内置函数的组合？
- **中提示**：区分「能生产迭代器的工厂」与「迭代器本身」——list 是哪种？生成器对象是哪种？
- **强提示**：`iter(list_obj)` 每次返回新的 list_iterator；而 `iter(gen)` 返回 gen 自己——工厂和消费者是同一个对象，自然一次性。
- **复习线变式题**：`itertools.tee` 能让生成器「被两个人消费」吗？它的代价是什么？

### C5 GIL 三层
- **判分点**：①GIL 是 CPython 解释器的互斥锁，保护的是**解释器内部状态（引用计数等内存管理结构）**，效果是同一时刻只有一个线程执行 Python 字节码；②CPU 密集：线程拿锁轮流跑，无并行还多了切换开销；IO 密集：线程在等 IO 时**释放 GIL**，别的线程可跑，所以有收益；③multiprocessing 是多个独立进程、各有独立解释器与独立 GIL，真并行（代价是内存不共享、序列化开销）。
- **弱提示**：先问「GIL 保护解释器的什么东西不被多线程弄坏」。
- **中提示**：线程在 IO 阻塞时的 GIL 状态是关键差异点。
- **强提示**：GIL 锁的是 CPython 全局状态（根源是引用计数的线程安全），IO 等待时释放、CPU 计算时持有；进程 = 多个解释器实例。
- **复习线变式题**：numpy 的矩阵运算为什么能「绕开 GIL」加速？（C 扩展计算时主动释放 GIL）

### C6 装饰器三连
- **判分点**：①`@deco` ≡ `f = deco(f)`，本质是高阶函数 + 闭包；②带参装饰器是三层：`retry(times=3)` 先执行返回真正的装饰器，再套用到函数——多了「装饰器工厂」一层；③不加 wraps 丢 `__name__`/`__doc__` 等元信息，影响调试、文档、以及依赖函数名的框架（路由、测试收集）。
- **弱提示**：把 `@deco` 手动展开成一行赋值试试。
- **中提示**：`retry(times=3)` 里，先被调用的是谁？它的返回值是什么角色？
- **强提示**：`@retry(times=3)` ≡ `f = retry(times=3)(f)`；wraps 把被装饰函数的元属性抄回 wrapper。
- **复习线变式题**：类也可以当装饰器（实现 `__call__`）——相比闭包版多了什么能力？（可持有状态、可被实例化多次）

## 二、争议焦点参考立场（考边界，不考站队）

- **F1 GIL 缺陷论**：合理立场是「有条件成立」——对 CPU 密集多线程是限制（历史包袱：为引用计数选的全局锁），但对单线程性能与 C 扩展生态是保护性设计；证据面：numpy/torch 在 C 层释放 GIL 实现并行、3.13 free-threading 实验说明社区正在移除它、「IO 密集场景 GIL 无感」。站死「是缺陷」或「不是缺陷」而无条件边界 = 半过。
- **F2 类型注解门禁**：合理立场分场景——大型/多人/长期项目值得全量注解 + mypy 门禁（无编译器兜底的替代纪律）；一次性脚本、数据探索、重 duck typing 的框架胶水层强制全量是过度工程。能挂靠「Swift 编译器兜底 vs Python 测试+注解兜底」的迁移视角加分。
- **F3 惰性 vs 急切**：放弃惰性的场景——需要多次遍历、需要随机访问/长度、需要复用中间结果、调试要看全量数据、数据量小且后续要排序（排序本就需物化）。只答「内存大就用生成器」无条件 = 半过。

## 三、代码题评分要点与提示

### Q1 引用语义翻车合集（挂项目 1.4）
- **判分点**：三个现场都能用运行输出证明翻车（不是靠注释声称）；修复版分别对应：None 哨兵、逐行新建（推导式）或 deepcopy、调用方传副本或函数内 `dict(d)`；末尾断言真实执行；文件头有撞墙记录。
- **弱提示**：每个翻车现场先打印 `id()` 找证据。
- **中提示**：三个修复的公共思路是「在边界处新建对象」——分别在哪个边界？
- **强提示**：默认参数用 `items=None: items = [] if items is None else items`；矩阵用 `[ [0]*3 for _ in range(3) ]`；dict 隔离用 `copy.deepcopy(d)` 或 `dict(d)`（注意后者只隔一层）。

### Q2 生成器分页加载器（挂项目 1.1）
- **判分点**：`paged_loader` 是生成器函数（含 yield）；source 是生成器（如 `(i for i in range(N))`），全程未物化；分页边界正确（最后一页不足 page_size）；「第二次消费为空」有实测输出 + 注释讲到「生成器即迭代器、状态已 Exhausted」。
- **弱提示**：页内收集用什么结构？页满时用 yield 交出什么？
- **中提示**：source 耗尽时内层 for 自然结束——最后一批残余怎么处理？
- **强提示**：骨架：`page=[]; for item in source: page.append(item); if len(page)>=page_size: yield page; page=[]`，循环结束后 `if page: yield page`。

### Q3 带参重试装饰器（挂项目 1.3）
- **判分点**：三层结构正确（工厂 → 装饰器 → wrapper）；异常类型可配或至少捕获指定异常；重试计数与最终抛出正确；`functools.wraps(fn)` 生效（`__name__` 打印为原函数名）；演示函数前两次失败第三次成功有输出证据。
- **弱提示**：对比无参装饰器，`retry(times=3)` 这行代码先执行的是什么？
- **中提示**：把三层函数从外到内命名成 factory/decorator/wrapper，各接收什么？
- **强提示**：`def retry(times, delay=0): def decorator(fn): @functools.wraps(fn) def wrapper(*a, **kw): for attempt in range(times): try: return fn(...) except ...`。

### Q4 并发边界实测（挂项目 1.5）
- **判分点**：预测写在作答稿且四象限齐全（CPU×3方式、IO×3方式）；实测输出贴回；结论命中：CPU 密集多线程≈或慢于单线程、多进程明显快；IO 密集多线程明显快、多进程也行但没必要；能归因到 GIL 与 IO 释放锁。工作量超时（>15s 总时长）扣分——工程约束也是考点。
- **弱提示**：先确认你的 CPU 密集函数没有偷偷调 C 扩展（numpy 会破坏实验）。
- **中提示**：IO 场景多进程为什么「也行但不该」？想想进程创建成本与数据不共享。
- **强提示**：CPU 用纯 Python 循环（如大数累加/质数筛），IO 用 `time.sleep(0.5)`×8 个任务；threading 8 线程 vs sequential 对拍。
