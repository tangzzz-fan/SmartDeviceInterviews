# MIT 三问攻坚：iOS 老手复习 Python 与 LLM 前置数学 —— 学习计划

> 目标：学员 agent（人设见 [[01-学员人设卡.md|01-学员人设卡]]）用 MIT 三问法复习 Python 基础、LLM 前置数学（线代、概率论）、PyTorch 基础与基础算法，达到能独立写 Python 工程代码、读懂并训练基础神经网络的水平。
> 方法基座：[[04-方法论基座-MIT三问与测试协议.md|方法论基座]]（MIT 三问学习法四点改造 + C1–C5 纪律，自包含，与 Swift 线同一份方法论）。
> 分支：**双分支协议**——教练分支 `feat/mit-python-study`（计划+密卷+批改）与学员分支 `feat/mit-python-study-student`（题干+学员产出），见第三节。本文件只是计划与台账，出题/作答/批改产出另起文件，落在对应分支的本目录。
> 案例参照：[`../MIT-Swift-migration/`](../MIT-Swift-migration/) 是同一方法的完整闭环案例（T1–T6 四件套 + 代码实跑），本线格式照它对齐。

## 一、原料策略

本线是**复习线**而非迁移线：无外部教材依赖，模型骨架与考点由教练按既有知识重建并自洽（各 `T{n}-01` 文件头须注明）。学员的存量骨架是 **iOS/Swift 工程功底 + 大学数学残存记忆 + 浅度 Python 使用经验**——三问的共识模型主动挂靠这些旧知做锚点（如 Swift 值语义 → Python 引用语义反例、actor → GIL、Swift Array/Dictionary → list/dict、大学线代 → 张量运算），挂靠不上的地方（动态类型心智、autograd、Pythonic 习惯）才是真正的学习区。

## 二、主题与顺序

顺序逻辑：语言地基（T1）→ LLM 数学前置（T2 线代 → T3 概率论，线代是概率向量化的前置）→ 框架落地（T4 PyTorch，吃 T2/T3 的数学）→ 算法收束（T5，用 Python 手感 + 工程直觉收）→ 工程落地（T6，async/await + LLM 企业落地实操，吃 T1 并发心智与 T4/T5 工程手感；T6 为学员明确要求的显式增量轮）→ LLM 企业落地补齐（T7–T9，2026-08-17 学员要求按独立文件补齐全链路：API 客户端与提示工程 → Embedding/向量检索（RAG 基座）→ 模型面 tokenizer/Transformer，均为独立增量轮）。

| 序 | 主题 | 拷问重点 |
|---|------|---------|
| T1 | Python 基础：数据模型、引用语义、迭代器/生成器、装饰器、并发（GIL） | 可变对象陷阱、可变默认参数、深/浅拷贝、duck typing 与协议、GIL 与 asyncio 心智 |
| T2 | 线性代数（LLM 前置）：向量/矩阵、矩阵乘法、线性变换、特征分解、SVD | 矩阵乘法的三重解释（变换/组合/内积）、形状推导、PCA 直觉、为什么神经网络全是矩阵乘法 |
| T3 | 概率论（LLM 前置）：随机变量、分布、条件概率与贝叶斯、期望/方差、MLE 与交叉熵 | 贝叶斯更新直觉、softmax 的来历、MLE → 交叉熵损失推导、数值稳定性 |
| T4 | PyTorch 基础：Tensor、autograd、nn.Module、训练循环 | 计算图与动态图、梯度为何累加、view 共享存储陷阱、为什么要 zero_grad、Dataset/DataLoader |

## 三、每主题执行流程（教练 + 学员双 agent 仿真）

沿用双 agent 仿真格式（四件套规范见 [[04-方法论基座-MIT三问与测试协议.md|方法论基座]]，格式范例见 Swift 线 T1–T6 既有产出），每主题产出四件套：

1. **教练出题**：出「共识五模型 + 争议三焦点」→ 出拷问题（概念口述题 + 代码任务题，各配弱/中/强三级提示与评分要点）。落 `T{n}-01-教练出题-<主题>.md`。
2. **学员作答**：严格按 [[01-学员人设卡.md|人设卡]] 作答——该对的凭 iOS 工程功底与残存数学记忆对，该错的地方如实错，禁止全知全能。落 `T{n}-02-学员作答-<主题>.md`。
3. **批改判定**：逐题判 过关 / 半过（拆判分点）/ 未过；概念题看「能否讲出为什么并迁移新场景」，代码题看本机是否跑通。落 `T{n}-03-批改与判定-<主题>.md`。
4. **费曼写回**：全过的主题用自己的话重写一篇草稿落本目录（`T{n}-04-费曼草稿-<主题>.md`，含 Swift/iOS 对照小节）；未过的缺口记台账复攻，不写草稿。

**代码通道环境**（2026-08-15 搭建，2026-08-16 torch 就绪）：统一用 **uv 管理的项目虚拟环境**——`MIT-Python-Migration/.venv`（CPython 3.12.13，uv 0.11.32 创建，已装 numpy 2.5.2 与 torch 2.13.0）。规则：
- 全部代码题用 `.venv/bin/python` 运行（不再用系统 python3 3.9.6），每个文件顶部注释标注对应题号；
- 依赖安装走 `uv pip install --python .venv/bin/python <包名>`；
- `.venv` 不入库（.gitignore 已配），环境重建命令：`uv venv --python 3.12 .venv`；
- 输出贴回批改文件作为硬验证证据，「AI 说我懂了」不算数，跑通才算数。

### 双分支协议（防假学习）

目的：让学员（含真人使用者）在作答前**物理上看不到**评分要点、三级提示与参考答案，从机制上堵死「先看答案再复述」的假学习。

| 分支 | 角色 | 持有内容 |
|------|------|---------|
| `feat/mit-python-study`（教练分支） | 教练 agent | 00–04 骨架文档、`T{n}-01-教练出题`（含共识模型/争议焦点/题干）、`T{n}-01-教练密卷`（评分要点、三级提示、参考答案）、`T{n}-03-批改与判定`、掌握度台账 |
| `feat/mit-python-study-student`（学员分支） | 学员 agent / 真人学员 | 从教练分支分出：骨架文档 + 题干 + 学员产出（`T{n}-02-学员作答`、`代码/T{n}/`、`T{n}-04-费曼草稿`）+ `学员须知.md` |

**文件拆分约定**：每主题出题时拆两份——`T{n}-01-教练出题-<主题>.md`（题干，两分支都有）与 `T{n}-01-教练密卷-<主题>.md`（评分要点+提示+参考答案，仅教练分支）。

**每轮同步流程**：① 教练在教练分支出题（题干+密卷）→ ② 题干文件同步到学员分支（仅拷贝题干文件，**严禁 merge/cherry-pick 整个教练分支**，否则密卷泄漏）→ ③ 学员在学员分支闭卷作答并提交 → ④ 教练把学员分支合并回教练分支，阅卷出 `T{n}-03` → ⑤ 费曼稿落学员分支，教练复核。

**合并方向速记（唯一合法方向：学员 → 教练）**：

```
main（Swift 线归档，Python 线不碰）
  └── feat/mit-python-study（教练分支：骨架+密卷+批改+台账）
        │   ② 选择性同步题干（单文件拷贝，绝不整支合并）
        ▼
      feat/mit-python-study-student（学员分支：题干+作答+费曼）
        │   ④ git merge feat/mit-python-study-student（教练阅卷=合并学员交卷）
        ▲
```

- 你在 git log 里看到的合并（如 `merge(T1): 教练合并学员分支阅卷`）都是**学员分支并入教练分支**——这就是「交卷→阅卷」动作本身，不是合进 main；`main` 始终停在 Swift 线归档，两条学习分支在整线收官前不合入 main。
- 反方向（教练→学员）永远不走 merge，只允许单文件选择性同步（`git checkout feat/mit-python-study -- <题干文件>` 后在学员分支单独提交）。

**用户视角操作手册（真人学员）**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 开工 | `git checkout feat/mit-python-study-student` | 日常只在学员分支干活；本分支看不到密卷和批改 |
| 领题 | 新题出现 = 教练在本分支新提交了一个 `T{n}-01-教练出题` 文件 | 教练用选择性同步放入，不会带入密卷 |
| 作答 | 写 `T{n}-02`、代码放 `代码/T{n}/`，用 `.venv/bin/python` 实跑 | 见 [[学员须知.md|学员须知]] |
| 交卷 | `git add -A && git commit -m "feat(T{n}): ..."` | 提交即交卷，等教练合并阅卷 |
| 判定 | 教练口头/对话传达判定；`T{n}-03` 批改文件闭轮前只留教练分支 | **闭轮后**教练可将批改文件选择性同步到学员分支归档复盘（复攻记录中的提示此时查看无害） |
| 费曼 | 全销账后写 `T{n}-04` 并 commit | 教练复核后整轮收官 |

**失真红线**：学员分支出现任何提示、评分要点或参考答案内容（含误合并）= 泄漏，该轮作废重跑。教练每次同步后须自查学员分支文件清单（`git ls-tree` 确认无密卷文件）。

## 四、执行纪律（照搬测试协议 C1–C5）

| # | 纪律 | 在本攻坚中的含义 |
|---|------|----------------|
| C1 | 先弱提示 | 学员卡住时先只定位概念不给方向；学员立刻想到答案说明提示太强，降级重出 |
| C2 | 拒答代学 | 学员直接要答案 → 拒给，反问已排除了什么 |
| C3 | 双通道强制 | 概念口述过关后必须追加代码任务，只有口述不算过关 |
| C4 | 台账如实 | 未过不得写「过关」，半过必须拆判分点注明缺口；数学题的「会算但讲不出直觉」按半过处理 |
| C5 | 产出落本目录 | 全部产出落迁移目录内，不直写外部知识库 |

失败标准（出现即说明仿真失真，需重跑）：学员 agent 全题全对（人设失效）、或代码题全靠教练代写也能判过（C3 失守）。复习线特有的失真信号：**数学题全靠「套公式算对」而无几何/直觉解释也算过关**——这是复习掩盖理解空洞的典型病灶，批改时按半过拆判。

## 六、执行节奏

- 每主题一轮闭环（出题 → 作答 → 批改 → 费曼），跑完记台账再开下一主题；未过缺口先复攻再前进。
- 拷问与项目双线并行：拷问题暴露的缺口优先复攻，[[02-项目驱动实践路线.md|项目路线]] 的迭代提供硬验证实体；两边互相出题。
- T2/T3/T4 是复习线最容易「假过关」的区域（会算 ≠ 懂、会跑 ≠ 懂）：费曼草稿里必须含「能不能给一个 iOS 同事讲懂」的自检段落。
