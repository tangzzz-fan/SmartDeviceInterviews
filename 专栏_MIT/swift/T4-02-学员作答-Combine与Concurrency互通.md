# T4 学员作答：Combine 与 Concurrency 互通

> 学员背景自述：delegate/KVO/通知玩了十年，发布订阅是我主场——但 T3 刚教过我「主场最容易轻敌」。本轮先读五篇原料、标 KVO/通知锚点，再闭卷作答。人设卡预告的三病灶（背压、边界判定、AnyCancellable）我作答时尽量不提前看答案，错了如实错。

## 一、共识复述：M1–M5 用自己的话

**M1 订阅是合同不是通知**：通知是广播、注册完不返回值；Combine 的 sink 返回一个「凭证」，要自己存着。这个「存」字我读的时候心里咯噔一下——T2 的 Q2 注释里好像埋过这个钩子，当时没深究。方向我信，细节等 Q2 代码验证。
**自评：半懂半猜**（方向对，「为什么非存不可」的机制空白）。

**M2 背压**：原料说「需求逆流而上」——我第一反应还是「发了就收」，这是十年通知刻出来的。Demand 这个词我能读，但「订阅时先报需求、处理完再要」这个协议我没有任何实感锚点。KVO 和通知里根本没有「下游说话」的机会。
**自评：纯猜以下**（字面读过，心智没动）。

**M3 操作符是声明式管道，错误是一等公民**：操作符链我类比「流水线工位」没问题——每个工位返回新的流水线，装配完才开机。错误走 Failure 类型参数这个跟 T3 的 throws 一个路数，方向顺。retry/catch 是阀门的比喻我接受，但 retry 到底「重」的是什么我说不准。
**自评：半懂半猜**（管道类比稳，retry 语义悬）。

**M4 边界与桥**：T3 费曼稿里我站了分界线（单值/序列走 async、复杂流算子走 Combine），这轮要把它变成可执行规则。`publisher.values` 变 AsyncSequence 这个桥我见过 API 没用过。
**自评：半懂半猜**（分界线有，判定细则和桥都悬）。

**M5 @Published 是插座**：T2 的 Q2 我亲手跑过 @Published 的发射器，will 语义是撞墙撞出来的。对象级广播这个说法我有印象分（T2 D3），但「改一个属性、全部依赖重算」的完整机制链我还没亲手验过。
**自评：半懂半猜**（T2 存量够一半，粒度细节等 Q2）。

## 二、概念拷问题作答

### C1 订阅的生命周期：sink 的返回值是什么？

第一反应（如实）：sink 了就开始收数据，返回值……好像是有的？T2 Q2 的注释里提过「不存 cancellable 订阅立刻取消」，当时我记成「记得存就行」，没问为什么。
按 ARC 硬推：返回的 AnyCancellable 应该是个引用类型对象，代表这个订阅关系。不存的话——临时变量出作用域就释放了……那订阅关系还在吗？如果取消逻辑挂在它的 deinit 上，那确实一释放就取消。这个推理我自己都不太信：设计成这样岂不是坑人？
KVO 对照我能说：KVO 的义务是「手动 removeObserver」，忘删会崩；Combine 看起来把义务换成了「必须持有凭证」。
**自评：半懂半猜**（ARC 推理方向摸到了，但「为什么不存就取消」的设计意图推不动，等代码验证）。

### C2 背压：Combine 和通知到底差在哪？

「Combine 是通知升级版」哪里对：都是发布订阅、都能一对多。哪里断裂——老实说我现在的答案还是「发了就收，跟通知一样」，只是通知没有类型、没有操作符。
Demand 我按原料复述：订阅方先报「我要多少」，上游按需求发。但我的脑子一直在问：那我 sink 的时候也没见让我报数啊？Publisher 是推还是等——我猜推（不然怎么叫响应式）。
下游处理不过来会怎样：按通知经验，收不过来就是丢或者卡主线程。Combine 应该……也差不多？
**自评：纯猜以下**（这题基本交白卷，「sink 不用报数」的观察和原料矛盾，我分不清谁对——病灶如实暴露）。

### C3 PassthroughSubject vs CurrentValueSubject：该选哪个？

差异我抓到一半：一个带当前值，一个不带。「当前登录用户」我直觉 CurrentValue——新开的页面总得知道现在是谁登录了，Passthrough 晚订阅就什么都拿不到。这个我能推。
按钮点击我选 Passthrough——点击是事件，没有「当前的点击」这种东西。这个也有直觉。
搜索框文本我卡：文本是状态还是事件？输入框里总归有个「当前文本」……但搜索管道要的是每次击键的流？我押 CurrentValue，理由是「新订阅方应该看到已输入的内容」，但心里不稳。
@Published 跟谁更像：包着值、变更即发——CurrentValue。这个挂 T2 的知识顺。
**自评：半懂半猜**（②③有把握，①押题，选型轴「有无快照」能摸到但没总结成轴）。

### C4 retry 与 debounce：管道上的阀门怎么拧？

retry(3) 重的是什么：我的第一反应是「重新执行闭包」——网络请求的闭包再跑一遍。但转念想，管道是装配出来的，闭包早就执行完了，哪来的「重新执行」……那应该是**重新订阅上游**？上游的 publisher 被重新订阅，网络请求因此重新发起。这个推理我半信半疑。
retry 后错误类型变了吗：猜不变——重试完了还是失败，错误还是那个错误。
debounce 和 throttle：debounce 是「等你不动了再发」——电梯关门按钮的心智，有人按就重新等；throttle 是「固定节拍发一次」——节流阀。方向我有，但「debounce 丢中间留最后、throttle 取样」这么精确的表述我给不出。
操作符顺序：debounce 在 retry 前——先决定该不该发，再决定失败了重几次。这个用常识能推。
Failure 流转：catch 之后错误应该被消化了，管道不再可能出错——Failure 变成 Never？猜的。
**自评：半懂半猜**（retry=重新订阅是现推的、不稳；debounce/throttle 方向对精度差；顺序和 Failure 靠猜）。

### C5 边界判定：这个需求走 Combine 还是 async？

按 T3 的分界线硬推五题：
①拉一次用户资料——单值任务，**async**。这个我有把握，T3 Q1 刚做过。
②搜索框防抖后请求——防抖是流算子，async 里没现成的（得手写 sleep+取消，T3 的教训是手写取消容易漏），**Combine**。
③多数据源并发拉取合并渲染——卡了。并发拉取我会想到 T3 的 TaskGroup；但「合并渲染」如果是一路一路来要 combineLatest……我押 **Combine**，理由是「合并」是流算子主场。不稳。
④WebSocket 持续推送——持续流，两边都行？我押 **Combine**，直觉「持续推送 = 响应式主场」。
⑤定时器心跳——Timer.publish 我有印象，但 AsyncTimerSequence 也听说过……押 **Combine**。
桥：Combine→async 我背过 `publisher.values` 可以 for-await；async→Combine 完全空白，Future？Deferred？名词见过，形状不会写。
**自评：半懂半猜**（①②稳，③④⑤押，桥单向——三个押题全押了 Combine，我怀疑自己有一边倒的病但自查不出来）。

### C6 @Published 与 SwiftUI：插座的两头

@Published 底下是 publisher——T2 Q2 的 `objectWillChange` 发射器我亲手跑过，will 语义撞墙验证过，这块我稳。
objectWillChange 的粒度：对象级——改任何一个 @Published 属性都发一次广播，通知里不含「哪个属性变了」的信息，所有观察这个对象的视图全重算。这个 T2 D3 有印象分，但「一次改两个属性是发一次还是两次」我真不知道。
@Observable 的对照：属性级依赖收集，视图读到哪个属性才依赖哪个——T2 复攻时讲过方向，机制细节仍浅。
sink $属性 vs 观察对象：$query 拿的是这一个属性的流，细粒度；但拿到的 cancellable 得自己管——这里是不是又回到 C1 的义务了？这个勾连我自己想到的。
**自评：半懂半猜**（T2 存量扛住一半，粒度的精确行为没验过）。

## 三、代码任务作答

四道题落在 `代码/T4/`，思路与疑点：

- **Q1 防抖+重试+缓存搜索管道**：管道装配是这道题的主体。debounce 的时间参数和 RunLoop 驱动我凭记忆写。retry 的计数打点是我自己坚持加的——不计数就证明不了「重新订阅」。缓存字典挂在管道外层，我拿不准它该放在 debounce 前还是后。
- **Q2 @Published 数据流**：三组打点 + 「不存即取消」对照组。对照组的设计我一眼看懂——T2 埋的钩子这回要亲手埋掉。will 语义断言沿用 T2 Q2 的手法。
- **Q3 桥接实验**：桥 A 复用 T3 Q1 的 continuation 桥，我有信心。桥 B 的 AsyncStream 我只背过 `AsyncStream { continuation in }` 的形状，finish 的时机凭感觉写。Timer.publish 版要对拍输出，RunLoop 的驱动方式我可能要撞墙。
- **Q4 Sendable 收账 + 判定器**：@unchecked 实操是 T3 欠的账，这回真写。NSLock + 字典的形状是 OC 肌肉记忆，担保注释按 C3 纪律三连写。判定器把 C5 的口述编码——如果我 C5 押错了，这里会一起错，正好互相印证。

**自评：Q1 半懂半猜，Q2 有把握，Q3 半懂半猜（桥 B 悬），Q4 段一有把握段二跟着 C5 走**。
