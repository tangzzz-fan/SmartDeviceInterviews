## 二、复攻记录

**C2 复攻**（学员重读原料「状态-Observed与StateObject」+ 对照 Q2 模拟实验后补答）：

> 补答：卡点「重算又不是重新 init……吧？」——错就错在这个「吧」。视图值每次重算都在被重新构造，构造就要执行 init，init 里写 `= UserStore()` 就重新执行一次。@ObservedObject 的存储不在框架手里，它只是「你传给我什么我用什么」——所以谁在 init 里写它谁就是在每帧重建对象，状态跟着旧对象死，还每帧新发一轮 objectWillChange。Q2 策略 A 的三轮 n=1 就是这个病的最小模型。@StateObject 的存储跟 @State 一样由框架按「视图身份」保管，初始化表达式只在身份首次出现时执行一次。反诘①：全用 @ObservedObject 意味着每个状态都要先造一个 class 再传进来——私有小状态（筛选枚举）本来 @State 一个值就完事，硬上 Observed 是把所有权搞散：本该视图私有的东西被迫外部化，谁创建、谁释放又说不清。反诘②一句话：**StateObject = 我创建、按身份保管、只建一次；ObservedObject = 别人创建、我只是接过来用**。

判定：两反诘均落到「所有权 + 重建时机」，且有 Q2 实跑交叉验证 → **C2 复攻过关**。

**C3 复攻**（学员重读「基础范式转换」重算章节后补答）：

> 补答：纠错先认——首轮猜的「树形全量重算」是错的。机制是三层：①**重算 body**：只是把读到了变化状态的视图的 body 函数重新调用一遍，产出新描述值——struct 造值，无引用计数、无堆分配大头，这层廉价；②**diff**：拿新旧描述按身份对齐比对，找出真正变了的节点；③**最小渲染更新**：只把变化落到屏幕上，贵的是这一步。所以「重算范围」不是树形而是**依赖图**：谁读过这个状态谁才重算，没读过的子树连 body 都不调——这跟 UIKit 的「谁订阅了通知谁刷新」一个思路，只是订阅关系框架自动记了。框架敢频繁重算的底气：正因为 ①廉价、③被 ②裁剪，成本结构跟「整树重画」完全两回事。

判定：三层机制齐、范围纠错到位、且主动挂靠 UIKit 通知订阅旧知 → **C3 复攻过关**。

**C4 复攻**（Q3 代码结论回填概念通道）：

> 补答：拿 Q3 的实跑输出说话——三行异构语句不是装数组，是 `buildBlock` 按个数打包成嵌套类型（我打印出 `(String, MiniConditional<String, Int>, String)`，每个成分的具体类型都在，没被擦掉）；if/else 两分支走 `buildEither(first/second)` 成对入口，被同一个「二选一」容器接住——SwiftUI 里对应 `_ConditionalContent<A,B>`，位置恒定、类型二选一，这就是切分支时 diff 眼里「旧死新生」的类型学根源；if 无 else 走 `buildOptional` 包成 Optional。跟 T1 的 some View 接上了：body 返回类型之所以恒定，正是因为 builder 把任意分支组合都收敛成一个确定的静态类型——**builder 是 some View 的幕后担保人**。

判定：手动翻译（代码即翻译件）、类型形状、与 some View 勾连三层齐全，且是撞墙后自建的知识 → **C4 复攻过关**。

**C5 复攻**（学员重读原料 + 教练只点「想想结构化并发」后补答）：

> 补答：viewDidLoad 与 onAppear 三点差异——①触发语义：viewDidLoad 是对象生命周期钩子，一个控制器一辈子调一次；onAppear 是**出现事件**，导航推出去再回来会再触发，跟「对象」无关；②与重算无关：body 重算一百次，只要视图没「消失再出现」，onAppear 不重触发——它挂在事件上不是挂在构造上；③没有对象语义可挂：SwiftUI 里根本没有「这个页面的对象」，所以也不存在「加载」，只有「出现」。.task 与 onAppear 的关键差异：task 能直接写 async 是面子，**视图消失自动取消任务**是里子——任务的生命周期绑在视图身份上，身份没了任务跟着取消（结构化并发的取消传播，T3 的预告）；onAppear 里手动 `Task {}` 得自己存 handle、自己记得在 onDisappear 取消，GCD 式手动活，漏一个就是后台幽灵任务。我之前「不信自动」是拿旧世界的账算新世界的钱。

判定：三点差异齐全、取消语义接住且能自我批判旧经验负资产 → **C5 复攻过关**。

**C6 复攻**（学员重读「性能优化体系」Identity 章节 + T1 M4 复习后补答）：

> 补答：两种身份——**结构身份**：类型 + 在树中的位置，框架默认靠这个对齐新旧节点；**显式身份**：`.id(value)` 或 ForEach 的 id 参数，用户覆写。AnyView 的伤害链条现在能完整说了：它把所有具体类型擦成同一种（T1 的 any 装箱），diff 对齐时类型信息全丢，只能靠位置硬对——位置稍动就认不出；且 AnyView 内部换了具体类型，外层看还是 AnyView，框架不得不深入盒子内部做内容比较，diff 退化。AnyView 不是「慢一点」，是把身份系统打残。`.id()` 改值的后果：身份变 = 框架认定「这是换了个视图」——三个后果：①该子树的 @State 全部重置（存储跟着旧身份走了）；②转场动画按「移除旧的 + 新增新的」走而不是原地更新；③整棵子树重建。例子：列表里把某行 id 从 1 改成 2，那行里的 @State 输入框内容会凭空消失——这个我能想到场景了。

判定：身份二分清晰、AnyView 论证链完整（且与 T1 装箱知识勾连）、.id 三后果齐 + 自造例子 → **C6 复攻过关**。T1 遗留观察项 1 清偿。

**代码通道复攻确认**：Q2 的 willChange 时机撞墙、Q3 的两次撞墙均已写入 `代码/T2/` 对应文件头注释并修复实跑（输出见上表）；Q4 选型反复过程（visitCount model→@State）理由已入注释，复跑仍通过 → **Q2/Q3/Q4 复攻过关**。
