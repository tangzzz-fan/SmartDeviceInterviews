# 项目驱动实践路线（代码通道载体）

> 定位：本文件是 [[00-学习计划.md|学习计划]] 代码通道的**工程载体**——MIT 三问负责拷问与判定纪律，本路线的 23 个迭代项目负责提供「可运行的完整骨架」。各 Phase 与 T1–T5 的绑定见 [[00-学习计划.md#七、代码通道载体绑定|学习计划第七节]]。
> 方法论说明：原文档把「MIT 学习方式」理解为项目驱动实践风格；[[04-方法论基座-MIT三问与测试协议.md|方法论基座]] 中的 MIT 三问指的是三问拷问法。两者不冲突：本路线的五条原则作为学员学法约束保留，验收判定仍以三问体系为准。

## Agent 角色定义

**身份**: 从 UIKit + Objective-C 向 Swift/SwiftUI 迁移的 iOS 开发者 Agent  
**背景**: 具备扎实的 OC 与 UIKit 开发经验，熟悉 MVC、Delegate、KVO、GCD 等经典模式；对 Swift 有基础语法接触，但缺乏系统性工程实践。  
**目标**: 以 MIT 学习方式（项目驱动、快速迭代、从实践中学习）快速掌握 Swift 语言深度、SwiftUI 声明式开发、Swift Concurrency 异步编程、Combine 响应式编程及对应性能优化方向。  
**约束**: 所有学习必须通过可运行的代码项目验证，禁止纯理论阅读；每个阶段必须有明确的可交付物（Deliverable）。

---

## MIT 学习方式核心原则

1. **项目驱动 (Project-Based)**: 每个知识模块都绑定一个真实可运行的 App 项目，而非孤立练习。
2. **快速迭代 (Rapid Iteration)**: 每个项目从 MVP 到优化版控制在 3-5 个迭代周期内，每个周期有明确的功能增量。
3. **从错误中学习 (Learning by Debugging)**: 主动制造边界场景，通过 Instruments、Crash Log、编译错误反向推导底层机制。
4. **第一性原理 (First Principles)**: 不满足于"怎么做"，必须追问"为什么这样设计"——从语言/框架的底层约束推导最佳实践。
5. **迁移对比 (Migration Lens)**: 始终对比 OC/UIKit 中的等效实现，明确范式差异，避免用旧思维写新代码。

## 学习路线图

### Phase 1: Swift 语言深度重构 (Week 1-2)
**核心目标**: 从"会写 Swift 语法"到"用 Swift 思维写代码"，完成从 OC 面向对象到 Swift 协议导向 + 值类型的范式迁移。

| 迭代 | 项目 | 交付物 | 核心知识点 |
|------|------|--------|-----------|
| 1.1 | OC 旧项目 Swift 重写 | 一个用 Swift 重写的简单 OC 项目（如天气 App） | 基础语法迁移、Optional、Guard、Switch 模式匹配 |
| 1.2 | 值类型 vs 引用类型实验 | 内存布局分析文档 + 可复现的 Copy-on-Write 自定义实现 | Struct vs Class、Copy-on-Write、引用语义陷阱 |
| 1.3 | 协议导向编程实践 | 一个纯协议组合构建的 UI 组件库（无继承） | Protocol、Extension、Associated Type、Self 约束 |
| 1.4 | 泛型与类型系统挑战 | 类型安全的网络层封装（替代 OC 的 id/NSObject） | Generic、Type Erasure、Opaque Type (some)、Existential Type (any) |
| 1.5 | 内存管理与错误处理 | 循环引用检测报告 + 自定义 Result 类型错误链 | ARC 差异、Weak/Unowned、Error Protocol、do-catch、Result |

**关键对比任务**: 将 Phase 1 的每个项目同时用 OC 和 Swift 实现，对比编译器报错信息、运行时行为、内存占用。

---

### Phase 2: SwiftUI 声明式思维重塑 (Week 3-5)
**核心目标**: 彻底摆脱命令式 UI 更新思维，建立"状态即真理"的声明式心智模型；掌握与 UIKit 的混合开发策略。

| 迭代 | 项目 | 交付物 | 核心知识点 |
|------|------|--------|-----------|
| 2.1 | 命令式 → 声明式迁移 | 将 Phase 1.1 的 Swift UIKit 版本改写为纯 SwiftUI | @State、@Binding、@ObservedObject、@StateObject、@Environment |
| 2.2 | 复杂布局系统实战 | 一个类似 Twitter 时间线的复杂 Feed 页面 | VStack/HStack/ZStack、Spacer、GeometryReader、PreferenceKey、Anchor |
| 2.3 | 自定义 View & Modifier | 一套可复用的设计系统组件库（Button、Card、Toast） | View Protocol、body 属性、ViewModifier、Custom Modifier 链式调用 |
| 2.4 | UIKit 桥接与混合架构 | 在一个 SwiftUI 项目中嵌入 UICollectionView、MapKit、Camera | UIViewRepresentable、UIViewControllerRepresentable、Coordinator 模式 |
| 2.5 | 导航与状态管理架构 | 一个多 Tab + 深层导航的 App，使用 NavigationStack | NavigationStack/NavigationSplitView、Path 管理、全局状态树设计 |

**关键对比任务**: 对比同一 UI 在 UIKit (OC) 与 SwiftUI 中的代码行数、状态同步复杂度、动画实现方式。

---

### Phase 3: Swift Concurrency 异步编程 (Week 6-7)
**核心目标**: 从 GCD/Block 思维彻底迁移到 async/await 与结构化并发；理解 Actor 模型与数据竞争安全。

| 迭代 | 项目 | 交付物 | 核心知识点 |
|------|------|--------|-----------|
| 3.1 | GCD → async/await 迁移 | 将 Phase 1 项目的网络层从 URLSession 回调改写为 async/await | async/await、Continuation、Task、Task.detached |
| 3.2 | 结构化并发与取消传播 | 一个并发下载多张图片并支持中途取消的 Gallery | TaskGroup、withTaskGroup、Task Cancellation、CheckedContinuation |
| 3.3 | Actor 与数据竞争安全 | 一个多线程写入的计数器/缓存系统，通过编译器验证安全 | Actor、Global Actor (@MainActor)、Sendable、nonisolated |
| 3.4 | 并发性能调优 | 对比 GCD DispatchGroup vs TaskGroup 的 CPU/内存占用报告 | 线程爆炸问题、Cooperative Thread Pool、优先级继承 |

**关键对比任务**: 用 Instruments 的 Thread Sanitizer 和 Time Profiler 对比同一并发任务在 GCD 与 Swift Concurrency 下的线程使用模式。

---

### Phase 4: Combine 响应式编程 (Week 8)
**核心目标**: 掌握声明式事件流处理，理解 Combine 与 SwiftUI、Concurrency 的协同边界。

| 迭代 | 项目 | 交付物 | 核心知识点 |
|------|------|--------|-----------|
| 4.1 | 事件流替代 Delegate/KVO | 将 Phase 2 项目中的 Delegate 回调改写为 Publisher | Publisher、Subscriber、Subject (Passthrough/CurrentValue)、Cancellable |
| 4.2 | 操作符链与错误处理 | 一个带搜索防抖、重试、缓存的网络请求管道 | map、filter、debounce、retry、catch、flatMap、merge |
| 4.3 | Combine + SwiftUI 集成 | 使用 ObservableObject + @Published 构建响应式数据流 | @Published、objectWillChange、sink、assign |
| 4.4 | Combine vs Concurrency 边界 | 明确何时用 Combine（事件流）vs async/await（异步任务） | Future、asyncPublisher、兼容性设计 |

**关键对比任务**: 对比同一功能用 OC (KVO + Notification + Block) vs Combine 的实现复杂度与类型安全性。

---

### Phase 5: 性能优化与工程化 (Week 9-10)
**核心目标**: 建立性能意识，掌握 Instruments 工具链，能在 Swift/SwiftUI/Concurrency 场景下定位并解决性能瓶颈。

| 迭代 | 项目 | 交付物 | 核心知识点 |
|------|------|--------|-----------|
| 5.1 | SwiftUI 渲染性能优化 | 一个长列表 App 的 60fps 优化版本（对比掉帧版本） | View Identity、EquatableView、@ViewBuilder、LazyVStack vs List、Cell 复用 |
| 5.2 | Swift 编译时间与二进制优化 | 编译时间分析报告 + 优化前后对比 | 增量编译、Whole Module Optimization、Generic 特化、@inlinable |
| 5.3 | 内存与启动优化 | 使用 Instruments 定位并修复内存泄漏与启动耗时 | Allocations、Leaks、Time Profiler、App Launch 阶段分析 |
| 5.4 | Concurrency 性能基准测试 | 高并发场景下的 Actor 隔离 vs 锁性能对比报告 | Actor 开销、Continuation 性能、Task 调度开销 |
| 5.5 | 综合实战项目 | 一个完整的生产级 App（如 Reddit 客户端），应用全部所学 | 架构整合、模块化、测试覆盖、CI 集成 |

**关键对比任务**: 将 Phase 5.5 的综合项目与 OC/UIKit 版本的假想实现对比，输出迁移收益报告（开发效率、运行时性能、维护成本）。

## 学习检查清单 (Checklist)

每个 Phase 完成后必须自检：

- [ ] 能否不看文档手写该 Phase 核心代码？
- [ ] 能否向一个 OC 开发者清晰解释范式差异？
- [ ] 能否用 Instruments 证明性能优化前后的数据变化？
- [ ] 能否在代码审查中识别出"用 OC 思维写的 Swift 代码"？
- [ ] 能否解释底层实现原理（如 SwiftUI Diffing、Actor 调度器）？
