# T3 学员作答：Concurrency

> 学员背景自述：GCD/队列/锁/数据竞争排查十年，这是我的主场——但主场最容易轻敌。本轮先读五篇原料、标 GCD 锚点，再闭卷作答。人设卡预告的三个病灶（Task 套公式、actor 当串行队列、Sendable 讲不清）我作答时尽量不提前看答案，错了如实错。

## 一、共识复述：M1–M5 用自己的话

**M1 await 是挂起不是阻塞**：这个我有锚点——OC 的网络请求本来就不占线程干等，回调来了再干活。await 的差异是把「回调里才干的事」拉平成了顺序代码：心智上是同步写法，成本上还是异步的。「等」不再付一根线程的税。
**自评：有把握**（回调十年的直觉直接挂靠）。

**M2 结构化并发**：任务有父子树、父结束子必了结——这个概念我读懂了但没实感。GCD 的世界观是 dispatch 完就撒手，任务跟调用方从此两清；「发出去的任务还有人管」对我来说是反直觉的。
**自评：半懂半猜**（概念能复述，直觉还是 GCD 的）。

**M3 actor 是可重入的隔离域**：原料说「await 处松手、别的调用能进来」——我读的时候嘴上点头，心里不信。串行队列十年，「一个没跑完下一个进不来」是刻在骨头里的。这个模型我预告自己会栽，C2/Q3 见真章。
**自评：半懂半猜**（字面读过了，心智还没改写）。

**M4 Sendable 是编译期契约**：数据竞争我在 OC 里靠 TSan 事后抓、靠 review 事前防；Sendable 把这事提前到编译期，方向我能理解——类型系统管安全，跟 T1 的 Optional 一个路数。但「编译器具体拦什么、为什么 closure 默认不放心」我讲不细。
**自评：半懂半猜**。

**M5 取消是协作式传播**：NSOperation 的 isCancelled 检查义务是我唯一能挂的锚——取消从来不是 kill，是插旗 + 自己看。GCD 里连这个都没有（DispatchWorkItem.cancel 半成品）。T2 学 .task 时刚建过「插旗-检查-了结」的概念，这轮应该有实感了。
**自评：半懂半猜**（概念有了，等 Q2 用手感验证）。

## 二、概念拷问题作答

### C1 Task {} 与 DispatchQueue.global().async 差在哪？

第一反应（如实记录）：「Task 就是新 GCD 嘛，异步丢后台」——我知道这是人设卡点名的套公式病，但这就是肌肉记忆。
硬推差异：①Task 有返回值能 await、错误走 throws——GCD block 全靠出参和回调，类型不进系统；②取消——Task 有 cancel，GCD 没有对应物；③还有吗……上下文继承？GCD 的 block 在哪个队列跑是 dispatch 时定死的，Task 的「继承」我说不清继承什么。detached 砍什么我更说不清。
「和创建它的上下文还剩什么关系」——按 M2 推：Task {} 不强制等待，但应该还挂在某种结构上？句柄能拿来 await/cancel，这比 GCD 强（dispatch 完就失联）。
**自评：半懂半猜**（三层只扎实说出两层，继承/砍掉的细节空白）。

### C2 actor 的可重入：串行队列经验哪里骗了你？

我按原料复述：方法里遇到 await 会挂起，挂起期间 actor 松手、别的调用能进来——合法。
但「为什么敢这么设计」我推不动。串行队列堵门的直觉一直在拽我：不堵门不就乱了吗？「挂起时不松手会怎样」这个反问我想不到答案。
bug 场景我构造不出：如果读-改之间隔着 await 会失效……逻辑上我能点头，但让我现场写一个翻车场景，我写不出来。
**自评：纯猜以下**（这题我基本交白卷，等 Q3 代码撞完墙再回来）。

### C3 Sendable：编译器到底在拦什么？

可变 class 跨 actor：两个隔离域同时拿到同一个可变引用，同时读写——数据竞争。这个我熟，OC 里查过这种事故。编译器拦的就是把事故种子传递出去。
值类型为什么容易 Sendable：全 let 的 struct 拷贝出去就是独立一份，没有共享可变——这个挂 T1 值语义的知识很顺。
closure 为什么默认不放心：这里我卡。猜：闭包捕获的东西编译器看不清？捕获了可变对象就危险，但捕获列表里到底捕了什么、是不是共享，编译器没法静态验证——只能默认不信。
@unchecked Sendable：猜是「绕过检查」的标签，性质……大概是开发者自己担保？风险多大说不准。
**自评：半懂半猜**（不变量的方向对，closure 与 @unchecked 的细节靠猜）。

### C4 结构化并发与取消传播

T2 刚学过 .task 的「插旗-检查-协作了结」链条，复述没问题：视图消失 → 根任务被 cancel → 旗子沿任务树传下去 → 子任务在检查点了结；不检查旗子的代码会跑完。
但 withTaskGroup vs detached 的命运差异我推不顺：group 里的任务取消时，父在等所有子了结——那取消了是立刻返回还是等它们了结？detached「与任何父无关」我理解成没人等它、也没人给它传旗子？取消 detached 是不是得自己拿句柄手动 cancel？这块半生不熟。
「取消是立刻杀死代码吗」——T2 的教训：不是 kill，是协作。这个我敢答。
**自评：半懂半猜**（链条会背，group/detached 的命运差异推不动）。

### C5 Continuation：回调世界的独木桥

这题是我主场翻译：OC 的 completion block 改 async，需要一座桥——桥这边是「await 在等值的人」，那边是「回调兑现时送值的人」。continuation 就是那张欠条。
一次性义务我能推出来：欠条兑现两次 = 同一笔账结两遍，肯定要出事（运行时崩）；一次都不兑现 = await 的人永远等下去——这不就是 OC 时代「completion 忘了回调导致页面永远转圈」的同款病吗！查过太多次这种事故，原来是同一个病换了语法。
checked 的「检查」：猜就是运行时盯着这两条义务，违规给你崩或警告。
**自评：有把握**（十年回调事故经验的直接翻译，「欠条」比喻我自己都信服）。

### C6 Task 的寿命：谁在强持有它？

T1 的 unowned 教训先跳出来：寿命判断靠直觉会栽，这次我先不信自己。
第一反应还是想答「task 变量置 nil 任务就没了」——ARC 直觉：句柄没了对象就释放。但 T1 栽过同款，我按住这个直觉。
按 T1 的环分析硬推：任务本体总得有人持有才能跑——运行时/调度器持有本体，句柄只是个遥控器？扔遥控器电视还开着，要停得按 cancel（遥控器上的按钮）。这么推的话置 nil 不停任务。
.task 的句柄：T2 说框架按视图身份保管、消失时替你 cancel——复述没问题，但「句柄存在哪」的细节我没实感。
**自评：半懂半猜**（结论是靠「不敢信直觉 + 遥控器类比」推的，不是自然长出来的）。

## 三、代码任务作答

四道题落在 `代码/T3/`，思路与疑点：

- **Q1 回调→async 迁移**：机械迁移是我的主场，桥的形状基本一次写对——但**撞了个小墙**：第一版用 `withCheckedContinuation` 把整个 Result 当值还回去，调用点类型对不上，才换成 `withCheckedThrowingContinuation + resume(with:)`。心跳任务的设计是我自己加的：await 期间心跳还在跳，「挂起不阻塞」才有肉眼证据。
- **Q2 可取消 Gallery**：**撞墙了，而且是认知墙**。第一版两轮的 sleep 都写成 `try await`，结果第一轮（本该不协作）也被取消得干干净净——我才意识到 `Task.sleep` 本身就是检查点，被取消时直接抛错。要演示「不协作」得用 `try?` 吞掉信号。这个发现比题目本身值钱：原来检查点无处不在，取消不住不是因为没旗子，是因为不睁眼。
- **Q3 actor 缓存**：**撞墙撞得最狠**。第一版我断言 fetchCount == 1——串行队列的骨头在说话：「actor 堵着门，第二个请求排队呢，怎么可能重复 fetch」。实跑 fetchCount = 2，断言当场炸。盯着输出想了半天才把 M3 那句话真正读进去：挂起时松手，第二个请求在窗口期里读到空缓存。修复用 in-flight 去重：把「我正在 fetch」这个承诺也存进状态，重入者复用任务。
- **Q4 Sendable 关卡**：反例我是直接写在主文件里撞的编译错（Swift 6 模式 typecheck），报错文案抄进了注释；然后把反例拆成独立文件「勿运行」，主文件只留修复版。修复路线我选了值化——class 改 struct，这是 T1 值语义知识的回收。@unchecked 路线我在注释里写了风险性质，但没实际用：真到生产里我会先问「能不能值化」，问不了再谈担保。

**自评：Q1 有把握，Q2 半懂半猜（认知墙已撞），Q3 纯撞墙重塑，Q4 半懂半猜（值化顺手，@unchecked 只有概念）**。
