# T6 学员作答：Combine → async 迁移实操

> 学员背景自述（校准后画像）：这轮跟我的真实处境对上了——我用纯 Swift 做过完整项目，Combine 用过但不多（搜索防抖、几个 $ 管道），现在要迁 SwiftUI + Concurrency。所以这轮不是「学 Combine」，是「把我半生不熟的 Combine 换成 async」——切分、回退、边界这些工程活我有把握，AsyncStream 手写算子和 @Observable 重构细节我没干过，如实说。

## 一、共识复述：M1–M5 用自己的话

**M1 推 vs 拉两种流**：Combine 我用 sink 的时候就是「发了就收」，从来没想过上游在按我的 demand 发货（T4 段一才懂）。`for await` 是「我要才给、没货就挂着」——拉模型这个词我接受，但「多播留 Combine、单链迁 async」这条选型规则我是第一次拿到手，还没用它判过真实管道。
**自评：半懂半猜**（推模型有手感，拉模型的选型规则待 C1/Q4 验）。

**M2 操作符映射账本**：map/filter 我两边都写过，同构我信。debounce 我在 Combine 里用过，async 侧……标准库没有？要 AsyncAlgorithms 或手写——这个我真不知道，我一直以为 for-await 上能直接 `.debounce`。retry 更没概念：async 里重试难道不是再写个循环？如果就这么朴素，那我反而有底了。share 的多播语义我在 Combine 里也没深用过，「重设计」我理解但给不出方案。
**自评：半懂半猜**（map/filter 稳，debounce/retry 的 async 形态是本轮最大盲区，等 Q1 手写）。

**M3 寿命所有权移交**：「Set<AnyCancellable> 存一屏的订阅」这代码我写过不止一次，忘存即取消我也踩过（订阅建立后立刻没了，当时查了半天）。「.task 绑视图寿命、TaskGroup 绑作用域」——T2/T3 学过，对应关系我能推：存进视图的凭证换成 .task，存进 ViewModel 的换成作用域 Task。「跨作用域存活翻译不动」这条我有共鸣：我项目里有个全局通知总线式的订阅，确实塞不进任何视图寿命里。
**自评：有把握**（凭证管理经验是存量，对应表现推成立，反例形态有真实共鸣）。

**M4 @Observable 重构不是逐行翻译**：「无内建 publisher」这条把我问住了——我以为 @Observable 就是 @Published 换个写法，管道直接跟着走。原来 @Published 上的 $query.debounce 这种链在 @Observable 里**没有发布点可挂**，管道要搬家（.task + AsyncStream 或保留桥）。T5 Q4 量过 6:3 的爆炸半径我知道是赚的，但「赚粒度、赔管道」这笔账我今天才算全。
**自评：半懂半猜**（爆炸半径有存量，管道搬家的具体手感欠，等 Q2）。

**M5 按屏切、桥是边界**：这条我读着最顺——MRC→ARC 我迁过，UIKit 混编我干过，「切大了回不去」是真金白银的教训。一屏+状态闭环当单位、叶子屏起手、边界单向——这些把我原来的直觉钉成了规则。「桥不删、边界移动不消失」这个说法新鲜但成立：混编期桥是脚手架，迁完桥是接口。
**自评：有把握**（主场，直觉被规则化的感觉）。

## 二、概念拷问题作答

### C1 迁移决策：那条搜索管道换不换

工程直觉先答：**不能一刀切**。那条搜索管道（debounce→去重→retry→缓存→刷 UI）我拆开看：它是**单消费链**（只有列表页在消费）、算子全是查询类、寿命天然跟搜索框/页面走——这条**适合迁**。判定框架我给四变量：①订阅者数量——多播共享的上游别动，动了就是多个消费方一起回归测试；②算子可映射性——链上每个算子 async 侧有没有等价物（这题我心虚，M2 账本我还没建全）；③寿命归属——迁过去之后取消归谁管，能交给 .task/视图是加分项；④回归风险——跑通的管道重写，没有对拍就是裸奔。
还有一条工程底线：**迁完的标准是对拍，不是删掉**——同一输入序列两版输出一致才算迁完。这是我迁 MRC 时的老规矩：双实现并行跑一段。
**自评：有把握**（分档+对拍是工程存量；算子映射变量我知道自己没底，如实标）。

### C2 操作符映射账本

照 M2 逐行过：map/filter/compactMap——内建，直迁，我用过两边，零风险我认。debounce/throttle——我以为内建有，原来要 AsyncAlgorithms 或手写；手写 debounce 我想了想应该是「记下最新值，静默够一个时间窗才发出」，但起算点、窗口内新值怎么续期，细节我没把握。merge——async 有 merge 吗？我猜有但不确定。**retry——标准库没有**，手写循环：试 n 次，catch 了计数，最后一次仍失败抛出去——这个形态我能写，朴素得让我意外。combineLatest——AsyncAlgorithms 有，没用过。share——async 侧没有直接等价，多播要重设计，我给不出方案，诚实挂账。
「能映射的不是重点」我现在懂了：map/filter 迁起来不花脑子，**花脑子的是 retry 这种你以为有、其实没有的，和 share 这种真没有的**——迁移估时要按账本的缺项栏估，不是按行数估。
**自评：半懂半猜**（账本框架立住了，debounce 手写细节与 merge/combineLatest 归属在押，等 Q1）。

### C3 寿命移交：cancellable 的义务怎么翻译

对应表我照存量推：存进视图的 cancellable → `.task`（视图消失框架自动取消，T2 学的）；存进 ViewModel 的长订阅 → ViewModel 作用域里的 Task，或者干脆 AsyncStream + for await，让消费循环自己拥有迭代；一屏多个订阅要一起了结 → TaskGroup，作用域结束全取消——这个跟 DispatchGroup 等一组回调的心智有点像，但取消是白送的。
「翻译不动」的形态：要**跨作用域活着**的订阅——我项目里那个全局总线就是：它不属于任何视图、任何作用域，结构化并发里没有「全局凭证」这个位置。这种要么显式起一个长寿命 Task 手动管取消（等于把旧义务又请回来了），要么就留 Combine 不迁。
收益我说得出来：「忘存 cancellable」这类 bug 在结构化世界里编译结构就防住了——义务从记忆力移交编译器。代价也认：跨作用域场景反而要更费脑子设计。
**自评：有把握**（凭证管理的痛是存量，对应表现推成立，跨作用域边界有真实案例背书）。

### C4 @Published → @Observable：哪些能直译

逐行过那个 ViewModel：`@Published var query` → @Observable 类里的普通 var，直译；`@Published private(set) var results` → 属性加 private(set)，保护语义要留着，这点我有意识（接口别放宽）。init 里那条 `query.$debounce→请求→results` 管道——**这里断了**：@Observable 没有 $query，没有发布点。管道的家我只能另找：在 UI 侧起 `.task`，用 withObservationTracking 或 AsyncStream 观察 query 变化、手写 debounce、再请求。等于把「声明式管道」拆成了「观察+循环」，代码量涨了，但寿命白拿（.task 跟视图走）。
「无内建 publisher 是取舍不是缺失」：@Observable 是读时追踪（谁读了它它才知道），不是写时广播——天然没有发布点；管道是少数需求，用 AsyncStream 组合补，不绑死在底座上。这个解释我接受。
重构判定清单我给三档：纯状态无管道的 ViewModel 先迁（白赚属性级）；管道重的缓迁（先想好管道的家）；部署底线卡 iOS 16- 的不迁。
**自评：半懂半猜**（判定清单推得顺，但「观察+循环」具体怎么搭我没写过，等 Q2）。

### C5 增量切分：10 屏应用的刀怎么下

主场题，按我做过的迁移给规则：
切分单位：**一屏 + 它的状态闭环**，不按文件切——文件级切分会把一屏的状态劈在两个世界里，桥开得满地都是。
第一屏：**叶子屏**——依赖最少（最好是纯展示+一个服务调用）、可独立替换、出问题一键回退。千万别从首页/核心流开刀。
桥的位置：**屏边界**。新屏嵌进旧的导航壳 → UIHostingController；旧屏里要嵌新组件 → UIViewRepresentable。方向上这两个别搞反。
流向约束：**单向**——新屏可以吃旧服务（用 values 桥把 Combine 服务拉上来），但旧屏不吃新状态；双向依赖一开，回退和并行开发全乱。
顺序规则：数据流上「下游先行」——叶子屏先迁，越往共享服务走越晚，最后收口服务层；每迁完一屏，桥向内移一格。全部迁完，桥剩服务层边界一处，能删则删、不能删就是长期接口（M5 说的「桥是边界不是过渡品」）。
**自评：有把握**（全是存量迁移直觉的规则化，回退意识是 MRC 时代交的学费）。

### C6 混合桥的时序账

寿命归属：values 桥的迭代归 for-await 循环（消费侧控制，循环退出迭代就停）；AsyncPublisher 把 async 流变回 Publisher，订阅它又是 cancellable 语义——**回到旧世界的存凭证义务**。等于说过桥不免除义务，只是义务换了形态。
热 Subject 翻车我 T5 Q4 段二亲手撞过三版：订阅前的 send 没人收。迁移场景的防线我给三条：①生产侧带节拍——消费者就位再开始生产（先挂后发）；②能用冷启动就用 AsyncStream 按需起生产，天然没这个坑；③非要热 Subject，CurrentValueSubject 带个初始状态兜底。
丢件归责：桥是边界契约，两侧各打点计数，**丢件 = 两侧计数差**，先查「谁的生命周期没覆盖谁」。T4 Q1 的打点手艺这里直接复用。
**自评：半懂半猜**（教训是存量，AsyncPublisher 的 cancellable 义务是现推，等 Q4 验）。
