# T1 学员作答：Swift 语言核心

> 学员背景自述：写了 10 年 iOS，前 8 年纯 OC + UIKit，MRC→ARC 经历过，GCD/RunLoop/KVO 是吃饭家伙。Swift 混编项目里读过同事代码、写过几个简单页面，但值语义陷阱、泛型约束、some/any 这些东西没系统碰过。作答按人设卡执行，类比用 OC 老物件，错的地方如实错。

## 一、共识复述：M1–M5 用自己的话

**M1 拷贝 vs 共享身份**：OC 十年我所有赋值都是「指针复制」，改谁都改的是同一块。Swift 的 struct 赋值是真的复制一份内容出来，两边从此独立——不过教材里那句「关键字只是默认倾向」我记下了，struct 里塞个 class 就等于把 OC 的共享语义偷渡进来。CoW 我理解是「先共享着，真要写的时候再复制」，标准库的 Array 就这么干。
**自评：有把握**（ARC 时代天天和「共享还是拷贝」打交道，这个挂靠得很顺）。

**M2 Optional 是枚举**：`Int?` 就是 `Optional<Int>`，两个 case：.some 包着值、.none 表示没有。和 OC 的 nil 本质不同——OC 的 nil 是指针 0，消息发过去运行时兜底返回零；Swift 把「可能没有」变成了类型的一部分，编译器逼你先处理。可选链我理解成连着拆几个包裹，有一个是空就整个结果为空。
**自评：有把握**（枚举这个说法我之前没想过，但一读就通，和 NSError** 出参的思路对比很清晰）。

**M3 协议一等公民 + 静态分发**：OC 里协议是「约定」，遵守不遵守运行时才知道，靠消息转发找实现。Swift 的协议是积木：用 extension 给默认实现，组合着叠能力，不靠继承树。泛型调用时编译器知道具体类型，直接生成对应的代码（特化），不像 OC 每次都要查表发消息。
**自评：半懂半猜**（「静态分发」方向我能对上，但 PWT 具体怎么传、特化的代价我没实感，放到 C2/C3 里硬推）。

**M4 some 是账本条目，any 是运行时箱子**：这个比喻第一遍读有点晕。我猜 `some P` 是「编译器账本上记着具体是谁，但调用方只能看到协议」；`any P` 是「装进一个标准尺寸的箱子，运行时才开箱」。OC 里 `id<MyProtocol>` 给我的感觉更像后者。为什么 SwiftUI body 用 some——我猜和性能有关，具体说不清，见 C3。
**自评：半懂半猜**（比喻方向对了，机制细节是猜的）。

**M5 闭包逃逸付内存代价**：闭包捕获的东西如果活得比栈帧长，就得搬到堆上。@escaping 就是告诉编译器「这闭包要带出函数」，编译器据此管理内存并强制你想清楚捕获了谁。OC block 的直觉能迁移大半：block 捕获 self 也会循环引用，我们也写 __weak typeof(self)。区别大概是 Swift 把「会不会逃逸」变成了签名的一部分，OC 里全靠约定。
**自评：有把握**（block 十年的坑都踩过，这题是存量直接挂靠）。

## 二、概念拷问题作答

### C1 struct 包 class 的「假值语义」

先推：`var b = a` 时，struct 逐字段拷贝。`cache` 是个 class，struct 拷的是**那个引用本身**，不是引用指向的对象——所以 a 和 b 的 cache 字段值相同，指向堆上同一个对象。改 `b.cache` 里的内容，a 自然跟着变。这不违背「struct 拷贝」的规则，违背的是 M1 里「值语义 = 赋值后独立」的**承诺**——关键字没给你承诺，内容才给。
修法两条：一是把 class 成员换成值类型（如果它本来就只是数据）；二是保留 class 存储盒但包一层 CoW——写之前先查这个盒子是不是只有我一家引用，不是就先复制再改。Substring 那个例子教材提过：切片共享大字符串的存储，也是「值切片共享存储」，出边界要 `String(...)` 切断——同构案例我能对上。
**自评：有把握**（这个我在 OC 里天天见：两个属性指向同一个 NSMutableArray，改一个另一个变——一模一样的病，只是 Swift 让它看起来像新病）。

### C2 为什么带 associatedtype 的协议不能直接当类型用？

我先说我推得到的。Cat 的 Food 是 String，Dog 的 Food 可能也是 String 但也可能是别的。数组 `[Animal]` 要求每个元素占同样大小的格子、每个元素的 `eat` 长同样的签名。关联类型没定死之前：
第一层困难，**格子尺寸**：编译器不知道一个 Animal 元素多大（Cat 和 Dog 尺寸可能不同，而且 Food 不同还可能带不同的关联数据）。
第二层困难……我卡在这。我猜是方法调用：`zoo[0].eat(?)` 传什么类型进去？每个元素要的食物类型可能不同，调用点的类型检查没法写。但「编译器具体怎么愁」我只能推到这一层，更深的（什么存在容器装不下之类）我推不动。
出路我扫过教材但记不牢：好像有个 `any Animal<String>` 的写法把关联类型定死，还有个手动包盒子的方案叫什么擦除。**这两条我只有模糊印象，不敢保证细节**。
另外题里问 some 为什么救不了异构数组——我猜 some 是「固定一种类型」，数组里要求所有元素同一种，所以 some 反而更做不到异构？这个推理我没底气。
**自评：半懂半猜**（两层困难我只扎实推出一层半，出路基本是背的残影）。

### C3 some 与 any：同一个协议两种写法差在哪？

按 M4 的比喻推：`-> some Animal` 返回时，编译器知道实际返回的是 Cat 还是 Dog，但调用方只拿到「某个遵守 Animal 的东西」，而且每次调用返回的**具体类型必须一致**（我猜的，账本条目不能一会一个样）。`-> any Animal` 是装箱，这次可以 Cat 下次可以 Dog，运行时靠箱子找到真实类型。
派发上我推：some 编译器知道底细，可以直接调用（静态）；any 得查表（动态）。性能差在这。
SwiftUI body 为什么 some View——这里我卡住，只能猜：body 会被框架反复调用做 diff，如果每次返回的箱子类型飘忽，框架对不上「这是哪个视图」，刷新就乱。教材里那个词「AnyView 伤 Identity」我有印象，但 Identity 具体怎么个伤法、diff 具体怎么用类型对齐，我讲不出来。
**自评：半懂半猜**（some/any 的分工方向推对了，body 那半是印象分）。

### C4 Optional 的本质

`Int?` 是 `Optional<Int>` 的糖，.some / .none 两个 case。OC 的 nil 是地址 0，`[nil foo]` 运行时一看接收者是 0 就直接返回零值——这是运行时的兜底。Swift 里 nil 是 `.none` 这个枚举值，它不是「一个能接收消息的对象」，而是「表示缺席的 case」——类型系统里 `Optional` 上根本就没定义你想调的那个方法，所以编译期直接拦住。
因果链：把缺席做成类型 → 方法只在有值的 case 上有意义 → 编译器强制你先拆包（if let / switch / !）→ 把 OC 里「静默吞掉的 nil 崩溃源」提前到编译期暴露。代价是代码里到处 if let，收益是不再有一类「nil 穿透十层调用后在莫名位置炸」的事故——这种事故我在 OC 里查过太多次。
可选链 `a?.b?.c` 脱糖，我手写大概是：

```swift
// a?.b?.c 的等价形状
var result: C? = nil
if let aUn = a {
    if let bUn = aUn.b {
        result = bUn.c
    }
}
```

任一层 .none 就短路，整体返回 .none；全拆开就拿到 c 包回 .some。
**自评：有把握**（脱糖那个结构我是现推的，写法可能和编译器内部不一样，但逻辑形状我有信心）。

### C5 @escaping 的本质与 OC block 的差异

闭包捕获的变量本来可以待在栈帧里，函数一返回栈就回收了。如果闭包要活得比这次调用长——存进属性、交给 DispatchQueue / URLSession 异步执行——它捕获的东西就必须搬到堆上，这就是逃逸。不标 @escaping 编译器就按「不逃逸」优化，你一旦把它带出去就编译报错（我混编项目里撞过这个错，当时就是无脑加关键字糊过去的，现在才知道它在说什么）。
循环引用的环：self 强持有闭包（存在属性里），闭包强捕获 self——两条边成环，谁也不释放。和 OC 比：block 也这么成环，我们靠团队约定写 `__weak typeof(self) weakSelf`；Swift 的差异——我想了想——是 Swift 把「逃不逃逸」写进了类型签名，编译器先强制你承认这个事实（多了这层义务），但捕获列表 `[weak self]` 还是要自己写，编译器不代劳（没有自动保护，义务落在写代码的人身上）。还有个细节：OC 里 block 赋给属性默认 copy 到堆，这个行为是固定的；Swift 里逃逸与否取决于用途，你得显式声明。
weak 和 unowned：weak 是弱引用、对象没了自动变 nil，要 optional 处理；unowned 是不做 nil 检查的裸引用，对象先死就崩。闭包寿命不确定用 weak，确定活得比 self 短才敢 unowned——这个和 OC 的 unsafe_unretained 的教训一致。
**自评：有把握**（这题基本是十年 block 经验的翻译，@escaping 的「类型契约」角度是新收获）。

### C6 mutating 与 let

推：struct 是值，方法默认拿到的是 self 的拷贝，改拷贝没意义。mutating 就是把 self 变成 inout 语义——copy-in copy-out：进来时拷贝，改完写回原处。class 不需要 mutating，因为方法拿到的是引用，改的是引用指向的那块共享内存，本来就「人见人变」，没有写回问题。
let 的 struct 不能调 mutating：let 承诺这块内存只读，mutating 的 copy-out 写回动作要覆盖原值，直接违反承诺，所以编译器不让调。let 的 class 实例倒是能改内部——因为 let 锁的是「引用本身不许改指向」，引用指着的对象内容不在承诺范围。这一层「let 到底锁的是什么」的差异，根源就是值/引用有没有那层间接。
**自评：有把握**（从 inout 的 copy-in copy-out 推，这是我在原料里读到后马上能对上 OC 认知的点）。
