## Q1. App 启动慢，你的优化思路是什么？

**结论先行**：先度量、再归因、后优化，最后建防劣化卡点——启动优化不是攒技巧，是把 pre-main 和 post-main 两段链路拆开分别治理，并保证不会随版本回退。

**原理展开**：启动分两段。pre-main 是 dyld 加载到 main() 之前：加载动态库、rebase/bind、ObjC runtime 注册（+load 方法和 category）、C++ 静态构造器、Swift 类型元数据初始化。手段包括：减少动态库数量（合并成少数几个 framework）、删掉 +load 改成 +initialize 懒加载、清理无用类和静态全局变量。post-main 是从 main() 到首屏可交互：核心是压缩 `didFinishLaunching` 里的同步工作——SDK 初始化分级（必须/延迟/首次使用时）、网络预热异步化、首屏数据懒加载。度量上，开发期用 Instruments 的 App Launch 模板看 dyld 和主线程 trace，关键阶段插 `os_signpost` 打区间；线上用 MetricKit 的 `MXAppLaunchMetric` 拿按天的启动耗时分布，再配自己埋的 signpost 数据上报做版本对比。

**实战案例**：我们 App 启动 P95 一度涨到 2.8s，我先把启动阶段用 signpost 拆成五段上报，发现是某个统计 SDK 在 didFinishLaunching 里同步读磁盘配置 + 两个业务模块在启动时预热缓存。改成懒加载 + 后台队列预热后，P95 降到 1.4s 左右。更重要的是之后我在 CI 加了卡点：每次合入主干用固定真机跑冷启动基准脚本，超阈值直接 fail。<!-- 需替换为真实经历 -->

**边界与权衡**：冷启动、热启动、后台恢复要分开度量，MetricKit 也区分 applicationResume 和 launch；另外启动优化容易伤害可读性（比如把 SDK 初始化散成懒加载），我会维护一份"启动任务清单"文档并分级标注，避免后人再加同步任务。

## Q2. 内存问题怎么排查？你处理过 OOM 吗？

**结论先行**：处理过，而且可穿戴 App 长驻内存，OOM 是高频问题。排查路径是：先确认是不是 jetsam 杀的、再看 footprint 分布找大头，线上靠 MetricKit 和用户复现，开发期靠 Memory Graph Debugger 和 Allocations。

**原理展开**：iOS 内存不足时由 jetsam 机制按优先级杀进程，前台 App 的内存上限随机型不同（老机型可能只有 1.4G 左右，且受系统整体压力动态影响）。被 jetsam 杀掉的进程在崩溃日志里通常没有传统 crash 堆栈，只能从 termination reason 里看到 `Jetsam`。线上区分前台/后台 OOM 的思路：如果下次启动前收到 MetricKit 的 `MXMemoryMetric` 峰值异常，配合自己记录的"进后台时的内存水位"日志，能判断是前台涨上去的还是后台被唤醒时超标。开发期主力工具是 Xcode Memory Graph Debugger（看对象图和循环引用）和 Allocations/Leaks 模板。超标大户通常是：解码后的大位图（一张 4000×3000 图解码后约 45MB）、不设上限的图片/数据缓存、SQLite 连接或文件句柄泄漏、长生命周期单例持有的大数组。

**实战案例**：我们 App 在同步多天历史数据时有用户反馈被杀。我加了一条"同步时内存水位"埋点，发现一次拉全量数据时把 JSON 全部驻留在内存，峰值冲到 900MB+。改成流式解析 + 分批入库后，峰值压到 200MB 以内，该场景 OOM 归零。<!-- 需替换为真实经历 -->

**边界与权衡**：内存优化的代价往往是性能（流式解析更慢、缓存变小命中率降低），所以要看场景取舍——同步链路宁可慢一点也不能爆，UI 图片缓存则保留较大额度。另外不要用 `didReceiveMemoryWarning` 当唯一防线，收到警告时往往已经很晚，关键路径要主动控制峰值。

## Q3. 可穿戴 App 的功耗怎么优化？

**结论先行**：功耗优化的本质是"减少无线电活跃时间 + 减少 CPU 唤醒次数"，BLE 场景重点在扫描策略、连接参数和同步批量化，度量靠 Energy Log 和 MetricKit 交叉验证。

**原理展开**：BLE 的耗电大头是射频。扫描侧：扫描窗口是主要耗电点，所以要用服务 UUID 过滤、关掉 duplicate 回调、控制扫描时长和间隔（比如扫 10s 停 30s 的占空比），能用已缓存的 peripheral identifier 直连（`retrievePeripherals`）就不扫描。连接侧：connection interval 是核心权衡——interval 短延迟低但双方射频频繁唤醒，可穿戴产品常见做法是前台交互时请求短 interval、空闲和后台请求长 interval；slave latency 允许从机连续跳过若干 interval，是省电利器。数据侧：传输用批量、MTU 协商到最大（`maximumWriteValueLength`），减少来回次数；notify 频率在固件侧做聚合（比如传感器 100Hz 采集但 10Hz 上报）。CPU 侧：避免后台频繁被 `BGTaskScheduler` 唤醒，定时任务合并执行；定位类功能用 significant-change 而不是持续高精度。度量用 Xcode Energy gauges 和 Instruments 的 Energy Log，线上用 MetricKit 的 `MXCPUMetric` / `MXGPUMetric` 和 locationActivity 等维度佐证。

**实战案例**：有用户反馈我们 App 装了就耗电。我用 Energy Log 抓了一晚上，发现是后台保活逻辑在每 15 分钟唤醒一次做无效扫描。改成：后台只靠系统 restoration 代管连接、不主动扫描；同步任务攒到用户回前台或充电时才批处理。优化后后台功耗在 Energy Log 里几乎归零，商店里"耗电"相关差评也基本消失。<!-- 需替换为真实经历 -->

**边界与权衡**：功耗和实时性天然冲突——AI 可穿戴如果要做实时音频/事件流，interval 没法拉太长，这时要把预算花在"传输效率"而不是"少连接"上。另外功耗问题经常是固件侧的锅（广播间隔、天线发射功率），要用电流仪或固件日志确认归属，别全在 App 层打补丁。

## Q4. 从 0 搭建崩溃监控与稳定性体系，你会怎么做？

**结论先行**：我会按"采集 → 上报 → 符号化 → 聚合 → 告警"五段链路搭，客户端采集用 Mach exception + Unix signal + NSException 三层捕获，基建侧用 KSCrash 的思路自建或直接用成熟 SDK（如 Firebase Crashlytics），但 founding 角色必须理解每一层在干什么，不能只调初始化。

**原理展开**：崩溃捕获三层各管一类问题。**Mach exception** 是内核层异常，比如 `EXC_BAD_ACCESS`（野指针）、`EXC_BAD_INSTRUCTION`，通过给当前 task 注册 exception port（`task_set_exception_ports`）并在独立 Mach 线程上监听消息来捕获，这是最底层也最完整的一层。**Unix signal** 是内核把 Mach 异常转成的信号，如 `SIGSEGV`、`SIGBUS`、`SIGABRT`、`SIGTRAP`，用 `sigaction` 注册 handler 捕获；注意信号 handler 里只能调 async-signal-safe 函数，所以成熟实现都是 handler 里只做最少工作（写标志位/把上下文 dump 到文件），真正的分析放到下次启动。**NSException** 是 ObjC 层的未捕获异常，走 `NSSetUncaughtExceptionHandler`，但注意它触发后程序仍会继续走到 signal 层（SIGABRT），要避免重复上报。三类信息汇总后在下次启动时生成 crash 报告，附上 binary UUID（image list）上报。**符号化**：崩溃地址是 image 基址 + 偏移，要用对应构建的 dSYM 通过 `atos` / `symbolicatecrash` 把地址还原成函数名行号，关键是 image load address 和 slide 的计算。**dSYM 管理**：CI 构建（`xcodebuild archive`）后自动归档 dSYM 并上传到 App Store Connect（bitcode 重编译场景）和自建符号表服务，按 binary UUID 索引，保证线上包一定找得到符号。**卡顿（hang）监控**：起一个 watchdog 线程，定时检查主线程是否在预期时间内响应（比如向主线程投递任务并等待信号量），超时即认为 hang，此时抓取主线程堆栈——MetricKit 的 `MXHangDiagnostic` 是系统给的免费补充。

**实战案例**：我在上一家从 0 搭过这套：客户端采集层参考 KSCrash 的三层结构自己封装，服务端先用 Crashlytics 兜底、再逐步切到自建聚合（按堆栈 top frame 聚类 + 版本维度趋势），CI 里 dSYM 上传做成打包流水线的强制步骤，曾因一次漏传导致整版本符号化失败，之后加了上传校验告警。上线后崩溃率从 0.4% 降到 0.15% 以下，且每个 crash 都能在当天归因到 commit 级别。<!-- 需替换为真实经历 -->

**边界与权衡**：自建采集层的风险是 handler 里出 bug 造成二次崩溃，所以我会控制自研范围——采集用成熟实现、聚合和归因逻辑自建。另外 OOM、watchdog kill（0x8badf00d）不属于可捕获崩溃，要靠 MetricKit 和启动时启发式检测补充；崩溃率指标也要分版本看，别被老版本长尾稀释。

## Q5. 设计这个 App 的 CI/CD 流水线。

**结论先行**：单人团队下流水线就是"第二个工程师"，我会设计成：PR 检查快而严（lint + 单测 + 增量构建），主干构建全而自动（完整测试 + TestFlight 分发），发版走分阶段放量，签名和证书全程自动化，人只做"合入"和"发版"两个决策点。

**原理展开**：**触发结构**分三层。PR 层：push/PR 触发 lint（SwiftLint + SwiftFormat）、单元测试（xcodebuild test，跑在模拟器）、以及只编译受影响 target 的增量构建，目标 10 分钟内给结果，卡不过不让合入。主干层：merge 到 main 后跑全量测试 + UI 冒烟 + Release 构建，成功后自动打 beta 版本号、archive、上传 TestFlight，配 `xcodebuild` 的 `-resultBundlePath` 收集测试产物。**签名自动化**用 fastlane match：证书和 profile 加密存在 git 仓库（或云存储），CI 机器上 `match appstore` / `match development` 一键拉取，避免"某人电脑上的证书"这种单点。**自动分发**：TestFlight 内部测试组自动收到新 build，外部测试组按 build 元数据（版本号、commit 摘要、变更清单）自动更新"本次测试重点"说明；给硬件/固件同事的调试版单独一个 build configuration，打开详细日志和调试面板。**发版**：App Store 开 phased release 分阶段放量，配合 MetricKit/崩溃率监控，异常时暂停放量；`deliver` 提交审核和元数据版本化，审核被拒的应对记录进 runbook。**工具选型**：startup 阶段我会用 GitHub Actions + 一台自托管 Mac runner（M 系列 Mac mini），因为 iOS 构建绕不开 macOS 且自托管比云 Mac 便宜可控；团队扩张后可迁 Bitrise/Xcode Cloud。

**实战案例**：我在前一个从 0 起步的项目里就是这么搭的：第一周先跑通 lint + 单测 + TestFlight 自动上传三件事（先让链路闭环），第二周加 match 签名自动化，之后逐步补 UI 冒烟和构建缓存。上线后主干平均每天自动发一个 TestFlight 版本，发版人工操作压缩到 5 分钟以内，半年内没有出过一次签名/证书相关的发版事故。<!-- 需替换为真实经历 -->

**边界与权衡**：全量 UI 测试进 CI 会显著拖慢流水线，我只放冒烟级用例，重交互靠人工 beta 验证；另外 Mac runner 挂了流水线就停，我会给 runner 配健康检查和备用机策略。单人团队最忌讳流水线本身成为维护负担，所以脚本全部进仓库、能声明式不写 shell。

## Q6. 自动化测试策略怎么定？投入产出比怎么权衡？

**结论先行**：单人团队的测试策略必须务实：测试金字塔倒过来用——重单元测试在纯逻辑层（协议解析、同步引擎、状态机），集成测试覆盖关键链路，UI 测试只做冒烟，硬件依赖全部抽象成协议做 mock。

**原理展开**：哪类代码最值得测？标准是"逻辑密度高 + 出错代价大 + 容易隔离"：BLE 协议帧的编解码、数据同步的冲突合并逻辑、连接状态机、OTA 的分片校验——这些纯函数/纯状态机代码测起来便宜、收益极高，一个字节序 bug 线上代价可能是变砖。BLE 与硬件依赖的测试方法：把 `CBCentralManager`/`CBPeripheral` 的能力抽象成协议（如 `BluetoothTransport`），生产实现包一层 CoreBluetooth，测试实现是内存模拟器，可以脚本化"连接 → 断连 → 恢复"等场景，甚至模拟固件的异常包来测 App 的容错。更进一步可以做协议级的回放测试：把真实设备交互抓包（PacketLogger）存成用例文件，测试时喂给解析层验证。UI 测试只保留登录、配对、同步三条主路径的 XCUITest 冒烟，跑在 CI 的模拟器上；其余靠 TestFlight 人工 beta。快照测试对 UI 回归有效但维护成本高，startup 阶段我倾向缓行。

**实战案例**：我们 OTA 模块上线前，我把固件团队提供的协议文档翻成表驱动的编解码测试（正常帧、截断帧、CRC 错误帧、粘包），CI 里每次提交都跑。后来固件改过一个字段长度没通知，就是这批测试第一时间抓到的，避免了一次量产固件和 App 不兼容的事故。<!-- 需替换为真实经历 -->

**边界与权衡**：覆盖率不是目标，"关键路径 100%、边缘代码看 ROI"才是；测试代码本身也要维护，没人维护的烂测试比没测试更糟（给假安全感）。另外真机硬件回归永远无法被完全替代，我会维护一台"常驻测试设备 + 自动化配对脚本"做每日巡检。

## Q7. 日志体系怎么设计？线上问题如何远程定位？

**结论先行**：日志体系分三层：本地结构化日志（分级 + 环形缓冲）、按需回捞（用户触发或后台指令）、聚合分析（关键事件上报而非全量日志）。软硬件场景还要多一条：设备端日志通过 BLE 拉回来。

**原理展开**：本地层我用 `os_log`（unified logging，系统级、可用 Console.app 和 log 命令检索）加自建内存/磁盘环形缓冲：业务关键日志按 level（error/warn/info/debug）分级写入环形文件，滚动覆盖、控制总大小（如 5MB），避免无限写盘。日志必须带结构化上下文：会话 ID、设备固件版本、连接状态、当前同步阶段——可穿戴问题没有这些上下文根本没法查。敏感数据（token、用户健康数据）在写入前统一走脱敏管道，只做掩码或哈希，这条在健康类产品上是红线。回捞层：App 内置"反馈"入口，用户触发时打包最近 N 天的环形日志加密上传；也可以服务端下发开关，远程临时提高某用户的日志级别（远程配置 debug profile）。线上定位不能依赖全量日志——成本不现实，所以把"关键状态迁移"（连接建立/断开、同步开始/失败、OTA 各阶段）做成轻量埋点事件常量上报，日志用于深挖、事件用于面。设备端日志：固件把日志写到 flash 环形区，App 通过专用 BLE 特征值按页拉取，断点续传，拉回来后和时间轴上的 App 日志对齐分析。

**实战案例**：有个"同步到一半失败"的线上问题，靠常埋点只能看到失败率高，定位不到原因。我通过反馈通道回捞了三个用户的日志包，发现都是同步中途设备发了一个固件异常事件码，再对照设备日志确认是固件某个传感器驱动挂起拖垮了 BLE 栈——一个 App 层完全看不出来的固件 bug，两天内定位并推动固件出了补丁。<!-- 需替换为真实经历 -->

**边界与权衡**：高频日志（如每包 BLE 数据）默认关闭，只在调试 profile 下开，否则既耗电又淹没有效信息；日志采样要分层——错误日志永不采样，info 按会话采样。另外日志 schema 变更要向后兼容，服务端解析器要容忍老版本格式。

## Q8. App 和设备的数据同步怎么设计？断网、冲突、重复怎么处理？

**结论先行**：我会把同步建模成"设备 → 手机 → 云端"的三段最终一致管道，核心三原则：一切数据带全局唯一事件 ID 做幂等、冲突用确定性的合并规则而不是最后写入赢的裸时间戳、离线优先（本地是权威，网络只负责传播）。

**原理展开**：**设备→手机段**：设备侧数据（传感器记录、事件）在固件端就分配单调递增的序列号或事件 ID + 设备时钟戳，存在 flash 环形区；App 同步时按"水位线"拉取——本地持久化"已同步到序号 X"，每次从 X+1 增量拉，天然幂等且支持断点续传，断连/断电后重启接着拉即可。重复问题靠事件 ID 去重：入库用 `INSERT ... ON CONFLICT DO NOTHING`（SQLite upsert），重复拉取无副作用。**手机→云端段**：App 本地数据库是唯一权威（offline-first），写操作先落本地、进"待上传队列"，再由同步引擎批量推云；上传以事件 ID 为键，服务端幂等接收（同 ID 重传直接返回成功）。**冲突处理**：分两类。设备数据（采集类）基本只增不改，冲突极少，若 App 端做了编辑（如给睡眠段加标签），用"字段级 last-write-wins + 向量时钟或混合逻辑时钟"兜底；用户档案类数据（多端编辑）我会用操作日志（operation-based）而非整对象覆盖，合并操作序列，保证收敛。**断网**：离线时全部写本地队列，恢复网络后后台任务（前台回前台时优先 + `BGProcessingTask` 兜底）补推；长时间离线导致队列过长时做压缩合并。**进度呈现**：同步进度用"水位线推进"驱动 UI（已同步条数/总条数），而不是简单的转圈，中断时明确展示"已同步到何时"。**一致性校验**：定期对账——App 和云端按时间窗比对记录数和校验和，不一致触发修复流程（以事件 ID 集合做 diff 补传）。

**实战案例**：我做手环同步时踩过最狠的坑是"重复记录"：断连重连后设备重新上报了部分数据，加上手机端两个入口并发触发同步，云端出现过三倍重复。之后我做了三件事——设备序号水位线持久化、入库强制 ID 去重、同步引擎单 actor 串行化入口，重复问题归零，同步中断后的恢复也从"全量重拉"变成秒级增量。<!-- 需替换为真实经历 -->

**边界与权衡**：设备时钟不可信（掉电重置、漂移），所以事件排序不能完全依赖设备时间戳，要以"设备本地序号 + 手机接收时刻"组合为准，云端再做归一化；另外全量对账很耗流量，只在 Wi-Fi/充电时跑。离线优先的代价是多端可见性延迟，产品层面要设计好"未同步"状态的表达，别让用户以为数据丢了。

## Q9. 发版流程怎么设计？热更新在 iOS 上可行吗？

**结论先行**：发版走"TestFlight 内测 → phased release 分阶段放量 → 崩溃率监控决策"的标准流程；热更新在 iOS 上基本不可行，任何动态下发可执行代码的方案都违反 App Store 审核指南 2.5.2，只能靠配置下发和快速发版通道来弥补。

**原理展开**：完整发版链路：feature 分支 → PR 审核 + CI → main 自动出 TestFlight build → QA/内测组验证 → 打 release tag 触发 archive + 提交审核 → 审核通过后开 phased release（苹果按 1%→2%→5%→10%→20%→50%→100% 七天阶梯放量），放量期间盯崩溃率（MetricKit/自建监控）和用户反馈，异常就暂停放量；严重问题直接撤回该版本（remove from sale）并发 hotfix 版本。**审核被拒**常见原因要有预案：蓝牙权限用途描述不清晰（2.5.1/5.1.1）、后台模式声明与实际不符、健康数据隐私合规（App Privacy 声明）、硬件配套 App 审核时设备不在审核员手里——针对最后这条，我会准备详细的 demo 视频和说明文档随审核备注提交。**热更新**：JSPatch 这类通过 runtime swizzle 动态替换方法的方案，2017 年起苹果大规模警告并下架，因为它可绕过审核执行任意代码；现在合规的"热"手段只有：远程配置（行为开关、阈值、文案）、服务端驱动的功能开关（feature flag）、以及 React Native 这类框架内的 JS bundle 更新（也需在审核时披露）。所以真正的兜底是"快速发版能力"——把发版周期压到天级，加急审核（expedited review）作为紧急通道。

**实战案例**：我们曾发过一个版本在特定系统版本上启动即崩，当时就是靠 phased release 在 2% 阶段被崩溃监控抓到，暂停放量后影响面控制在几千人；hotfix 走加急审核约一天过审，同时用远程配置关掉了触发崩溃的功能入口做临时止血。<!-- 需替换为真实经历 -->

**边界与权衡**：phased release 的代价是问题暴露被拉长七天，如果监控不到位反而延误发现，所以放量期必须有人盯指标；feature flag 用多了会变成组合爆炸的测试负担，要定期清理过期 flag。

## Q10. 线上出现一个偶现崩溃，复现不了，你怎么办？

**结论先行**：不复现就靠"信息包围"：先从崩溃堆栈和聚类里榨线索，再用埋点/日志缩小变量空间，同时评估影响面决定优先级——偶现崩溃的解法往往是"让它变得可复现"或"用代码审查直接锁定可疑路径"，而不是等运气。

**原理展开**：第一步看崩溃报告本身：exception 类型 + 崩溃线程堆栈 + 各线程状态。`EXC_BAD_ACCESS` 配野指针特征（地址是 0x0d 之类魔数或小数值）指向 use-after-free；`SIGABRT` 往往是断言或容器越界；主线程堆栈停在锁上、其他线程也在等锁，说明是死锁。堆栈聚类（crash 平台按 top frame 分组）能告诉你这是单一原因还是多入口汇聚。第二步看维度分布：只在特定系统版本/机型/App 版本/语言地区出现，往往直接锁定原因（比如只在 iOS 某 beta 出 → 系统 bug 或 API 行为变更）。第三步加针对性侦察：在可疑路径加 breadcrumb 日志（上次关键状态上报），下个版本上线后看崩溃前最后一条 breadcrumb；MetricKit 的 `MXCrashDiagnostic` 能提供系统级补充堆栈。第四步用代码审查替代复现：把崩溃点的所有调用方列出来，逐一审查线程安全和生命周期——偶现 crash 七成是多线程竞态，重点看共享可变状态有没有锁/actor 保护。本地构造压力测试（并发循环调用可疑接口）有时能把低概率竞态放大成必现。

**实战案例**：遇到过一例占比 30% 的偶现 `EXC_BAD_ACCESS`，堆栈在某个异步回调里访问已释放对象。维度分析发现都发生在"断连瞬间"，代码审查确认是 BLE delegate 回调在专用队列、对象释放走主线程，没有生命周期保护。修复方式是回调持 weak 引用 + 队列统一收口，发版后该聚类归零——全程没有复现过一次。<!-- 需替换为真实经历 -->

**边界与权衡**：影响面决定投入：崩溃率 <0.01% 且只在老系统出现的可以先记录观察，别无限投入；另外修"看起来像"的崩溃要谨慎——没有根因确认就改代码，可能掩盖真问题导致换个姿势再崩，所以每次修复后必须跟踪该聚类的曲线是否真正归零。

## Q11. MetricKit 能给你什么数据？你如何建立性能基线与防劣化机制？

**结论先行**：MetricKit 提供系统聚合的、按天投递的设备端性能/诊断数据，是线上性能监控的免费基座；防劣化则靠"线上 MetricKit 定基线 + CI 真机基准测试设卡点"双保险。

**原理展开**：实现 `MXMetricManagerSubscriber` 后，系统每天投递一次 `MXMetricPayload` 和 `MXDiagnosticPayload`，可通过 `didReceive` 回调拿到并 `jsonRepresentation()` 上报。指标类包括：`MXAppLaunchMetric`（启动耗时直方图）、`MXAppResponsivenessMetric`（hang 时长分布）、`MXMemoryMetric`（峰值内存）、`MXCPUMetric` / `MXGPUMetric`（累计 CPU/GPU 时间）、`MXNetworkTransferMetric`（上下行流量）、`MXDiskIOMetric`、`MXLocationActivityMetric`、`MXAnimationMetric`（掉帧率）等。诊断类包括 `MXCrashDiagnostic`、`MXHangDiagnostic`、`MXDiskWriteExceptionDiagnostic`，自带部分符号化堆栈。注意两点：数据是系统聚合后的直方图而非逐事件明细、有采样（不是全量用户），所以适合看分布和趋势，不适合精确定位单用户。**防劣化体系**我会搭两层：CI 层——合入主干前在固定机型、固定系统版本上用脚本跑冷启动/关键页滚动基准（清缓存、重启多次取中位数），对比历史基线超阈值（如启动劣化 >10%）就阻断或告警；线上层——每天拉 MetricKit 上报进数据库，按版本维度跟踪 P50/P95，新版本发布后自动和上一版对比生成报告，劣化超阈值在群里告警。阈值定法：用最近三个稳定版的数据算均值和波动带，阈值设在波动带之外，避免误报。

**实战案例**：我在 CI 里建了启动时间基准：一台固定真机 + 自动化脚本冷启动 10 次取中位数，历史数据入库画趋势图。某次有人往启动路径里加了一个同步数据库迁移，基准直接涨了 300ms 被卡点拦下，没进主干——比上线后靠用户数据发现早了整整一个版本。<!-- 需替换为真实经历 -->

**边界与权衡**：MetricKit 有版本门槛（iOS 13+，部分指标更晚）和投递延迟（最长一天），急性问题还得靠自建埋点；CI 真机基准对环境敏感（温度、电量、后台进程），结果波动要靠多次采样和统计方法压下去，别被噪声逼着天天调阈值。

## Q12. 包体积（App Size）怎么控制？

**结论先行**：包体积治理分"资源、代码、依赖"三块，靠工具量化（link map、App Store Connect 的 build size 报告），并把体积检查做进 CI；App Thinning 保证用户实际下载量最小化。

**原理展开**：**资源层**通常是最大头：图片用 Asset Catalog 管理并按需清理未使用的 image set，大图优先 HEIC/WebP 或矢量化（PDF/SVG 模板渲染），音视频走按需下载而非内置；Asset Catalog 还支持 App Thinning 按设备 scale 分发（只下载 2x 或 3x 那套）。**代码层**：开启 Dead Code Stripping（`DEAD_CODE_STRIPPING`）和 `-dead_strip` 链接选项剥离未引用符号；清理无用类和语言本地化（`KNOWN_REGIONS`）；C/C++ 静态库注意只链需要的目标架构切片，调试符号确认不进发布包。**依赖层**：每引入一个第三方库前先评估体积成本——用 link map 文件（`LD_MAP_FILE_PATH`）看每个 .o 贡献多少，优先选轻量库或只引入需要的子模块；能三行代码实现的别引一个 2MB 的库。**App Thinning 三件套**：slicing（按设备裁剪架构和资源）、on-demand resources（按需资源标签下载）、（bitcode 已随 Xcode 14 退役，不再考虑）。度量上，App Store Connect 的 App File Sizes 报告能看通用包和各设备变体的真实下载大小，CI 里每次构建对比 `.app`/archive 体积，超增长预算告警。

**实战案例**：我们 App 一度从 60MB 涨到 110MB，我拉了 link map 和资产清单排查，大头是两套未使用的字体、历史活动页遗留的位图、和一个只为一个工具函数引入的库。清理后回到 65MB，并在 CI 加了"体积增长 >2MB 需说明"的检查，之后每个版本体积都可见可控。<!-- 需替换为真实经历 -->

**边界与权衡**：体积优化有边际成本——过度压缩图片伤画质、激进 strip 可能误删靠反射引用的符号（ObjC 动态特性下 dead strip 要配合 `-ObjC` 等选项验证）。我的原则是设"体积预算"让每次超标都可见，而不是临发版才突击瘦身。
