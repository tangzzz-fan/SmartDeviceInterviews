## Q1. 从 0 设计这个 AI 可穿戴 App 的客户端架构，你会怎么做？

**结论先行**：我会按"设备通信优先、UI 可以晚做"的原则，先搭一个五层架构：BLE 传输层、设备会话层、领域层、本地存储层、UI 层，依赖方向严格单向向下，前两个月把 80% 的精力压在前两层。

**原理展开**：

- **BLE 传输层**：直接封装 Core Bluetooth，对上只暴露协议化的接口，比如 `DeviceTransport` 协议定义 connect / send / receive。这一层不关心业务语义，只处理 CBCentralManager 状态机、重连、分包粘包、MTU 协商。这样做的核心目的是可替换——未来接第二颗芯片或者做 Android 对齐协议时，只动这一层。
- **设备会话层**：在传输层之上做业务语义的会话管理，比如"一次数据同步"是一个 session，有明确的开始、进度、超时、失败重试。固件协议版本协商也在这层完成。
- **领域层**：纯 Swift，不 import UIKit 也不 import CoreBluetooth，放设备模型、同步策略、数据聚合逻辑。这层是可以直接跑单测的。
- **存储层**：本地优先，传感器时序数据入库后 UI 只读本地，上传云端是异步的事。
- **UI 层**：只订阅状态，不直接碰 BLE。

依赖方向：UI → 领域 ← 存储，BLE 层实现领域定义的协议，靠构造注入挂进去。

**实战案例**：我之前做一款手环 App 时就是这么分层的。最早版本把 CBCentralManager 的回调直接写进了 ViewModel，结果固件协议改版时，业务代码和蓝牙代码纠缠在一起，改一个字段要动十几个文件。重构后我把传输层抽成独立的本地 Swift Package，固件协议变更的影响范围收敛到一个包里，协议升级的适配周期从一周缩到两天，BLE 相关崩溃也降了一个量级。 <!-- 需替换为真实经历 -->

**边界与权衡**：单人团队最大的风险是过度设计。所以我的纪律是：分层只分到"未来三个月确定会变"的地方，不预留想象中的多设备矩阵；路由框架、组件化中间件这类东西，团队到 3 个人之前都不引入。另外 BLE 层的抽象有个代价——多一层就多一次状态同步，调试时要能从 UI 一路 trace 到 ATT 层日志，所以我会从第一天就把分层日志和链路 ID 做进去。

## Q2. MVVM、MVC、TCA、Clean Architecture 你怎么选？

**结论先行**：这个 App 我会选 MVVM + 单向数据流，配合协议化的依赖注入；不会上完整的 TCA，也不会用传统 MVC。

**原理展开**：

- **MVC** 在 iOS 上天然退化成 Massive View Controller，因为 UIViewController 同时扛着视图和生命周期，业务逻辑没地方放，不适合 BLE 这种状态复杂的场景。
- **MVVM**：ViewModel 持有可观察状态（我倾向 `@Observable` 或 AsyncSequence，而不是 Combine 全家桶），View 只订阅不反写，形成事实上的单向数据流。BLE 连接状态、同步进度这类东西天然适合"一个可信状态源 + 多方订阅"的模型。
- **TCA** 的优势是状态变更完全可追溯、测试极其友好，但代价是：样板代码多、学习曲线陡、第三方库适配费劲，单人团队引入它会显著拖慢前期迭代速度。它的收益要在团队多人协作、状态极度复杂时才兑现。
- **Clean Architecture** 我取它的思想——依赖指向抽象、领域层独立——但不做教科书式的四层切分，单人团队撑不起那个仪式成本。

**实战案例**：我做手环 App 时，连接状态这一块最初用双向绑定（ViewModel 和 View 互相改），断连重连时状态到处飞，出过好几次"UI 显示已连接但实际没连上"的 bug。后来重构成单一状态源：BLE 层产出状态流，ViewModel 聚合，View 只读，同类 bug 基本清零，新功能的 UI 开发也快了很多，因为状态从哪来一目了然。 <!-- 需替换为真实经历 -->

**边界与权衡**：MVVM 的问题是它不约束你——写烂了照样烂，所以我会配两条纪律：ViewModel 不 import CoreBluetooth，状态变更必须可追溯到输入事件。另外如果后面团队扩到三四个人、状态管理开始失控，我会考虑把核心状态域迁到 TCA，这也是为什么我坚持领域层纯净——迁移成本能控制住。

## Q3. Swift 的 actor 和 async/await 解决了什么问题？Sendable 是干什么的？

**结论先行**：async/await 解决的是回调地狱和异步代码可读性，actor 解决的是数据竞争——它把共享可变状态圈进一个串行隔离的域里；Sendable 是编译器用来检查"这个值能不能安全跨并发域传递"的类型约束。

**原理展开**：

- **async/await** 让异步代码像同步代码一样线性书写，配合 structured concurrency（`Task`、`async let`、`TaskGroup`），任务的生命周期跟作用域绑定，取消可以自动向下传播。
- **actor** 内部状态只能在 actor 自己的隔离域内访问，外部访问必须 await，编译器保证同一时刻只有一个任务在 actor 内执行，数据竞争在编译期就被挡住。比如我会把 BLE 连接管理做成 actor，连接状态、待发队列都是它的私有状态。
- **关键点：actor 是可重入的**。await 挂起时会让出执行权，其他消息可以插进来，所以"检查再操作"之间状态可能已经变了，必须重新校验。这是和串行队列最大的认知差异。
- **Sendable** 标记一个类型可以安全跨隔离域传递：值类型天然满足，引用类型要求不可变或自带同步。不满足时编译器在 Swift 6 的严格并发检查下直接报错。
- **@MainActor** 标注的类型/方法保证在主线程执行，从 `@MainActor` 上下文发起的调用会继承隔离；配合 structured concurrency，父 task 取消会沿 `TaskGroup` 和子 task 传播，协作式取消要求代码在循环里检查 `Task.isCancelled`。

**实战案例**：我们的同步模块最初是用 GCD 串行队列保护状态的，后来一次偶现的"同步进度回退" bug，查了两天才发现是两个队列交叉写入。迁移到 actor 之后，我把状态读写全部收进去，又针对重入问题补了状态版本校验，这个 bug 再也没有复现过，而且 Swift 6 严格模式下编译器帮我们又抓出了三处潜在的跨线程逃逸闭包。 <!-- 需替换为真实经历 -->

**边界与权衡**：actor 不是银弹——所有跨 actor 调用都是潜在挂起点，actor 里千万别做长耗时计算，会饿死其他消息；另外和 Core Bluetooth 这种 delegate 回调模型桥接时，要小心回调线程和 actor 隔离的衔接，我通常用一个入口统一 hop 进 actor。

## Q4. 说说 ARC 下常见的内存问题及你的排查手段。

**结论先行**：最常见的是循环引用导致的泄漏（闭包捕获 self、delegate 强引用、timer/observer 没解除），其次是野逻辑——对象没泄漏但活着不该活；排查靠 Memory Graph 定位，Instruments Allocations/Leaks 定量，再加 CI 上的泄漏检测兜底。

**原理展开**：

- **闭包捕获**：闭包默认强引用捕获，`self` 被闭包持有、闭包又被 self 持有就成环。判断标准不是"闭包里有 self 就 weak"，而是看闭包的生命周期是否超过预期——比如存进属性的 escaping 闭包、NotificationCenter 的 block observer；一次性网络回调虽然不泄漏，但会延长对象寿命，通常也 weak。
- **delegate 用 weak**：delegate 模式是"被委托方持有委托方"的反向关系，强引用几乎必然成环，而且语义上 delegate 的生命周期不该被持有者决定。
- **timer / CADisplayLink**：RunLoop 会强持有 target，必须 invalidate，且 invalidate 得发生在正确的线程。
- **排查手段**：Xcode 的 Debug Memory Graph 是首选，直接可视化看哪个对象还活着、被谁引用，环一目了然；Instruments 的 Allocations 看增长曲线、Leaks 做泄漏扫描；线上则靠崩溃监控 SDK 的内存水位上报加上 OOM 归因。

**实战案例**：之前有个用户反馈 App 用半小时后明显发烫掉电快。我用 Allocations 挂了一段时间线分析，发现设备连接管理对象每断连重连一次就多活一个实例，根因是重连逻辑里一个 stored 的 completion 闭包强捕获了 self，而 self 又持有这个闭包。改成 weak 捕获并在 deinit 里加日志断言后，内存峰值降了大约三成，发热投诉也消失了。 <!-- 需替换为真实经历 -->

**边界与权衡**：actor 和 async 场景下有个新变化：`Task { }` 闭包同样会捕获 self，长生命周期的 task 相当于变相强持有；另外 Task 的弱捕获写法 `[weak self]` 里每次访问都要解包，状态一致性要自己保证。我的习惯是长任务一律 weak + 显式检查，短任务不强求，避免到处 weak 到失去可读性。

## Q5. UIViewController 的生命周期里有哪些容易出错的点？

**结论先行**：最容易出错的有三类：在 view 还没加载时访问视图属性、把只该做一次的事放进 viewWillAppear 反复执行、以及忽视内存警告和视图销毁时机。

**原理展开**：

- **loadView → viewDidLoad → viewWillAppear → viewWillLayoutSubviews → viewDidAppear**。`viewDidLoad` 适合做一次性初始化：绑定 ViewModel、启动订阅、配置静态 UI；`viewWillAppear` 每次出现都会调用，适合做刷新数据、恢复动画这类"每次都要最新状态"的事。把一次性订阅放进 viewWillAppear 是经典 bug——重复注册、回调翻倍。
- **提前访问 view**：view 是懒加载的，init 之后、loadView 之前访问 `self.view` 会强行触发加载，顺序就乱了；正确做法是构造期只存数据，视图相关全放 viewDidLoad。
- **内存警告**：`didReceiveMemoryWarning` 时系统可能把不在屏幕上的 VC 的 view 置 nil（现代系统上主要是非活跃的 VC），所以视图状态不要只存在 view 上，回到前台要能从数据重建。
- **SwiftUI 的差异**：`onAppear` 不严格等于 viewWillAppear——在 NavigationStack 里它依赖视图出现在层级中，时机和调用次数随导航结构变化，且 body 重算很频繁；副作用更适合用 `task` 修饰符，它跟视图生命周期绑定且自动取消，天然适配 async 加载。

**实战案例**：我做设备详情页时踩过一个坑：把"进入页面自动发起一次同步"放在了 viewWillAppear，用户从设置页返回时又触发一次，两次同步并发把设备端的会话状态搞乱了。后来改成 viewDidLoad 触发 + 显式的下拉刷新入口，并给同步层加了同会话去重，问题才彻底闭环。 <!-- 需替换为真实经历 -->

**边界与权衡**：生命周期没有"绝对正确"的放法，关键是问自己：这件事需要发生一次还是每次？它依赖的数据在哪个时机才就绪？我现在团队里推的规矩是——副作用进 `task`/viewDidLoad，状态刷新事件显式化，不依赖生命周期做业务触发。

## Q6. App 的数据持久化方案你怎么选型？

**结论先行**：我会分域选型：传感器时序数据用 GRDB（SQLite 之上）落本地库，配置和轻量状态用 SwiftData 或 UserDefaults 分情况，敏感数据进 Keychain；不会全局押注单一框架。

**原理展开**：

- **时序数据**（心率、睡眠、原始传感器帧）：写入吞吐高、按时间范围查询、还要做聚合降采样，关系型表 + 索引最合适。GRDB 对 SQLite 的封装很薄、线程安全模型清晰（DatabasePool/DatabaseQueue），批量插入性能好，迁移是显式的；直接用 SQLite 也行，但手写 C API 维护成本高。
- **Core Data** 适合对象图复杂、需要撤销/关系建模的场景，但它的并发模型（context 归属、perform 块）对新人不友好，出问题堆栈很难读。**SwiftData** 是 iOS 17+ 的现代替代品，写起来舒服，但最低版本要求和成熟度要评估，量产周期长的硬件 App 我会谨慎。
- **Realm** 自带响应式订阅很方便，但二进制依赖、加密模块收费、和 Swift 并发演进一直有摩擦，新项目我不优先选。
- **加密与迁移**：敏感字段字段级加密或者整库用 SQLCipher；迁移必须有版本号和前向迁移脚本，且要能在真机数据上演练——可穿戴设备换机恢复是最容易丢数据的场景。

**实战案例**：手环 App 上我们把原始活动数据存 GRDB，设计了"未上传标记 + 上传确认"两列来做本地优先同步：端上写入即成功，后台任务按批上传，服务端确认后清标记，弱网下数据零丢失。上线后统计过，用户数据完整性投诉从早期版本的每周好几起降到基本没有。 <!-- 需替换为真实经历 -->

**边界与权衡**：分域选型的代价是没有统一的"存储层心智模型"，团队里会有人问"为什么这个用那个不用"。我的回应是把边界写进规范：什么样的数据进什么库，一张表说清。另外 GRDB 的代价是要懂 SQL——但对可穿戴这种数据密集场景，这恰恰是优势不是负担。

## Q7. iOS 后台任务有哪些机制？可穿戴 App 的数据同步在后台怎么保证？

**结论先行**：iOS 后台机制没有一个是"保活"，全是"机会窗口"——BGTaskScheduler、后台音频/定位这类 background mode、以及系统事件唤醒。可穿戴数据同步的正确姿势是：前台尽力同步完，后台只做兜底补偿，核心靠 BLE 后台模式 + 通知唤醒。

**原理展开**：

- **BGTaskScheduler**：`BGProcessingTask`（长时间、可要求充电态）和 `BGAppRefreshTask`（短时间刷新）。调度由系统决定，看用户使用习惯、网络、电量，没有任何时间保证，真机上可能几小时甚至一天才给一次机会。
- **BLE 后台**：声明 `bluetooth-central` background mode 后，App 可以在后台维持与已连接设备的通信，但连接间隔会被拉长、吞吐量下降；如果连接断了，可以用 `retrievePeripherals` + 自动重连在设备重新出现时被唤醒。**前提是连接建立在 App 进程内**——系统蓝牙设置里配对的设备不会唤醒你的 App。
- **后台传输的现实**：后台 BLE 传大文件不可靠也不快，OTA 这种长任务必须在 App 前台且用户可感知的场景做。
- **为什么不能依赖保活**：iOS 的哲学是公平调度，任何"想办法不被杀"的方案（音频 hack、静默推送拉活）都在跟系统对抗，轻则被限制重则被审核拒绝。

**实战案例**：我们手表 App 的同步策略是三层：用户打开 App 时立即增量同步（前台优先级最高）；连接保持期间后台静默补齐小数据；BGProcessingTask 每天兜底做一次对账，把漏传的时间段补上。同时我们把"设备数据满了"做成推送提醒引导用户打开 App。这套组合下来，即使重度用户一天不开 App，数据丢失率也控制在可忽略水平。 <!-- 需替换为真实经历 -->

**边界与权衡**：要诚实告诉产品侧：iOS 上做不到"实时后台同步"，这是平台边界，不是工程能力问题。我会把体验设计成"打开即最新"，而不是承诺后台实时。另外 BGTaskScheduler 有个坑——必须提前 `register` 并调试过真机调度行为，模拟器上的表现完全不可信。

## Q8. 你如何做模块化？模块间通信用什么方式？

**结论先行**：我用本地 Swift Package 做物理模块化，模块间通信只认两种方式——向下依赖用协议 + 构造注入，横向事件用轻量事件总线；不用 URL 路由，不在早期引入服务注册中心。

**原理展开**：

- **物理边界**：每个模块一个 local SPM package，好处是编译边界强制存在——import 不到就是依赖没声明，比口头约定靠谱得多，还能换来增量编译加速。对比 CocoaPods：SPM 是原生方案，Xcode 集成零摩擦，CocoaPods 只在必须依赖老的 pod-only 库时才保留。
- **依赖方向**：业务模块可以依赖基础模块，基础模块绝不反向依赖业务；模块间不允许互相依赖实现，只依赖对方暴露的协议接口（放在独立的 Interface 包里）。循环依赖在编译期就会被 SPM 拒绝，这是物理模块化的最大红利。
- **通信方式**：A 需要 B 的能力，A 定义协议、B 实现、在组装层（App target）注入——依赖倒置。跨模块的广播事件（如设备断连，多方关心）走一个极简事件总线，本质是个类型化的 AsyncStream 分发器。
- **路由**：页面导航我倾向用类型安全的枚举目的地而不是字符串 URL，字符串路由在原生世界里收益有限还丢类型检查。

**实战案例**：我从零给手环 App 拆过模块：BLEKit（传输）、SyncEngine（同步）、Domain（领域模型）、各业务 feature 包。拆完最直观的收益是编译时间——干净构建后改一个业务页面，只需重编对应 package，日常迭代构建时间大概省了一半；更重要的是新同事上手时，看 package 列表就能理解系统边界，不用靠口口相传。 <!-- 需替换为真实经历 -->

**边界与权衡**：模块化有维护成本：package 一多，发版时的版本协调、接口变更的连锁修改都变多。单人团队阶段我只拆"确定会长大"的模块（BLE、同步），业务 feature 先留在主 target，等第二个人接手某块时再拆出去——边界跟着团队规模走，不为了架构图好看而拆。

## Q9. 网络层怎么设计？弱网和断连场景怎么处理？

**结论先行**：我会做一个薄而统一的网络层：async/await 封装 + 声明式 endpoint + 分层重试，核心思想是"本地优先、网络兜底"——业务操作先落本地，网络只负责把本地状态同步出去，弱网就退化为延迟同步而不是失败。

**原理展开**：

- **分层**：传输层用 `URLSession` 封装统一的 `request<T: Decodable>(Endpoint) async throws -> T`，集中处理超时、编解码、鉴权刷新、日志埋点；Endpoint 用 enum + 属性声明 path/method/body，类型安全且可 mock。
- **重试与退避**：幂等请求（GET、带幂等键的写入）自动重试，指数退避 + 抖动，避免断网恢复瞬间打爆服务端；非幂等请求不自动重试，上抛给用户。401 单独处理走 token 刷新队列，防止并发请求重复刷 token。
- **幂等性**：所有写操作带客户端生成的 UUID 幂等键，服务端去重。这是可穿戴场景的刚需——弱网下超时重发是常态，没有幂等键就会出现重复记录。
- **离线操作队列**：用户操作先写本地（数据库 + 待同步标记），一个同步器按序出队上传，成功清标记，冲突按"服务端为准 + 本地补偿"或业务定义的合并策略处理。UI 状态从本地读，网络结果只影响"同步中/失败"角标。

**实战案例**：我们的 App 在地铁、电梯这类断网高发场景早期丢过用户手动修正的数据，后来我把所有写路径改成"先落库再入队"，配合幂等键和服务端去重，做了两周灰度对比，弱网环境下的数据不一致反馈降到接近零，运营侧再也不用人工修数据了。 <!-- 需替换为真实经历 -->

**边界与权衡**：本地优先的代价是冲突处理变复杂——离线改了、服务端也改了怎么办？我的原则是能避免冲突就避免：可穿戴数据大多是"追加型"（新记录不修改旧记录），天然无冲突；少数可编辑字段才做合并策略，并且给用户提供"同步失败，保留本地版本"的兜底出口，不静默丢用户数据。

## Q10. 讲一个你做过的最有成就感的技术决策，当时有哪些备选方案？

**Situation**：我做可穿戴 App 时，OTA 升级最初是"整包一次性推送"：App 把完整固件发给设备，设备写入后重启生效。

**Task**：随着固件体积增长到几百 KB，问题集中爆发：单次传输遇到 BLE 丢包就要从头再来，升级成功率在弱信号环境下不到七成；用户中途杀 App 设备直接变砖风险也悬在头上。我负责重新设计 OTA 方案。

**Action**：当时有三个备选：① 维持整包但加重传，改动小但治标不治本；② 分块传输 + 设备端 flash 断点续传，每块独立校验、已写入的块不重传；③ 双分区（A/B）方案，设备端维护两个固件槽，失败可回滚，但对当时的 flash 容量和固件架构改动太大。我推动选了方案②，并做了三件配套的事：固件头带版本号和 CRC 做整包校验、App 端做传输进度持久化（杀进程重进能续传）、升级前强制电量检查。同时和固件团队约定了握手指令序列，把"设备当前收到哪一块"做成可查询状态，而不是靠 App 猜。

**Result**：升级成功率从不到七成提升到 99% 以上，单次升级耗时也因为免重传而下降；更重要的是变砖风险清零——任何阶段失败都能从已确认的块继续，或停在旧固件安全退出。

**English one-liner**: I redesigned our OTA pipeline from monolithic push to chunked transfer with resumable flashing, lifting upgrade success rate from under 70% to over 99% and eliminating bricking risk. <!-- 需替换为真实经历 -->

**边界与权衡（如果重来）**：重来我会更早做"升级埋点"——前期我们只知道成功率，不知道失败卡在哪个阶段，定位靠用户复现，走了弯路。另外方案②后来确实暴露过问题：分块校验拖长了整体流程，固件团队上 A/B 分区后我们才获得真正的回滚能力，这说明架构决策要跟着硬件代际走，没有一步到位的方案。

## Q11. SwiftUI 和 UIKit 你如何取舍？这个 App 你会用哪个？

**结论先行**：这个 App 我会以 SwiftUI 为主干（最低版本直接定 iOS 17+），配 UIKit 处理三类场景：自定义硬件相关交互视图、需要精细控制导航的页面、以及性能敏感的大数据列表。

**原理展开**：

- **SwiftUI 的优势在这个场景被放大**：BLE 连接状态、同步进度这种全局状态，SwiftUI 的声明式刷新模型是天然适配的——一个 `@Observable` 的设备状态对象注入环境，所有页面自动保持一致，不用手写一堆通知和回调。`task` 修饰符管理异步生命周期、自动取消，也很省心。
- **SwiftUI 的坑**：body 重算范围控制不好会出性能问题，大列表要用 `LazyVStack`/`List` 并注意行内视图的等值判断成本；和 Core Bluetooth 的结合本身没问题——delegate 回调收敛到 Observable 对象里即可——真正麻烦的是高频数据流（比如传感器实时波形），几百 Hz 的数据直接驱动 SwiftUI 刷新会卡，这类视图我会用 `UIViewRepresentable` 包一个 Metal/Core Animation 层的 UIKit 视图，数据走 CADisplayLink 或专用绘制通道，绕开 diff 开销。
- **UIKit 保留地**：复杂的自定义转场、需要精确手势仲裁的交互、以及某些 SwiftUI 至今不完善的控件行为。

**实战案例**：我在手环 App 里做过一次对比实验：设备状态面板用 SwiftUI 重写，实时波形图保留 UIKit 自绘。SwiftUI 部分把原本散在三个 VC 里的状态同步代码收敛成一个 Observable 模型，这块代码量减了约四成，"状态不同步"类 bug 基本消失；波形图那边坚持自绘，帧率稳定 60fps 不随页面复杂度劣化。 <!-- 需替换为真实经历 -->

**边界与权衡**：纯 SwiftUI 的风险在导航和第三方 SDK 兼容性上，我的策略是"主干 SwiftUI、叶子可下沉"——任何叶子视图允许换 UIKit 实现而不影响架构。另外 founding 阶段我会接受 iOS 17+ 起步，换取 SwiftData、Observation 这些现代 API 的开发效率，量产前如果用户覆盖有压力，再评估最低版本策略。

## Q12. 单元测试和依赖注入在 iOS 里怎么落地？

**结论先行**：落地关键不在测试框架，而在可测性设计——依赖全部走构造注入 + 协议抽象，测试金字塔以领域层和同步逻辑为主力；BLE 层用"协议 mock + 录制回放"来测。

**原理展开**：

- **依赖注入**：所有外部依赖（网络、存储、时钟、BLE 传输）以协议形式从构造器注入，App 入口统一组装。不用 service locator 那种隐式容器——单人团队阶段显式注入最不容易藏 bug。
- **BLE 怎么 mock**：给传输层定义协议（如 `DeviceTransport`），测试里注入一个可编程的 fake：能模拟连接、断开、延迟回包、返回畸形数据包。更进一步，我会把真实设备通信录成二进制 fixture（真机抓的 ATT 数据流），测试时回放给协议解析层，固件协议回归测试就不依赖实体设备了。
- **测试优先级**：同步引擎、协议编解码、离线队列这些"错了会丢用户数据"的逻辑覆盖率要高（我会要求分支级基本全覆盖）；UI 层不做单测，靠少量快照测试和 UI 测试守关键路径。
- **覆盖率不教条**：我定目标的口径是"数据正确性相关模块 80%+，纯展示层不设硬指标"，在 CI 上只对关键模块设门禁，避免团队为了凑数字写无意义测试。

**实战案例**：我给同步引擎搭测试时就吃过录制的甜头：有一次固件改了时间戳编码，正是回放 fixture 的用例在合并前抓出了兼容性断裂，避免了线上丢数据；日常开发中这套测试也让重构同步状态机有了安全网——改完一跑，十几秒就知道有没有破坏既有行为，重构周期明显变短。 <!-- 需替换为真实经历 -->

**边界与权衡**：要承认 UI 测试的投入产出比很低，尤其 BLE 相关 UI 依赖设备状态，自动化成本极高，我选择把这部分预算让给"协议层测试 + 手动探索测试清单"。另外 mock 有个风险：mock 和真实实现漂移——我的对策是给关键协议保留至少一组对着真机跑的集成冒烟用例，每次固件发版必跑。
