## 面试官为什么问这些

AI 可穿戴的客户端价值不在页面，而在这几条链能不能交付：

- 低功耗：设备能戴整天，App 不能把射频打满。
- OTA：字段升级不能变砖。
- 离线同步：设备不总在线，数据不能丢、不能乱序覆盖。
- 音频 / 传感器：采集、时钟、带宽、隐私同时成立。
- C/C++ 与协议：你能和固件用同一套字节说话。
- EVT 到量产：你知道硬件阶段在冻什么，客户端该配合什么。

加分项不是「听说过名词」。面试官要听：iOS 侧旋钮、固件侧旋钮、失败路径、以及你站在哪条边界上。

## 白板 5：功耗预算

```
电池寿命 ≈ 容量 / (射频 + MCU + 传感器 + 漏电)

射频通常是大头：
  广播 interval
  连接 interval / slave latency
  notify / write 频率
  扫描窗口（主要在手机侧）

App 能直接搞砸的：
  不停 scan
  Ready 后高频无响应写
  后台无预算重连
  日志 / 定位 / 音频会话常开

SLA 先和产品冻：
  目标续航
  状态新鲜度（例如 2s / 30s / 仅打开 App 时）
  是否允许后台实时
```

原则：先定 SLA，再选连接参数，再决定 App 行为。不要先「实时同步所有传感器」。

---

## 白板 6：离线同步管线

```
Device flash ring buffer
  -> BLE pull / push（seq + window + ack）
  -> Phone pending store（requestId 持久化）
  -> Cloud（可选）
  -> 冲突：device truth / field merge / 版本号

时钟：
  设备常见是单调 tick，不是墙钟
  手机侧转墙钟时记录 offset，断连后 offset 失效要重标定

失败：
  只重传缺失 seq
  成功必须幂等
  旧包不得覆盖新版本状态
```

---

## 白板 7：传感器 / 音频数据面

```
采样 -> 设备缓冲 -> 分包（seq/ts/codec）-> BLE/经典蓝牙
     -> App 重组 -> 会话/文件 -> 本地处理或上行

两条通道不要混：
  控制面：短命令 + 可靠 ack
  数据面：吞吐优先 + 校验 + 可丢或可补

AI 可穿戴常见坑：
  时钟域不同导致对齐失败
  MTU 小导致音频/IMU 打满通知
  后台录音 / 音频中断把会话打掉
  隐私：麦克风、健康明细默认不进日志和模型
```

## 白板 8：EVT 到量产，客户端在冻什么

```
EVT  接口还在变     App：多 firmware profile，日志拉满，功能克制
DVT  协议应冻结     App：恢复 / 功耗 / 回归集，开始谈 SLA
PVT  接近出货形态   App：兼容矩阵、灰度、工厂固件差异
试产 缺陷回流       App：按 SN / 固件版本切片，能停能回
量产 规模与版本斜   App：分阶段放量、kill switch、防砖 OTA
```

每一阶段问自己：现在该冻接口，还是还在探路？冻错了会拖硬件；冻晚了会让试产不可回归。

# A. 低功耗优化

面试官在听：你会不会把「省电」说成关动画。可穿戴省电首先是射频和采样策略。

### Q-A1: 低功耗你真正关心哪些旋钮？

**60 秒**  
先定产品 SLA：续航、状态新鲜度、要不要后台在线。再动三类旋钮：连接参数、通知/写入频率、App 扫描与重连预算。传感器采样率和音频会话是下一层。UI 优化几乎不是电池寿命的一阶因素。

**3 分钟机制**  
连接 interval 越大越省电，状态越不新鲜。Slave latency 允许从机多次不答，适合低频状态。广播 interval 影响发现速度和未连接功耗。App 侧：已绑定不要持续 scan；重连有预算；控制面合并写入；数据面批量而不是逐采样 notify。iOS Energy Log 看的是手机，设备续航必须拿真机和固件电流账，不能只看 Xcode。

**追问**  
「实时」和「两天续航」冲突时听谁的？听产品书面 SLA。没有 SLA 就自己提一版：打开 App 时 2 秒内新鲜，后台 30 秒或按事件。把选择做成可测项，而不是口头感觉。

**Trade-off**  
激进省电会让断连恢复变慢、OTA 变慢、传感器丢点。联调和演示阶段可以临时用「性能档」，但要有 profile，不能把试产参数直接当量产。

`[人设案例]` 默认连接参数为了跟手，设备待机电流偏高。和固件拆成 interactive / idle 两档：App 在前台或数据上传时切 interactive，空闲回 idle。可替换指标：日续航从约 14h 回到目标 24h 量级，状态延迟仍低于约定 SLA。

### Q-A2: App 怎样把设备打成耗电大户？

高频事故：后台无限重连、扫描过滤失败导致长扫、notify 订阅了不需要的高频特征、调试日志在设备侧 printf 过密、定位权限被蓝牙扫描连带拉起。排查先看「射频是否一直醒」，再看 MCU 是否被通知风暴打断睡眠。

缺口：没拿过电源分析仪时，也能讲：用固件电流日志 + 手机 Energy Log + 连接参数表三件套，先定位是扫描、连接还是数据面。

# B. 设备 OTA

`03` 白板 2 是 happy path。加分项要能讲：提交点、防砖、吞吐、版本矩阵、工厂升级 vs 用户升级。

### Q-B1: OTA 的提交点在哪里？失败时什么还能启动？

**60 秒**  
OTA 不是传完文件就算成功。要有明确 commit：校验通过、写完元数据、下次启动才切新镜像。commit 前必须能回旧镜像或进恢复模式。App 的职责是条件检查、可靠传输、阶段打点、升级后确认版本；砖不砖首先是镜像布局和恢复策略，必须和固件一起冻。

**3 分钟机制**  
常见布局：双分区最干净；单分区必须保留恢复体。传输：分片 seq、per-chunk crc、窗口、断点。iOS 侧注意 MTU、Write Without Response 的流控、应用层 ack，避免写爆导致断连。升级中掉电、校验失败、重启后连不上、版本回退、刷错硬件型号，每一条都要有状态码打到 App。字段升级成功后做最小 smoke：握手、电量、关键模式。

**追问**  
工厂 OTA 和用户 OTA 有何不同？工厂可以更激进、有夹具和串口；用户路径必须防砖、可提示、可中断恢复。客户端不要把两套协议混成一套无模式状态机。

**Trade-off**  
双分区安全，Flash 和成本更高。早期可用「旧镜像 + 超时进恢复」，但恢复入口（按键、USB、BLE 广播）必须可测，不能只写在口头。

`[人设案例]` 试产 80% 掉电。约定未 commit 前旧镜像可启动；App 在 reboot 窗口内循环 retrieve；超时引导恢复模式。可替换指标：该失败模式从不可恢复变为可重试，OTA 成功率提到 99% 量级。

### Q-B2: 版本兼容怎么做？

矩阵至少三维：硬件 revision、固件版本、App build。App 拒绝对不支持的硬件刷包；固件拒绝过旧协议。最小版本写进包头并签名。灰度按固件版本切片，出问题能停。Founding 阶段先做「能停、能看成功率」，再谈复杂差分包。

没完整做过量产 OTA：承认，迁移点放在校验、分片、失败重试、升级后握手；回滚和防砖要在入职后和固件冻清单。见缺口话术 1。

# C. 离线数据同步

面试官在听：你会不会把同步理解成「连上就 POST 一次」。设备侧有 flash 队列，手机侧有本地库，两边都可能先走。

### Q-C1: 设备离线时数据怎么不丢、上线后怎么不乱？

**60 秒**  
设备用环形缓冲和单调 seq 持久化。App 连上后按 cursor 拉缺失段，ack 之后设备才丢。手机自己的用户操作进 pending store，带 requestId，发送成功以设备 ack 为准。冲突默认：设备状态赢，或按字段合并；禁止用到达时间覆盖。

**3 分钟机制**  
墙钟不可靠：设备 tick 在断连后和手机 NTP 对不上。状态类数据用 version；波形/传感器用 seq。重连只补洞，不从头 dump，除非设备声明 buffer reset。云如果存在，是第三副本，不能在 BLE 未确认时当成功。iOS 后台被杀时 pending 必须落盘。

**追问**  
两边同时改同一个开关？以设备当前模式为准，App 显示冲突并拉 snapshot。不要静默打一场「最后写入获胜」。

**Trade-off**  
强确认可靠、耗电、吞吐差。状态和控制命令走可靠通道；高频传感器走窗口 + 可丢策略，丢了要在 UI 上可解释。

`[人设案例]` 通勤场景手机离线，设备继续记事件。早期实现按墙上时间合并，夏令时 / 时区把顺序打乱。改成设备 seq 为真相，手机只存 offset。可替换指标：同步错序客诉降到 0。

### Q-C2: 如何定义同步成功率？

分母：应同步的 requestId / seq 段。分子：在 SLA 内收到匹配 ack。按固件版本、网络、前台/后台切片。不要把「用户打开过 App」当成功。

# D. 音频采集或传感器数据处理

人设默认：音频 / 健康不是主战场，但必须能讲数据面。若你有真实音频项目，替换人设。

### Q-D1: 传感器数据从设备到 App，你会怎么设计？

**60 秒**  
控制面和数据面分开。数据面：采样率、batch、seq、设备 tick、压缩/编码、窗口重传。App 负责重组、缺包可见、反压。先算带宽：采样率 × 字节 × 通道，对比 BLE 有效吞吐，不够就降采样、批处理或换链路。

**3 分钟机制**  
IMU 100Hz 三轴 float 会打爆小 MTU 通知。常见做法：设备批 20–50ms、量化成 int16、带一个 tick。App 用 jitter buffer 对齐，而不是每包立刻上 UI。时钟：定期发一个锚点（tick + 手机时间），中间包插值。缓冲满时设备必须有策略：丢最旧、停采、或降频，并上报 overflow。

**追问**  
缺包怎么处理？控制面不允许缺。数据面允许缺，但要在质量和功耗上可见，不能静默当成完整波形。

**Trade-off**  
无损 + 实时几乎一定费电。AI 可穿戴通常接受短窗完整、长窗可抽稀。

### Q-D2: 音频采集在 iOS 上的边界是什么？

**60 秒**  
先问音频走哪条物理链路：经典蓝牙 HFP/A2DP、BLE 自研帧、还是设备本地识别只上传事件。三条的会话、后台、吞吐完全不同。App 要处理音频中断、路由变化、以及录音权限。麦克风数据默认不进普通日志，不进模型提示词。

**3 分钟机制**  
若是设备端 VAD / 短命令，再经 BLE 传压缩帧：按传感器数据面设计，额外处理丢帧和会话超时。若走系统通话音频：AVAudioSession 类别、中断回调、和 BLE 控制面同时存在时不要互相重置连接。后台连续录音受系统策略限制，产品如果假设「App 被杀仍连续录」，要尽早和产品拆穿。

**追问**  
为什么不把 PCM 直接走 BLE notify？带宽、功耗、丢包对语音质量不友好。优先设备端压缩或只传事件。

**Trade-off**  
云端识别更灵活，隐私和离线差；端侧识别省带宽，模型更新要走 OTA。Founding 先冻「谁采、谁编码、谁存」。

`[人设案例]` 未做过完整健康链路。迁移经验：传感器分包、tick 对齐、overflow 上报。若 Nirva 以音频为核心，入职 30 天先补：链路选择、会话冲突、后台边界、隐私红线。见缺口话术 3。

### Q-D3: 健康类数据多问什么？

权限、敏感数据最小化、是否出设备、是否出手机。同步策略更保守。面试里主动提红线，比假装做过 PPG 算法加分。

# E. C/C++、嵌入式、硬件通信协议

面试官在听：你是不是只能调 `writeValue`。Founding iOS 不要求你会写驱动，但要求你能读懂包，并对齐字节。

### Q-E1: 客户端和固件的协议你怎么定义？

**60 秒**  
一页契约：opcode、seq、length、payload、crc、协议版本、错误码。示例 hex 比长文有用。多字节有端序。版本可扩展（TLV 或保留字段），禁止静默改含义。App 用解析器吃字节，不要在 Swift 里硬填 C 结构体对齐。

**3 分钟机制**  
C 结构体有 padding，直接 `memcpy` 到 iOS 会错位。生产上用显式编解码，或 protobuf 但要注意嵌入式代码体积。CRC 放整包，分片 crc 另算。错误码分传输失败和业务拒绝。日志两边打同一 seq，才能对线。

**追问**  
你会自己写固件吗？不会当主业。能读关键状态机、看 map/日志、用逻辑分析仪截图和固件讨论「第几个字节」。UART/SPI/I2C 是板级；App 只通过 BLE GATT 看到它们的结果。

**Trade-off**  
Protobuf 演进方便，MCU 成本高。早期手写 TLV + 版本号往往更快。选了就要冻，不能每周换。

`[人设案例]` 一次「偶发解析失败」是固件改了字段宽度没改 version。之后协议变更必须 bump version，App 对未知 version 拒绝业务命令并提示升级。

### Q-E2: C/C++ 在 iOS 工程里可能出现在哪？

编解码、crc、加密、音频 codec、与跨平台核心。用 C 边界时注意：内存所有权、线程、错误码，不要让 Swift 直接分享可变缓冲给 BLE 回调线程。

缺口：不是嵌入式工程师。迁移点是协议、hex、状态机阅读。见缺口话术 5。

# F. EVT / DVT / PVT / 试产 / 量产

把阶段翻译成客户端工作，不要背字母。

| 阶段 | 硬件在做什么 | iOS 该做什么 | 不该做什么 |
| --- | --- | --- | --- |
| EVT | 能亮、能连、接口狂变 | 多 profile、日志、最小闭环 | 堆完整设置页、谈极致动画 |
| DVT | 形态接近、开始谈功耗和可靠 | 冻协议、恢复路径、回归、功耗档 | 继续让握手字段每周改含义 |
| PVT | 小批量接近出货 | 兼容矩阵、灰度、工厂固件分支 | 只在开发者手机上验证 |
| 试产 | 产线 + 真实用户前夜 | 缺陷按 SN/固件切片、能停发布 | 把试产 bug 当个例忽略 |
| 量产 | 规模、版本长期共存 | 分阶段 OTA、监控、回滚 | 假设全员同一固件 |

### Q-F1: 你在这些阶段分别对客户端负责什么？

**60 秒**  
EVT 负责最小可联调闭环和可观测。DVT 负责把恢复、功耗、协议冻结成回归。PVT / 试产负责版本矩阵和缺陷回流。量产负责放量与刹车。我没有以 owner 身份完整走完一条消费电子量产线，但小批量联调已经逼出过协议不兼容和广播字段变更，所以我把「冻结」和「切片」当成客户端责任，而不是硬件部门的内部流程。

**3 分钟机制**  
EVT 用 firmware profile 切换方言，避免 if-else 洒在业务里。DVT 把白板 1/2/4 变成测试用例。PVT 起 TestFlight 分组：内部、试产设备、公开。试产问题必须带 SN、固件、App sha。量产 OTA 看成功率曲线，掉下去先停。

**追问**  
EVT 能不能上 TestFlight 给非工程师？可以，但要标明不稳定、可回厂刷。不要把 EVT 包和 PVT 包用同一个 build 号。

**Trade-off**  
过早冻协议会卡硬件；过晚冻会让 App 和测试集崩溃。DVT 入口是谈判点：进 DVT 就必须有版本号和错误码表。

`[人设案例]` 试产发现同一广播名被产线烧成重复。App 从「按名字绑定」改成 identifier + 产线序列号校验。这是试产教给客户端的课，不是功能需求文档里写出来的。

### Q-F2: 量产交付对 iOS 意味着哪些具体产物？

- 固件兼容矩阵（可发布的组合）
- OTA 包签名与最低 App 版本
- 关键链路监控：连接、同步、OTA
- 发布刹车：谁能停、停了用户看到什么
- 已知失败路径文档，给客服和固件

没有百万出货经历时，讲小批量灰度 + 能停，不要编出货数字。见缺口话术 4。

## 口播串联：把加分项讲成一条产品链

「可穿戴客户端我按四条链看。功耗链：SLA、连接档、扫描预算。OTA 链：传输、commit、防砖、版本矩阵。同步链：设备 seq、手机 pending、冲突以设备状态为准。数据链：控制和数据分开，先算带宽再谈音频或传感器。这些链在 EVT 可以松，进 DVT 就要冻协议和回归；试产以后看切片指标，能停。C/C++ 和板级总线我用来读包、对字节，不当固件 owner。」

I treat plus items as one wearable loop. Power is an SLA plus radio parameters, not UI polish. OTA is a commit and recover problem.
