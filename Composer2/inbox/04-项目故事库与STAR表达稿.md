# 项目故事库与 STAR 表达稿

状态：inbox 草稿，暂不落库。所有故事均为 `[人设案例]`，项目名和数字可替换成你的真实经历。

## 使用说明

面试里不要讲六个故事。准备六个，上场只用 2 到 3 个，其中一个必须同时覆盖 BLE、联调和交付。

替换时只改：项目名、团队结构、指标、你的具体动作。结构不要散。

## STAR 模板

- S：场景，15 秒。什么产品、什么阶段、约束是什么。
- T：你要负责的结果，不是「我被安排做 BLE」。
- A：3 到 5 个可验证动作，含机制，不含形容词。
- R：一个指标 + 一个沉淀（文档、状态机、门禁、复盘）。

## 故事 1：复杂模块 / 核心架构

`[人设案例]` 可穿戴 App 设备会话层重构。

**面试目的**：证明你能独立负责复杂客户端模块，而不是堆页面。

**S**  
消费级耳机 / 手环 App，扫描、连接、设置页、同步服务各自维护一份 `isConnected`。功能能跑，断连和后台恢复后状态经常撕裂。

**T**  
在不停业务迭代的前提下，把设备会话收成单一状态机，让页面只消费快照。

**A**  
1. 画出合法状态和非法跳转，禁止页面直接调 `connect`。  
2. 外部只发意图：`bind` / `connect` / `disconnect` / `reconcile`。  
3. BLE 回调统一 hop 进会话队列，UI 只拿不可变 snapshot。  
4. 给非法迁移打断言和日志，方便联调。

**R**  
连接相关崩溃 / 断言从每周数次降到接近 0（可替换）。新功能接入从「改四处」变成「注册一个命令处理器」。

**90 秒讲法**  
「我负责把设备连接从散落逻辑收成会话层。以前每个页面自己改连接状态，后台一恢复就错。我做了单一状态机和意图入口，页面只渲染快照。结果是连接问题可归因，后续 OTA 和同步都挂在同一层上。」

## 故事 2：BLE / 设备通信

`[人设案例]` 绑定设备异常断连与误连。

**面试目的**：证明 Core Bluetooth 是做过的，不是背过的。

**S**  
试产阶段用户反馈「明明连着，按键没反应」和「连到别人的设备」。

**T**  
把扫描过滤、重连预算和 Ready 定义做对，让连接成功率可测。

**A**  
1. 未绑定用 manufacturer data + 接近阈值；已绑定走 identifier，不再靠名字。  
2. `didConnect` 只是 Connecting，Ready 必须发现服务、打开 notify、握手成功。  
3. 异常断连分类：用户 / 系统 / 链路，链路才走有限退避。  
4. 连接成功率按固件版本和 iOS 版本切片。

**R**  
误连投诉清零（可替换）。某固件版本握手超时被切出来，固件修完后该版本连接成功率回升到 99% 量级（可替换）。

**必须体现**  
过滤、Ready 定义、断连分类、指标切片。

## 故事 3：联调排障

`[人设案例]` 按钮无响应，跨 App / 固件对线。

**面试目的**：证明你不会甩锅，能建共同证据。

**S**  
深圳固件和客户端都说「我这边是对的」。现象间歇出现，只在 OTA 失败后的设备上。

**T**  
在 48 小时内定位层级，并补上以后能自助排查的观测点。

**A**  
1. 按 App -> 队列 -> BLE -> 协议 -> 固件拆日志点。  
2. 对齐 SN、build、固件版本、时间戳。  
3. 发现 App 显示已连接，固件卡在非法 OTA 模式，命令被丢。  
4. 和固件约定非法模式必须重新广播错误码；App 识别后引导恢复，而不是继续写特征。

**R**  
该问题从「会议争议」变成 10 分钟可复现。后续同类问题先看设备模式字节，不再先改 UI。

**可用句式**  
「我先不判断是谁的 bug。我要求每一层都有可验证观测点。证据对齐之后，责任自然清楚。」

## 故事 4：性能 / 稳定性优化

`[人设案例]` 冷启动和连接页卡顿。

**面试目的**：证明优化是指标驱动。

**S**  
首页启动时同步初始化蓝牙扫描、日志上报、配置拉取，低端机冷启动超过 3 秒（可替换），连接页掉帧。

**T**  
首屏可交互降到 2 秒内（可替换），同时不牺牲已绑定设备的恢复速度。

**A**  
1. 启动关键路径只留崩溃捕获和首屏渲染。  
2. 蓝牙会话懒启动，首页先展示 stale 状态。  
3. 扫描对象复用，避免每次进页新建 manager。  
4. 用 signpost 看各段耗时，用崩溃率守住回归。

**R**  
冷启动 P50 从约 3.2s 到约 1.6s（可替换）。连接页主线程卡顿下降。启动任务清单写进发布检查。

**必须体现**  
定义指标、拆路径、验证、防回归。

## 故事 5：工程体系建设

`[人设案例]` 从「能出包」到「周更可测」。

**面试目的**：证明 founding 工程师会建秩序。

**S**  
早期两个人出包靠手编，符号表经常丢，线上崩溃看栈看不懂，联调包和正式包混。

**T**  
两周内做到每次提交出可测包，崩溃可符号化，关键链路有冒烟。

**A**  
1. CI 打 TestFlight，build 号绑定 git sha。  
2. 崩溃收集 + dSYM 上传。  
3. 连接 / 握手 / 断连三条冒烟，跑在 PR。  
4. 发布清单：协议版本、固件兼容矩阵、已知失败路径。

**R**  
联调不用问「你这是哪一包」。崩溃从无法处理变成可分类。迭代速度没有变慢，返工变少。

## 故事 6：ownership / 0 到 1 推进

`[人设案例]` 协议未定时先打通最小闭环。

**面试目的**：证明你能在模糊里推进，而不是等完美文档。

**S**  
产品还在改交互，固件协议每周变字段。如果等冻结再写 App，试产窗口会错过。

**T**  
两周内打通：绑定、连接、读一个关键状态、断连恢复。功能字段允许后补。

**A**  
1. 先冻握手、错误码、版本号，功能 TLV 可扩展。  
2. App 用 profile 切换固件方言，而不是写死一版。  
3. 每天和固件 15 分钟对一次包示例，不开会空聊。  
4. 明确告诉产品：这周交付闭环，不交付全部设置项。

**R**  
试产当天能连、能看状态、能抓日志。后续设置项没有推翻会话层。

**面试官关注点**  
你如何做优先级、如何拒绝范围膨胀、如何让跨团队形成节奏。
