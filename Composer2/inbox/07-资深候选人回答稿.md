## 3. 讲一下你理解的 iOS 并发模型

**60 秒**  
核心不是把事情并行跑起来，而是任务边界、切换成本、共享状态由谁改。GCD 是调度，Swift Concurrency 是结构化并发。UI 在 MainActor；连接状态进单一隔离域。取消和错误要收敛，不能让 BLE 回调直接改 UI 状态。

**追问展开**  
历史代码不必一次重写。Core Bluetooth 回调线程不稳定，进状态机前要 hop。`actor` 不能替代所有锁，可重入和 C API 仍要设计。我不会把整个蓝牙栈放主线程。

## 4. ARC 下最常见的内存问题是什么

**60 秒**  
表面是循环引用，本质是所有权不清。Delegate、Timer、通知、长订阅、缓存和单例最容易让连接管理器活过页面。

**追问展开**  
设备产品里常见：Session 持有页面，页面又订阅读连接。页面没了，重连回调还在。先画谁拥有谁，再决定 `weak`。用 memory graph 进页 20 次看对象是否回到基线。

## 5. BLE 连接的完整流程是什么

**60 秒**  
扫描过滤、连接、发现、订阅和握手、稳定通信、异常恢复。这是状态机。`didConnect` 只是 Connecting，不是 Ready。

**追问展开**  
已绑定走 identifier。Ready 等于关键特征可写、notify 已开、握手通过。之后才允许业务命令。发现只做需要的服务，超时失败而不是挂起。详见白板 1。

## 6. BLE 断连后你会怎么设计恢复策略

**60 秒**  
先分类：用户主动、系统蓝牙、链路异常。只有链路异常才有限退避重连。目标是回到可信状态，不是盲目连上。

**追问展开**  
恢复后重新确认发现和订阅，拉 snapshot，再 reconcile，再决定补发。命令带 requestId，ack 未到不当成功。无限重连会耗电、打满日志、掩盖硬件故障。

## 7. App 从后台恢复后，设备状态不一致怎么办

**60 秒**  
不信任内存旧状态。按白板 4 重建：系统蓝牙、连接、订阅、快照、对账，再更新 UI。

**追问展开**  
`[人设案例]` 后台回来 UI 还显示某模式开着，设备已经关了。本地 cache 只能标 stale。过期命令丢弃。全量快照会多一次往返，换状态可信。

## 8. 你如何设计一个 OTA 升级流程

**60 秒**  
高风险链路。检查条件、校验包、分片传输、重启、再连、确认版本。失败路径和防砖是设计本身。

**追问展开**  
未提交新镜像前旧镜像可启动。传输可断点。重启后连不上要有恢复窗口。包要签名和型号匹配，防降级。每个阶段打点。我没有完整带过百万量产 OTA 的话，会明确边界：做过校验、分片、失败重试和升级后握手，回滚策略要和固件一起冻。

## 9. 你如何做启动优化和稳定性治理

**60 秒**  
数据驱动。启动拆冷启动和首屏可交互；稳定性看崩溃率、连接成功率、同步成功率。有闭环才叫治理。

**追问展开**  
启动不做扫描、上报、拉配置。已绑定设备可以发起连接，但不阻塞首页。稳定性按固件版本切片，而不是只看大盘。日志要结构化，debug 包再拉满。

## 10. 软硬件联调时，如何定位问题属于哪一层

**60 秒**  
按 App、队列、BLE、协议、固件、云拆观测点。没有共同证据不谈责任。

**追问展开**  
`[人设案例]` 按钮无响应，App 显示已连接，固件卡在非法 OTA 模式。对齐 SN、版本、时间戳后，问题从「写入失败」变成「设备模式非法」。后来错误码打到广播里，App 引导恢复。

## 11. 作为 founding iOS engineer，你会优先建设什么

**60 秒**  
先秩序，不先平台。模块边界、日志和符号化、关键链路冒烟、能周更的 CI。基础设施为交付服务。

**追问展开**  
两三人阶段用清晰边界就够，不必先上完整包管理。第一周能看懂崩溃，第二周能出可测包，第三周有发布清单和固件兼容矩阵。

## 13. 为什么你适合创业型团队

我适合的原因不是更能加班，而是能在没有标准答案时先定义最小闭环。先抓住连接、恢复、日志这些决定能不能联调的事，再把临时解法收成状态机和门禁。Founding 要的是推进加秩序，不是等完美再动手。

## 15. English: Tell me about a challenging technical problem

One challenging problem was a state mismatch after a failed OTA. The app showed connected, but taps did nothing. It was intermittent and crossed teams, so people argued from memory. I split the flow into observable stages and aligned logs and versions. The device was stuck in an illegal mode and dropping commands. We fixed the firmware error code and the client recovery path, and we kept the observation points. The win was the debugging process, not just the patch.
