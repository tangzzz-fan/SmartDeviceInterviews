## 白板 1：BLE 连接 / 恢复状态机

```
Idle
  -> Scanning（按 UUID / manufacturer data / 已绑定 ID 过滤）
  -> Connecting
  -> Discovering（service / characteristic）
  -> Ready（notify + 握手 + 首包校验）
  -> Streaming / Commanding
  -> Disconnected

Disconnected 分类：
  用户主动 -> Idle，不自动重连
  蓝牙关闭 / 权限 -> WaitSystem，提示用户
  链路异常 -> Reconnecting（有限次数 + 指数退避）
  恢复成功 -> 不一定直接 Streaming，先 Reconciliation
```

要点：Ready 不等于可信。重连后必须重新发现或确认订阅，再拉关键状态，再决定是否补发命令。

---

## 白板 2：OTA 链路

```
Check(型号 / 电量 / 版本 / 是否充电)
  -> Download + Verify(hash / 签名)
  -> EnterOTA
  -> Transfer(分片 + seq + ack + 窗口)
  -> Validate on device
  -> Reboot
  -> Reconnect + Version confirm + Smoke
  -> Success

失败路径：
  下载失败 -> 不进升级模式
  校验失败 -> 丢包，保留旧固件
  传输中断 -> 断点或从头，设备保持可连
  重启后连不上 -> 超时窗口 + 恢复模式（和固件约定）
  版本不匹配 -> 拒绝启动新功能，上报
```

OTA 是高风险链路。没有失败路径和可观测性，等于没有设计。

---

## 白板 3：联调分层归因

```
现象：点击后设备无响应

L1 App UI / ViewModel     命令有没有发出？参数对不对？
L2 连接与队列             当前是 Ready 吗？命令有没有入队？
L3 BLE 传输               write 成功？notify 回来了吗？
L4 协议                   seq / opcode / crc / 版本对吗？
L5 固件                   收到了吗？执行了吗？状态机在哪？
L6 云 / 账号（如有）      是否还依赖服务端授权？

每个 L 必须有：日志点、时间戳、版本号。
```

先建共同证据，再谈责任。

---

## 白板 4：前后台状态重建

```
WillEnterForeground
  1. 不信任内存里的 connectionState
  2. 读 CBManager.state
  3. 对已绑定外设 retrieve / connect
  4. 确认 service 与 notify
  5. Snapshot：设备模式、电量、固件版本、待同步队列
  6. Reconcile：本地预期 vs 设备实际
  7. 再恢复 UI 与待发命令
```

后台恢复是一次小型重连，不是「把页面重新显示出来」。

## 模块 1：Swift 并发与线程模型

### Q1: Swift Concurrency 和 GCD 的关系是什么？

**60 秒结论**  
GCD 是调度原语，Swift Concurrency 是语言级结构化并发。生产代码里两者会共存，关键不是站队，而是谁拥有状态、谁能改状态、取消和错误怎么收敛。

**3 分钟机制**  
`async/await` 把异步写成线性控制流。`Task` / `TaskGroup` 提供结构化生命周期。`actor` 隔离可变状态。UI 更新走 `MainActor`。历史模块如果已经是 callback + 串行队列，不必为了新而新，可以在边界用 continuation 包一层。BLE 回调线程不稳定，进入自己的状态机前要明确 hop。

**追问**  
`actor` 能不能完全替代锁？不能。跨 actor 可重入、同步 IO、以及需要和 C API 共享内存时，仍要额外设计。

**Trade-off**  
全面 Swift Concurrency 可读性更好，但和 Core Bluetooth 回调、第三方 SDK 混用时，错误的 hop 会造成「偶发 UI 更新不在主线程」和状态撕裂。渐进迁移比一次重写更适合 founding 节奏。

### Q2: 你如何避免并发下的数据竞争？

**60 秒结论**  
先消灭共享可变状态。必须共享时，把连接状态、同步队列收到单一所有者（actor 或串行状态机），禁止多个模块各自改同一份 state。

**3 分钟机制**  
`[人设案例]` 可穿戴 App 里，扫描、连接、页面、同步服务都曾直接改 `isConnected`。表现是 UI 显示已连接，写入却失败。后来把设备会话收成 `DeviceSession` 单一状态机，外部只发意图，状态只能由状态机迁移。可替换指标：连接相关崩溃 / 断言从每周数次降到接近 0。

**追问**  
MainActor 上放整个蓝牙栈？不。蓝牙 I/O 不要堵主线程；主线程只拿不可变快照渲染。

**Trade-off**  
集中状态机会增加一次间接层，换来可测试和可归因。Founding 早期这层值得付。

## 模块 2：内存管理

### Q3: ARC 下最常见的内存问题是什么？

**60 秒结论**  
表面是循环引用，本质是所有权没设计清楚。Delegate、Timer、通知、长时间订阅、缓存和单例最容易把对象活过页面。

**3 分钟机制**  
设备型产品里，`ConnectionManager` 持有页面，页面又订阅连接状态，前后台切换后管理器还在重连，页面已经销毁，就会出现幽灵回调或泄漏。先画谁拥有谁：Session 拥有连接，页面只拿弱代理或异步流。`unowned` 只在生命周期确定短于被持有对象时用。

**追问**  
如何证明修掉了？Instruments + memory graph + 进页 20 次后对象数量应回到基线。

**Trade-off**  
全部 `weak` 会掩盖所有权错误，该由父对象强持有的子对象被弱化后会提前释放，表现为更难复现的空回调。

### Q4: 你如何定位内存问题？

**60 秒结论**  
先分类：泄漏、峰值过高、还是抖动。再用工具和场景化复现，而不是先改代码。

**3 分钟机制**  
泄漏：重复进出连接页。峰值：OTA 分包或日志暴涨。抖动：频繁创建扫描对象。结合页面生命周期、设备连接切换、后台前台切换做场景。设备日志里打对象 identifer，避免只看 Allocations 曲线猜。

**追问**  
缓存无上限怎么处理？按会话级缓存，断连或登出必须可丢；不能按进程生命期无限涨。

**Trade-off**  
过早做对象池对 founding 不划算；先修生命周期和缓存边界。

## 模块 3：生命周期与后台任务

### Q5: iOS 后台任务有哪些约束？

**60 秒结论**  
后台不是无限运行。必须按场景选系统允许的模式：蓝牙 Central 状态恢复、后台处理、推送唤醒。把「我想一直连着」当成产品愿望，把「系统允许什么」当成约束。

**3 分钟机制**  
可穿戴常用：`bluetooth-central`、State Restoration、必要时 Background Processing。扫描在后台会被节流。连接参数、通知频率直接影响功耗和被系统杀的概率。不要用长时间后台任务冒充长连接。

**追问**  
State Restoration 能恢复到 Ready 吗？通常只能恢复 manager 和外设对象，订阅和业务握手要自己重做。

**Trade-off**  
打开更多后台模式能提高在线性，但审核、耗电、用户感知都会变差。只开产品真正需要的能力。

### Q6: App 从后台恢复后，设备状态不一致怎么办？

**60 秒结论**  
不信任内存旧状态。走白板 4：系统蓝牙 -> 连接 -> 订阅 -> snapshot -> reconcile -> 再展示。

**3 分钟机制**  
`[人设案例]` 后台回来后 UI 仍显示降噪开，设备实际已关。根因是页面读了本地 cache，连接其实已断。修复：前台恢复先拉设备真实模式再渲染；本地 cache 只做占位并标 stale。可替换指标：相关客诉 / 错误状态展示下降。

**追问**  
待发命令怎么办？先 reconcile，再按幂等补发；过期命令丢弃并提示用户。

**Trade-off**  
每次前台都做全量快照会增加一次往返，换来状态可信。可对关键字段做短 TTL，而不是每次全量 dump。

## 模块 4：Core Bluetooth / BLE

### Q7: BLE 连接的完整流程是什么？

**60 秒结论**  
扫描过滤 -> 连接 -> 发现 -> 订阅与握手 -> 稳定通信 -> 异常恢复。这是状态机，不是一串 callback。

**3 分钟机制**  
见白板 1。扫描要按已绑定 ID / service UUID / manufacturer data 过滤，避免连错设备。连接成功后必须发现服务。Ready 的定义是：关键 characteristic 可写、notify 已开、握手通过。之后才允许业务命令。

**追问**  
为什么不在 `didConnect` 就允许发命令？服务未发现、MTU 未交换、设备还在初始化，这时发命令是随机故障的来源。

**Trade-off**  
发现全部服务更稳，但慢。生产上只发现需要的服务，超时则失败并重试，而不是挂起。

### Q8: 扫描不到设备，你会怎么排查？

**60 秒结论**  
按系统权限 -> 蓝牙状态 -> 广播是否存在 -> 过滤条件 -> 距离/干扰 -> 固件广播间隔，分层排。

**3 分钟机制**  
确认 `CBManager.state`、Info.plist、系统蓝牙权限、精确位置（若需要）。用第三方 BLE scanner 看广播在不在。对比 App 过滤条件是否过严（名字、UUID、manufacturer data 版本变更是高频坑）。再看固件是否在已连接后停广播、是否在低功耗下拉长 interval。

**追问**  
已绑定设备还要扫描吗？优先 `retrievePeripherals` / `retrieveConnectedPeripherals`，扫描当补充。

**Trade-off**  
放宽过滤能提高发现率，误连风险上升。已绑定走 identifier，未绑定才用可解释的广播字段。

### Q9: BLE 断连后，你会怎么设计恢复策略？

**60 秒结论**  
先分类断连，再受控重连。目标不是「重新连上」，而是「重新回到可信状态」。

**3 分钟机制**  
用户主动断开不重连。系统蓝牙关闭就等待。异常断开：有限次数、指数退避、页面仍需要连接才继续。恢复后走发现 / 订阅 / snapshot / reconcile，再处理命令队列。幂等：命令带 seq 或 requestId，ack 未到不当成功。

**追问**  
无限重连为什么不行？耗电、打满日志、和固件侧连接资源打架，还会把真正的硬件故障掩盖成「一直在重试」。

**Trade-off**  
激进重连体验上「比较连得上」，功耗和稳定性更差。给重试预算和用户可见状态。

### Q10: 你如何处理 BLE 数据包和状态同步？

**60 秒结论**  
分包、序号、ack、窗口，和应用层状态机分开。设备状态以设备上报为准，本地是预期，不一致就 reconcile。

**3 分钟机制**  
`[人设案例]` 传感器批量上传曾在通知风暴下丢包。做法：固件侧窗口 + App 侧重组超时；失败只重传缺失 seq。状态同步用版本号，避免后到的旧包覆盖新状态。

**追问**  
Write Without Response 什么时候用？吞吐优先且能接受丢失的数据面；控制面用带响应或 notify ack。

**Trade-off**  
强确认更可靠，吞吐下降、功耗上升。控制命令走可靠通道，日志/波形走尽力而为加校验。

## 模块 5：OTA

### Q11: 你如何设计一个 OTA 升级流程？

**60 秒结论**  
按白板 2。先条件检查和包校验，再传输，再重启验证。失败路径和防砖策略是设计的一部分。

**3 分钟机制**  
`[人设案例]` 试产时出现升级到 80% 掉电。和固件约定：未提交新镜像前保持旧镜像可启动；传输可断点；超时退出 OTA 模式并重新广播。App 侧每个阶段打点：check / transfer / reboot / confirm。可替换指标：OTA 成功率从约 92% 提到 99%+（可替换）。

**追问**  
如何防降级和刷错型号？包里带 hardware revision 和最小版本，签名校验失败直接拒绝。

**Trade-off**  
双分区最安全，Flash 和固件成本更高。早期可用「旧镜像保留 + 恢复模式」，但必须和硬件约定进恢复的按键或超时。

没做过完整量产 OTA 时，改用 `02` 缺口话术 1。

## 模块 6：性能与稳定性

### Q12: 你如何做启动优化？

**60 秒结论**  
先拆冷启动和首屏可交互，再看主线程同步 IO、过早初始化、阻塞锁。非关键初始化后移。

**3 分钟机制**  
启动只做：崩溃捕获、最小依赖注入、首屏渲染、已绑定设备的懒连接。蓝牙扫描、日志上传、AB 配置不进首屏关键路径。用 signpost 量各段耗时，而不是凭感觉。

**追问**  
预连接设备要不要放启动？可以发起，但不能等 Ready 才进首页。首页先展示 stale，后台 reconcile。

**Trade-off**  
延迟初始化会让首屏后出现二次卡顿。用空闲任务分片，避免一进首页就打满。

### Q13: 你如何做稳定性治理？

**60 秒结论**  
定义指标，分类错误，按专题治理，形成发现-定位-修复-验证闭环。

**3 分钟机制**  
核心指标：崩溃率、关键链路成功率（连接、同步、OTA）、卡顿。错误按 domain 分类：蓝牙、协议、UI、存储。告警看趋势不是单点。`[人设案例]` 连接成功率按固件版本维度看，曾发现某一固件在 iOS 特定版本上握手超时。可替换指标：周崩溃率、连接成功率。

**追问**  
没有数据怎么治理？先补日志和符号表，比先补测试更紧急。

**Trade-off**  
日志太全会耗电、涨包、有隐私风险。对关键链路做结构化日志，debug 包再拉满。

## 模块 7：联调与问题定位

### Q14: 软硬件联调时，如何定位问题属于哪一层？

**60 秒结论**  
按白板 3 把链路拆成可验证观测点。没有共同证据就不谈责任。

**3 分钟机制**  
统一：时间源、设备 SN、固件版本、App build、复现步骤。App 打发送/ack；固件打接收/执行。对不上就先对时钟和日志格式。`[人设案例]` 「按钮无响应」最终是固件在 OTA 失败后卡在错误模式，广播仍在，但命令被丢。App 显示已连接。共同日志把问题从「写入失败」改写成「设备模式非法」。

**追问**  
两边日志都没有怎么办？先加最小观测点，再复现。拒绝在会议里凭感觉对线。

**Trade-off**  
观测点太多会影响时序。先在控制面打，数据面抽样。

### Q15: 你如何和固件工程师高效合作？

**60 秒结论**  
先冻协议和错误码，再冻版本兼容矩阵，再用问题单同步：现象 / 假设 / 证据 / 下一步。

**3 分钟机制**  
协议变更走版本号，不做静默改字段。联调计划按阶段：能扫到、能连上、能握手、能稳定传、能异常恢复、能 OTA。英文同步用短段落，不写长故事。

**追问**  
协议还没定完怎么开工？先定最小握手和错误码，功能字段允许扩展。Founding 不能等完美文档。

**Trade-off**  
文档过重会拖速度；完全口头约定会在跨时区爆炸。一页协议 + 示例包是最小集。

## 模块 8：工程体系

### Q16: 作为 founding iOS engineer，你会优先建设什么？

**60 秒结论**  
先建秩序，不先建平台。优先：模块边界、日志与符号化、关键链路测试、能周更的 CI/CD。

**3 分钟机制**  
第一周：项目结构、设备会话边界、崩溃收集。第二周：连接/同步的冒烟测试、TestFlight 节奏。第三周：基础 lint 和发布清单。基础设施服务于交付，不为看起来完整。

**追问**  
要不要上完整模块化包管理？早期 2-3 人用清晰文件夹 + 边界协议就够。人变多再拆包。

**Trade-off**  
过早平台化会吞掉 0 到 1 速度；完全无秩序两周后联调会崩。只修当下最拖速度的那一层。

## 模块 9：AI-native

### Q17: 你如何把 AI 融入研发流程？

**60 秒结论**  
AI 是生产力层，不是责任人。方案比较、样板、测试用例、日志归纳、英文草稿可以用；协议对错、根因、发布决策自己验。

**3 分钟机制**  
编码：生成样板和边界清单，我跑测试。调试：把日志喂进去列假设，我用观测点否证。文档：先出英文同步草稿，我改证据。`[人设案例]` 模型曾把「没收到 notify」判成权限问题，实际是固件没开 CCCD；因为有分层清单，这个假设第一轮就被否。

**追问**  
如何避免把密钥和用户数据喂给模型？默认剥离 SN 以外的标识、音频、健康明细。

**Trade-off**  
全流程 AI 会快，也会把错误写进协议。关键路径保持人审。

## 模块 10：P2 扩展

### Q18: EVT / DVT / PVT 对客户端意味着什么？

EVT：接口还在变，App 要可切换固件 profile，日志要足够。  
DVT：协议应冻结，开始回归集、功耗和异常恢复。  
PVT：版本兼容、产线/试产缺陷回流、灰度。  
没完整走过就用 `02` 缺口话术 2。

### Q19: 低功耗你关心哪些旋钮？

扫描窗口、连接间隔、通知频率、是否需要长连接、日志采样、定位权限。产品「实时」和电池寿命直接冲突，要和产品一起定 SLA。

### Q20: 离线同步怎么做？

本地队列持久化，带 requestId。上线后按版本号推拉。冲突：设备侧状态赢，或按字段合并。失败可重试，成功必须幂等。
