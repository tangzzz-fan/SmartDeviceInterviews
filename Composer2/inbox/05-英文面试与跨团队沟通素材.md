Three reasons. First, it is not a narrow feature role; it asks someone to own the iOS client. Second, the hard part is the device loop: BLE, recovery, power, OTA, and bring-up with firmware. Third, I work well when the spec is incomplete, as long as we can freeze a small interface and keep moving.

## 3 分钟项目讲述

`[人设案例]`

We had a wearable app where connection state was owned by several screens at once. After backgrounding, the UI could show connected while writes failed. I pulled connection into a single session state machine. Screens could only send intents and render snapshots. Ready was defined as service discovery, notifications, and handshake, not `didConnect`. We also sliced connection success by firmware version and found one firmware that timed out on handshake. After the firmware fix and the client recovery path, connection became diagnosable instead of anecdotal.

If asked for numbers: cold start and crash rate are replaceable; the point is that we defined Ready, measured by firmware version, and stopped arguing from memory.

## 英文技术短答

### Tell me about a challenging technical problem

One difficult case was an intermittent “tap does nothing” bug after a failed OTA. The app still showed connected. We broke the path into observable layers: app queue, BLE write, protocol, firmware mode. Shared logs showed the device was stuck in an illegal OTA mode and dropping commands. We added an error code on advertising and a recovery prompt on iOS. The important part was turning a cross-team argument into a shared evidence trail.

### How do you work with cross-functional teams

I try to freeze the smallest contract first: handshake, error codes, versioning. Then I send short written updates with evidence, not long narratives. If we disagree, we add an observation point before we assign blame.

### How do you use AI in your work

I use it to draft boilerplate, test cases, log summaries, and English updates. I do not let it decide root cause, protocol correctness, or ship / no-ship. I still need to disprove hypotheses against logs.

### How do you handle ambiguity

I separate what must be frozen from what can change. For a wearable, I freeze connection, recovery, and logging first. Feature fields can wait. I also say no to scope that would miss the bring-up window.

## 跨时区书面更新模板

Subject: `[device SN / build / firmware] tap-no-response after failed OTA`

- Problem: After a failed OTA, taps do not move the device. App UI still shows connected.
- Evidence: App write succeeds; no notify; firmware log shows mode=`OTA_BAD` at T+12s. Repro: fail OTA at 80%, reboot app, tap once.
- Hypothesis: Device stays in an illegal mode and drops commands; app does not detect mode.
- Next step: Firmware advertises error code; iOS shows recover CTA; I will send a build tomorrow 18:00 PT.
- Ask: Need a 15-min overlap to confirm the recover advertisement payload.

短会议口播：

We are not debating ownership yet. The evidence says the write leaves the phone and the device drops it in `OTA_BAD`. I need the error code on advertisement, then I can ship the recover path.
