# 题库与答案 · iOS 核心（P0）

> 用法：P0 题可脱稿复述；每题答案控制在 1.5–2 分钟。答题走五层：结论 → 机制 → 案例 → 取舍 → 指标。
> 案例中的数字为示范值，必须替换为自己的真实数据。

## A1. Swift 并发：async/await 相比 GCD 解决了什么？actor 解决什么？

**答案**：

GCD 的问题是异步逻辑被拆散成回调闭包嵌套，错误处理和取消都很难做，线程安全完全靠程序员自觉（锁、串行队列）。async/await 把异步代码线性化，让编译器参与生命周期管理，配合结构化并发（TaskGroup、withTaskGroup）能清晰表达父子任务和取消传播。

actor 解决的是「共享可变状态」的并发安全：编译器保证对 actor 内部状态的访问串行化，把数据竞争从运行时问题变成编译期问题。比如 BLE 管理器维护连接状态、待确认包队列，多线程回调同时写就会竞争，用 `actor BleManager` 或 `@MainActor` 把所有状态操作串到一个执行域，就不需要手工加锁。

**追问应对**：
- `Task.detached` 不继承外层上下文；`Sendable` 是跨并发域传值的编译期约束；`@unchecked Sendable` 表示自己负责安全性。
- actor 能不能完全替代锁？不能。跨 actor 可重入、同步 IO、需要和 C API 共享内存时，仍要额外设计。

**取舍**：全面 Swift Concurrency 可读性更好，但和 Core Bluetooth 回调、第三方 SDK 混用时，错误的 hop 会造成「偶发 UI 更新不在主线程」和状态撕裂。渐进迁移比一次重写更适合 founding 节奏。BLE 回调线程不稳定，进入自己的状态机前要明确 hop。

## A2. ARC 原理与循环引用，怎么定位？

**答案**：

ARC 在编译期插入 retain/release，对象强引用计数归零时释放，确定性、无全局暂停，和 GC 不同。循环引用最常见的三类：delegate 被强持有（应 weak）、block 捕获 self（用 `[weak self]`）、Timer/DisplayLink 强持有 target 且 target 又持有 timer。

表面是循环引用，本质是所有权没设计清楚。设备型产品里常见：`ConnectionManager` 持有页面，页面又订阅连接状态，前后台切换后管理器还在重连，页面已经销毁，就会出现幽灵回调或泄漏。先画谁拥有谁：Session 拥有连接，页面只拿弱代理或异步流。

定位用两步：先复现，再用 Xcode Memory Graph 看对象间的引用环，能直接看到「谁持有谁」；Leaks 模板负责找泄漏对象；Allocations 看内存持续增长判断隐性泄漏。验证释放写 deinit 打印。

**追问应对**：
- `unowned` 在对象提前释放时会野指针崩溃，除非能保证生命周期更长，否则优先 weak。
- 如何证明修掉了？Instruments + Memory Graph，进页 20 次后对象数量应回到基线。

**取舍**：全部 `weak` 会掩盖所有权错误，该由父对象强持有的子对象被弱化后会提前释放，表现为更难复现的空回调。

## A3. App 从启动到首帧经历了什么？如何优化启动？

**答案**：

链路分两段：pre-main 和 main 之后。pre-main 包括 dyld 加载动态库、rebase/bind 修正、执行 +load 和 C++ 构造器；main 之后是 didFinishLaunching、首屏 UI 构建到首帧渲染。

优化手段按收益排序：pre-main 减少动态库数量（能静态就静态）、去掉 +load（改用 +initialize/懒加载）、减少 ObjC 元数据；main 之后把启动任务分级——首帧必需的任务留在同步路径，非关键的（埋点 SDK、推送注册、日志）全部异步化/延迟化，主线程避免 I/O 和大型解码。

可穿戴 App 特有：启动只做崩溃捕获、最小依赖注入、首屏渲染、已绑定设备的懒连接；蓝牙扫描、日志上传、AB 配置不进首屏关键路径。已绑定设备可以发起连接，但不能等 Ready 才进首页——首页先展示 stale 状态，后台 reconcile。

指标要埋：pre-main 时长、didFinishLaunching 到首帧；真机 release 基线，CI 上做回归监控。示范数字：pre-main 450ms→180ms（减库+去 +load），冷启 2.8s→1.2s。

**追问应对**：首帧后仍有可感知白屏，要考虑首屏数据预取与骨架屏；延迟初始化会让首屏后出现二次卡顿，用空闲任务分片避免一进首页就打满。

## A4. 网络层怎么设计？

**答案**：

分层：APIClient（URLSession 封装）→ 路由/请求模型 → Codable 编解码 → 错误处理与重试 → 缓存 → 业务仓库（Repository）向上提供数据。每层职责单一，方便替换和测试。

关键设计：重试用指数退避加抖动（1s/2s/4s 封顶 3 次），只重试幂等请求，5xx 和网络错误区分处理；超时分请求超时和资源超时；GET 走缓存（ETag/版本号），写操作进离线队列；NWPathMonitor 监听网络恢复后重放队列，写请求带幂等键防止重复提交。

并发细节：token 过期刷新要做互斥，只允许一个刷新请求，其余等待；请求与页面生命周期绑定，离开页面取消，避免回调操作已释放对象。

**追问应对**：大文件下载用 background session + 断点续传，与普通请求分开管理。

## A5. 存储怎么选型？

**答案**：

按数据形态选：结构化关系数据用 Core Data/SwiftData（模型迁移、关系）；查询复杂或库大用 SQLite（工程上常用 GRDB）；可穿戴健康数据这种时序数据，倾向 GRDB 按天分表 + 增量同步 + 定期清理，时间戳对齐方便对账；固件包、音频这类大文件走文件系统 + 下载管理 + 校验，不塞数据库；敏感信息进 Keychain；轻量配置用 UserDefaults。

缓存分级：NSCache 内存 + 磁盘缓存（图片走 ImageIO downsampling）。

**追问应对**：Core Data 并发注意 context 类型（viewContext/backgroundContext perform）；模型升级做轻量迁移；SwiftData 适合新项目但生态还在成熟。

## A6. 后台任务与数据同步怎么做？

**答案**：

现代方案是 BGTaskScheduler：BGAppRefreshTask 给一个较短窗口（约 15 分钟级别，由系统按使用习惯调度），BGProcessingTask 适合更重的批处理。注册在 didFinishLaunching，handleExpiration 里必须收尾。

它不能被当作定时器用，也不要拿它当 BLE 保活手段。可穿戴 App 的可靠同步触发点是 push：收到通知再拉增量。数据同步只做增量对账和关键数据补传，绝不全量。App 被杀后没同步完的数据，靠下次启动补偿 + 服务端对账兜底。

可穿戴真正可用的后台能力：`bluetooth-central` 后台模式维持已建立连接的收发、State Restoration 让系统代管连接并在事件到达时唤醒 App。把「我想一直连着」当产品愿望，把「系统允许什么」当约束。

**追问应对**：performFetch 已废弃；后台时间窗内做不完的任务要断点续传，记录进度而不是重来；用户从多任务划掉 App 后系统不会拉起，产品上要在前台把数据尽量同步完。

## A7. App 从后台恢复后，设备状态不一致怎么办？

**答案**：

不信任内存旧状态。后台恢复是一次小型重连，不是「把页面重新显示出来」。流程：

1. 读 `CBManager.state`，不信任内存里的 connectionState；
2. 对已绑定外设 retrieve / connect；
3. 确认 service 与 notify 订阅；
4. Snapshot：拉设备模式、电量、固件版本、待同步队列；
5. Reconcile：本地预期 vs 设备实际；
6. 再恢复 UI 与待发命令。

本地 cache 只做占位并标 stale；过期命令丢弃并提示用户；待发命令先 reconcile 再按幂等补发。

示范案例：后台回来后 UI 仍显示降噪开，设备实际已关。根因是页面读了本地 cache，连接其实已断。修复：前台恢复先拉设备真实模式再渲染，相关错误状态展示客诉清零。

**取舍**：每次前台都做全量快照会增加一次往返，换来状态可信。可对关键字段做短 TTL，而不是每次全量 dump。

## A8. 讲讲你的架构演进经验。

**答案**：

经历过 MVC 到 MVVM 的演进：业务膨胀后 ViewController 巨型化，先引入 ViewModel 让逻辑可测，再用 Coordinator 收敛导航。之后按 feature 拆模块（SPM），core 层（网络/存储/设计系统）下沉，依赖方向保持单向，避免模块环。

依赖注入用构造器注入优先，容器按需引入，不用 Service Locator 滥用。对状态复杂的地方（比如设备连接状态机 + 数据流），评估过单向数据流（TCA 思想），但初创项目以简单可维护为先，只在真正需要的地方引入。

**追问应对**：模块化的代价是启动和包体积，收益是编译速度和边界清晰；循环依赖用协议下沉到 core 层破解。

## A9. 怎么把崩溃率做到 99.9%+？

**答案**：

四个环：收集、分析、预防、灰度。收集用 Crashlytics/Sentry + dSYM 符号化，并关联用户操作路径日志；分析做崩溃聚类，按版本/机型/系统过滤，定位回归 commit；预防是自动化测试（单元/UI/冒烟）+ 静态分析 + OOM 单独统计 + 卡顿监控（主线程 ping），因为 OOM 不算 crash 但体验更差；灰度分阶段发布（5%→20%→100%），异常即停，远程开关做功能级热修通道。

设备类产品额外一招：指标按固件版本维度切片——曾靠这个发现某一固件在 iOS 特定版本上握手超时。

指标定义要清楚：crash-free sessions、OOM 率、卡顿率，各自设 SLA 和负责人。把「崩溃率」从结果指标变成「每个环都有可执行动作」的过程指标。

**追问应对**：线上崩溃复现不了就加强现场采集（设备状态、内存水位、最近操作），再按版本灰度二分；没有数据怎么治理？先补日志和符号表，比先补测试更紧急。

## A10. 主线程卡顿怎么排查？

**答案**：

先用监控确认：RunLoop 观察（BeforeSources 与 AfterWaiting 间隔超过 50ms 记为卡顿）或子线程 ping 主线程，收集堆栈。定位用 Instruments Time Profiler 看主线程热点，配合 os_signpost 在关键阶段打点看耗时分布。

常见原因：主线程 I/O、大图解码（应 ImageIO downsampling）、复杂 Auto Layout、锁竞争/等待子线程结果、高频日志和字符串拼接。治理方向就是把这些移出主线程或预计算。

量化很重要：卡顿率从 x% 降到 y%，单次最长卡顿从多少降到多少，否则面试官会认为你在背方案。

**追问应对**：FPS 和卡顿不完全等价；SwiftUI 的排查要用 Instruments 的 SwiftUI 模板看 body 计算。

## A11. Sendable 是什么？值语义和并发有什么关系？

**答案**：

Sendable 是编译器层面的并发安全检查：标了 Sendable 的类型可以安全地跨并发域传递。struct 在成员都 Sendable 时可自动满足；引用类型通常要不可变或 @unchecked Sendable。它把「并发安全」从运行时锁提升到编译期，比如 Task 闭包捕获、actor 方法参数都会检查。

值语义天然隔离：struct 传递即副本，但 COW（Array/String）共享底层缓冲，写时复制，所以多线程只读安全、写会触发复制。需要共享可变状态时，交给 actor 或锁保护的容器，而不是裸的 @unchecked Sendable。

**追问应对**：全局常量之所以安全是因为不可变；`@MainActor` 是把执行域约束到主线程，和 Sendable 解决的是两类问题。不要把整个蓝牙栈放主线程——蓝牙 I/O 不要堵主线程，主线程只拿不可变快照渲染。

## A12. 你如何避免并发下的数据竞争？（设备场景深挖）

**答案**：

先消灭共享可变状态。必须共享时，把连接状态、同步队列收到单一所有者（actor 或串行状态机），禁止多个模块各自改同一份 state。

示范案例：可穿戴 App 里，扫描、连接、页面、同步服务都曾直接改 `isConnected`，表现是 UI 显示已连接，写入却失败。后来把设备会话收成 `DeviceSession` 单一状态机，外部只发意图（bind/connect/disconnect/reconcile），状态只能由状态机迁移，BLE 回调统一 hop 进会话队列，UI 只拿不可变 snapshot。连接相关崩溃/断言从每周数次降到接近 0。

**取舍**：集中状态机会增加一次间接层，换来可测试和可归因。Founding 早期这层值得付。
