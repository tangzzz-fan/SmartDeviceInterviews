## C1. 怎么定义 App 与设备的通信协议？

**答案**：

在 GATT 之上做分层二进制帧协议：GATT characteristic 只当字节流管道，帧层负责组包/校验/请求响应匹配，命令层负责业务语义。三层解耦后换传输介质（以后加 Wi-Fi）业务层不用动。

- **GATT 层**：两个数据特征（write + notify）加一个控制特征（查版本/查缓冲余量）。不要「一个业务一个特征值」——特征值多了服务发现慢、固件维护成本高，业务扩展靠命令字不靠加特征值。
- **帧格式**：`SOF(2B) | 版本+标志(1B) | seq(1B) | cmd(2B) | length(2B) | payload | CRC16(2B)`。大小端统一小端与 MCU 一致；首字节带版本位供新旧端互相识别；保留位留扩展。
- **粘包/拆包**：BLE notify 按 MTU 切片，一次回调可能半帧也可能两帧，接收侧必须维护字节缓冲 + 状态机：扫 SOF → 读 length → 攒满校验 → 通过才上交命令层。GATT 不提供消息边界，这是协议层必须自己做的。
- **请求/响应**：请求带 seq，响应回带同一 seq，App 用 seq 挂起 continuation 设超时（1–3s），超时重发、重试 2 次后上报。所有命令设计成幂等，因为重发不可避免。
- **大数据块**：payload 超单帧上限时拆 chunk 带 offset，帧层只保单帧可靠，块级重组和断点由上层子协议处理。
- **协议治理**：一份机器可读定义（如 YAML）描述所有 cmd 和字段，代码生成 Swift 和 C 两端编解码，杜绝手抄不一致；协议变更走版本号 + PR 双端 review，不做静默改字段。

**取舍**：帧头 + CRC 约 10% 带宽开销，默认全帧校验可靠性优先。早期不追求协议完美，留好版本字段和未知命令容错（收到不认识的 cmd 回 NAK 而不是断连）——演进能力比初始设计完美更重要。

## C2. 联调出问题，怎么定位是 App 还是固件的锅？

**答案**：

按白板 3 把链路拆成可验证观测点，**没有共同证据就不谈责任**：

```
L1 App UI / ViewModel     命令有没有发出？参数对不对？
L2 连接与队列             当前是 Ready 吗？命令有没有入队？
L3 BLE 传输               write 成功？notify 回来了吗？
L4 协议                   seq / opcode / crc / 版本对吗？
L5 固件                   收到了吗？执行了吗？状态机在哪？
L6 云 / 账号（如有）      是否还依赖服务端授权？
每个 L 必须有：日志点、时间戳、版本号。
```

分层隔离四步：① nRF Connect 直接对设备发包读特征，验证固件行为是否符合协议；② 桩设备/模拟器验证 App 侧解析与逻辑；③ BLE sniffer 抓 ATT 层真实收发（PacketLogger/Ellisys/nRF Sniffer）；④ 对齐固件 UART 日志与 App 日志时间线。

先统一五件事：时间源、设备 SN、固件版本、App build、复现步骤。App 打发送/ack，固件打接收/执行，对不上先对时钟和日志格式。

高频低级坑：MTU 分包不一致、CCCD 没订阅、字节序、长度字段错、服务发现缓存、时间戳单位。

**案例**：「按钮无响应」最终定位是固件 OTA 失败后卡在错误模式——广播仍在但命令被丢，App 显示已连接。共同日志把问题从「写入失败」改写成「设备模式非法」。

**追问应对**：两边日志都没有怎么办？先加最小观测点再复现，拒绝在会议里凭感觉对线。

**取舍**：观测点太多影响时序，先在控制面打点，数据面抽样。输出规范：问题归属结论 + 复现步骤 + 证据（抓包/日志）+ 修复后验证。

## C3. 和固件对 bug 归属有分歧怎么办？

**答案**：

原则：**不争论归属，先共同复现；用证据代替立场；事后把判定标准沉淀成测试。**

示范故事（替换为真实经历）：OTA 联调升级到 60% 偶发中断回滚旧版本。固件认为 App 发包太快打爆 buffer，我这边日志显示按 credit 正常流控。处理方式：提议停掉互贴日志的拉扯，改联合复现——同一台设备、逐包时间戳日志 + 固件收包处理耗时 + 空口抓包，并明确表态「证据指向 App 我当天修，指向固件也一样」。四次复现后证据清晰：固件写 flash 期间停止消费 buffer 又不回收 credit，自己卡死自己。

更重要的产出是两个机制：① OTA 链路协议一致性测试用例集，双方 CI 都跑；② 约定「归属争议以联合复现证据为准，不以单方日志为准」。

**边界**：对方拒绝配合就升级到两边 leader 定仲裁方式，不私下耗。即使证据指向对方，表达聚焦「机制问题」而不是「谁的错」——startup 里长期协作关系比赢一次争论值钱。

## C4. 怎么和固件工程师高效合作？协议还没定完怎么开工？

**答案**：

三步走：先冻协议和错误码，再冻版本兼容矩阵，再用问题单同步——问题单一律四段：**现象 / 假设 / 证据 / 下一步**。

联调计划按阶段递进：能扫到 → 能连上 → 能握手 → 能稳定传 → 能异常恢复 → 能 OTA。协议变更走版本号。英文同步用短段落，不写长故事。

协议没定完不能等完美文档（founding 节奏）：先定最小握手和错误码，功能字段允许扩展。

**取舍**：文档过重拖速度；完全口头约定会在跨时区爆炸。一页协议 + 示例包是最小集。

## C5. EVT / DVT / PVT 各阶段 App 侧做什么？

**答案**：

一句话：**EVT 验证「设计能不能跑通」，DVT 验证「能不能达标并量产」，PVT 验证「产线能不能稳定造出来」。** 判断原则：软件能力必须跑在硬件改动窗口关闭之前。

- **EVT（工程验证）**：样机阶段，硬件问题多。App 做 bring-up：调试版协议打通连接/收发/传感器读数；准备 debug 面板（发原始命令、看裸数据）；固件每改一版硬件回归一轮通信。接口还在变，App 要可切换固件 profile，日志要足够。
- **DVT（设计验证）**：设计冻结，做跌落/高低温/续航等可靠性测试。App 的关键词是「收口」：**OTA 必须在 DVT 完成并充分验证**——DVT 后硬件改动窗口关闭，量产只能靠 OTA 修固件；同时做功耗联调（前后台不同连接参数下的整机功耗）、兼容性测试、主流程全量回归。
- **PVT（生产验证）**：小批量试产。App 支持产测：产线工装通过 BLE 自检传感器/射频、出厂测试模式；开箱配对流程稳定性；售后工具（日志回传、远程诊断）必须在此之前就绪。出货版本冻结，缺陷回流。

测试固件 vs 量产固件：同一份代码用构建配置区分 feature，版本号带 build variant 标识，App 读到 variant 决定开放哪些调试能力，防止量产设备误刷测试固件。

**案例**：DVT 阶段做「升级中途断电/断连/切后台」破坏性测试上百轮，逼出 A/B 分区回滚的低电量边界 bug，赶在 PVT 前修掉；PVT 配合定义产测 BLE 指令集，单台检测压到 30 秒内。

**边界**：各公司节点命名有差异，不装懂所有流程细节。硬件延期常见，App 侧要有在模拟器/上一代硬件上先行验证的预案，不被硬件节奏完全卡死。没完整走过用缺口话术 2。

## C6. 软硬联调的测试体系怎么搭？（不能每次真机测）

**答案**：

核心思路：把「硬件依赖」从开发循环里剥出来。

1. **传输层抽象**：通信模块面向 `Transport` 协议编程（send/receive/状态回调），真机实现是 CoreBluetooth，测试实现是内存管道。帧层/命令层单测完全不碰蓝牙，CI 秒级完成。
2. **模拟设备**：Mac 上用 `CBPeripheralManager` 起模拟器 App 按协议实现设备行为，一键注入异常（丢包/乱序/超时/错误 CRC）。
3. **录制回放**：真机原始字节流按时间戳录成用例文件，回放喂给帧层状态机。「只在某台设备上出现」的畸形数据录下来就是永久回归用例，价值高于手写用例。
4. **真机层**：每日冒烟（几台代表机型 + 射频屏蔽箱），里程碑全量回归。
5. **HIL（硬件在环）**：工装 + 脚本驱动端到端场景，适合量产前长稳；没有全自动就做半自动（屏蔽箱 + 脚本控制开关机和信号衰减）。

**边界**：模拟器只能复现你认知内的设备行为——射频干扰、不同手机协议栈差异模拟不出来，真机永远不能省，只是从「每次」变「每天」。

## C7. 固件和 App 发布节奏不同，怎么管版本兼容？

**答案**：

固件是「发出去就收不回来」的资产（永远有用户不升级），铁律是**向后兼容**：新 App 必须兼容所有在售固件，新固件必须继续支持老协议（固件无法强更）。

具体手段：
1. **版本协商**：连接后先交换固件版本 + 协议版本 + 能力位图，只用交集能力；App 维护「固件版本 → 能力表」，调用前查表，不支持就优雅降级；
2. **最低固件版本**：不写死在客户端，服务端下发 `minFirmwareVersion`；低于下限分级处理——能降级的降级，涉及安全的引导升级，极端才强制；
3. **强制 OTA 是核选项**：只有安全漏洞或数据损坏风险才用，强制前先灰度验证 OTA 成功率，提供「稍后提醒」；日常一律「新功能置灰 + 升级解锁」软引导；
4. **服务端 feature flag**：设备能力开关、新协议灰度走服务端配置，出问题分钟级关闭；
5. **兼容包袱管理**：老协议代码集中打标记，按服务端固件版本分布统计决定何时下线老版本支持。

**案例**：新 App 默认启用新数据格式但三成用户固件太老不支持，客诉爆炸。之后上线「协商 + 服务端 min 版本 + 能力表」机制，发布流程加卡点：依赖新固件的功能必须同时提交降级方案 review，此后版本兼容类线上事故归零。

**取舍**：永远有用户拒绝升级固件，「最低版本」只能逼近不能等于最新——产品设计要为最老固件永远留一条能用的路。

## C8. 设备日志怎么采集？用户现场出问题怎么拿第一手信息？

**答案**：

原则：「平时低功耗地记，出事拿得到」。

- **设备端环形日志区**：flash 上划环形区，分级记录（error 必记，warn/info 按策略），记满覆盖最旧。统一时间戳（设备时钟 + 与 App 同步后的墙钟映射），记连接事件、断连原因、传感器异常、OTA 进度、看门狗复位原因。写 flash 耗电，正常态只记关键事件。
- **回传通道**：App 触发「日志上传」，设备 BLE 分块回传（压缩 + 断点续传）；也可自动触发：设备严重错误打标志，下次连接 App 主动拉。
- **App 端**：结构化日志（事件名 + 关键字段）滚动保留 N 天；BLE 层记状态迁移和关键命令收发。
- **一键反馈**：反馈入口点一下，自动拉设备日志 + 打包 App 日志 + 附型号/固件/App 版本直传工单系统。售后定位「连不上」从邮件来回几天降到半天级。
- **隐私**：采集必须有用户明确触发或授权，不带传感器原始隐私数据。

**追问应对**：设备时间不准两端日志拼不起来——必须做时间同步协议且记录「上次同步时刻」。环形区几百 KB 到几 MB，「记什么」按事件价值严格筛选，别幻想全量记录。

## C9. 嵌入式基础了解多少？怎么协作？

**答案**：

边界要说清楚：**不是会写固件，而是联调时能听懂对方在说什么、能从固件视角推断问题。** 让我写驱动不行，让我对着固件代码定位协议层 bug 没问题。

联调真正用到的概念：
- **中断**：中断上下文不能做耗时操作；固件说「这个要放任务里」意味着延迟和时序影响；
- **RTOS 任务**：「设备偶发不响应」常是低优先级任务饿死或队列满，App 侧表现为超时但抓包看不出异常，必须看固件日志；
- **看门狗**：固件「崩溃」往往只是一次看门狗复位，没有 crash stack，现场靠复位原因寄存器 + 日志残留还原——所以固件日志回传能力格外重要；
- **其他**：flash 页擦除特性（影响 OTA）、低功耗模式与唤醒源（影响连接参数）、ADC 采样与滤波（影响数据可信度）。

知道 MCU 与 BLE SoC（nRF52/53、STM32WB）、UART/SPI/I2C、BLE 协议栈（Zephyr/SoftDevice）。

**案例**：设备收大量数据时偶发重启，抓包 App 侧正常。直接读固件代码，发现收包在低优先级任务、写 flash 在高优先级任务，高峰期队列积压触发越界被看门狗救回——画出时序图和固件对齐，很快确认修复。读代码 + 懂调度模型，比互相贴日志快得多。

**边界**：补学习路径是「问题驱动」——每次联调遇到不懂的概念当场问到懂，配合读代码巩固。这个岗位需要的是协作共同语言，不是第二专业。寄存器级调试、PCB 信号完整性不懂就明说并请教。

## C10. 系统验证怎么做？「设备连不上」怎么系统性解决？

**答案（系统验证）**：

回答「组合起来可靠吗」，单端测试答不了。三件套 + 验收门槛：
1. **端到端场景用例**：按用户旅程设计（开箱配对 → 日常同步 → 断连恢复 → OTA → 换手机重绑），重点覆盖跨端状态组合：低电量 OTA、同步中断连、后台被杀时设备来数据；
2. **长稳测试**：7×24 混合场景脚本 + 屏蔽箱模拟射频衰减，量产前跑满一到两周。曾暴露「72 小时后连接参数漂移导致功耗翻倍」——单端测试永远测不出来；
3. **矩阵裁剪**：机型 × iOS 版本 × 固件版本笛卡尔积不现实——iOS 取主流三档 + 最低支持版，机型按蓝牙芯片代际取样，固件取当前 + 前一版，pairwise 压缩 + 历史客诉机型重点覆盖。
4. **定量 gate**：如首连成功率 ≥ 98%、同步成功率 ≥ 99.5%、OTA ≥ 99%、崩溃率 < 0.1%、长稳无变砖——App/固件/QA 立项时共同定，避免临门扯皮。

**答案（连不上漏斗）**：

「连不上」是第一大客诉，但是症状集合。解法：
1. **漏斗埋点**：扫描发现 → 发起连接 → 连接成功 → 服务发现 → 绑定完成，每步上报成功率（带机型/系统/固件/错误码），「连不上」立刻变成「卡在哪一步」；
2. **归因三分类**：环境（蓝牙未开/权限/没电/超距，占比最高，靠引导）、固件（广播停止/参数异常，靠设备日志和抓包）、App（状态机 bug，靠 App 日志）；
3. **App 内自检**：「连接诊断」逐项检查并给人话指引，大部分环境类问题用户自助解决；
4. **疑难单闭环**：一键回传双端日志，定位后归修复队列，新失败模式补回埋点分类。

示范数字：连接类客诉占比 40% → 15% 以下，首连成功率 92% → 98%+。要承认一部分连接问题永远归因不清，做好降级体验（清晰指引 + 人工兜底）。
