# 题库与答案 · 行为、动机与 AI-native（P0）

> 用法：行为题一律 STAR + 量化结果，每个故事配一句英文摘要。示范故事必须替换为真实经历。
> 完整 STAR 稿件见 [../06_STAR故事库.md](../06_STAR故事库.md)；英文表达见 [../07_英文与跨团队沟通.md](../07_英文与跨团队沟通.md)。
> AI-native 会被深挖真实用法：准备 3+ 案例 + 1 个「AI 出错被我拦下」的反例。

## F1. 为什么加入初创硬件公司做 founding engineer？

**要点**：三条线——对 AI 可穿戴方向的理解（软硬一体 + AI 是差异化）、对 0→1 ownership 的渴望、与硅谷团队协作的成长。避免只说「想冒险」。

**示范骨架**：我在上一家就是从十几人阶段加入的，对「0 到 1 是什么状态」没有幻想，不是被光环吸引。我想找的是能完整定义产品技术形态的位置——在大公司我维护别人定好的架构，影响力有边界。上一份工作我主动拿了可穿戴 App 从 0 到 1：BLE 架构、CI/CD、发布流程都从零搭，最享受的是「我的决策直接决定产品体验」——连接成功率、启动速度就是架构选择的直接反馈。

**诚实补充**：我挑的是「值得做的方向」，不是「创业」这个标签。如果进来发现产品方向没想清楚、只是用速度掩盖混乱，我会先把问题摊开对齐，而不是闷头硬冲。

> English: I'm not romanticizing startups — I joined one before and know how messy 0-to-1 really is; I'm here because I want full ownership over the shape of a product.

## F2. 讲一个在模糊环境中主动推进的事。

**要点**：先定目标与边界（问对问题）→ 出最小可验证方案 → 快速验证 → 透明同步。

**示范骨架**：项目早期固件只给了粗略协议草案，两边互相等，卡了两周。没人指派，我判断再等发布计划会滑，主动牵头：先写第一版协议文档草稿（包结构/命令 ID/错误码/版本协商）拿去和固件对；同时用 iOS 模拟外设做固件模拟器，让 App 在硬件未定型时并行开发；每周把联调不一致整理成 issue 清单逐条闭环。三周协议定稿，模拟器一直用到量产。

**边界**：主动牵头不等于越界——先和固件负责人对齐「协议 owner 仍在固件侧，我是推动者和 iOS 代表」。模糊环境里主动性的边界：你来推动，决策权和 credit 留给该拥有它的人。

## F3. 快速交付时「快」和「质量」怎么平衡？

**要点**：功能分级（必保/可降级/可砍）+ 主动欠债但记账（每笔债写进迭代计划定偿还期）+ 底线不碰（连接管理和数据写入一步不让）。

**拒绝「快」的场景**：涉及用户数据和 OTA 的部分不欠债——这两块出问题不是体验问题，是用户信任问题。如果「快」的代价是核心链路不可控，直接拒绝并把代价摆到台面上让决策者选。

## F4. 讲一个 owns 到底的问题（不在你职责内）。

**要点**：选「主动揽责/接手烂摊子/没人要求但你做了」的故事，必须有量化结果。

**示范骨架**：量产前一类偶现崩溃（重连瞬间 crash），iOS 怀疑固件、固件怀疑系统栈，挂了三周没人认领。崩溃统计上算 iOS 的但根因跨层，我决定认领：先 App 层加防御性状态机和全链路日志把崩溃率先压下去；再拿抓包约固件对两轮，定位到某固件版本状态机缺陷；推动固件修复排期，期间 iOS 防御逻辑兜底不让用户等。三周后根因修复，崩溃清零，复盘时成为跨层协作样板。

**为什么是我**：用户看到的只有「App 崩了」，不会关心锅在哪个团队。ownership 的代价是花时间担风险，对 founding 角色这本来就是职责本身。

## F5. 项目严重延期或方向出错时怎么处理？

**要点**：坏消息趁早讲（越拖成本越高）；上报时带选项而不是只带问题；给诚实的时间评估。

**示范骨架**：OTA 方案严重低估 iOS 后台限制，DVT 才发现真实用户不可能前台等十几分钟。确认不可行的第二天就上报，带两个备选 + 诚实工期（方案一需四周、赶不上原计划明说）。最终砍掉首版后台 OTA，前台升级 + 体验优化按时发布。复盘后推动建立「平台约束评审清单」：iOS 后台限制、功耗、权限这类硬约束，方案设计阶段逐条过。

**判断标准**：如果今天从零开始，还会不会选这个方案？不会就立刻换——不被沉没成本绑架。

## F6. 和硅谷团队跨时区协作的方法？

**要点**（详见 [../07_英文与跨团队沟通.md](../07_英文与跨团队沟通.md)）：

1. **异步优先**：需求和决策落共享文档，会议结论补文字记录；复杂方案录两三分钟屏幕讲解视频，比十几条消息高效；
2. **黄金一小时**：重叠时段只做决策和解除阻塞，普通进度同步一律异步；
3. **决策权前置划分**：文档写清 iOS 实现层我定、产品方向和 API 契约对方定，谁 own 谁拍板。

**代价**：异步决策天然慢，文字丢语气，文化误会靠定期一对一视频化解。晚上留弹性窗口应对紧急，但那是例外不是常态。

## F7. 讲一次失败与复盘 / 最近一年最重要的技术教训。

**要点**：选真实失败，重点在「归因准确 + 机制改进」，不甩锅不过度自责，结果是流程上防止再发。

**示范骨架**：线上 OTA 失败在测试机复现不出来，浪费两天查 App 逻辑。最后发现是 iOS 后台挂起时机 × 蓝牙断开的组合问题，特定系统版本才触发。两个改变：① BLE 功能测试标准从「模拟器 + 一台真机」升级为「真机矩阵 + 弱信号 + 后台场景」；② 「系统版本 × 场景」写进 bug 模板第一个字段——排查任何问题先问环境再读代码。

> English: Cross-layer BLE bugs often hide in OS version and background-state combinations you can't reproduce on a simulator — my rule now is environment first, code second.

## F8. 这个岗位前六个月怎么开展工作？

**要点**：

- **前两个月**（泡进产品）：拿开发版硬件和嵌入式跑通 BLE 全链路、吃透协议；和硅谷对齐产品节奏与接口契约；CI/CD 和崩溃监控第一天就搭——最便宜也最不能晚做的事；
- **三到六个月**（聚焦交付）：核心链路「连接—同步—OTA」，把连接成功率/同步耗时/OTA 成功率做成 dashboard，用数据和两地团队对话；招人放在架构骨架稳定之后；
- **优先级原则**：影响用户首次体验的永远优先，内部工具和界面美化永远靠后。

**预期产出**：可量产评估的 iOS 端 + 可度量的质量体系 + 第二个人能直接上手的代码骨架和文档。

## F9. 对我们产品有什么了解？想问什么？

**要点**：对已确认事实引用准确，不确定的用「我的了解是……对吗」句式——产品意识第一条是诚实。

**反问清单**（现场保留 2–3 个）：
1. iOS 端是零基础还是已有原型？BLE 协议已定稿还是会演进，我是否早期就参与协议定义？
2. 深圳硬件、硅谷产品、国内 iOS 三地之间技术决策权怎么划分，异步协作的主要载体是什么？
3. 硬件量产时间表（EVT/DVT/PVT 节奏）——直接决定我这边的发布和稳定性优先级。
4. 从产品视角，这个设备最不可替代的用户价值是什么，验证到什么程度了？

## F10. 你期望的管理方式？

**要点**：目标对齐 + 低干预。没有外部监督时自建反馈回路：① 核心链路自动化测试覆盖；② 关键决策写 ADR 留痕；③ 主动把关键决策抛公开渠道征求意见，把「没人管」变成「主动拉取反馈」。长期没人 review 不会等——主动推动建立机制（和硅谷同事定期互审）。founding 阶段没人管是常态，机制要靠第一个人建起来。

## F11.（英文）Tell me about a project you built from scratch.

**骨架**（90 秒讲到 Action 结束，Result 留给追问）：

I built the companion app for a wearable device from scratch — no codebase, no process, not even a finalized firmware protocol. I owned the entire iOS side. The hardest technical decision was how to structure the Bluetooth layer: instead of writing Core Bluetooth callbacks straight into the app, I split it into layered packages — a transport layer wrapping CBCentralManager (state machine, reconnection, framing), a session layer with timeout/retry semantics, and a local-first data layer. Transport exposed protocol-based interfaces only, so firmware protocol changes were contained in one place. I also set up CI and crash monitoring from day one. Result: shipped on schedule; a later breaking protocol revision took about two days to adapt instead of a week-plus.

**追问点**："hardest technical decision" 必被追问，可替换为 OTA 断点续传或本地优先存储。

## F12.（英文）Describe a conflict with a teammate and how you resolved it.

**骨架**：与固件工程师对 OTA 校验时机有分歧（我要传输前全量校验 fail fast，他坚持传输后校验）。我停止争论观点，提议做实验：两个流程都做原型，用弱信号中断连接的真实 trace 测试。数据显示他基本是对的——预校验多一次完整往返，且不覆盖传输中的损坏。我在 sync 里公开认账、采纳他的设计，并加了 chunk 级校验和作为折中。结果首季度零校验类现场故障；更重要的团队规则：**技术分歧靠实验或书面设计文档解决，不靠谁争得久。** 关系反而更强——他后来主动找我评审协议变更。

**成熟度信号**：必须保留「实验证明我错了、我公开认账」这个转折。冲突对象选平级跨团队比选上下级安全。

# AI-native 专题（高频差异化点）

## AI1. 日常怎么用 AI？三个具体场景。

**答案**：AI 是默认项不是可选项。

1. **编码加速**：日常 Copilot 补样板/单测骨架/正则；重构或跨文件改动切 Cursor/Claude Code，喂整个模块上下文让它给修改计划再执行；
2. **单测生成**：纯逻辑层（协议解析、数据聚合）按「正常路径 + 边界 + 异常输入」三组生成用例，自己补业务断言。示范：覆盖率 40% → 80%+；
3. **调试与文档**：崩溃堆栈、断连日志先丢给 AI 初步归因；PR 描述、技术方案、英文邮件打初稿。

**试过后放弃的**：让 AI 直接写 BLE 状态机核心逻辑——它对 Core Bluetooth 回调时序和重入问题经常给出看似正确实则有竞态的代码，宁可自己写、只让它写测试来验证。

**案例**：分包粘包解析器，把协议文档 + 三个真实抓包样本喂给模型，20 分钟生成完整解析器 + 12 个测试用例，修了两处字节序进主干——以前至少半天。

**边界**：效率保守估，编码环节省约 30%，但 review 时间相应增加。AI 省的是「敲代码」的时间，省不了「想清楚」的时间，架构决策从不外包。

## AI2. AI 生成的代码怎么验证？出过什么问题？

**答案**：原则——**按新同事的代码对待**，过 review、过测试、过静态检查，没有例外。

三道防线：
1. 编译器和静态检查：SwiftLint + Swift 6 严格并发检查全开，AI 最容易在并发安全和可选值处理上出问题；
2. 测试：实现和测试不让同一次生成产出，避免「错误实现配错误测试」的自洽陷阱；人为注入几个黄金用例做锚点；
3. 人工 review 重点三处：边界条件、资源释放（闭包捕获/observer 注销）、以及「自信地调用不存在的 API」——幻觉 API 编译能挡，幻觉的业务假设挡不住。

流程：PR 明确标注哪些代码 AI 生成、我改了什么，方便追溯。

**翻车案例（必备反例）**：AI 写 BLE 重连用 `DispatchQueue.asyncAfter` 做退避，没考虑重连期间用户手动断开，定时器到期后发起「幽灵重连」——偶现、难复现，靠日志反查定位。从那以后对 AI 写的任何涉及定时器和状态机的代码都额外问一句「中途取消会发生什么」。

## AI3. 用 AI 辅助调试复杂 bug 的流程？

**答案**：AI 是加速器，不是裁判。

1. **组织上下文**：不甩一坨日志，整理成结构化输入——环境（系统/机型/版本）→ 复现步骤和频率 → 关键日志堆栈（脱敏）→ 已排除的假设。信息组织质量决定输出质量；
2. **让它列假设清单**：「按可能性排序给 5 个假设，每个附验证方法」，不直接要答案。追问固定句式：「如果是 X，日志里应该看到什么？没看到说明什么？」；
3. **最小化验证**：每个假设用最小实验验证，让 AI 帮写一次性诊断代码和日志增强；
4. **AI 帮不上的**：时序竞态、特定硬件才复现、需要系统内部知识的 bug——让它查资料总结案例，定位靠自己加仪器（Instruments、抓包、符号断点）。

**案例**：偶现「后台断连后无法自动恢复」，把 20 条正常/异常对照日志喂进去，模型指出异常日志里 `centralManagerDidUpdateState` 在断连后才到达——推测状态恢复时序问题，这个方向我没想过。加状态快照日志验证，定位到后台恢复时 delegate 设置晚于状态回调，提前注册 delegate 修复。卡了三天 → 一天半定位。

**边界**：「AI 给了合理解释」不等于找到根因——它的解释永远自洽，验证不可省。涉密日志和固件源码先脱敏再喂，这是底线。

## AI4. 为初创团队建立 AI 研发工作流，从哪入手？

**答案**：按 ROI 排序三步走，第一个月只推一件事，跑出数据再扩展。

1. **PR 描述与评审辅助**（ROI 最高）：三地协作，PR 上下文写不清，跨时区一轮澄清就是一天——AI 生成结构化 PR 摘要 + 变更风险提示立刻见效；
2. **测试生成**：单人团队最缺测试人力；commit message 规范化成本最低顺手做；
3. **规范沉淀**：文档模板、术语表写进项目规范文件，AI 生成前先读规范。

CI 挂 AI 初审（明显问题/测试覆盖/命名），但明确「AI 初审不替代人审」；误报多了团队会直接无视它，阈值宁缺毋滥。

**效果指标**：不考核「AI 使用率」虚荣指标，看 PR 提交到合入平均时长、线上逃逸 bug 数、每周自评节省时间，每月复盘，不好用的砍掉。示范：PR 平均合入时间 1.8 天 → 1 天内。

**安全红线第一天就定**：固件源码、密钥、用户数据不出本地/私有部署；选零数据保留政策的商业许可；规则写进团队规范而不是靠自觉。安全红线永远排在效率前面。

## AI5. 怎么判断任务该交给 AI、哪些必须人做？

**答案**：标准——「可验证性高、错误代价低、模式重复」交给 AI；「不可逆、难验证、需要价值判断」人来做。**AI 永远是执行者，人是责任人。**

- **放心交给 AI**：单测生成、样板代码、格式转换、日志初筛、文档初稿、正则脚本——产出可被编译器/测试/人眼快速验证，错了重来成本低；
- **AI 起草人深度把关**：架构方案扩写、API 设计、重构——AI 出选项和对比，决策是我做，因为决策背后的约束（团队规模、时间窗口、演进）它掌握不全；
- **必须人做**：架构决策（对未来的承诺）、安全相关代码（加密/密钥/OTA 签名校验，错一次就是事故）、协议设计最终拍板（量产就改不动，每个字段亲自过）、用户数据和隐私处理；
- **兜底**：提交前问自己「如果这段代码上线炸了，我能解释它为什么这么写吗？」不能解释就不提交。

**边界在持续移动**：不把边界当教条，每次在新场景用「错误代价 × 验证成本」重新算一遍。

## AI6. 给 AI 团队定义接口（模型能力接入 App）有什么考虑？

**答案**：三个维度 + 一个默认假设：**AI 能力不可靠是默认假设**。

1. **推理位置**：端侧（Core ML，低延迟/强隐私/离线，如传感器实时预处理）vs 云端（大模型对话/复杂推理）。接口层抽象，业务只声明「能力需求」（延迟等级/隐私等级/是否允许离线降级），路由层决定走哪边，不绑死实现；
2. **流式交互**：云端 LLM 用 SSE/WebSocket 流式返回，iOS 用 URLSession 逐块读取 + AsyncSequence 抛 token 流，UI 增量渲染。处理半包粘包、中途断流续接、用户打断生成（取消请求 + 停止渲染）；
3. **失败与降级**：模型慢/失败是常态。三级体验：正常流式 → 超时展示「仍在处理」中间态 → 失败提供确定性兜底（缓存结果/简化功能/重试入口）。**AI 接口失败绝不阻塞核心链路**——BLE 数据同步和 AI 问答必须解耦；
4. **工程契约**：接口 schema 版本化（模型和 prompt 会变，客户端不能天天发版），关键路径超时 + 重试预算，AI 指标单独上报（首 token 延迟、完成率、降级触发率），灰度放量。示范：首 token 超时 3s、整体 15s，超时走缓存兜底，云端抖动用户几乎无感知，降级触发率 < 2%。

**取舍**：接口抽象只做「过去三个月验证过的变化方向」，不为想象中的多模型矩阵预留；端侧模型体积内存压力大，低端机型要有明确降级路径，设计时就要求 AI 团队提供性能基准。
