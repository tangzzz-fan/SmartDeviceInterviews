# 题库与答案 · 场景设计题（P1，系统设计必出）

> 用法：系统设计题先画链路再讲机制，主动给失败路径和指标。每题对应一张白板图，见 [../05_白板图解.md](../05_白板图解.md)。
> 答题五层：结论 → 机制 → 案例 → 取舍 → 指标/故障。

## E1. 设计可穿戴设备的数据同步架构（端到云）。

**答案**：

链路三段：**设备 → App（BLE 网关）→ 云**。建模为三段最终一致管道，核心三原则：

1. **一切数据带全局唯一事件 ID 做幂等**；
2. **冲突用确定性合并规则**，不是裸时间戳的 last-write-wins；
3. **离线优先**：本地是权威，网络只负责传播。

**设备→手机段**：设备侧数据在固件端分配单调递增 seq + 设备时钟戳，存 flash 环形区；App 按水位线拉取——本地持久化「已同步到序号 X」，每次从 X+1 增量拉，天然幂等 + 断点续传。重复靠事件 ID 去重（SQLite `ON CONFLICT DO NOTHING`）。

**手机→云端段**：App 本地库是唯一权威，写操作先落本地、进待上传队列（requestId 持久化，App 被杀不丢），同步引擎批量推云；服务端按事件 ID 幂等接收。

**冲突处理**分两类：设备采集数据基本只增不改；App 端编辑（如睡眠标签）用字段级合并 + 版本号；多端编辑的用户档案用操作日志（operation-based）合并而非整对象覆盖。

**补偿三路**：前台回前台优先补推 + BGProcessingTask 兜底 + 下次启动对账。定期按时间窗对账（记录数 + 校验和），不一致用事件 ID 集合 diff 补传；全量对账只在 Wi-Fi/充电时跑。

**体验**：实时指标（心率）前台实时，批量数据（睡眠）后台静默；进度用「水位线推进」驱动 UI（已同步条数/总数），中断时明确展示「已同步到何时」。

**案例**：最狠的坑是重复记录——断连重连后设备重报部分数据 + 手机端两个入口并发触发，云端三倍重复。三件事修复：设备序号水位线持久化、入库强制 ID 去重、同步引擎单 actor 串行化入口。重复归零，中断恢复从全量重拉变秒级增量。

**边界**：设备时钟不可信（掉电重置、漂移），排序不能只依赖设备时间戳，以「设备本地序号 + 手机接收时刻」组合为准，云端再归一化。

## E2. 离线同步怎么保证不丢不乱？（白板 6）

**答案**：

管线：

```
Device flash ring buffer
  -> BLE pull/push（seq + window + ack）
  -> Phone pending store（requestId 持久化）
  -> Cloud（可选，第三副本）
  -> 冲突：device truth / field merge / 版本号
```

关键规则：
- **设备侧**：环形缓冲 + 单调 seq 持久化；App 连上后按 cursor 拉缺失段，**ack 之后设备才丢**；
- **手机侧**：用户操作进 pending store 带 requestId，发送成功以设备 ack 为准，iOS 后台被杀时 pending 必须落盘；
- **重连只补洞**，不从头 dump，除非设备声明 buffer reset；
- **失败只重传缺失 seq**；成功必须幂等；旧包不得覆盖新版本状态；
- **冲突默认设备状态赢**，或按字段合并；禁止用到达时间覆盖。两边同时改同一开关：以设备当前模式为准，App 显示冲突并拉 snapshot，不静默打「最后写入获胜」。

时钟问题：设备常见是单调 tick 不是墙钟；手机侧转墙钟时记录 offset，断连后 offset 失效要重标定。

**案例**：通勤场景手机离线、设备继续记事件，早期按墙上时间合并，夏令时/时区把顺序打乱。改成设备 seq 为真相、手机只存 offset，同步错序客诉降到 0。

**指标**：同步成功率 = SLA 内收到匹配 ack 的 requestId/seq 段 ÷ 应同步总数，按固件版本/网络/前后台切片。不要把「用户打开过 App」当成功。

**取舍**：强确认可靠但耗电、吞吐差——状态和控制命令走可靠通道，高频传感器走窗口 + 可丢策略，丢了要在 UI 上可解释。

## E3. 设计 BLE 自动重连状态机（白板 1）。

**答案**：

状态：idle / scanning / connecting / discovering / ready / streaming / backoff / disconnected，事件驱动 + 定时器，每个迁移打点。

参数与规则：
- 退避：1/2/4/8s + 抖动，设总预算；前台/后台策略不同；最大重试后给用户明确入口（引导开蓝牙/重新配对），不无限重连；
- 断连三分类决定去向：用户主动 → idle 不重连；系统蓝牙关 → WaitSystem 提示；链路异常 → Reconnecting；
- 恢复成功不直接回 Streaming，先走 **Reconciliation**：重发现/重订阅 → snapshot 拉关键状态 → reconcile 本地预期 → 再处理命令队列；
- 幂等：命令带 seq/requestId，ack 未到不当成功；
- 可测性：状态机纯逻辑可单测，BLE 调用层注入 mock（见 [04-性能与基建.md](./04-性能与基建.md) D6）。

**追问应对**：
- 为什么不在 didConnect 就允许发命令？服务未发现、MTU 未交换、设备还在初始化，随机故障来源。Ready = 关键特征可写 + notify 已开 + 握手通过。
- 后台靠什么？保持 connect pending 让系统代管 + State Restoration，App 无法后台持续扫描。

**指标**：首连成功率、重连成功率、断连后 1 分钟恢复率、平均恢复时长，都要能讲优化前后。

## E4. 线上事故怎么处理？

**答案**：

响应顺序：**判断影响面 → 止血 → 定位 → 修复 + 灰度 → 复盘**。

- 止血三板斧：远程开关关功能入口、暂停 phased release 放量、严重则撤回版本；远程开关是止血通道不是修复手段；
- 定位：崩溃聚类、breadcrumb 日志、版本二分；设备类问题按固件版本切片；
- 修复走加急审核 + 灰度发布验证；
- 复盘产出：根因文档、补测试、补监控告警、防再发清单。

**案例模板**（替换为真实经历）：某版本在特定系统启动即崩，phased release 2% 阶段被监控抓到，暂停放量影响面控制在几千人；hotfix 加急审核一天过审，同时远程配置关入口止血。重点讲**止血速度和复盘质量**，不是故障本身。

## E5. 作为 founding iOS engineer，你会优先建设什么？

**答案**：

**先建秩序，不先建平台。** 基础设施服务于交付，不为看起来完整。

- **第一周**：项目结构、设备会话边界（单一状态机）、崩溃收集 + dSYM 链路；
- **第二周**：连接/同步的冒烟测试、TestFlight 自动出包节奏；
- **第三周**：基础 lint、发布清单、监控看板（连接/同步/OTA 成功率）。

**追问应对**：
- 要不要上完整模块化包管理？早期 2–3 人用清晰文件夹 + 边界协议就够，人变多再拆包；
- 测试先测什么？协议编解码、状态机、同步引擎——纯逻辑、出错代价大、容易隔离；
- 和固件先冻什么？协议和错误码，再冻版本兼容矩阵。

**取舍**：过早平台化会吞掉 0 到 1 速度；完全无秩序两周后联调会崩。只修当下最拖速度的那一层。
