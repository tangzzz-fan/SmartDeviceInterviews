# 题库与答案 · 性能与基建（P1）

> 用法：本模块每题必须有数字。没做过的不要硬装，讲方法论 + 可迁移经验。
> founding 视角加分：回答时带一句「单人团队下我会怎么排优先级」。

## D1. 启动优化怎么量化？

**答案**：

思路：**先度量、再归因、后优化，最后建防劣化卡点**——不是攒技巧，是把两段链路拆开分别治理。

- **pre-main**（dyld 到 main 前）：加载动态库、rebase/bind、+load 与 category 注册、C++ 构造器。手段：减动态库（能静态就静态）、去 +load 改 +initialize/懒加载、清理无用类。
- **post-main**：压缩 didFinishLaunching 同步工作——SDK 初始化分级（必须/延迟/首次使用时）、网络预热异步化、首屏数据懒加载。

可穿戴 App 启动只做：崩溃捕获、最小依赖注入、首屏渲染、已绑定设备的懒连接。蓝牙扫描、日志上传、AB 配置不进首屏关键路径。预连接可以发起，但不能等 Ready 才进首页——首页先展示 stale，后台 reconcile。

度量：开发期 Instruments App Launch 模板 + os_signpost 分段；线上 MetricKit `MXAppLaunchMetric` 看分布。冷启/热启/后台恢复分开度量。

示范数字：pre-main 450ms → 180ms，冷启 2.8s → 1.2s（注明机型与 release 基线）。

**追问应对**：
- 延迟初始化会让首屏后二次卡顿，用空闲任务分片，避免一进首页就打满。
- 防回归：CI 每次合入用固定真机跑冷启基准脚本（重启多次取中位数），超阈值 fail。曾有同步数据库迁移混进启动路径，基准涨 300ms 被卡点拦下。

## D2. 内存优化与 OOM 怎么处理？

**答案**：

可穿戴 App 长驻内存，OOM 是高频问题。iOS 内存不足时 jetsam 按优先级杀进程，被杀的进程没有传统 crash 堆栈，termination reason 里是 `Jetsam`。

排查路径：先确认是不是 jetsam 杀的 → footprint 分布找大头 → 线上靠 MetricKit `MXMemoryMetric` + 「进后台时内存水位」日志区分前台/后台 OOM；开发期 Memory Graph Debugger（对象图/循环引用）+ Allocations/Leaks。

超标大户：解码后大位图（4000×3000 图解码约 45MB，走 ImageIO downsampling）、无上限缓存、文件句柄泄漏、单例持有大数组。治理：分页加载、缓存上限与淘汰、内存警告时降级——但 `didReceiveMemoryWarning` 不能当唯一防线，收到时往往已经太晚，关键路径主动控制峰值。

监控：footprint 上报、OOM 单独统计（区别于 crash）。

**案例**：同步多天历史数据把 JSON 全驻留内存，峰值 900MB+ 被杀。改流式解析 + 分批入库，峰值压到 200MB 内，该场景 OOM 归零。

**取舍**：内存优化常以性能为代价（流式解析更慢、缓存变小命中率降），按场景取舍——同步链路宁可慢也不能爆，UI 图片缓存保留较大额度。

## D3. App 侧功耗怎么优化和测量？

**答案**：

本质：**减少无线电活跃时间 + 减少 CPU 唤醒次数**。

- 定位：按需 + 精度降级，用 significant-change 不用持续高精度；
- 网络：合并请求、批量上报；
- BLE：见 [02-ble与corebluetooth.md](./02-ble与corebluetooth.md) B13——扫描占空比（扫 10s 停 30s）、identifier 直连不扫描、空闲长 interval + latency、传感器高采低报（100Hz 采集 10Hz 上报）；
- 后台：合并 BGTask、减少唤醒；后台只靠系统 restoration 代管连接，不主动扫描。

度量闭环：Xcode Energy Log / Instruments Energy gauges 看趋势，真机电流计测绝对值，线上 MetricKit CPU/location 维度佐证，优化前后出数字。

**案例**：用户反馈装了 App 就耗电。Energy Log 抓一晚发现后台保活每 15 分钟唤醒做无效扫描；改成 restoration 代管 + 同步攒到前台/充电时批处理，后台功耗几乎归零，「耗电」差评基本消失。

**边界**：功耗问题经常是固件侧的锅（广播间隔、发射功率），用电流仪或固件日志确认归属，别全在 App 层打补丁。AI 可穿戴若做实时音频/事件流，interval 拉不太长，预算花在传输效率而不是少连接上。

## D4. 从 0 搭崩溃监控与稳定性体系？

**答案**：

按「采集 → 上报 → 符号化 → 聚合 → 告警」五段链路搭：

- **采集三层**：Mach exception（EXC_BAD_ACCESS 等，最底层最完整）→ Unix signal（SIGSEGV/SIGABRT 等，handler 里只能调 async-signal-safe 函数，只做最少工作，分析放下次启动）→ NSException（触发后仍会走到 SIGABRT，避免重复上报）。下次启动生成报告，附 binary UUID 上报。
- **符号化**：崩溃地址 = image 基址 + 偏移，用对应 dSYM 通过 atos/symbolicatecrash 还原；**CI 构建后自动归档上传 dSYM 做成强制步骤**，按 binary UUID 索引，加上传校验告警（曾漏传导致整版本符号化失败）。
- **聚合**：按堆栈 top frame 聚类 + 版本维度趋势；founding 期用 Crashlytics 兜底，逐步自建。
- **卡顿监控**：watchdog 线程定时检查主线程响应，超时抓主线程堆栈；MetricKit `MXHangDiagnostic` 做免费补充。
- **预防与止血**：灰度分阶段（5%→20%→100%）异常即停；远程开关是止血通道，不是修复手段。

指标：crash-free sessions、OOM 率、卡顿率，各自 SLA。设备类产品额外：指标按固件版本维度切片——曾发现某固件在 iOS 特定版本握手超时。

**边界**：OOM 和 watchdog kill（0x8badf00d）不属于可捕获崩溃，靠 MetricKit 和启动时启发式检测；崩溃率分版本看，别被老版本长尾稀释。

## D5. CI/CD 怎么从 0 建？

**答案**：

单人团队下流水线就是「第二个工程师」：PR 检查快而严，主干构建全而自动，人只做「合入」和「发版」两个决策点。

- **PR 层**（10 分钟内出结果，卡不过不合入）：lint（SwiftLint + SwiftFormat）+ 单测 + 增量构建；
- **主干层**：merge 后全量测试 + UI 冒烟 + Release 构建，自动打 beta 版本号、archive、上传 TestFlight；
- **签名**：fastlane match，证书 profile 加密存仓库，避免「某人电脑上的证书」单点——签名与证书是最容易卡住的环节；
- **分发**：TestFlight 内部组自动收新 build；给固件同事的调试版单独 build configuration（详细日志 + 调试面板）；
- **发版**：phased release 分阶段放量 + 崩溃监控，异常暂停；构建产物可追溯（commit → 包号）；
- **选型**：startup 用 GitHub Actions + 自托管 Mac mini runner（iOS 绕不开 macOS，自托管比云 Mac 便宜可控），给 runner 配健康检查和备用机。

**案例**：第一周先闭环 lint + 单测 + TestFlight 自动上传三件事，第二周加 match 签名，之后补 UI 冒烟和构建缓存。之后主干每天自动发一个 TestFlight 版本，发版人工操作 5 分钟内，半年零签名事故。

**取舍**：全量 UI 测试进 CI 会拖垮流水线，只放冒烟级；脚本全部进仓库、能声明式不写 shell——流水线本身不能成为维护负担。

## D6. 自动化测试策略？投入产出怎么权衡？

**答案**：

务实标准：**逻辑密度高 + 出错代价大 + 容易隔离**的代码优先测——协议帧编解码、同步冲突合并、连接状态机、OTA 分片校验。一个字节序 bug 线上代价可能是变砖。

- 硬件依赖抽象成 `BluetoothTransport` 协议，生产实现包 CoreBluetooth，测试实现是内存模拟器，可脚本化「连接 → 断连 → 恢复」和异常包注入；
- 录制回放：PacketLogger 真实抓包存成用例文件喂给解析层——表驱动的编解码测试（正常帧/截断帧/CRC 错/粘包）曾第一时间抓到固件偷改字段长度，避免一次量产不兼容事故；
- UI 测试只保登录/配对/同步三条主路径冒烟，其余靠 TestFlight 人工 beta；快照测试 startup 阶段缓行；
- 覆盖率不是目标：关键路径 100%，边缘看 ROI。没人维护的烂测试比没测试更糟。

**追问应对**：真机回归无法完全替代——维护一台常驻测试设备 + 自动化配对脚本做每日巡检。核心模块覆盖率目标 70%+。

## D7. 日志体系怎么设计？线上问题如何远程定位？

**答案**：

三层 + 设备侧一条：

1. **本地结构化日志**：os_log + 自建环形缓冲（分级 error/warn/info/debug，滚动覆盖约 5MB）。必带上下文：会话 ID、固件版本、连接状态、同步阶段——可穿戴问题没这些上下文没法查。敏感数据（token、健康数据）写入前统一脱敏，健康类产品红线。
2. **回捞**：用户反馈触发打包近 N 天日志加密上传；也可服务端下发开关远程提高某用户日志级别。
3. **聚合**：线上定位不靠全量日志——把关键状态迁移（连接建立/断开、同步开始/失败、OTA 各阶段）做成轻量埋点常量上报：**日志用于深挖、事件用于面**。
4. **设备侧**：固件日志写 flash 环形区，App 经 BLE 拉回对齐时间线（见联调模块 C8）。

采样分层：错误日志永不采样，info 按会话采样，高频每包日志默认关闭只在调试 profile 开。日志 schema 变更向后兼容。

**案例**：「同步到一半失败」埋点只能看到失败率高，回捞三个用户日志包发现都是同步中途设备发了固件异常事件码，对照设备日志确认是固件传感器驱动挂起拖垮 BLE 栈——App 层完全看不出来的 bug，两天定位并推动固件补丁。

## D8. 发版流程怎么设计？热更新可行吗？

**答案**：

链路：feature 分支 → PR + CI → main 自动出 TestFlight → 内测验证 → release tag 触发 archive + 提审 → **phased release**（1%→2%→5%→10%→20%→50%→100% 七天阶梯）→ 放量期盯崩溃率，异常暂停；严重问题撤回版本 + hotfix。

审核被拒预案：蓝牙权限用途描述（5.1.1）、后台模式声明与实际不符、健康数据隐私声明、硬件配套 App 审核员手里没设备——准备 demo 视频和说明文档随审核备注提交。

**热更新基本不可行**：动态下发可执行代码违反审核指南 2.5.2（JSPatch 类已被大规模警告下架）。合规的「热」手段只有：远程配置（开关/阈值/文案）、feature flag。真正的兜底是**快速发版能力**——发版周期压到天级 + expedited review 加急通道。

**案例**：某版本特定系统启动即崩，phased release 2% 阶段被监控抓到，暂停放量影响面控制在几千人；hotfix 加急审核约一天过审，同时远程配置关掉触发崩溃的功能入口止血。

**取舍**：phased release 把问题暴露拉长到七天，监控不到位反而延误——放量期必须有人盯指标；feature flag 定期清理，否则组合爆炸成测试负担。

## D9. 偶现崩溃复现不了怎么办？

**答案**：

靠「信息包围」，不是等运气：

1. **榨堆栈**：exception 类型 + 崩溃线程堆栈。EXC_BAD_ACCESS 地址是魔数/小数值 → use-after-free；SIGABRT → 断言或越界；主线程停在锁上且其他线程等锁 → 死锁。聚类看是单一原因还是多入口汇聚；
2. **看维度分布**：只在特定系统/机型/版本出现往往直接锁定原因；
3. **针对性侦察**：可疑路径加 breadcrumb（崩溃前最后一条状态上报），MetricKit `MXCrashDiagnostic` 补充；
4. **代码审查替代复现**：列出崩溃点所有调用方，逐一审查线程安全和生命周期——偶现 crash 七成是多线程竞态；本地并发循环压测可把低概率竞态放大成必现。

**案例**：占比 30% 的偶现 EXC_BAD_ACCESS，维度分析都发生在「断连瞬间」，审查确认 BLE delegate 回调在专用队列、对象释放走主线程没有生命周期保护。回调持 weak + 队列统一收口，发版后聚类归零——全程没复现过一次。

**边界**：影响面决定投入，<0.01% 且只在老系统的先观察；没确认根因别乱改「看起来像」的代码，每次修复后跟踪聚类曲线是否真正归零。

## D10. MetricKit 能给什么？怎么建性能基线防劣化？

**答案**：

MetricKit 提供系统聚合的按天投递的设备端性能/诊断数据，是线上监控免费基座。实现 `MXMetricManagerSubscriber`，每天收到 payload 上报。

- 指标类：`MXAppLaunchMetric`（启动直方图）、`MXAppResponsivenessMetric`（hang）、`MXMemoryMetric`（峰值）、CPU/GPU、网络流量、磁盘 IO、定位活跃度、`MXAnimationMetric`（掉帧）；
- 诊断类：`MXCrashDiagnostic`、`MXHangDiagnostic`、`MXDiskWriteExceptionDiagnostic`，自带部分符号化。

注意：是聚合直方图不是逐事件明细、有采样——看分布趋势，不适合定位单用户；有版本门槛和最长一天投递延迟，急性问题靠自建埋点。

**防劣化双保险**：
- CI 层：固定真机 + 脚本跑冷启动/关键页基准（清缓存、多次取中位数），劣化超阈值（如启动 >10%）阻断；
- 线上层：MetricKit 按版本跟 P50/P95，新版本自动对比上一版生成报告，超阈值告警。阈值用最近三个稳定版均值 + 波动带定，避免误报。

**追问应对**：CI 真机基准对环境敏感（温度/电量/后台），靠多次采样和统计压噪声，别被噪声逼着天天调阈值。

## D11. 包体积怎么控制？

**答案**：

三块：资源、代码、依赖，工具量化（link map、App Store Connect build size 报告），体积检查进 CI。

- **资源**（通常最大头）：清理未用 image set，大图 HEIC/WebP 或矢量模板渲染，音视频按需下载；Asset Catalog 配合 App Thinning 按设备 scale 分发；
- **代码**：Dead Code Stripping + `-dead_strip`，清理无用类和多余本地化；静态库只链需要的切片，调试符号不进发布包；
- **依赖**：引入前评估体积成本，link map 看每个 .o 贡献；能三行代码实现的别引 2MB 的库；
- **App Thinning**：slicing + on-demand resources（bitcode 已随 Xcode 14 退役）。

**案例**：App 从 60MB 涨到 110MB，link map + 资产清单排查，大头是两套未用字体、历史活动页遗留位图、为一个工具函数引的库。清理回 65MB，CI 加「体积增长 >2MB 需说明」检查。

**取舍**：过度压缩伤画质；激进 strip 可能误删反射引用的符号（ObjC 动态特性，dead strip 要配合 `-ObjC` 验证）。原则是设「体积预算」让超标可见，不是临发版突击瘦身。
