# 英文与跨团队沟通

> 硅谷团队要的不是华丽口语，而是能在异步环境里把 **problem / evidence / hypothesis / next step** 讲清楚。
> 练习顺序：先练短版（30–60 秒）求稳定清楚，再练长版（90 秒）；录音回听，重点改停顿、重复和句子过长。术语保持前后一致（notify / characteristic / bonding / supervision timeout 等）。

## 一、英文自我介绍

### 90 秒版（背熟，一次过不超时）

> I am an iOS engineer who owns client architecture and device-facing systems, not just feature screens. Over the last few years I have worked on wearable and IoT products, including BLE connection management, state sync, reliability, and release quality. I am used to working with firmware teams in Shenzhen and product or software teams overseas. What attracts me to this role is that it is a founding iOS seat: the job is to make the wearable product actually ship, with hardware, firmware, and software in the same loop.

### 60 秒压缩版

> I focus on iOS architecture, BLE, and shipping hardware-connected products. I have owned connection state, recovery, and the client-side engineering needed to debug with firmware. I'm highly AI-native: I use AI across coding, test generation, and code review, but I keep the judgment calls — protocol correctness and ship/no-ship — to myself. I want this role because it combines client ownership, device communication, and founding-stage execution.

## 二、Why this role（动机题）

> Three reasons. First, it is not a narrow feature role; it asks someone to own the iOS client. Second, the hard part is the device loop: BLE, recovery, power, OTA, and bring-up with firmware. Third, I work well when the spec is incomplete, as long as we can freeze a small interface and keep moving.

## 三、英文项目讲述

### 3 分钟版（旗舰故事英文版，对应 [06_STAR故事库.md](./06_STAR故事库.md) S1/S3）

> We had a wearable app where connection state was owned by several screens at once. After backgrounding, the UI could show connected while writes failed. I pulled connection into a single session state machine. Screens could only send intents and render snapshots. Ready was defined as service discovery, notifications, and handshake, not `didConnect`. We also sliced connection success by firmware version and found one firmware that timed out on handshake. After the firmware fix and the client recovery path, connection became diagnosable instead of anecdotal.

被追问数字时：数字可替换，重点是「我们定义了 Ready、按固件版本切片测量、不再凭记忆争论」。

### 5–10 分钟深挖框架

结构：What it is → My role → Architecture → Hardest problem → Result → What I'd do differently。

> *This app pairs with a wearable device over BLE. My role was the iOS lead: I owned the architecture, the BLE layer, and the data-sync pipeline.*
>
> *Architecture-wise, the app acts as a gateway. The device pushes sensor data over BLE; the app validates each packet, persists it locally first, then syncs to the cloud in the background. For BLE, we negotiate MTU and connection parameters per use case — tight interval during sync, relaxed in idle to save power. We added sequence numbers and CRC so the app can resume from an offset if the connection drops.*
>
> *The hardest problem was reliability: the device kept disconnecting in the EVT phase. I isolated the issue using a sniffer and direct GATT tests, aligned the timeline with firmware logs, and we found the firmware buffer was the bottleneck. After the fix, disconnects went to nearly zero.*
>
> *As a result, OTA success rate reached 99%+, and the same protocol is reused in production testing. If I did it again, I'd add contract tests between app and firmware earlier.*

## 四、英文技术短答（高频四问）

**Tell me about a challenging technical problem**

> One difficult case was an intermittent "tap does nothing" bug after a failed OTA. The app still showed connected. We broke the path into observable layers: app queue, BLE write, protocol, firmware mode. Shared logs showed the device was stuck in an illegal OTA mode and dropping commands. We added an error code on advertising and a recovery prompt on iOS. The important part was turning a cross-team argument into a shared evidence trail.

**How do you work with cross-functional teams?**

> I try to freeze the smallest contract first: handshake, error codes, versioning. Then I send short written updates with evidence, not long narratives. If we disagree, we add an observation point before we assign blame.

**How do you use AI in your work?**

> I use it to draft boilerplate, test cases, log summaries, and English updates. I do not let it decide root cause, protocol correctness, or ship / no-ship. I still need to disprove hypotheses against logs.

**How do you handle ambiguity?**

> I separate what must be frozen from what can change. For a wearable, I freeze connection, recovery, and logging first. Feature fields can wait. I also say no to scope that would miss the bring-up window.

**其他高频题速答要点**：

| 问题 | 答法要点 |
| --- | --- |
| Why do you want to join us? | 方向认同（AI 可穿戴）+ 0→1 ownership + 软硬一体挑战 |
| How do you handle disagreement with firmware? | 数据 + 原型验证，先对齐目标再谈方案 |
| What are your weaknesses? | 真实弱点 + 已建立的补偿机制，不装完美 |

## 五、技术解释模板（把复杂讲简单）

结构：One-line answer → Why it matters → Concrete example。

示例 —— *"Why does the connection keep dropping?"*

> BLE connections have a supervision timeout — if the device and phone don't exchange packets within that window, the link is considered dead. In our case the device was busy handling large writes, so it missed the window. We solved it by tuning the connection parameters and adding app-side retry with backoff.

## 六、跨时区书面更新模板（problem / evidence / hypothesis / next step）

Subject: `[device SN / build / firmware] tap-no-response after failed OTA`

- **Problem**: After a failed OTA, taps do not move the device. App UI still shows connected.
- **Evidence**: App write succeeds; no notify; firmware log shows mode=`OTA_BAD` at T+12s. Repro: fail OTA at 80%, reboot app, tap once.
- **Hypothesis**: Device stays in an illegal mode and drops commands; app does not detect mode.
- **Next step**: Firmware advertises error code; iOS shows recover CTA; I will send a build tomorrow 18:00 PT.
- **Ask**: Need a 15-min overlap to confirm the recover advertisement payload.

短会议口播：

> We are not debating ownership yet. The evidence says the write leaves the phone and the device drops it in `OTA_BAD`. I need the error code on advertisement, then I can ship the recover path.

## 七、Daily Sync 与风险同步

**每日汇报（3 句）**：

> Yesterday I finished 【X】. Today I'm working on 【Y】; it's about 【60%】 done. I need 【input from firmware / a device / a decision on Z】 — can we align on it?

**被卡住时**：

> I'm blocked on 【X】 because 【reason】. I've tried 【A】 and 【B】. My plan is 【C】, and I need 【D】 to unblock. Does that work?

**表达不确定性**：

> I don't want to jump to a conclusion yet. Based on the current evidence, I have two working hypotheses, and I'd like to validate them with logs before we decide on the fix.

**风险同步句式**：

- This is a ship blocker if recovery is not in the firmware build by Thursday.
- I can ship a client workaround, but it will hide the real mode error. I do not recommend that.
- Latency will slip one day if we keep changing the handshake fields.
- I need a decision: battery life vs. 2-second state freshness.

**表示异议**：

> I see the tradeoff differently — from the data I have, 【your point】. Could we validate 【my suggestion】 with a quick prototype before committing?

**会议常用句**：

- Let me clarify the problem statement first.
- I think there are two separate issues here.
- The key question is whether the state mismatch starts on the app side or the device side.
- Can we align on the expected behavior before discussing the fix?
- What evidence do we already have, and what is still missing?
- The short-term fix and the long-term fix may be different.

## 八、英文红线

不要说 → 改成：

| ❌ 不要说 | ✅ 改成 |
| --- | --- |
| I have done some BLE. | I owned the session state machine and recovery budget. |
| We optimized performance a lot. | Cold start P50 moved from about 3.2s to about 1.6s on the devices we measured. |
| AI makes me much faster. | AI drafts the test matrix; I still verify the protocol against traces. |

原则：不用模糊形容词（some / a lot / much faster），每句带机制或数字。
