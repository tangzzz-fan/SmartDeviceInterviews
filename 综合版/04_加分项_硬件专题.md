## 一、低功耗优化

面试官在听：你会不会把「省电」说成关动画。**可穿戴省电首先是射频和采样策略，UI 优化几乎不是一阶因素。**

**三层视角**：
- App 系统层：后台任务、唤醒频率、定位/网络占用；
- BLE 链路层：connection interval、slave latency、扫描窗口、notify 合并；
- 硬件协作层：谁决定连接参数、谁聚合数据、传感器 ODR。

**先定 SLA 再选旋钮**：目标续航、状态新鲜度（2s / 30s / 仅打开 App 时）、是否允许后台实时。「实时」和「两天续航」冲突时听产品书面 SLA；没有 SLA 就自己提一版，把选择做成可测项而不是口头感觉。

**App 能直接搞砸的**：不停 scan、Ready 后高频无响应写、后台无预算重连、日志/定位/音频会话常开、订阅了不需要的高频 notify 特征。

**测量闭环**：Xcode Energy Log 看的是手机；设备续航必须拿真机和固件电流账。场景矩阵：待机 / 空闲连接 / 实时同步 / 夜间监测 / OTA 分别测。

**答题模板**：先建测量基线（三场景电流计各测 30 分钟）→ 砍三刀：① 空闲 interval 30ms → 300ms + slave latency，同步期临时收紧；② 传感器数据固件聚合批量 notify，减少唤醒；③ 后台任务合并。结果空闲电流 15mA → 3mA（示范值），沉淀功耗回归场景每次发版前测。

**案例**：默认连接参数为了跟手，待机电流偏高。和固件拆成 interactive / idle 两档：App 前台或上传时切 interactive，空闲回 idle。日续航从约 14h 回到 24h 目标量级，状态延迟仍在 SLA 内。

**追问应对**：
- 怎么证明是 App 还是固件的锅？分层测量——App 关闭 BLE 看系统基线，再分别开扫描/连接/同步，看哪一步抬升最明显；
- 激进省电的代价：断连恢复变慢、OTA 变慢、传感器丢点。联调期可用「性能档」，但要有 profile，不能把试产参数当量产。

**翻车点**：只讲方案没数字；把功耗全归固件；不知道 Low Power Mode 下系统限制后台能力。

## 二、设备 OTA（进阶：commit 点、防砖、工厂 vs 用户）

基础流程见 [03_题库与答案/02-ble与corebluetooth.md](./03_题库与答案/02-ble与corebluetooth.md) B9。加分项要能讲：

**commit 点**：OTA 不是传完文件就算成功。要有明确 commit——校验通过、写完元数据、下次启动才切新镜像。**commit 前必须能回旧镜像或进恢复模式。** App 的职责是条件检查、可靠传输、阶段打点、升级后确认版本；砖不砖首先是镜像布局和恢复策略，必须和固件一起冻。

**协议细节**：DFU service 含控制点（start/data/verify/abort）与传输特征；包格式 opcode + 总长度 + 包序号 + 数据 + CRC；App 记录已传 offset 与最后确认包序号，重连后从 offset 续传。iOS 侧注意 Write Without Response 流控，避免写爆导致断连。

**失败路径每条都要有状态码打到 App**：升级中掉电、校验失败、重启后连不上、版本回退、刷错硬件型号。升级成功后做最小 smoke：握手、电量、关键模式。

**工厂 OTA vs 用户 OTA**：工厂可以更激进（有夹具和串口）；用户路径必须防砖、可提示、可中断恢复。客户端不要把两套协议混成一套无模式状态机。

**版本兼容矩阵至少三维**：硬件 revision × 固件版本 × App build。App 拒绝对不支持的硬件刷包；最小版本写进包头并签名；灰度按固件版本切片，出问题能停。Founding 阶段先做「能停、能看成功率」，再谈复杂差分包。

**量产复用**：同一套 DFU 协议在产测用于首版固件烧录，App 侧 OTA 代码与产测脚本共用解析/校验逻辑。

**追问应对**：
- 传输中设备关机？bootloader 恢复模式 + 双 bank 回滚 + 断点续传三层兜底；
- 固件包防篡改？签名校验 + 传输 CRC + 整体哈希三重验证。

**翻车点**：只讲「上传固件」不讲协议与恢复；不知道双 bank；不提协议版本兼容；不提 commit 点。

## 三、离线数据同步（设备侧视角补强）

基础设计见 [03_题库与答案/05-场景设计题.md](./03_题库与答案/05-场景设计题.md) E1/E2。加分项追问补强：

- **设备缓冲满**：水位上报 + 优先同步最旧数据 + 告警，必要时提示用户；缓冲大小按「最坏离线时长 × 数据速率」设计；
- **丢数据场景与对策**：连接中断（断点续传）、App 被杀（本地持久化 + 启动对账）、设备端覆盖（环形缓冲 + 定期上报水位）；
- **云如果存在是第三副本**，不能在 BLE 未确认时当成功；
- **同步成功率定义**：分母是应同步的 requestId/seq 段，分子是 SLA 内收到匹配 ack，按固件版本/网络/前后台切片。

**答题模板**：App 当网关、先落盘再上传。设备端数据带 seq 和 CRC，未确认的持久化；App 收到先写本地库再回 ack；云同步走增量 + 幂等键，失败进队列，后台任务、push、启动对账三路补偿。冲突规则提前定：设备采集数据以设备为准，用户编辑走版本号合并。断网、杀 App、换设备都不丢。

## 四、音频采集与处理

**先问音频走哪条物理链路**：经典蓝牙 HFP/A2DP、BLE 自研帧、还是设备本地识别只上传事件——三条的会话、后台、吞吐完全不同。

**吞吐测算（必备数字）**：16kHz/16bit 单声道 = 256 kbps ≈ 32 KB/s；48kHz/16bit ≈ 96 KB/s。BLE notify 实测约 200–600 KB/s（2M PHY + 大 MTU，受外设栈限制）——16k 直传可行，48k 需端侧压缩（Opus 24–64 kbps）或加大缓冲。为什么不把 PCM 直接走 BLE notify？带宽、功耗、丢包对语音质量不友好，优先设备端压缩或只传事件。

**链路**：麦克风采集 → 环形缓冲（防丢帧）→ 时间戳标注 → 编码/压缩 → BLE 分块传输 → App 解码 → 播放/存储/上传。实时场景（通话/语音助手）缓冲小控时延；录音/上传场景缓冲大防丢帧。

**iOS 边界**：AVAudioSession 类别、中断回调、路由变化；和 BLE 控制面同时存在时不要互相重置连接。后台连续录音受系统策略限制——产品如果假设「App 被杀仍连续录」，要尽早和产品拆穿。

**端云分工**：降噪、AEC、唤醒词放端侧（低时延省流量）；大模型语音理解在云侧；断网端侧降级。云端识别更灵活但隐私和离线差；端侧识别省带宽但模型更新要走 OTA。Founding 先冻「谁采、谁编码、谁存」。

**追问应对**：
- 音频和传感器时间戳为什么要对齐？语音+传感器融合需要精确时间关系，不对齐特征错位；
- 掉包？包序号 + 重传/FEC + 缓冲隐藏（PLC），按场景取舍。

**隐私红线**：麦克风数据默认不进普通日志、不进模型提示词。健康类数据同理：权限、敏感数据最小化、是否出设备、是否出手机——面试里主动提红线，比假装做过 PPG 算法加分。

**翻车点**：说不清吞吐数字；把降噪全推云侧；不知道 Opus 在低码率下的位置。没做过完整音频链路用缺口话术 3。

## 五、传感器数据处理

**常见传感器与 ODR**：PPG 光学心率（25–100Hz）、加速度计（50–200Hz）、陀螺仪（100–400Hz）、磁力计、温度、气压、皮肤电导。

**数据链路**：采样 → 缓冲 → 滤波（低通去噪，截止频率按场景：静息 vs 运动）→ 特征提取 → 算法（计步/睡眠分期/活动识别/心率）→ 存储 → 同步。

**数据面设计**（白板 7）：控制面和数据面分开——控制面短命令 + 可靠 ack；数据面吞吐优先 + 校验 + 可丢或可补。IMU 100Hz 三轴 float 会打爆小 MTU 通知：设备批 20–50ms、量化 int16、带一个 tick；App 用 jitter buffer 对齐而不是每包上 UI。缓冲满时设备必须有策略（丢最旧/停采/降频）并上报 overflow。缺包处理：控制面不允许缺；数据面允许缺但要在质量和功耗上可见，不能静默当完整波形。

**时间戳对齐**：设备本地单调时钟 + 定期对时（App 校准 offset），或统一到设备相对时间；不对齐导致多传感器融合特征错位、云侧算法无法复现。

**数据质量**：与参考设备对比误差（心率 ±3bpm 量级）、缺失率、异常值比例；运动伪影用质量标签而非硬算；端侧算省流量省功耗，云侧只做长期趋势。默认上传特征/摘要，原始数据按需。

**取舍**：无损 + 实时几乎一定费电。AI 可穿戴通常接受短窗完整、长窗可抽稀。

## 六、C/C++ 与嵌入式基础（App 工程师视角）

**边界**：Founding iOS 不要求会写驱动，要求能读懂包、对齐字节。

- **C/C++**：指针与引用（引用是别名不可空，指针可空可重指）、栈/堆/静态区、struct 对齐与 padding、大小端（BLE 协议普遍小端）、volatile（寄存器/中断共享变量）、位操作；
- **关键坑**：C 结构体有 padding，直接 memcpy 到 iOS 会错位——生产上用显式编解码，App 用解析器吃字节，不要在 Swift 里硬填 C 结构体对齐；
- **嵌入式概念**：ISR 要短（置标志 + 主循环处理）、看门狗、RTOS 任务/信号量/队列、DMA；
- **总线**：UART（调试/低速率）、SPI（传感器/Flash，高速同步）、I2C（传感器，多设备寻址）——板级总线 App 只通过 BLE GATT 看到结果；
- **BLE SoC 认知**：Nordic nRF52（SoftDevice）、nRF53（Zephyr）、STM32WB、ESP32；
- **C/C++ 在 iOS 工程出现的位置**：编解码、CRC、加密、音频 codec、跨平台核心。用 C 边界注意内存所有权、线程、错误码，不要让 Swift 直接共享可变缓冲给 BLE 回调线程。

**答题模板**：我日常不写固件，但能读懂固件日志、看懂 buffer 和时序概念。上次联调丢包，我判断是固件 buffer 溢出——App 发了 200 包但固件日志只收 150 包且没有 ack 窗口，和环形缓冲深度有关。能和固件一起定位，而不是只甩锅。

**案例**：一次「偶发解析失败」是固件改了字段宽度没改 version。之后协议变更必须 bump version，App 对未知 version 拒绝业务命令并提示升级。

**取舍**：Protobuf 演进方便但 MCU 成本高，早期手写 TLV + 版本号往往更快。选了就要冻，不能每周换。

**翻车点**：装懂被追问穿帮——只讲确定会的；把「会用 Arduino」说成「懂嵌入式」。不深就用缺口话术 5。

## 七、EVT / DVT / PVT 与量产交付

**阶段冻结表**（白板 8 展开）：

| 阶段 | 硬件在做什么 | iOS 该做什么 | 不该做什么 |
| --- | --- | --- | --- |
| EVT | 能亮、能连、接口狂变 | 多 firmware profile、日志拉满、最小闭环 | 堆完整设置页、谈极致动画 |
| DVT | 形态接近、谈功耗和可靠 | 冻协议、恢复路径、回归集、功耗档、开始谈 SLA | 让握手字段每周改含义 |
| PVT | 小批量接近出货 | 兼容矩阵、灰度、工厂固件分支 | 只在开发者手机上验证 |
| 试产 | 产线 + 真实用户前夜 | 缺陷按 SN/固件切片、能停发布 | 把试产 bug 当个例忽略 |
| 量产 | 规模、版本长期共存 | 分阶段 OTA、监控、回滚、kill switch | 假设全员同一固件 |

每阶段问自己：**现在该冻接口，还是还在探路？冻错了会拖硬件；冻晚了会让试产不可回归。** DVT 入口是谈判点：进 DVT 就必须有版本号和错误码表。

**产测项**：烧录 MAC/SN、校准（电池/温度/传感器）、BLE 连接与功能自检、固件版本校验；产测工具协议与正式 App 一致。

**试产/量产**：试产暴露产线问题（夹具、烧录速度、工位覆盖）；量产看直通率/良率/返工率；问题响应走 FA（失效分析）：复现 → 根因 → 纠正措施 → 预防。版本冻结后 App 必须维护已出货固件的兼容矩阵，变更走 ECO/变更控制。

**量产交付对 iOS 的具体产物**：固件兼容矩阵（可发布的组合）、OTA 包签名与最低 App 版本、关键链路监控（连接/同步/OTA）、发布刹车（谁能停、停了用户看到什么）、已知失败路径文档（给客服和固件）。

**案例**：试产发现同一广播名被产线烧成重复，App 从「按名字绑定」改成 identifier + 产线序列号校验——这是试产教给客户端的课，不是需求文档里写出来的。

**追问应对**：EVT 能不能上 TestFlight 给非工程师？可以，但要标明不稳定、可回厂刷；不要把 EVT 包和 PVT 包用同一个 build 号。

**翻车点**：说不出各阶段缩写含义；把量产问题当测试问题处理（没有 FA 思维）；不提兼容矩阵。没完整走过用缺口话术 2/4。

## 八、加分项高频快答（10 题）

1. **续航怎么优化？** → 三层视角 + 先定 SLA + 测量基线 + 数字（专题一）
2. **音频走 BLE 的瓶颈？** → 吞吐测算 32/96 KB/s + 压缩 + 缓冲时延（专题四）
3. **心率数据质量怎么保证？** → 质量标签 + 参考设备误差验证 + 时间戳（专题五）
4. **OTA 到一半断电？** → 双 bank 回滚 + 断点续传 + bootloader 恢复（专题二）
5. **离线同步什么时候会丢数据？** → 设备缓冲满 / App 被杀 / 云端去重，三路补偿兜底（专题三）
6. **你 C/C++ 到什么程度？** → 指针/内存/struct/大小端/volatile + 协作实例（专题六）
7. **EVT 发现协议问题怎么推动？** → 带数据（复现率/影响面）+ 兼容方案（版本协商/双协议）+ 联合评审（专题七）
8. **量产阶段 App 侧职责？** → 产测工具链、兼容矩阵、日志可追踪（专题七）
9. **传感器时间戳不对齐会怎样？** → 融合特征错位、云算法不可复现（专题五）
10. **低功耗下连接不能断怎么办？** → 分层参数 + 场景切换 + 断连快速恢复（专题一 + B7）

## 九、口播串联：把加分项讲成一条产品链

「可穿戴客户端我按四条链看。**功耗链**：SLA、连接档、扫描预算。**OTA 链**：传输、commit、防砖、版本矩阵。**同步链**：设备 seq、手机 pending、冲突以设备状态为准。**数据链**：控制和数据分开，先算带宽再谈音频或传感器。这些链在 EVT 可以松，进 DVT 就要冻协议和回归；试产以后看切片指标，能停。C/C++ 和板级总线我用来读包、对字节，不当固件 owner。」

**英文 60 秒版**：

> I treat the plus items as one wearable loop. Power is an SLA plus radio parameters, not UI polish. OTA is a commit-and-recover problem. Offline sync is sequenced device buffers plus an idempotent phone queue. Sensors and audio are a data plane with clocks and bandwidth math. EVT to production is about what we freeze: protocol, recovery, then a compatibility matrix. I can read C structs and hex with firmware; I do not pretend to own the embedded schedule.
