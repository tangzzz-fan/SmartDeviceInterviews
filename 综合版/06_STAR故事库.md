# STAR 故事库

> 用法：所有故事先用模板填真实经历（【】为占位、标注「示范」的数字为示范值），再压缩成 30 秒电梯版。
> 行为题只讲 1.5–2 分钟，结果必须有数字。**面试里不要讲全部故事：准备十个，上场只用 2–3 个，其中一个必须同时覆盖 BLE + 联调 + 交付（旗舰故事）。**
> STAR = Situation（背景 15 秒）· Task（你负责的结果，不是「我被安排做什么」）· Action（3–5 个可验证动作，含机制不含形容词）· Result（一个指标 + 一个沉淀）。

## ★ S1. 旗舰故事：设备会话层重构（架构 + BLE + 交付）

**面试目的**：证明你能独立负责复杂客户端模块，而不是堆页面。

- **S**：消费级可穿戴 App，扫描、连接、设置页、同步服务各自维护一份 `isConnected`。功能能跑，断连和后台恢复后状态经常撕裂——UI 显示已连接，写入却失败。
- **T**：在不停业务迭代的前提下，把设备会话收成单一状态机，让页面只消费快照。
- **A**：① 画出合法状态和非法跳转，禁止页面直接调 `connect`；② 外部只发意图：`bind` / `connect` / `disconnect` / `reconcile`；③ BLE 回调统一 hop 进会话队列，UI 只拿不可变 snapshot；④ 给非法迁移打断言和日志，方便联调。
- **R**：连接相关崩溃/断言从每周数次降到接近 0（示范值）；新功能接入从「改四处」变成「注册一个命令处理器」；后续 OTA 和同步都挂在同一层上。

**90 秒讲法**：「我负责把设备连接从散落逻辑收成会话层。以前每个页面自己改连接状态，后台一恢复就错。我做了单一状态机和意图入口，页面只渲染快照。结果是连接问题可归因，后续 OTA 和同步都挂在同一层上。」

**追问**：为什么不用现成的单向数据流框架？（founding 节奏以简单可维护为先，状态机纯逻辑可单测就够了。）状态机放哪个并发域？（actor/串行队列，主线程只拿快照。）

## S2. Ownership：接手线上稳定性烂摊子

- **S**：App 上线后 crash-free 只有 98.2%，差评集中在闪退，团队忙于新功能没人牵头。
- **T**：主动揽下「稳定性专项」，目标 crash-free 提升到 99.7% 以上。
- **A**：① 接入 Crashlytics + dSYM 自动符号化，按版本聚类定位 Top10；② 锁定 3 个主要崩溃源（内存泄漏 + 空数据崩溃 + 旧版本兼容）逐一修复；③ 建立 OOM 与卡顿监控，补回归测试。
- **R**：三个月 crash-free 98.2% → 99.8%，差评率下降 40%，沉淀稳定性巡检清单（每周看指标）。

**30 秒电梯版**：App 线上崩溃率 98.2%，没人牵头，我主动立了稳定性专项——先建崩溃聚类，再修 Top3 根因，三个月到 99.8%，并沉淀了每周巡检机制。

**追问**：为什么是这 3 个根因？线上复现不了的崩溃怎么处理？（加现场采集 + 版本二分。）

## S3. BLE 实战：误连与异常断连

**面试目的**：证明 Core Bluetooth 是做过的，不是背过的。

- **S**：试产阶段用户反馈「明明连着，按键没反应」和「连到别人的设备」。
- **T**：把扫描过滤、重连预算和 Ready 定义做对，让连接成功率可测。
- **A**：① 未绑定用 manufacturer data + 接近阈值；已绑定走 identifier，不再靠名字；② `didConnect` 只是 Connecting，Ready 必须发现服务、打开 notify、握手成功；③ 异常断连分类：用户/系统/链路，链路才走有限退避；④ 连接成功率按固件版本和 iOS 版本切片。
- **R**：误连投诉清零（示范值）；某固件版本握手超时被切片切出来，固件修完后该版本连接成功率回升到 99% 量级。

**必须体现**：过滤、Ready 定义、断连分类、指标切片——四个都要讲到。

## S4. 联调排障：按钮无响应（跨 App / 固件）

**面试目的**：证明你不甩锅，能建共同证据。

- **S**：固件和客户端都说「我这边是对的」。现象间歇出现，只在 OTA 失败后的设备上。
- **T**：48 小时内定位层级，并补上以后能自助排查的观测点。
- **A**：① 按 App → 队列 → BLE → 协议 → 固件拆日志点；② 对齐 SN、build、固件版本、时间戳；③ 发现 App 显示已连接，固件卡在非法 OTA 模式，命令被丢；④ 和固件约定非法模式必须重新广播错误码；App 识别后引导恢复，而不是继续写特征。
- **R**：该问题从「会议争议」变成 10 分钟可复现。后续同类问题先看设备模式字节，不再先改 UI。

**可用句式**：「我先不判断是谁的 bug。我要求每一层都有可验证观测点。证据对齐之后，责任自然清楚。」

## S5. 性能：冷启动与连接页卡顿

- **S**：首页启动时同步初始化蓝牙扫描、日志上报、配置拉取，低端机冷启超 3 秒（示范值），连接页掉帧。
- **T**：首屏可交互降到 2 秒内，同时不牺牲已绑定设备的恢复速度。
- **A**：① 启动关键路径只留崩溃捕获和首屏渲染；② 蓝牙会话懒启动，首页先展示 stale 状态后台 reconcile；③ 扫描对象复用，避免每次进页新建 manager；④ 用 signpost 看各段耗时，用崩溃率守住回归。
- **R**：冷启 P50 约 3.2s → 1.6s（示范值），连接页主线程卡顿下降；启动任务清单写进发布检查。

**30 秒电梯版**：冷启 3 秒，我从 pre-main 开始拆指标——减库、去 +load、任务异步化，蓝牙懒连接首页先展示 stale，优化到 1.6s，启动测试挂进 CI 防回归。

**必须体现**：定义指标、拆路径、验证、防回归。

## S6. 工程体系：从「能出包」到「周更可测」

**面试目的**：证明 founding 工程师会建秩序。

- **S**：早期两个人出包靠手编，符号表经常丢，线上崩溃看栈看不懂，联调包和正式包混。
- **T**：两周内做到每次提交出可测包，崩溃可符号化，关键链路有冒烟。
- **A**：① CI 打 TestFlight，build 号绑定 git sha；② 崩溃收集 + dSYM 上传；③ 连接/握手/断连三条冒烟跑在 PR；④ 发布清单：协议版本、固件兼容矩阵、已知失败路径。
- **R**：联调不用问「你这是哪一包」；崩溃从无法处理变成可分类；迭代速度没变慢，返工变少。

**取舍型讲法**（可直接答「讲一个你做取舍的例子」）：「不在 founding 第一周上完整模块化包管理，先做会话边界和崩溃符号化。因为当时最大的浪费是联调不可归因，不是编译边界。」

## S7. 模糊推进：协议未定先打通最小闭环

**面试目的**：证明你能在模糊里推进，而不是等完美文档。

- **S**：产品还在改交互，固件协议每周变字段。如果等冻结再写 App，试产窗口会错过。
- **T**：两周内打通：绑定、连接、读一个关键状态、断连恢复。功能字段允许后补。
- **A**：① 先冻握手、错误码、版本号，功能 TLV 可扩展；② App 用 profile 切换固件方言，而不是写死一版；③ 每天和固件 15 分钟对一次包示例，不开会空聊；④ 明确告诉产品：这周交付闭环，不交付全部设置项。
- **R**：试产当天能连、能看状态、能抓日志；后续设置项没有推翻会话层。

**面试官关注点**：你如何做优先级、如何拒绝范围膨胀、如何让跨团队形成节奏。

## S8. OTA 从 0 设计

- **S**：硬件要量产，OTA 完全没有：固件更新靠返厂。
- **T**：设计并实现 OTA 方案，支持断点续传、失败回滚。
- **A**：① 与固件团队定义 DFU 服务与包格式；② App 实现分块传输 + 每包 CRC + 断点续传；③ 推动固件做双 bank 回滚；④ 加电量保护与批量升级队列。
- **R**：OTA 成功率 99%+（示范值），返厂升级成本归零；产测工具链复用同一套协议。

**追问**：断点续传的 offset 存在哪？（App 持久化 + 设备侧可查已接收进度，以设备为准。）升级到一半设备重启怎么处理？（未 commit 前旧镜像可启动 + reboot 窗口内循环 retrieve + 超时引导恢复模式。）

## S9. 失败复盘：一次发布事故

- **S**：【一次发布】导致线上【崩溃/数据异常】，影响用户 x%。
- **T**：止血 + 复盘，确保不再犯。
- **A**：① 先远程开关/下架止血；② 定位根因是【没覆盖的场景/测试缺失】；③ 补测试与监控告警；④ 发布流程加灰度门槛。
- **R**：影响恢复时间 x 分钟；同类事故 6 个月未再发生。

**追问**：你自己在事故中的责任是什么？（必须有诚实答案，不甩锅。）

## S10. AI-native：AI 融入研发流程

- **S**：核心模块测试覆盖率只有 30%，排障靠人肉翻日志。
- **T**：把 AI 深度融入测试与排障，产出可量化收益。
- **A**：① 用 AI 批量生成 BLE 状态机与协议解析的单元测试，我负责审边界与正确性；② 联调日志交给 AI 对照分析，标注时间线差异；③ AI 做 PR 初审（协议/并发/内存风险点）；④ 沉淀团队 AI 使用规范（哪些能信、哪些必须人审）。
- **R**：核心覆盖率 30% → 78%（示范值），联调排障时间缩短约 40%。

**追问**：AI 生成测试你如何保证质量？（注入已知答案的黄金用例做锚点。）AI 建议错了你怎么发现？——准备一个「AI 出错被我拦下」的反例（见 [03_题库与答案/06-行为动机与AI.md](./03_题库与答案/06-行为动机与AI.md) AI2 幽灵重连案例）。

## 加分项短故事补丁（30 秒级）

- **S11 功耗档**：S 跟手优先导致续航不达标。T 不牺牲打开 App 时的新鲜度，把空闲电流压回去。A interactive/idle 两档、前台才高频、重连预算。R 续航回到目标量级，状态延迟仍在 SLA 内。
- **S12 离线错序**：S 离线事件按墙钟合并，时区打乱顺序。T 保证顺序和幂等。A 设备 seq 为真相，手机只存 offset，ack 后才删缓冲。R 错序客诉消失。
- **S13 试产重复广播名**：S 产线烧录导致广播名重复，用户误绑。T 绑定可靠性问题在试产暴露。A 绑定改 identifier + SN 校验，不再用名字当主键。R 误连/误绑可解释，产线问题能按 SN 回流。
