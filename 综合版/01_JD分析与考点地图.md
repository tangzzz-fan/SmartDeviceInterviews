# JD 分析与考点地图

> 一句话判断：这份 JD 的核心不是「会写 iOS App」，而是「能把 AI 可穿戴产品的 iOS 端从 0 到 1 扛起来，并和深圳硬件/固件、硅谷软件/产品一起把设备真正交付出去」。

## 一、岗位速览

| 维度 | 内容 |
| --- | --- |
| 岗位 | Founding iOS Engineer（Nirva 国内团队首批 iOS 工程师） |
| 产品 | AI 可穿戴设备 |
| 团队 | 国内（iOS/硬件/嵌入式）+ 硅谷（软件/产品/研究） |
| 阶段 | 从研发、测试到正式交付，0→1 |
| 本质 | 三个角色叠加：**架构师**（0 到 1 定架构）+ **软硬结合工程师**（BLE/OTA/联调是核心交付）+ **基建负责人**（CI/CD、监控、测试自己搭） |

**隐含信号**：
- "Founding" = 前 6-12 个月可能只有你一个人写 iOS，独立决策能力 > 团队协作话术。
- 三地协作 = 沟通效率和文档能力被放大。
- "从研发、测试到正式交付" = 面试会问完整生命周期，尤其量产阶段。
- "高度 AI-native" 单列 = 会深挖你的真实用法而非泛泛而谈。

## 二、五大能力簇拆解

| 能力簇 | JD 原文依据 | 面试怎么考 | 权重 |
| --- | --- | --- | --- |
| A. iOS 核心工程 | 架构设计、Swift、并发、内存、生命周期、网络、存储、后台任务 | 深挖题：并发模型、内存泄漏、后台同步；设计题：网络层/存储选型 | 20% |
| B. BLE 与设备通信 | Core Bluetooth、配对、连接管理、状态同步、数据传输、异常恢复、OTA | 场景题：断连重连、OTA、数据一致性；系统设计必出 | 25% |
| C. 软硬件联调 | 定义通信协议、系统接口、问题定位、系统验证 | 排障题：联调问题定位；协议设计 | 15% |
| D. 性能与基建 | 启动、内存、功耗、稳定性、后台、数据同步、测试、CI/CD、监控 | 体系题：稳定性怎么建；数据题：启动/崩溃/功耗怎么优化 | 18% |
| E. Ownership + AI-native + 英文 | 0→1、模糊环境、AI 融入研发、与硅谷英文协作 | 行为题 + AI 案例 + 英文面 | 22% |

**备考优先级**：BLE > iOS 架构 > 联调案例 > 性能基建 > 行为故事 > AI-native > 英语。

## 七、红线项与主动埋点

**红线项**（回答空泛风险极高）：
1. Core Bluetooth / BLE 没做过却硬说做过
2. 只讲 UI 和业务逻辑，讲不出工程基础设施
3. 没有任何联调经验，又无法迁移说明
4. 只会背概念，讲不出真实故障案例
5. 英文协作表达非常弱，无法做基本技术同步

**必须主动展示的证据点**（不等被问）：
1. 一个完整交付故事（需求→上线→运维，端到端 ownership）
2. 一个疑难 bug 定位故事（跨层：App ↔ 系统 ↔ 硬件）
3. 一个从 0 搭建的东西（模块/组件库/CI/监控，「我建的」而非「我用的」）
4. 一个数据结果（启动提速 X%、崩溃率降至 Y、连接成功率 Z%）
5. 对 Nirva 产品的思考（结尾提 1-2 个有质量的产品/技术问题）

**出题风格预判**（startup + AI-native 公司）：少问八股多问「你实际怎么做的」；系统设计题概率极高（BLE OTA / 数据同步 / App 架构三选至少一）；追问深；文化面直接。
