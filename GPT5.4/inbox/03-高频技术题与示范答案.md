# 高频技术题与示范答案

## 使用方式

这不是背诵稿，而是答题骨架。每道题都建议按以下结构回答：

1. 先给结论
2. 再讲机制
3. 再讲真实场景
4. 最后讲 trade-off 或异常处理

## 模块 1: Swift 并发与线程模型

### Q1: Swift Concurrency 和 GCD 的关系是什么？

回答骨架：

- GCD 是较底层的并发调度机制，Swift Concurrency 是更高层的语言级并发模型。
- `async/await` 让异步流程更线性、更易维护。
- `Task`、`TaskGroup`、`actor` 帮助我们管理结构化并发与数据隔离。
- 在 iOS 工程里，我会根据历史代码和场景决定是否逐步迁移，而不是一次性重写。

追问点：

- MainActor 的作用
- actor 是否能完全替代锁
- cancellation 如何处理

### Q2: 你如何避免并发下的数据竞争？

回答骨架：

- 优先通过数据所有权和隔离设计避免共享可变状态。
- 需要共享时优先考虑 `actor`、串行队列或受控同步机制。
- 核心不是“加锁”，而是先把状态边界设计清楚。
- 如果是 BLE 连接状态、同步状态这类关键状态，我会集中到单一状态管理器，避免多个模块各自维护。

## 模块 2: 内存管理

### Q3: ARC 下最常见的内存问题是什么？

回答骨架：

- 常见的是循环引用、对象生命周期过长、缓存失控和闭包捕获不当。
- 在 iOS 中我会重点检查 delegate、timer、closure、notification、Combine/异步订阅。
- 真正有效的方法不是背 `weak` / `unowned`，而是先判断所有权关系是否合理。

### Q4: 你如何定位内存问题？

回答骨架：

- 先定义现象：泄漏、峰值过高还是频繁抖动。
- 再用 Instruments、Xcode memory graph、业务日志去定位对象生命周期。
- 如果是复杂模块，会结合页面进入退出、设备连接切换、后台前台切换做场景化排查。

## 模块 3: 生命周期与后台任务

### Q5: iOS 后台任务有哪些约束？

回答骨架：

- iOS 后台运行不是无限制的，是否允许取决于具体场景和系统策略。
- 需要区分普通后台切换、蓝牙相关模式、后台刷新、长连接场景和系统唤醒机制。
- 设备类产品要特别注意后台恢复后的状态一致性，而不是假设连接永远在线。

### Q6: App 从后台恢复后，设备状态不一致怎么办？

回答骨架：

- 不直接信任内存中的旧状态。
- 恢复时先做状态重建：连接状态、服务发现状态、设备当前模式、本地缓存待同步队列。
- 需要一个明确的 reconciliation 过程，而不是页面一打开就直接展示旧值。

## 模块 4: Core Bluetooth / BLE

### Q7: BLE 连接的完整流程是什么？

回答骨架：

1. 扫描设备并做过滤。
2. 发现目标设备后发起连接。
3. 连接成功后发现 service 和 characteristic。
4. 建立通知订阅或写入通道。
5. 做状态同步和首包校验。
6. 进入稳定通信阶段。
7. 对断连、超时、失败做恢复处理。

### Q8: 扫描不到设备，你会怎么排查？

回答骨架：

- 先确认设备端是否在广播、广播间隔和广播内容是否正确。
- 再看 App 侧扫描参数、权限、蓝牙状态、前后台影响。
- 再结合现场因素，例如距离、干扰、系统蓝牙状态异常。
- 排查时优先拿证据，不靠猜。

### Q9: BLE 断连后，你会怎么设计恢复策略？

回答骨架：

- 先区分主动断开还是异常断开。
- 需要有重连策略，但不能无脑无限重连。
- 要考虑重试次数、指数退避、用户提示、是否需要重做服务发现。
- 如果存在命令队列或待同步数据，还要考虑幂等和恢复后补发。

### Q10: 你如何处理 BLE 数据包和状态同步？

回答骨架：

- 先定义协议层边界：消息格式、序列号、校验、应答机制。
- 如果有 MTU 限制，需要考虑分包、重组和顺序。
- 状态同步不能只靠“最后一次消息”，应有明确的状态源与纠偏机制。

## 模块 5: OTA

### Q11: 你如何设计一个 OTA 升级流程？

回答骨架：

1. 检查设备版本和升级条件。
2. 下载并校验固件包。
3. 进入升级模式。
4. 分片发送并确认进度。
5. 升级完成后重启设备。
6. 重新建连并校验版本与功能。
7. 对失败场景制定恢复策略。

重点强调：

- 断点恢复
- 失败回滚
- 版本兼容
- 安全校验

## 模块 6: 性能与稳定性

### Q12: 你如何做启动优化？

回答骨架：

- 先分阶段量化：冷启动、热启动、首屏可交互时间。
- 再看初始化是否过重，例如同步 IO、过早创建对象、阻塞主线程。
- 优化原则是延迟非关键初始化、减少主线程压力、用数据验证效果。

### Q13: 你如何做稳定性治理？

回答骨架：

- 先建立崩溃、卡顿、关键流程失败率等核心指标。
- 再建设日志、埋点、错误分类和告警。
- 对高频问题做专题治理，而不是零散修 bug。

## 模块 7: 联调与问题定位

### Q14: 软硬件联调时，如何定位问题属于哪一层？

回答骨架：

- 我会按 `App -> BLE 链路 -> 协议 -> 固件 -> 服务端` 分层排查。
- 每层都要拿到证据，不做情绪化归因。
- 如果现象是“按钮点击后设备没反应”，我要先确认命令是否发出、设备是否收到、是否返回 ack、状态是否上报、页面是否正确消费状态。

### Q15: 你如何和固件工程师高效合作？

回答骨架：

- 用结构化问题单，而不是口头说“好像有问题”。
- 提供时间点、设备版本、App 版本、日志、复现路径、预期与实际结果。
- 共同对齐观测点，缩小分歧空间。

## 模块 8: 工程体系

### Q16: 作为 founding iOS engineer，你会优先建设什么？

回答骨架：

1. 基础项目结构与模块边界
2. 日志与问题定位能力
3. 最小必要测试
4. CI/CD 与发布流程
5. 核心业务链路的质量门禁

说明：

- 创业早期不能把基础设施做成大工程，但不能完全没有秩序。

## 模块 9: AI-native

### Q17: 你如何把 AI 融入研发流程？

回答骨架：

- 用 AI 辅助方案拆解、代码草拟、测试用例生成、日志分析和文档整理。
- 但关键逻辑、协议边界、性能敏感代码和发布前验证，我不会完全依赖 AI。
- 我更关注的是把 AI 变成稳定工作流，而不是单次问答。
