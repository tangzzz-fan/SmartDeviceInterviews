# 模拟面试脚本与执行清单

## 目标

把前面的材料从“看过”变成“能说出来”。

## 模拟轮次设计

### Round 1: 电话筛 / HR 初筛

目标：

- 解释你为什么匹配这个 JD
- 建立靠谱、清晰、ownership 强的第一印象

建议问题：

1. 请做一个自我介绍。
2. 为什么想做这个岗位？
3. 你过去做过哪些相关项目？
4. 为什么你适合创业型团队？

示范回答要点：

1. 自我介绍控制在 60 到 90 秒，突出 `iOS + 复杂模块 + 跨团队协作 + ownership`。
2. 岗位动机要强调这是 `移动端 + 设备通信 + 产品交付` 的复合型角色。
3. 相关项目不求全，优先讲最接近设备、稳定性、联调、工程建设的经历。
4. 创业型团队匹配度要强调你能在目标不完全清晰时先澄清、再推进、再补秩序。

通过标准：

- 2 分钟内讲清核心背景
- 不空泛
- 能自然带出 iOS、设备、跨团队和 ownership

### Round 2: 技术一面

目标：

- 验证 iOS 基础是否扎实
- 验证 BLE 和设备通信是否可信

建议问题：

1. 讲一下你理解的 iOS 并发模型。
2. ARC 下常见内存问题有哪些？
3. BLE 连接全流程是什么？
4. 断连和状态不一致你会怎么处理？
5. 后台恢复后设备状态错乱怎么办？

示范回答要点：

1. 并发题先讲 `语言层抽象 + 调度机制 + 场景取舍`。
2. 内存题先讲 `所有权关系`，再讲 `weak / closure / observer / timer` 等常见坑。
3. BLE 题必须能完整口述 `扫描 -> 建连 -> 服务发现 -> 通知/写入 -> 同步 -> 恢复`。
4. 断连恢复要体现 `重试策略、状态机、幂等处理、用户提示`。
5. 后台恢复要体现 `状态重建`，不要假设内存状态仍然可信。

通过标准：

- 每题先给结论
- 能讲机制
- 能落到真实场景

### Round 3: 深挖 / 系统设计 / 联调

目标：

- 验证你是否真正适合这个岗位的核心场景

建议问题：

1. 如果让你从 0 搭一个设备型 iOS 客户端，你先做什么？
2. 你会如何设计 BLE 状态机？
3. 你如何设计 OTA 升级链路？
4. 你如何和固件团队一起定位一个疑难问题？
5. 你如何建设日志、监控、测试和发布流程？

示范回答要点：

1. 从 0 搭建优先讲 `核心链路、状态边界、日志观测、最小工程秩序`。
2. BLE 状态机要讲清状态、事件、转换条件和异常分支。
3. OTA 要覆盖 `版本检查、校验、分片传输、失败恢复、升级后校验`。
4. 联调题要强调 `统一日志、统一时间线、逐层归因`。
5. 工程建设要讲 `先建最小闭环，不做过度基础设施`。

通过标准：

- 能讲架构
- 能讲边界
- 能讲取舍
- 能讲失败场景

### Round 3.5: 加分项深挖

目标：

- 验证你是否具备设备型产品更深一层的系统认知
- 验证你是否能把“了解”讲成可信的工程判断

建议问题：

1. 你如何看低功耗优化，通常会从哪里入手？
2. 离线数据同步最难的点是什么？
3. 音频采集或传感器数据处理有哪些工程约束？
4. 你如何理解协议设计、嵌入式约束和客户端的协作边界？
5. EVT / DVT / PVT 分别意味着什么，客户端要怎么配合？

示范回答要点：

1. 低功耗不要只讲代码微优化，要讲 `采样、扫描、同步、唤醒、后台策略`。
2. 离线同步要讲 `谁是源、如何幂等、如何补发、如何处理冲突`。
3. 音频 / 传感器要讲 `采样率、缓冲、实时性、功耗、数据质量`。
4. 协议和嵌入式要讲 `状态机、错误码、版本兼容、ack、资源约束`。
5. EVT / DVT / PVT 要讲阶段目标差异，不要只背名词。

通过标准：

- 不空泛
- 能讲系统约束
- 能讲取舍
- 能诚实说明直接经验边界

### Round 4: 行为面 / Founder Mindset

目标：

- 验证 ownership、沟通与模糊环境推进能力

建议问题：

1. 讲一个你主动推动的事情。
2. 讲一个你在信息不完整时做判断的例子。
3. 讲一个跨团队冲突或分歧。
4. 讲一个高压排障案例。

示范回答要点：

1. 主动推动题重点不是辛苦，而是你为什么判断这件事值得做。
2. 信息不完整题要讲你如何在证据不足时先建立假设和验证路径。
3. 跨团队分歧题要讲你如何把讨论从观点拉回事实。
4. 高压排障题要有 `止血 -> 定位 -> 复盘` 三段式。

通过标准：

- 不只是讲苦劳
- 要讲判断力、推进力和结果

## 反问面试官的问题

建议准备以下问题：

1. 当前 iOS 端和设备端协作中最难的挑战是什么？
2. 现在 BLE / OTA / 同步链路上最大的工程风险在哪里？
3. 这个岗位在前 3 个月最重要的交付目标是什么？
4. 团队目前如何做软硬件联调、日志采集和问题跟踪？
5. 对 founding engineer 来说，什么样的人会做得特别好？

为什么这些问题有用：

1. 能看出团队真实难点是不是集中在联调、稳定性还是交付节奏。
2. 能判断他们对工程问题是否有清晰认知，而不只是笼统说“挑战很多”。
3. 能帮你确认入职后是偏救火、偏建设，还是偏产品落地。
4. 能看出他们是否已经建立基础观测与协作机制。
5. 能反向获取他们对这个岗位的隐性期待。
