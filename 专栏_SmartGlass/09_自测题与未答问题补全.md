## 一、语音链路自测题（7 题）

### 1. 流式 ASR 的音频包建议多长？为什么不能忽快忽慢？
每包 100–200ms（200ms 最优）。服务端 VAD、断句、包等待超时全部建立在连续均匀的音频流上：帧间隔抖动会被误判静音而提前断句（丢尾字），或触发包等待超时（如 `45000081`）。所以采集用独立线程 + 固定节奏定时器，发送队列不被 UI 阻塞，结束显式发 final 包。

### 2. 大模型流式 ASR 鉴权需要哪几个 header？X-Tt-Logid 有什么用？
请求头：`X-Api-Key`、`X-Api-Resource-Id`（计费资源，如 `volc.seedasr.sauc.duration`）、`X-Api-Request-Id`（uuid）、`X-Api-Sequence: -1`。`X-Tt-Logid` 在握手响应头返回，是服务端为该请求生成的日志 id——排查和提工单时拿它对账，比自己描述「刚才那次失败」有效得多。

### 3. 一句话识别的 1001 和大模型流式的 45000001 分别代表什么？
两者都是**请求参数无效**（缺必需字段 / 字段值无效 / 重复请求），只是协议族不同：1001 属一句话识别（SAUC 同族二进制协议），45000001 属大模型流式 ASR。排查方向一致：对照契约查请求 JSON 与音频参数，而不是怀疑服务挂了。

### 4. TTS 双向流式里打断用哪个事件？wav 为什么不适合流式？
打断用 `CancelSession`（同一连接还可以复用多会话）。wav 带文件头，流式分块合成时每块都会重复文件头，拼接播放会杂音/解码异常；流式场景官方建议 pcm 或 ogg_opus。

### 5. 端到端时延超标的三个可能瓶颈？怎么逐个定位？
① **建连开销**（每次对话重新 TCP+TLS）：看 t2→t4 是否偏高 + 抓包确认连接是否复用（`wsReuse` 打点）；② **LLM 首 token**（通常是大头）：看 t4→t5，属云端生成速度，App 侧能做的是切句即送 TTS 掩盖它；③ **播放保守**（预缓冲过大/播放器初始化晚）：看 t6→t8，调预缓冲阈值并监控 underrun。工具就是 t0–t8 分段对比 + 单变量对照。

### 6. 半开 WebSocket 怎么发现、怎么恢复？
发现：应用层心跳（10–15s ping，连续 3 次无 pong 判死）；或「持续发音频但长时间无任何回包」也可疑。恢复：主动断开 → 指数退避重连（1s/2s/4s…封顶 30s）→ 重连后重发会话上下文不丢对话 → 监听网络切换事件主动重建 → 全程 Request-Id 对账。详见 02-C7。

### 7. 降级预案有哪几级？
ASR 失败：重试一次 → 降级「转写失败」文字提示；LLM 超时：预设兜底话术；TTS 失败：展示文本；全链路不可用：端侧弱网提示，用户永远看得到结果。架构级：协议层抽象不绑定单一厂商，供应商可开关切换。

## 二、Flutter / Android 自测题（6 题）

### 1. Activity 旋转屏幕会发生什么？状态怎么保存？
默认销毁重建：走 `onPause → onStop → onDestroy` 后重新 `onCreate`。瞬时状态用 `onSaveInstanceState` 保存、`onCreate`/`onRestoreInstanceState` 恢复。对本题的引申：**BLE 连接绝不能由 Activity 持有**，否则旋转就断——连接放 Service 或进程级 BleManager。

### 2. ANR 是什么？插件回调里能直接 result.success 吗？重复调用会怎样？
ANR = Application Not Responding，主线程被阻塞超过时限（输入事件约 5s）系统弹「无响应」。插件回调里的 `result.success` **必须切回主线程**再调——平台消息只在 Platform Thread 安全收发，后台线程调用消息会丢、Dart Future 永远挂起（我修过的 1/500 挂起就是这个）。`result` 只能调用一次，重复调用直接抛异常（Reply already submitted），所以异步路径要做防重入。

### 3. Flutter 里如何把耗时计算放到后台？Isolate 和线程的区别？
`compute()`（短任务）或 `Isolate.spawn`（长生命周期，自己管 SendPort，页面销毁要 kill）。区别：原生线程共享内存、要靠锁保证安全；Isolate 不共享内存、只传消息（对象默认拷贝，大二进制用 `TransferableTypedData`）。代价换安全，适合切句、CRC、大 JSON 这类纯 CPU 活；硬件回调（BLE/音频）仍在原生线程，不进 Isolate。

### 4. EventChannel 的 onCancel 不实现会有什么问题？
Dart 侧 cancel 后原生收不到通知，会继续扫描/推送：① 扫描不停 = 耗电；② 持续往已释放的 EventSink 推数据，轻则静默错误、重则崩溃；③ 原生侧监听器泄漏。所以 `onCancel` 必须置空 sink 并停掉底层订阅，与 `onDetachedFromEngine` 一起构成插件的「退出纪律」。

### 5. federated plugin 和普通 plugin 的区别？为什么大厂要用 federated？
普通插件一个包混装双端实现；federated 拆三层：platform_interface（Dart 契约）+ 门面包 + 各平台独立实现包（`_android`/`_ios`）。好处：双端独立演进互不阻塞、可以只替换单端实现、新增平台（Web/桌面）不动存量代码、契约层可单独做测试。本质是「契约先行」在插件工程的应用。

### 6. Android 14 前台服务有什么新要求？
必须声明 `foregroundServiceType`（如 `connectedDevice`、`microphone`、`mediaPlayback`、`specialUse`）并申请对应权限；`specialUse` 还要在 Manifest 声明用途理由。眼镜 App 的保连与采音正好对应 `connectedDevice` + `microphone` 类型。再往上是厂商 ROM 的电池策略，需要电池白名单引导。

## 三、BLE 自测题（5 题）

### 1. GATT 133 和 8 分别代表什么？怎么处理？
133 = GATT_ERROR：含义模糊，常见是对端主动断开、协议栈异常或配对问题；8 = 连接超时。处理：不直接暴露给用户，映射进统一错误码表（133 → `connect_timeout`/`device_disconnected`），原始 status 打日志；按类别决定重试策略，133 常需要重新扫描而不是原地无限重连。

### 2. 为什么 BLE 传大文件要先协商 MTU？默认 MTU 是多少？
默认 ATT MTU 23 字节（3 字节头 + 20 字节 payload）。不协商就按 20 字节切包：包数量爆炸、每包都有协议开销，OTA 和信令又慢又碎。Android 必须主动 `requestMtu()`（最大 517），在 `onMtuChanged` 拿到实际值后按 mtu−3 分包；iOS 系统自动协商，读 `maximumWriteValueLength`。协商失败要能退回 20 字节兜底。

### 3. Android 12 扫描需要哪几个权限？为什么 11 及以下还要定位权限？
12+：`BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT`（运行时授权）；`BLUETOOTH_SCAN` 加 `neverForLocation` 标志可免定位权限。≤11：`BLUETOOTH`/`BLUETOOTH_ADMIN`（安装时）+ `ACCESS_FINE_LOCATION`——因为 BLE 扫描结果理论上可被用于推断用户位置，系统把扫描当作位置能力管理，这是隐私模型决定的，不是技术缺陷。

### 4. Notify 和 Indicate 的区别？传音频帧选哪个？
Notify 无 ACK、快、尽力投递；Indicate 有 ACK、可靠但有流控、更慢。音频/高频传感器数据用 Notify + 应用层 seq 检测丢帧（丢旧保新或选择性重传）；关键控制应答可以用 Indicate 或 write-with-response。但先说一句更对的话：**16k PCM 这种量级根本不该走 GATT**，走数据面或经典蓝牙音频，GATT 只放信令。

### 5. 手机息屏 5 分钟，眼镜还连着吗？怎么保证？
不保证——Doze/后台限制、厂商 ROM 杀进程都可能断。保证手段：① 前台服务持有连接（Android 14 声明 type）；② `autoConnect=true` 让系统在后台帮忙捞回（慢，且 ROM 不保证）；③ 连接参数合理（interval/latency/supervision timeout 权衡功耗与恢复速度）；④ 电池优化白名单向用户说明用途后申请。iOS 对应 bluetooth-central 后台模式 + State Restoration，且明确「有机会恢复、不是保证唤醒」。产品上接受后台能力有上限，App 回来先问眼镜当前态。

## 四、蓝牙开发五大难点的工程回应（GPT5.4 只列了现象，此处补齐）

| 难点 | 现象 | 工程回应 |
|------|------|----------|
| 扫描结果不稳定 | 广播间歇、权限缺失、系统限制导致发现率低 | Service UUID 过滤；扫描窗口匹配设备广播周期；权限矩阵前置检查；扫描成功率按阶段打点，不报一个总数 |
| 连接容易断 | 设备休眠、距离变化、系统回收、前后台切换 | 重连状态机 + 指数退避；断连原因分类驱动策略；前台服务持连接；重连后完整重建（发现服务+重开 Notify） |
| 状态非常异步 | 调了 connect 不代表连上 | 一切以回调为准收敛进状态机；每个状态迁移带超时；未 Ready 禁止业务指令；非法事件打日志丢弃 |
| 数据包与协议解析 | 长度限制、并发写静默失败 | MTU 协商后按 mtu−3 分包；帧 = seq/type/payload/crc；GATT 操作串行队列；接收端按 seq 重组检丢 |
| 机型兼容性 | 厂商蓝牙栈碎片化 | 真机矩阵（不只模拟器）；小米/华为后台行为单独验证；成功率看板按机型×系统版本×固件拆分归因 |
