## 一、低功耗优化

### 1.1 先定边界

眼镜电池紧。功耗大头通常在：**射频常开、WiFi 常驻、无效扫描、无意义唤醒、音频通路空转**。  
App 控得了的是「场景策略」；固件控的是 interval、TX power、广播间隔。面试要主动切开。

### 1.2 你做过的（硬讲）

**策略一：控制面常驻、数据面按需。**  
BLE 心跳 + 打断常开，用户开对话才拉 WiFi。WiFi 未 ready 禁止大流量，避免半连接空耗。这是架构级省电，比「循环里 sleep 一下」值钱。

**策略二：扫描要贵。**  
已绑定设备不靠长扫。Service UUID 过滤；首次配对才扫描并设超时。后台狂扫是 AccuBattery 上的典型凶手。

**策略三：心跳自适应。**  
数据面有流量就抑制心跳；静默超过数秒再探活。WiFi 断了才加密探测。固定 100ms 心跳是耗电设计。

**策略四：音频通路用完释放。**  
会话结束停采、停播、放焦点。Speaking 乱开 ASR 既回声又耗电。

### 1.3 度量方法论（没眼镜电流计也能讲）

不要装做过实验室：

> 功耗专项我没拿电源分析仪画过电池曲线。方法论和启动优化一样：固定场景基线 → 归因子系统 → 再改。
>
> 手机侧：Instruments Energy Log 看 CPU / 网络 / 蓝牙唤醒；os_signpost 标扫描窗口、WiFi 建链、会话时长，对齐谁在唤醒。线上用 MetricKit 看长尾。
>
> 拆实验：只改扫描占空比、只改 notify 聚合、只改「WiFi 何时拉起」，一次一个变量。
>
> 眼镜侧 mA：要固件配合电流计或电量计寄存器。App 给场景标签（Idle / Listening / Speaking），两边时间轴对齐。

### 1.4 预算口径（设计题）

待机：只 BLE，长 interval（这是固件参数，App 发「进入待机」信令）。  
对话：允许 WiFi + 音频，会话结束立刻拆数据面。  
用户心智：后台连接类 App 一天几个点电量是体验红线，超了先查唤醒不是先查算法。

**iOS 连接参数：** App 不能设 connection interval。设备发 L2CAP Connection Parameter Update，系统有自己的接受区间。你只能和固件约定：待机要长 interval，开对话再请求短 interval。

**Android：** `requestConnectionPriority()` 有限；扫描 `SCAN_MODE_LOW_POWER` vs `LOW_LATENCY`。前台对话用低延迟，后台必须降下来。

### 1.5 追问短答

**App 耗电怎么归因？** 先问是否只戴眼镜、是否后台、是否一直对话。Energy 对齐蓝牙/网络。常见是扫描和 WiFi 没关。  
**和固件吵功耗？** 带场景时间戳和 RSSI，不带「你们芯片费电」。  
**定位和蓝牙一起开？** 眼镜主路径不要叠持续定位。

## 二、设备 OTA

### 2.1 一句话

OTA 不是把 bin 发出去。失败模式：下到一半损坏、分包丢、写 Flash 断电、校验过了激活起不来、App 显示成功设备还在旧槽。

### 2.2 眼镜项目怎么挂

大文件走 **WiFi 数据面**（见双链路）。BLE 只发「开始升级 / 进度查询 / 取消 / 当前 slot」。  
App 职责：版本检查、包下载与签名校验、传文件、进度与不可断电提示、失败后问设备仍能否启动。  
固件职责：双槽位或救援镜像、写 Flash、激活、回滚。

没有亲自写过 bootloader 就说：

> 双槽和回滚在设备侧。我负责的是升级会话状态机和传输可靠性。BLE 配网里用过的序号、窗口、CRC、断点，搬到 OTA 数据面是同一套。

### 2.3 App 侧状态机（默画）

```
Idle
  → CheckVersion     云端/本地版本与兼容矩阵
  → Download         HTTPS 断点续传，写临时文件
  → Verify           整包 hash / 签名（算法以项目为准，不编）
  → Precheck         电量、温度、RSSI/WiFi 质量门槛
  → Transfer         分片 + seq + ACK，进度持久化
  → DeviceVerify     等设备校验完成，不是发完即成功
  → Activate         明确「不可断电」窗口
  → Confirm          重启后读版本 / slot
  → Success / Rollback / Failed
```

原则：

- 禁止「写成功 = 升级成功」
- 进度游标在设备或双方约定，重连按游标续，不从头灌
- 电量低、通话中、弱网禁止进入 Transfer
- 强制 OTA 只留给安全漏洞；日常允许旧固件 + 新 App 降级能力

### 2.4 BLE OTA 若被追问

眼镜主路径是 WiFi。若小包或无 WiFi 降级：

- MTU 动态切包，失败退 20B
- Write without response + 应用层窗口，否则太慢
- Android GATT 必须排队
- 控制面仍走 BLE：取消升级不能跟数据挤一条堵车的路

### 2.5 兼容矩阵（量产相关）

App vN 要标明支持固件 [min, max]。新 App 连旧固件：隐藏新能力，不崩。新固件连旧 App：设备能力表让 App 发现，而不是假定特征都在。

## 三、离线数据同步

眼镜不是「云笔记同步」，是 **命令和状态在弱网下不丢、不重、不乱序**。

### 3.1 三源不要搅在一起

| 源 | 权威 | 例子 |
|----|------|------|
| 设备 reported | 当前硬件事实 | 电量、是否在录音、slot |
| 本地 desired / 队列 | 离线时用户意图 | 未发出的打断、未完成 OTA |
| 云 | 账号、会话历史、固件包 | 对话记录、版本元数据 |

冲突：近场以设备为准（电量不能听云的）；账号类以云为准；未完成命令重连后按 commandId 幂等重放或丢弃过期 TTL。

### 3.2 命令生命周期（配网 SDK 同构）

```
created → sent → acked → applied → verified
                 ↘ timeout / failed / expired
```

「HTTP 200」或「BLE write 成功」≠ 设备执行成功。UI 转圈必须绑 verified 或明确 timeout。

眼镜：打断指令必须有 ACK；会话中途 App 被杀，回来先问眼镜处于 Listening 还是休眠，再决定是否重放。

### 3.3 离线策略分层

- **控制类**（停播、断开）：本地立即 desired，近场能发就发，云不是前置条件  
- **对话历史**：可先落本地，上网再同步；冲突用 sessionId + 时间，不搞复杂 CRDT，除非被追问再提 LWW  
- **固件包**：只 Wi-Fi + 充电或电量阈值下载  
- **过期命令**：短 TTL 的「开始录音」过期就丢，避免迟到误触发

弱网音频队列（02-C6）就是离线/弱网同步的兄弟问题：有界、丢旧保新、恢复后重建 session 不灌过期 PCM。

### 3.4 后台同步四件套（被问 iOS 时）

| 机制 | 干什么 | 不要当成 |
|------|--------|----------|
| BLE State Restoration | 有机会恢复连接 | 保证保活 |
| 真实音频会话 | 对话中合法后台 | 静音骗后台 |
| BGTaskScheduler | 充电/Wi-Fi 时同步历史、查 OTA | 心跳保活 |
| Silent push | 尽力通知有新版本 | 可靠通道 |

Android：前台服务只在真正连接/录音时用，完了必须停，否则是耗电和商店问题。

## 四、音频采集与传感器数据

音频是你最硬的传感器经历。IMU 没有产品经历就**不要编**；被问传感器，说同构模型。

### 4.1 采集契约（眼镜）

- 16k / 16bit / mono PCM（或 SDK 指定编码），端云必须一致  
- 帧长固定（如 20ms），每帧带时间戳，才能和 TTS 下行做 AEC 参考对齐  
- 眼镜端粗 VAD 减无效上行；手机端再判端点——这是带宽也是功耗  
- 有界队列 + 弱网丢旧保新，见 02-C6

### 4.2 处理管线（App）

```
设备采样 → 传输（WiFi）→ 有界缓冲 → 契约检查
  → ASR 上行 / 本地预览波形（只发峰值）
  → 播放下行 → jitter buffer → 焦点
```

传感器（IMU、光感）换皮同一条：

- 定频 notify 或批量  
- 应用层帧：seq + 类型 + payload + crc  
- RingBuffer，生产快于消费就丢旧（姿态）或阻塞+背压（关键事件）  
- 时间戳对齐：眼镜时钟 vs 手机时钟，用采样序号比墙钟更稳  
- Flutter 只收降采样后的摘要，原始流留原生

### 4.3 C++ 环形缓冲 OOM（亲历口径，谨慎）

若用眼镜联调里第三方音频库的故事：Memory Graph 看不到 Swift 泄漏，Instruments 看到无主 Malloc 阶梯涨，定位到 C++ ring 无上限。修法是 App 侧背压，水位高就暂停读。  
**不要把这段说成你改了库源码**，除非当时真改了。默认：你在边界做了流控。

### 4.4 短答

**为什么不在 Flutter 里处理 PCM？** 单 Isolate + Channel 拷贝，掉帧且耗电。  
**传感器 50Hz 怎么展示？** 原生聚合 10Hz 峰值或姿态四元数再上 UI。  
**没做过 IMU？** 没做过融合算法。流控、分帧、时间戳、定责我在音频链路上做过。

## 五、C/C++、嵌入式、硬件协议

### 5.1 诚实定位

> 我的生产语言是 Swift / Dart / 能读 Kotlin。C/C++ 用来读第三方库、协议结构和崩溃栈，不是写 FreeRTOS。嵌入式同事出固件，我出 App 状态机和联调证据。

### 5.2 你必须能在白板上写的「协议」

不是 IP 栈，是设备协议：

```
帧 = seq | msgType | flags | length | payload | crc
可靠：窗口、ACK、幂等 commandId
控制面 GATT / BLE；数据面 TCP 或自定义
错误码分：可重试 / 用户可感知 / 需固件
```

联调：PacketLogger / HCI snoop 看空口；设备日志看是否 hvx；对不上就定责，见 04。

能读的 C 形状（口述即可）：

```c
typedef struct {
  uint16_t seq;
  uint8_t  type;
  uint8_t  flags;
  uint16_t len;
} __attribute__((packed)) MsgHdr;
```

对齐、大小端、packed，是联调时和固件对字节的基本功。

### 5.3 和嵌入式开会你听得懂的词

MTU、ATT、CCCD、连接间隔、supervision timeout、NACK、双槽、看门狗、Brown-out、Flash 磨损。  
听不懂就问「这条是 App 行为还是控制器行为」，不要装芯片专家。

## 六、EVT / DVT / PVT / 试产 / 量产

### 6.1 名词（嵌入式面试官用来测你是否一起交过货）

| 阶段 | 硬件在干什么 | App 该干什么 |
|------|----------------|--------------|
| EVT | 第一版能亮的板，射频/电源不稳，协议天天改 | Mock 先行；特性开关；日志拉满；协议当易变；不谈体验打磨 |
| DVT | 结构件接近，功能要齐，开始可靠性、功耗、OTA、认证预测试 | 状态机收口；升级路径打通；兼容表；和固件冻结主协议 |
| PVT | 小批量、工厂流程、良率、工装 | 产测模式（工厂 SSID、循环升级、写号）；日志可导出给 RMA；关掉调试后门的策略 |
| 试产 | 小规模出货验证渠道与客服 | 灰度版本；已知问题清单；回滚开关 |
| 量产 MP | 冻结、成本、备料 | 版本矩阵；强制升级策略极保守；监控断连/升级失败率 |

### 6.2 你怎么认，怎么不认

眼镜 0 到 1 + 固件联调，**最像 EVT→DVT 的软件角色**：板子不齐时用 Mock 并行；协议变更你吃；双链路、打断、弱网是 DVT 才暴露的问题。

不要说：

- 我负责 PVT 硬件签发  
- 我做过工厂 ICT/FCT 治具软件（除非真做过）  
- 我管过良率

可以说：

> 硬件阶段我是软件接口 owner。EVT 我用协议抽象和 Mock 不堵开发；DVT 我把失败路径、OTA 门槛、日志字段补齐，和固件对版本。若进入试产，我会先要兼容矩阵和产测指令，而不是继续堆功能。

### 6.3 产测指令（被问工厂）

常见：进入 DUT 模式、循环 BLE 连接、固定音源放录音、写 SN、读校准。  
走独立 GATT 或特殊 BLE 名，**与正式产品通道隔离**，正式包默认关闭。这是安全和产线效率，不是炫技。

### 6.4 量产最怕的三件事

1. 现场固件和 App 版本对不上 → 矩阵 + 能力发现  
2. OTA 变砖 → 救援镜像 + 不可断电文案 + 电量门槛  
3. 只有实验室日志 → 设备诊断特征 + 导出包（注意隐私）
