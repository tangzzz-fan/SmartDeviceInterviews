# 10 音频双链路选型说明（BLE 控制面 + WiFi 数据面）

> 已拍板：本项目音频通道口径为 **A. BLE 控制面 + WiFi 数据面**。被问「为什么这样设计」时，本文就是标准回答。

---

## 一、选型一句话

> **控制信令走 BLE（低功耗、常驻、可靠），音频大流量走 WiFi（带宽足、延迟低），各用各的长处，谁也不勉强干不擅长的事。**

---

## 二、候选方案对比（面试官说「还有别的做法吗」就用这张表）

| 候选 | 做法 | 致命短板 | 结论 |
|------|------|----------|------|
| ① 音频全走 BLE GATT | PCM 塞进 Notify | 16k/16bit 单声道 ≈ **32 kB/s**，GATT 实际吞吐（MTU/连接间隔/空口竞争）常态达不到，且持续高速 BLE 极耗电 | 弃 |
| ② 经典蓝牙音频（A2DP/HFP）+ BLE 控制 | 系统托管音频 | 音频链路被系统接管，App 拿不到原始 PCM 喂云端 ASR；HFP 强制降采样到 16k 且全双工体验差；链路形态与「眼镜采音→手机→云」的编排目标冲突 | 弃（与云端语音链路不兼容） |
| ③ 全走 WiFi | 控制+数据都走 WiFi | WiFi 常驻功耗高、配网/切换网络时控制面会一起断，心跳/打断这些轻指令没必要承担 WiFi 的稳定性风险 | 弃 |
| ④ **BLE 控制面 + WiFi 数据面** | BLE：配对/心跳/打断/状态同步；WiFi：PCM 上行、TTS 下行 | 多一条链路的建链与状态同步成本 | **选** |

**决策逻辑（三条，按顺序讲）**：

1. **带宽约束**：音频是硬需求里流量最大的一段，BLE 物理层撑不住连续 PCM，这是硬淘汰条件。
2. **可靠性约束**：打断、停播这类控制指令必须在数据面拥塞或重连时仍然可达，所以控制面必须是一条独立、轻量、低功耗的通道——BLE 天然合适。
3. **功耗约束**：BLE 常驻成本远低于 WiFi 常驻，平时只维持控制面，**按需拉起数据面**（用户发起对话才建 WiFi 通道），功耗和稳定性两头都占。

---

## 三、双链路的职责切分（被问「具体怎么分工」）

| 职责 | 通道 | 说明 |
|------|------|------|
| 配对/连接状态机 | BLE | 设备生命周期管理 |
| 心跳/在线检测 | BLE | 数据面断了控制面还能报活 |
| 打断（barge-in 停播指令） | BLE | **不能和音频抢同一条堵车的路**——WiFi 拥塞时停播指令照样到 |
| 状态同步（电量/模式/按键事件） | BLE | 轻量低频 |
| PCM 音频上行 | WiFi | 16k/16bit 定长分帧 |
| TTS 音频/文本下行 | WiFi | 大流量下行 |
| 视频码流下行（扩展） | WiFi | 与 TTS/OTA 同面；播放控制仍走 BLE，见 `16_眼镜视频播放.md` |
| 拉起/释放数据面信令 | BLE 下发 | 对话开始时 BLE 信令让眼镜开 WiFi，App 建 TCP/WebSocket |

状态机纪律：**控制面 Ready 才允许业务指令；数据面 Ready 才允许大流量入口**；两态独立上报 UI，避免「显示已连接但对话不可用」的假在线。

---

## 四、工程代价与取舍（主动讲，不等人挖）

1. **多一条链路就多一套状态**：BLE 与 WiFi 各自有状态机，UI 要合成展示；弱网下可能 BLE 在、WiFi 断，此时降级为「仅控制、提示网络不可用」，不假装对话可用。
2. **建链有顺序依赖**：先 BLE 握手拿到 capability，确认设备支持数据面，再按需建 WiFi；WiFi 建链失败不阻塞控制面。
3. **iOS 侧的诚实边界**：iOS 无法像 Android 一样任意切换系统 WiFi——实际走同局域网直连（设备开热点/同 AP）方案，`NEHotspotConfiguration` 有权限与审核约束。被追问时如实说「这部分平台差异是我做过对齐的」。
4. **为什么不直接蓝牙音频再内录**：绕系统回采拿到的音频不可控（延迟/音量/回声），喂给云端 ASR 会引入不可解释的识别错误，调试成本高于收益。

---

## 五、30 秒口播（背下来）

> 眼镜到手机的链路我们做了双通道分工。BLE 带宽扛不住 16k PCM 的连续上行，所以音频数据面走 WiFi；但停播、打断这类控制指令在数据面拥塞时也必须送达，所以控制面保留在低功耗的 BLE 上，平时只维持控制面，用户发起对话时按需拉起数据面。代价是多维护一条链路的状态同步，我们用两个独立状态机加合成 UI 处理，弱网时降级为仅控制并明确提示。

## 六、追问预案

| 追问 | 回答要点 |
|------|----------|
| 为什么不把音频压到 BLE 里硬传？ | 压缩能省带宽但增加端侧编码延迟和 CPU 功耗，且 GATT 吞吐上限仍不够连续音频；产品形态是实时对话，延迟预算不允许 |
| WiFi 数据面断了怎么办？ | 状态机感知 → 当次对话降级提示 → 重连数据面 → 下一次对话恢复；控制面始终在线，用户随时能停播/退出 |
| 两条链路怎么保证时序一致？ | 关键指令带 seq；音频帧带时间戳与 seq；接收端按 seq 重组，迟到帧丢弃不补偿（音频丢旧不丢新） |
| 安全怎么做？ | 控制面 BLE 配对 + 应用层握手；数据面会话级鉴权，音频不落盘 |
