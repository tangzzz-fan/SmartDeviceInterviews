# 11 攻坚案例实录：首包延迟劣化的完整排障

> 这是「遇到核心难题 → 我怎么分析、怎么解决」的主案例，选的是 02-C1 的深度展开版。
> 为什么选它：它横跨端侧、网络、云端三段，能完整展示**定界思维 + 埋点体系 + 取舍决策**，且全程 App 侧可主导，不冒认云端。

---

## 一、30 秒开场（先给结论）

> 印象最深的一次是：没有发版，用户反馈眼镜「反应变慢了」——从说话到出第一句回答的等待明显变长。我用分段埋点把延迟拆开，定界到上行建连这一段，抓包确认是 WebSocket 复用失效、每次对话都在重新做 TCP+TLS 握手。根因是一次会话管理改动把连接复用链路改断了。修复是恢复连接保活加预建连，并用复用率打点防回归。这件事让我把「延迟问题先分段、再定界」变成了肌肉记忆。

---

## 二、完整实录（追问时用，按时间线讲）

### 1. 现象与第一反应

- 反馈渠道：测试同学和用户反馈「反应变慢」，**近期没有 App 发版**。
- 第一反应不是猜原因，而是先问两件事：① 慢的是哪一段（首句慢？识别慢？全程慢？）；② 是全部用户还是特定场景。
- 初步复现：WiFi 信号一般的环境下慢得明显，信号好的办公网影响小——**环境相关，先怀疑网络链路而不是模型**。

### 2. 定界：把「慢」变成可观测的分段数字

靠体感说不清「慢了多少」，所以用 t0–t8 埋点把一次对话拆成六段：

```
t0 唤醒 → t1 数据面就绪 → t2 首帧上行 → t4 ASR 首 partial
→ t5 LLM 首 token → t6 TTS 首帧 → t7 开播 → t8 首句播完
```

对比劣化前后的埋点：

| 分段 | 劣化前（好网络） | 劣化后（弱网） | 结论 |
|------|------------------|----------------|------|
| t2→t4（上行到 ASR 首包） | 约 0.3s | 约 1.5–2s | **劣化集中在这里** |
| t4→t5（LLM 首 token） | 正常 | 正常 | 云端模型没问题 |
| t6→t8（下行到开播） | 正常 | 正常 | 播放侧没问题 |

**定界结论：问题压在上行建连到 ASR 出首包这一段，云端模型和播放端先排除。**

### 3. 假设与验证（逐个排除）

| # | 假设 | 验证手段 | 结果 |
|---|------|----------|------|
| 1 | 云端 ASR 变慢 | 对比同时段云端监控/工单查询 | 排除 |
| 2 | 采音节奏变了（帧间隔抖动） | 查采集侧日志，帧长与节奏 | 排除 |
| 3 | 音频参数配置被改 | 对照契约查请求参数 | 排除 |
| 4 | **建连开销变大** | 抓包看每次对话的握手序列 | **命中**：每次对话都出现完整的 TCP 三次握手 + TLS 握手，连接没有复用 |

### 4. 根因

近期一次**会话管理相关的改动**，把「连接保活复用」的链路改断了：每次对话结束连接被释放，下一次对话冷建连。

为什么平时没发现：办公网握手快，300–500ms 被流式并行掩盖；弱网下握手耗时被放大数倍，叠加每次都重来，首句延迟肉眼可感。**这是一个「好网络掩盖坏设计」的典型。**

### 5. 修复与取舍

- **连接层**：恢复保活 + 预建连——App 启动/控制面 Ready 后即预热 WebSocket，对话直接复用，不在对话关键路径上做握手。
- **会话层**：明确「连接 ≠ 会话」——连接保活复用，但每次对话仍新开 session，避免上下文串扰。
- **不选的方案**：把建连放进唤醒瞬间并行做——治标，弱网下仍可能来不及；不如直接不在关键路径建连。

### 6. 防回归（这是加分点）

- 新增 `wsReuse` 打点：每次对话记录「本次是否复用连接」，复用率进看板。
- 把「t2→t4 分段耗时」纳入版本对比，改动会话管理模块时强制看这两个指标。
- 复盘结论写进团队规范：**长连接的生命周期变更必须带可观测性一起上**。

### 7. 复盘（被问「有什么反思」）

> 两点。一是**好网络会掩盖坏设计**——弱网才是照妖镜，这类链路改动应该在弱网用例下回归；二是**延迟治理的前提是可观测**，如果当时没有 t0–t8 分段埋点，这个问题会变成「大家觉得慢了但不知道哪里慢」的悬案。所以之后我推动的原则是：动连接生命周期，必须带复用率打点。

## 三、追问预案

| 追问 | 回答要点 |
|------|----------|
| 为什么不直接看云端日志？ | 没有云端权限；但用「同时段对比 + 排除法」等价定界，最后拿抓包证据推动工单对账（X-Tt-Logid / requestId） |
| TLS 握手具体慢在哪？ | TCP 三次握手 + TLS 协商，弱网下 RTT 放大；HTTP/2 或 0-RTT 这些优化我没做，我做的是**干脆不在关键路径握手** |
| 保活会不会费电/占资源？ | WebSocket 空闲保活成本远低于每次重建；且数据面本来就是按需拉起，平时只有心跳 |
| 如果面试官说「这不就是个 bug 吗」 | 承认修复本身简单，强调价值在**定界路径和防回归机制**——把一次事故变成一类问题的免疫 |
| 有没有其他类似案例 | 引到 02 的 C5（云端抖动做降级）、C7（半开连接心跳探活）：同一套「定界→证据→降级→打点」打法 |
