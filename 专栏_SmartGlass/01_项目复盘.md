# 01 项目复盘：智能眼镜是怎么做的

对应简历：商汤 · 日日新大模型智能眼镜配套 App（独立开发，iOS 从 0 到 1）。
口径基于「日日新大模型 + 火山云 SDK + 双链路」；细节以真实实现为准，⚠️ 音频通道口径见 00 总览第四节。

---

## 一、3 分钟口述（开场必练）

> 这是商汤日日新方向的智能眼镜配套 App。产品目标是让用户通过眼镜完成免手持语音交互：唤醒、提问、听回复、做简单控制，并和手机 App 同步设备状态。
>
> 架构是「眼镜采音 → 手机编排 → 云端 AI」三段式。眼镜侧麦克风和扬声器走设备，手机 App 是会话中枢。控制面用 BLE：配对、心跳、打断、状态同步；数据面用 WiFi：PCM 上行和大模型 / TTS 下行。语音识别和合成接火山云 SDK，对话接日日新大模型。
>
> 我负责 iOS 端从 0 到 1：需求拆解、技术方案、核心模块、联调和上线。重点不是训练模型，而是把设备连接、音频进出、云服务调用、打断与超时、页面状态做成一条能用的链路。火山 SDK 让 ASR/TTS 能快速接入，但引擎内部是黑盒；App 的工程量在会话状态机、流式编排、弱网降级和可观测性。

## 二、白板架构（练到闭眼能画）

```
眼镜硬件                    手机 App                         云端
┌──────────┐  BLE 控制面   ┌──────────────────┐
│ mic / 扬声器│ 配对/心跳/打断 │ 会话编排器          │     火山云 ASR（流式）
│ BLE 模块  │ <----------> │ 设备状态机          │ ──>  partial / final
│ WiFi 模块 │  WiFi 数据面  │ 音频管线            │ <──
└──────────┘ <----------> │ TTS 播放队列        │
                           │ 流式渲染 / 埋点      │     日日新 LLM
                           └────────┬───────────┘ ──>  流式 token
                                    │             <──
                                    └──────────────>  火山云 TTS（流式）
```

一句话总览备用（更短）：

> 眼镜是「耳朵和嘴」，手机 App 是「中枢神经」，云端是「大脑」。音频上行做 ASR 输入，语义走 LLM，回复经 TTS 合成回传播报。

### 建链顺序（必须说清）

1. 先 BLE Ready：扫描、连接、MTU、能力读取，控制面可用。
2. 用户进入大模型对话时，BLE 下发切数据面信令，眼镜开 WiFi。
3. App 建 TCP / WebSocket；WiFi 未就绪时禁止大流量入口。
4. BLE 降为心跳 + 打断；音频和 Token 走 WiFi。

### 通道分工矩阵

| 数据 | 通道 | 原因 |
|------|------|------|
| 配对、配网、心跳、打断 | BLE | 低功耗、低延迟、后台更可恢复 |
| PCM 上行、TTS 下行、Token 流 | WiFi | BLE 带宽扛不住 16k PCM（约 32kB/s）和流式音频 |
| OTA | WiFi | 大文件 |

为什么打断走 BLE：WiFi 数据面可能拥塞或正在重连，「停止播放」这种命令不能和音频抢同一条堵车的路。

### iOS WiFi 数据面边界（主动说，防夸大）

- iOS 没有公开的通用 Wi-Fi Direct。
- 实际是设备热点 + `NEHotspotConfiguration` 引导加入，或同局域网 Bonjour + TCP。
- 体验受系统弹窗、本地网络权限、网络可达性限制，不是静默可控链路。

## 三、技术选型的「为什么」（高频追问）

| 选型 | 为什么 | 追问预备 |
|------|--------|----------|
| 语音与模型拆两家 | ASR/TTS 拼实时性（流式、首包、打断），LLM 拼理解生成；组合比等一家全家桶更快验证产品 | 代价全落在 App：三段流要拼接，这正是我的工程量 |
| 火山 ASR/TTS | 成熟流式链路、中文效果、免自研成本 | 为什么不自研/开源？端侧算力、交付周期、运维成本 |
| 手机 App 做中继 | 眼镜主控算力/功耗受限 | 眼镜直连云会增加成本重量与功耗 |
| BLE 控制面 | 低功耗常驻、后台可恢复 | 眼镜电池紧，WiFi 按需开 |

> 这句是工程价值所在：**不要把价值说成「我接了两个 SDK」**。价值是：ASR 的 partial 什么时候给 UI、什么时候进 LLM；LLM token 按什么标点切句送 TTS；TTS 首帧到了能不能开播；用户打断时三路请求怎么一起取消。

## 四、App 真正交付的模块（按分层讲，不按页面讲）

### 4.1 设备接入层
- BLE 扫描过滤、连接、服务发现、Notify、断连重连
- 设备能力协商：是否支持 WiFi 数据面
- 连接状态机：`idle → scanning → connecting → ready → recovering → disconnected`
- 非法路径 guard：未 ready 不允许开对话

### 4.2 音频交互层
- 眼镜采音经数据面上行；按火山契约送 16k / 16bit / mono PCM
- ASR 流式结果：UI 覆盖渲染 partial，下游只吃 final
- TTS 流式音频：jitter buffer → 播放 → 下行到眼镜
- 播放与录音互斥、音频焦点、来电打断

### 4.3 会话编排层（核心）

一次对话不是一次 API 调用，是状态机：

```
Idle → Listening(采音) → Recognizing(等 final) → Thinking(LLM 生成)
     → Speaking(TTS 播放) → Interrupted(打断，取消在途) / Failed / Timeout → Idle
```

必须能处理的边界：

- 用户说完但 ASR 还没 final
- TTS 播放中用户再说话（barge-in）
- BLE 临时断连，播放目标丢失
- 弱网重试，旧回调不能写进新会话
- 来电 / 音频焦点丢失

**工程原则：每个云请求带 `sessionId`；状态切换时取消旧请求，迟到回调按 sessionId 丢弃。**

### 4.4 业务能力层
问答、简单设备控制、状态查询、页面联动。被问「翻译还是助手」：按语音助手讲；翻译只是同一 pipeline 的 prompt/路由特化，别把没做过的翻译说成主线。

### 4.5 稳定性与可观测
结构化日志（sessionId/deviceId/requestId/阶段/耗时/错误码）、t0–t8 分段打点、错误三分类（鉴权/参数契约/服务抖动）、Mock 设备与假云服务。

## 五、一次完整问答的时序（8 步，能背）

```
用户触发（按键/唤醒）
  → App 确认 BLE ready，必要时拉起 WiFi 数据面
  → 开始采音，首帧打 t1
  → 音频 chunk 按帧上行（约 100–200ms/包），火山 ASR session 开始
  → 回 partial：只更新字幕；静音端点/松手 → 等 final
  → final 文本带上下文进日日新，LLM 流式 token
  → UI 增量渲染 + 按句切给 TTS；TTS 首帧到达即开播（预缓冲够才起播）
  → 播放结束或用户打断 → 状态回 Idle / Listening；任一环节超时失败 → 降级提示并回 Idle
```

**流式的意义不是每段都更快，而是并行流水**：ASR 出整句就进 LLM，LLM 出第一句就进 TTS，TTS 出首帧就开播。用户感知的是首句延迟，不是全链路总和。

## 六、项目里最难的三件事

### 难点一：多异步状态打架
设备连接、采音、ASR、LLM、TTS、播放同时存在。典型事故：ASR 还没 final 业务就拿 partial 调 LLM；TTS 还在播又开了一路合成，旧音频「复活」；WiFi 断了但 BLE 还在，UI 显示已连接实际对话不可用。
**解法**：显式状态机 + sessionId 隔离 + 打断时三联取消（停播、清 jitter buffer、取消在途合成）。

### 难点二：语音链路黑盒
火山 SDK 让功能很快通，但「慢、卡、识别错、自问自答」不能只看 SDK 报错。口径：

> 我没有改过云端引擎。我负责把问题收敛到端侧、网络或云端：端侧我修，云端我带 requestId 和音频样本推厂商，同时 App 必须有降级，用户不能裸奔。

### 难点三：跨端与原生边界
Flutter 适合业务 UI 和跨端复用；蓝牙、音频焦点、前后台、权限必须下沉原生插件。眼镜项目以 iOS 原生交付为主；跨端能力来自阿兹尔的 Flutter 混编和插件翻译——主动把两段拼起来，证明不是单一平台。

## 八、高频追问链

**Q：「你到底做了什么？」**
> 一句话：把智能眼镜的 AI 能力接到用户能用的移动端交互里。具体是端侧落地：设备连接与双链路、会话状态机、火山 ASR/TTS 与日日新的流式拼接、播放与打断、异常降级。我不是做模型训练的，也不是做语音引擎的。我擅长把已有云能力和硬件约束做成稳定交付。

**Q：端到端延迟做到多少？**
> 没有精确实测就不报绝对值。结构上体感延迟 = t8 - t0，其中 LLM 首 token 是大头；优化手段是流式并行 + 切句即合成 + 连接复用。我讲分段占比，不报口号数字。

**Q：为什么不用纯端侧方案？**
> 当时优先快速验证交互闭环。产品化要补的是连接复用、状态机、埋点、降级，不是先自研模型。端云结合（端侧唤醒词 + 云端识别）是常见折中。

**Q：项目里哪些是别人做的的？**
> 框架/算法选型是团队决策，但 App 端实现细节我有 ownership：状态机、编排、埋点、降级是我定的方案。

**Q：和嵌入式/算法怎么分工？**
> 端侧采音参数、AEC、唤醒词归嵌入式；模型效果、prompt 归算法/云端。App 拿到的契约是音频流进出 + 三段云服务 API，责任是把它们拼成可靠的会话体验。
