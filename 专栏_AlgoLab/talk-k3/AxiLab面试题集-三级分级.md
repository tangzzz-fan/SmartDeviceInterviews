# AxiLab 面试题集（基础 / 进阶 / 专家 三级）

> 基于 AxiLab Inc.「资深 iOS 开发工程师（算法实现 / BLE 通信）」JD 反向推导。
> 使用方法：

## 第一级：基础题（筛选关，错一题即危险）

### Q1.1 GATT 数据模型与操作语义
**考察点：** BLE 概念是否扎实，是否真写过 GATT 交互代码。

**答题骨架：**
- 层级一句话：Profile → Service → Characteristic → Descriptor，Characteristic 是数据交互的最小单元，Descriptor（如 CCCD）控制 notify/indicate 开关。
- 操作对比：read（请求响应）、write（有 ACK）、writeWithoutResponse（无 ACK、无流控）、notify / indicate（前者无确认、后者有）。
- 项目映射：实时波形用 notify（要吞吐不要逐包确认），OTA 传固件用 writeWithoutResponse + 应用层 ACK（为什么不用 indicate：开销大）。
- 坑点收尾：writeWithoutResponse 会受 iOS 端发送缓冲区限制，猛写会丢包或 `peripheralIsReady(toSendWriteWithoutResponse:)` 回调告诉你暂停。

### Q1.2 MTU 协商与吞吐影响因素
**考察点：** 是否理解吞吐的三个旋钮。

**答题骨架：**
- 协商流程：MTU 由外设或中央发起 ATT MTU Exchange，取双方最小值；iOS 上实际可协商到约 185 字节载荷（不要背死数，说"约 185，以 `maximumWriteValueLength` 实测为准"）。
- 三旋钮：连接间隔（iOS 典型 30ms 起，最低约 15ms，受苹果配件规范约束）、ATT MTU + DLE 数据长度扩展、PHY 模式（1M vs 2M PHY，理论翻倍）。
- 落地一句：三个旋钮两个在固件手里，所以吞吐优化一定是 App + FW 联合工程——顺势展示协作意识。

### Q1.3 CoreBluetooth 回调队列
**考察点：** 并发基本功。

**答题骨架：**
- 默认行为：不指定 queue，所有 delegate 回调在主队列。
- 风险：高频率 notify（波形流每秒几十上百包）在主队列做拼包解析会拖累 UI。
- 实践：初始化 `CBCentralManager(delegate:queue:)` 传自定义串行队列，接收链路全程在该队列，只在渲染/存储前做有界的队列切换。
- 边界提醒：跨队列切换处就是数据竞争高发区，RingBuffer 的读写指针归属要说清楚。

### Q1.4 断线重连的基本实现
**考察点：** 重连不是一句"重新 connect"。

**答题骨架：**
- 错误区分：`didDisconnect` 的 error 判断是用户主动断开、对端断开、还是超时/链路丢失——不同原因不同策略。
- 退避：立即重连 → 失败后指数退避（1s/2s/4s，上限 30s），连续失败降级为"等待用户操作"。
- 系统行为：`connect` 在 iOS 上没有超时（会一直挂着），需要自己实现超时 + `cancelPeripheralConnection`。
- 恢复动作：重连后必须重新 discover services、重新订阅 notify、必要时做时间同步和数据续传协商。

### Q1.5 典型 OTA/DFU 流程
**考察点：** 流程完整性，专家题的入场券。

**答题骨架：**
- 六步：前置检查（电量、版本兼容、空间）→ 切换/进入升级模式 → 分包传输（带进度持久化）→ 完整性校验（CRC/hash）与签名校验 → 激活重启 → 重启后版本回读确认。
- 关键认知：任何一步中断设备都必须可恢复，这就是状态机存在的理由（自然引出进阶题）。

### Q1.6 后台 BLE 与 State Preservation
**考察点：** 睡眠监测场景的硬门槛。

**答题骨架：**
- 声明 Background Modes：`bluetooth-central`（App 作为中央）。
- 初始化时传 `CBCentralManagerOptionRestoreIdentifierKey`，App 被系统挂起/终止后，系统在有 BLE 事件时唤醒 App 并通过 `willRestoreState` 交还现场。
- 恢复后要重建：central 状态、已连接外设列表、扫描状态，并重新挂 delegate。
- 诚实边界：用户手动杀 App 不触发恢复；这是产品层面要引导用户的点。

### Q1.7 BLE 场景下的内存与性能排查
**考察点：** Instruments 实战。

**答题骨架：**
- 循环引用高发位：单例 BLEManager 持有 delegate、closure 捕获 self、Timer。
- 工具链：Leaks/Allocations 看泄漏与增长曲线，Time Profiler 找热点，os_signpost 给关键路径打区间。
- 长连接特有问题：整夜监测场景看的是 8 小时内存曲线是否单调增长（缓慢泄漏在短测试里看不见）。

### Q1.8 为什么硬件协议用 Protobuf
**考察点：** 协议选型理由与兼容规则。

**答题骨架：**
- 对比 JSON：二进制体积小（BLE MTU 受限）、编解码快、schema 明确；代价是不可自描述、调试要工具。
- 兼容规则：field number 一旦分配不复用，删除字段用 `reserved` 占位；新增字段旧端自动忽略；`oneof` 适合命令/事件多态。
- 项目映射：你 CarKey/扫地机的 Protobuf 实战经验直接讲。

## 第二级：进阶题（主战场，决定 offer 档位）

### Q2.1 OTA 断点续传设计
**考察点：** JD 第一职责的核心深度。

**答题骨架：**
- 先画状态机（见配套图）：传输中任何断连进入"挂起"，重连后经"恢复协商"回到传输。
- 进度持久化分两端：App 端记录已确认的最大 offset（落盘，防 App 被杀）；固件端记录已写入 flash 的最大 offset。恢复时交换双方 offset，取较小者续传——为什么取小：App 以为发了不代表固件写进去了。
- ACK 粒度权衡：逐包 ACK 安全但慢，窗口批量 ACK（如每 16 包）快但失败重传成本高；给出你的取值和理由。
- 失败注入测试清单：传到 37% 断连、传到 99% 断电、校验阶段重启、升级中来电话/切后台。
- 数字收尾：固件多大、实际传输速率、断点续传把失败重传成本降了多少。

### Q2.2 实时波形卡顿的优化路径
**考察点：** JD 第二职责，必须度量驱动。

**答题骨架：**
- 第一步永远是度量：当前吞吐（KB/s）、丢包率、连接间隔实测值、MTU 实测值——没有基线不谈优化。
- 分层定位（物理层 RSSI → 链路层 interval/重传 → GATT 层 MTU/订阅方式 → 协议层包格式 → 应用层处理耗时）。
- 手段清单（按性价比排序）：协商 2M PHY、开启 DLE、压连接间隔、MTU 拉满、协议瘦身（去掉冗余字段、二进制替代文本）、notify 批量聚合（固件侧一帧塞多采样点）、App 侧接收队列串行化去锁。
- 验证：优化前后对照数字 + 防退化（把吞吐/丢包埋点纳入监控）。
- 如果没有真做过波形优化：讲 Jitter Buffer 的同构经验（眼镜音频流），说明方法论可迁移，但诚实标注场景差异。

### Q2.3 从 notify 到屏幕的管道架构
**考察点：** 流式架构能力（见配套流式管道图）。

**答题骨架：**
- 串行接收队列承接 delegate 回调 → 拼包校验（序列号 + CRC）→ RingBuffer。
- 三链路分流：显示链路（抽稀后渲染，允许丢帧）、存储链路（零丢失，缺口触发回填）、算法链路（滑窗 DSP）。
- 背压设计：下游消费慢时 RingBuffer 满的策略（覆盖最旧 vs 暂停上游，各自适用哪条链路）。
- 渲染侧：长波形用 min-max 分桶抽稀，实时段与历史段分开处理。

### Q2.4 显示可丢、存储不可丢，如何兼顾
**考察点：** QoS 分级思维。

**答题骨架：**
- 承认矛盾：一条物理链路，两种可靠性要求。
- 方案：序列号 + gap 检测，显示链路直接跳过缺口（波形跳一帧），存储链路记录缺口区间并向固件发回填请求。
- 前提条件：固件端必须维护一个循环缓存（最近 N 秒），回填能力与缓存深度绑定——这又是 App + FW 联合设计。
- 优先级调度：回填流量不能饿死实时流量，低优先级闲时补传。

### Q2.5 "连不上"的三方归因方法论
**考察点：** JD 明文要求的 Debugging 能力。

**答题骨架：**
- 三层日志对齐：App 侧结构化日志、iOS 侧 PacketLogger 抓 HCI、固件侧日志——三路时间戳对齐是基本功。
- 对照实验法：用 nRF Connect 连接同一固件，能复现 → 大概率固件/链路问题；不能复现 → 聚焦 App 层。这一招是排除法的杀手锏，面试官必认。
- 空口抓包（Ellisys/Frontline）作为终极手段：空中包是不会说谎的。
- 讲一个你的真实归因案例（按 STAR，30 秒讲完背景，重点讲分层排除的过程）。

### Q2.6 BLE 健康产品的日志与监控体系
**考察点：** JD 职责第五条。

**答题骨架：**
- 分层：连接事件（连上/断开/重连耗时）、协议事件（OTA 状态迁移、缺口/回填）、业务事件（会话开始结束）、崩溃与 ANR。
- 分级与采样：调试级本地留存，关键事件必上报，高频事件采样上报——控制流量与隐私。
- 隐私红线：生理波形原始数据不入日志，日志只记元数据（长度、序列号、时间戳）；神经数据属敏感信息，上报前脱敏 + 用户授权。
- 看板指标：连接成功率、平均连接耗时、OTA 成功率漏斗、crash-free rate、波形丢包率。

### Q2.7 既有代码的 BLE 层重构
**考察点：** JD 要求"在既有代码上演进"，不是推倒重来。

**答题骨架：**
- 诊断：BLE 调用散落在 VC/业务层、状态靠 Bool 标志位、无统一错误模型。
- 目标结构：传输层抽象（协议接口隔离 CoreBluetooth）、会话状态机集中管理、业务层只面对语义化 API。
- 灰度策略：新旧链路并存 + 开关切换，按设备灰度，出问题秒回退——重构不改行为是底线。
- 测试先行：重构前用 golden 向量/模拟外设补集成测试，否则不动手。
- 语言映射：Clean Architecture 的依赖方向 + Redux 的单向状态流，直接讲你的框架。

### Q2.8 Swift 集成 C 库的工程要点
**考察点：** 加分项第一条。

**答题骨架：**
- 集成方式：SPM 的 C target 或 module map，讲你 SPM 分包的实践经验。
- 性能边界三件事：零拷贝（`UnsafeBufferPointer` 直接包 C 数组）、按帧批量调用（逐点调用边界开销吃掉 DSP 收益）、明确内存所有权（谁分配谁释放）。
- 正确性边界：float32/float64 精度策略 + golden 数据集回归（引向专家题 Q3.3）。
- 线程模型：C 库在哪个队列被调用、是否可重入。

## 第三级：专家题（系统设计，考察判断力）

### Q3.1 神经调节设备的 App 安全架构
**考察点：** 能否意识到这不是普通健康 App。

**答题骨架：**
- 威胁建模先行：误启动、强度失控、会话中断后设备仍在刺激、非授权使用。
- 核心原则一句话：**断连安全由固件兜底，App 永远假设自己下一秒会死**——断连看门狗在固件侧，超时未收到心跳自动停止刺激并回到安全态。
- 双重互锁：硬件侧电极接触检测不通过不允许启动；软件侧会话状态机（Idle → Armed → Ramping → Active → Stopping），强度只能斜坡升降，不允许跳变。
- 审计：每次会话完整记录（谁、何时、强度曲线、终止原因），这是医疗边界的合规资产。
- 监管认知：wellness 宣称 vs 治疗宣称是两条完全不同的路（后者涉 FDA SaMD），App 的功能设计和文案都要配合定位。

### Q3.2 整夜睡眠监测的可靠性工程
**考察点：** 长时运行的系统性思维。

**答题骨架：**
- 风险清单：iOS 后台被杀、BLE 夜间断连、手机充电/低电量模式、固件看门狗复位、时间漂移。
- 设计对应：state restoration 恢复现场；固件端夜间数据本地缓存，晨间批量补传 + 对账（序列号连续性校验）；App 端不假设整夜在线，按"最终一致"设计。
- 预算意识：8 小时 BLE 长连接的耗电与发热预算，采样/传输频率夜间可降级。
- 度量：夜间数据完整率作为核心指标监控。

### Q3.3 算法工程化：端上结果与原型的一致性体系
**考察点：** 加分项的集大成者，你的 algo-engineering-lab 直接对口。

**答题骨架：**
- 总纲：**数值一致性不是测出来的，是流程保证的**。
- 三板斧：黄金数据集（Python 原型生成，覆盖病态输入，入库冻结）、中间快照（重采样后、加窗后、功率谱逐环对齐，哪环偏了立刻定位）、CI 回归（算法库 × App × 固件版本矩阵绑定）。
- 精度策略：累加类计算中间用 double、输出转 float；系数导出保留足够有效位；误差阈值按"产品无意义量级"定而不是越小越好。
- 频域指标专项：跨平台对不上 90% 是前置链路口径问题（插值方法、采样率、窗函数、FFT 归一化），不在 FFT 本身。
- 这套方法论的迁移性：与 BLE 三层归因同构——都是"分层打快照，定位偏差层"。

### Q3.4 万台设备的固件灰度发布
**考察点：** OTA 从功能到体系。

**答题骨架：**
- 分桶策略：内部设备 → 1% → 10% → 全量，按设备 ID 哈希分桶保证可重复。
- 强制 vs 可选：安全修复强制（但保留低电量豁免），功能升级可选。
- 熔断机制：升级失败率超阈值自动暂停推送并告警，人工确认后恢复。
- 回滚与兜底：双 Bank 支持回退旧版本；Bootloader 独立可救援，变砖率归零是设计目标。
- 监控：OTA 漏斗每一步转化率，按固件版本 × App 版本切片看。

### Q3.5 协议 v2 设计：新增 8 通道 EEG 且兼容旧固件
**考察点：** schema 演进与版本治理。

**答题骨架：**
- 能力协商：连接建立后先交换 capability（协议版本、支持的传感器、最大包长），App 按对端能力降级行为。
- schema 演进：Protobuf 新增字段旧端忽略；field number 不复用；`oneof` 管理消息类型扩展。
- 版本兼容矩阵：App 版本 × 固件版本 × 协议版本的允许组合，显式维护、测试覆盖。
- 过渡策略：新旧协议双栈并存一个周期，监控旧协议使用量，归零后下线。
- 兜底认知：协议即契约，契约治理本质是三方协作治理（引出 Q3.6）。

### Q3.6 开放题：这个岗位最难的事是什么
**考察点：** 判断力与格局，没有标准答案，但有高下之分。

**参考骨架：**
- 低分答案：某个单点技术（OTA 很难、BLE 很难）。
- 高分答案结构：单点技术都有成熟参照（Nordic DFU、业界吞吐实践），真正的难点在**三方（App / FW / Algorithm）接口的治理**——协议即契约，版本矩阵即秩序，联调基建（模拟外设、golden 向量、共享日志格式、对齐口径文档）决定迭代速度。
- 收尾升维：初创公司的资源约束下，"用最少的联调次数把问题关进测试里"是资深工程师的核心价值——这正是你建 algo-engineering-lab 这类验证基建的动机。
