# algo-engineering-lab 技术文档要求说明书

> **定位声明（先读这段）：** 这个 repo 的核心交付物不是代码，是**工程化思维的证据链**。面试官看不到你的联调现场，能看到的是文档——所以本文档要求先于代码存在（文档驱动），每份文档都有明确的验收标准（DoD）。本文档本身也是面试素材：被问"你怎么做算法工程化"时，回答"我先定规范，再写代码，规范如下"并展示本文件。

## 一、全局约定

### 1.1 目录结构约定

```
algo-engineering-lab/
├── README.md                    # 见 2.1
├── docs/
│   ├── 01-数值一致性规范.md       # 见 2.2
│   ├── 02-算法对齐口径/          # 见 2.3，每个算法一份
│   ├── 03-黄金数据集规范.md       # 见 2.4
│   ├── 04-C库集成规范.md          # 见 2.5
│   ├── 05-性能基准规范.md         # 见 2.6
│   └── 06-实验复盘/              # 见 2.7，每个 case 一份
├── python/                      # 原型与 golden 生成脚本
├── golden/                      # 黄金数据集（入库，版本化）
├── Sources/                     # AlgoC / AlgoSwift
└── Tests/                       # Parity 测试与 Benchmark 分离
```

### 1.2 通用规则

1. 所有文档使用简体中文正文，专有名词保留英文（如 golden dataset、RingBuffer、parity）。
2. 所有数字必须带测量环境（机型、iOS 版本、编译配置），裸数字无效。
3. 文档与代码同 PR 变更：改实现不改文档的提交打回。
4. 每份文档开头保留"版本/日期/作者/状态（草稿/生效/冻结）"四行元信息。
5. golden 目录下所有数据注明来源；使用公开生理数据库（PhysioNet 等）必须写明数据集名与许可。

## 二、七份文档的要求明细

### 2.1 README.md

**目的：** 10 分钟让一个陌生 iOS 工程师跑通 parity 测试并理解项目价值。

**必含内容：**
1. 一句话定位："验证 Python 算法原型 → C 库 → iOS 集成的数值一致性与性能链路"。
2. 链路架构图一张（Python 原型 → golden 数据集 → C/Swift 双实现 → parity 回归）。
3. 快速开始：不超过 3 条命令跑通全部 parity 测试；环境依赖（Xcode 版本、Python 版本、依赖安装）显式列出。
4. 结果看板：两张表——各 case 精度误差表（指标 / 阈值 / 实测误差 / 结论）、性能数字表（实现 / 耗时 / 加速比）。
5. 各 case 的入口导航链接。

**DoD（验收标准）：** 找一台干净机器按 README 操作，15 分钟内 parity 测试全绿；过程中需要问作者任何一句话，README 即不合格。

### 2.2 docs/01-数值一致性规范.md

**目的：** 全项目唯一的精度与单位口径来源，禁止 case 内私自定义。

**必含内容：**
1. **浮点策略表**：存储层 / 中间计算 / 输出层各自使用 float 还是 double，及理由（例：累加类中间态强制 double，输出转 float 以匹配嵌入式侧）。
2. **误差阈值表**：每行一个指标——指标名 / 阈值 / 阈值依据（必须写成"产品上无意义的量级"式论证，如 RMSSD 误差 <0.1ms 对 HRV 解读无影响，不接受"拍脑袋 1e-6"）。
3. **病态输入处理约定**：空数组、单点、NaN、Inf、极端值的行为定义（返回错误码还是 NaN 传播，全项目统一）。
4. **单位与时间戳约定**：ms vs s、Hz vs 采样间隔、时间基准（boot time vs wall clock），单源定义，跨语言一致。

**DoD：** 抽查任意 case 的实现与测试，其中出现的每一个精度与单位决定都能在本规范中找到对应条款；出现规范外的"本地约定"即违规。

### 2.3 docs/02-算法对齐口径/（每算法一份，如 `hrv-freq-domain.md`）

**目的：** 模拟与算法工程师的对齐确认单，是跨团队接口治理能力的直接证据。

**必含内容：**
1. **环节分解表**：算法拆成有序环节，每环节一行——环节名 / 参数 / 取值 / Python 侧对应实现（库+函数+版本）/ iOS 侧对应实现。以频域 HRV 为例，环节至少含：伪差校正、插值重采样（方法+目标采样率）、去趋势、加窗（窗型）、FFT（长度+归一化方式）、频带积分（方法+边界）。
2. **中间快照定义**：每个环节输出一个快照——快照名 / 数据格式 / 存储路径 / 与 Python 侧快照的比对阈值。
3. **已知差异记录表**：被接受的差异清单——差异点 / 量级 / 接受理由 / 确认人（练习时写"参考 NeuroKit2 文档第 X 节"）。

**DoD：** 仅凭本文档，第三方不看代码即可独立重写出对齐实现，且逐快照比对全部通过。

### 2.4 docs/03-黄金数据集规范.md

**目的：** golden 是"真值"，真值的生成与冻结必须制度化，否则回归测试失去意义。

**必含内容：**
1. **生成流程**：生成脚本入口、固定随机种子、Python 依赖版本锁定要求；golden 只允许由 Python 原型生成。
2. **数据格式约定**：JSON schema 说明——每条记录含输入、期望输出、中间快照、输入类别标签。
3. **覆盖矩阵**：输入类别（正常 / 边界 / 病态：缺失搏动、异位搏动、空、单点、极端噪声）× 每个算法，矩阵中每个格子要么有数据、要么显式标注"不适用+理由"。
4. **冻结与版本化规则**：golden 变更必须独立提交并说明原因；禁止从 C/Swift 实现反向生成或"修正"golden（防自我印证）；golden 变更后历史性能数字作废重测。
5. **数据规模约定**：每算法至少 N 条（建议 50+），病态输入占比不低于 40%。

**DoD：** 删除 golden 目录后按规范重跑生成脚本，产出与版本库中数据逐字节一致；覆盖矩阵无空白格。

### 2.5 docs/04-C库集成规范.md

**目的：** 定义 Swift↔C 边界的一切规则，review 集成层代码时直接对照执行。

**必含内容：**
1. **职责边界**：C 层做什么（纯数值计算、无 I/O、无日志）、Swift 层做什么（生命周期、错误翻译、线程调度）。
2. **内存所有权规则**：谁分配谁释放；跨边界指针的有效期约定；禁止返回指向 C 内部静态缓冲的指针给 Swift 长期持有。
3. **零拷贝约定**：使用 UnsafeBufferPointer 类方式包裹、禁止边界处数组逐元素拷贝；给出允许拷贝的例外情形。
4. **调用批次约定**：按帧/按窗口批量调用，禁止逐采样点跨界调用；一帧的建议粒度（如 1 秒窗口）。
5. **错误码表**：C 层错误码全集及 Swift 侧映射的 Error 类型。
6. **线程模型**：C 库可重入性声明、允许调用的队列、禁止并发调用的接口清单。

**DoD：** 集成层每一处跨边界调用都能在规范中找到对应条款；规范未覆盖的新模式必须先补规范再写实现。

### 2.6 docs/05-性能基准规范.md

**目的：** 性能数字的生产与记录方式制度化，保证面试时报出的每个数字可复现。

**必含内容：**
1. **基准环境记录格式**：机型 / 芯片 / iOS 版本 / 编译配置（Release）/ 电量与发热状态——五项缺一，数字无效。
2. **指标定义**：耗时报 p50 与 p95（不接受单次值）、内存峰值、单位吞吐；每项指标注明测量方法。
3. **记录格式**：markdown 表格追加式，每条记录带 commit hash 与日期，禁止覆盖历史。
4. **防退化门槛**：同环境回归超过 20% 必须在提交说明中解释原因，否则视为事故。
5. **精度与性能分离原则**：parity 断言永不被性能优化修改；优化版实现必须与 naive 版过同一套 golden——"优化不许改变行为"的落地条款。

**DoD：** 任取看板中一个数字，按其记录的环境与方法重测，结果落在记录值的 ±10% 内。

### 2.7 docs/06-实验复盘/（每 case 一份，如 `case-02-fir-filter.md`）

**目的：** 把练习过程固化为面试资产；这是最终口述卡片的来源。

**必含内容（固定六段结构）：**
1. **假设**：做这个 case 前预期踩什么坑。
2. **做法**：关键决策的取舍（不是流水账）。
3. **数字**：精度误差 + 性能前后对照，引用 05 规范的记录。
4. **坑**：实际遇到的、假设之外的坑，注明定位过程。
5. **结论**：可迁移的方法论一句话。
6. **面试卡片**：3 分钟口述要点（不超过 5 条 bullet），每条都能被追问一层。

**DoD：** 合上文档能脱稿讲满 3 分钟；评审人（或 AI）按卡片追问两层，答得出。

## 三、工程纪律要求

1. **测试结构**：Parity 测试（精度断言，CI 必过）与 Benchmark（性能记录，不阻塞 CI）必须分目录分 scheme，禁止混写。
2. **提交规范**：conventional commits；golden 变更、规范变更、实现变更三者不混在一个提交里。
3. **CI 要求**：每次提交跑 parity 全量；规范文档与实现不同步的 PR 禁止合入（人工 checklist 即可，不必自动化）。
4. **依赖锁定**：Python 侧 requirements 锁定版本；SPM 侧 Package.resolved 入库。
5. **诚实性条款**：复盘中数字不许修饰；这个项目对外口径是"面试前针对目标公司技术栈的验证性原型"，不是生产项目——文档里也不许出现暗示生产环境的措辞。

## 四、使用方式

1. 开工前：先写完 2.2 / 2.4 / 2.5 三份规范的初稿（规范先行，哪怕先写 60%）。
2. 每做一个 case：先补 2.3 对齐口径文档 → 生成 golden → 写实现 → 跑 parity → 记 benchmark → 写 2.7 复盘。
3. 全部完成后：README 结果看板收口，复盘文档提炼出三张口述卡片（精度漂移 / C 集成 / 流式状态）。
4. 面试时：README + 规范文档即"工程化体系"的物证，复盘文档即讲故事的弹药库。
