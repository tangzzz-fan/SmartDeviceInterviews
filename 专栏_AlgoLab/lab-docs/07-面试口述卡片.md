## 卡片 A · 精度漂移（怎么证明「算对了」）

1. 我先冻结对齐口径文档，再写代码；golden 只允许 Python 生成，禁止用 App 输出回写真值。
2. 时域指标用产品无意义量级设阈值（如 SDNN 0.1ms），不是盲目 1e-12。
3. 频域对不上 90% 是前置链路；我用中间快照逐环定位，和 BLE 分层抓包同构。
4. CoreML 上端后看验证集 **top-1 一致率** 和 **置信度分布**，不盯单样本 logits。
5. 预处理均值/方差必须单源——要么全烘进模型，要么全在 App，禁止各做一半。

**可追问：** 快照阈值怎么定？病态输入占比为什么 ≥40%？

## 卡片 B · C 集成（Swift↔C 边界怎么不翻车）

1. 职责切开：C 只做纯数值、无 I/O；Swift 管生命周期、错误翻译、线程。
2. 错误码表跨语言一致（empty / too_short / non_finite…），Parity 专测错误路径。
3. 热路径零拷贝：`withUnsafeBufferPointer`，禁止逐 sample 跨边界。
4. 系数完整 double 导出；截断有效位会毁频响——我用 truncation demo 证明过。
5. 规范（`docs/04`）先于实现；新模式先补规范再写代码。

**可追问：** 为什么 FIR 热路径应留在 C？Accelerate 为何没直接用整段 `vDSP_conv`？

---

## 卡片 C · 流式状态（BLE 经验怎么缝进算法）

1. 流式 FIR 必须保留延迟线跨窗；每窗 reset 会造成「每秒一跳变」——我做了负例测试。
2. RingBuffer 吸收 BLE 分片；凑满 1 秒窗再批处理，符合「按批次调用」规范。
3. 丢包策略可测：`zero_fill` 与「预插零再滤波」golden 对齐。
4. 流式用**因果** FIR；离线 `same` 对齐是另一条口径，文档里显式分家。
5. 传输不确定性和算法连续假设之间，**状态管理层**就是 iOS 工程师的价值。

**可追问：** zero_fill 和 skip 对心率/波形产品各有什么风险？
