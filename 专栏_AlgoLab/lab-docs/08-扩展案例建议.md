# 扩展案例建议（Roadmap）

版本：0.1.0 · 日期：2026-07-28 · 作者：lab · 状态：草稿

> 目的：为 `algo-engineering-lab` 提供下一阶段可落地 case。  
> 原则：继续沿用「Python 原型 → golden → C/Swift 实现 → parity/benchmark → 复盘」链路。

---

## Case A · HRV 伪差校正（Artifact Correction）

**要解决什么：** RR 序列里常见的异位搏动/漏搏会把 HRV 指标拉偏，先做鲁棒清洗。  
**建议实现：**

- Python：实现 Hampel/阈值法的 RR 异常点检测 + 插值回填
- C/Swift：同口径重写 correction 流程
- Golden：覆盖正常、异位、漏搏、连续异常段

**验收标准：**

- 校正后 SDNN/RMSSD 与 Python 真值误差在阈值内
- 病态输入覆盖比例仍 ≥40%

**面试价值：** 能讲清楚「算法结果不稳」时是输入质量问题，不是模型问题。

---

## Case B · 多通道同步与时间戳漂移校正

**要解决什么：** EEG/PPG/ACC 多通道在 BLE 分片下容易出现时间漂移与错位。  
**建议实现：**

- 协议层增加统一时间戳与序列号
- RingBuffer 增加按时间轴对齐输出
- 对比「不校正 vs 校正后」频域/时域指标差异

**验收标准：**

- 模拟时钟偏差（ppm 级）下，重建后对齐误差可控
- 丢包+乱序场景仍可恢复连续时间轴

**面试价值：** 直接对应 JD 里的大数据流吞吐与联调归因能力。

---

## Case C · OTA/DFU 断点续传仿真（纯协议侧）

**要解决什么：** 固件升级失败往往不是传不动，而是状态机与恢复策略不全。  
**建议实现：**

- 用 Python/Swift 模拟 DFU 状态机（chunk、ack、resume token）
- 注入中断：断连、App 重启、CRC 错误、电量不足
- 输出 OTA 漏斗指标：开始/续传/完成/激活

**验收标准：**

- 关键中断场景可恢复或安全失败（不进入未知态）
- 漏斗指标可复现并可用于回归比较

**面试价值：** 能拿出“工程化 OTA 方法论”，不仅是 API 调用经验。

---

## Case D · 睡眠分期后处理（Post-processing）

**要解决什么：** 单 epoch 分类噪声大，需要平滑与约束。  
**建议实现：**

- 输入：mock 的每 30s 分类概率
- 处理：Viterbi/HMM 或规则引擎（最小时长、状态跳转约束）
- 输出：平滑后的 hypnogram 与统计指标

**验收标准：**

- 相比原始序列，短时抖动显著降低
- 指标（总睡眠时长、入睡潜伏期）稳定性提升

**面试价值：** 可体现“模型后处理”与产品可解释性。

---

## Case E · CoreML 在线漂移监控（Monitoring）

**要解决什么：** 上线后输入分布改变会导致模型性能退化。  
**建议实现：**

- 记录输入统计（均值、方差、分位数）与训练分布对比
- 计算 PSI/KL 等漂移指标
- 报告告警阈值与回滚建议

**验收标准：**

- 合成分布漂移场景能触发告警
- 正常场景误报率低

**面试价值：** 体现“模型上线后持续运营”意识，不止离线验证。

---

## Case F · 端上性能与能耗画像（Perf + Power）

**要解决什么：** 可穿戴场景常见瓶颈是“能跑但耗电高”。  
**建议实现：**

- 同算法比较：C naive / Accelerate / CoreML
- 记录 p50/p95、峰值内存、CPU 占用
- 增加温升/电量条件说明模板

**验收标准：**

- 基准可复现（同环境 ±10%）
- 性能退化 >20% 时可被规则识别

**面试价值：** 数字化证明你能平衡精度与性能。

---

## 推荐优先级（建议顺序）

1. **Case A（伪差校正）**：复用现有 HRV 链路，投入小、收益高  
2. **Case C（OTA 状态机仿真）**：强贴合目标岗位核心痛点  
3. **Case B（多通道同步）**：提升流式与 BLE 联动深度  
4. **Case E（在线漂移监控）**：补齐模型运维视角  
5. **Case D / F**：按面试侧重点择一深入

> 上表 A–F 已在 Phase 2 落地。下一阶段 CoreML 深挖见下方。
